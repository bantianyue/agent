# Popping the GPU Bubble

Moondream Engineering

2026年6月4日

Photon, Moondream 的推理引擎，在 NVIDIA B200 上实现了接近实时的 VLM 推理（约 33ms）。本文是一窥它如何通过优化 GPU 工作方式来提供高达 35% 更高 decode 吞吐量。

---

如何让 AI 模型运行得尽可能快？这是我们在 Moondream 总部痴迷的问题。GPU 处理模型推理中涉及的所有数学运算，所以乍看之下似乎没什么好做的：只需告诉它做什么，然后等待答案。但如果你开始研究它实际在底层如何工作，你会发现 GPU 经常闲置——不是因为没活干，而是因为 CPU 还没有告诉它下一步该做什么。这种现象被称为 **GPU bubble**。

当典型的 AI 模型生成文本时，它一次只产生一个 **token**（token 是一段文本，大约几个字符）。每个 token 依赖于前面的 token，这种属性称为自回归（autoregressive），因此生成是顺序的。你无法在得到第二个 token 之前计算第三个。这个解码循环涉及 CPU 和 GPU 之间的往返。GPU 负责繁重的计算，执行数十亿次算术运算来产生下一个 token。但 CPU 也做了大量令人惊讶的工作：它选择接下来要运行哪些请求，设置 GPU 所需的元数据，从模型输出中选出实际的 token 并记录它，等等。

挑战在于，一个 token 的 GPU 工作量很**小**，而 CPU 的内务工作是每轮都需要支付的固定成本。如果 GPU 必须等待这些内务工作完成才能开始下一个 token，它就每轮都有一部分时间闲置。这就是 GPU bubble 的成因。

在这篇文章中，我们将深入探讨 Photon 如何用一种叫做**流水线解码（pipelined decoding）** 的技术来隐藏这些 bubble。其思路是重叠两类工作：我们在 CPU 仍在完成上一个 token 的处理时，就开始 GPU 对下一个 token 的工作。

## The bubble（气泡问题）

以下是问题的形态。

![](timeline-comparison.png)
<span style="font-size:12px;color:rgb(153,153,153);">阻塞 vs 流水线解码时间线</span>

在阻塞版本（上方）中，每一步都是接力棒传递。CPU 计划并启动一个前向传播，GPU 运行它，然后 CPU **同步**，等待结果落地，提交它们，然后才计划下一步。这是因为计划依赖于我们选择的 token。例如，如果模型表示已完成回答，那么我们需要从队列中调度一个新的待处理请求。GPU 在等待 CPU 完成其提交-计划-启动工作的过程中闲置。

解决方案是**将循环流水线化**，在当前步骤的 token 仍在返回和被提交时，启动下一个前向传播。这就是**流水线**版本（下方）：前向传播背靠背运行，CPU 工作被重叠在它们之下。

我们能做到的原因是，我们刚采样的 token 不需要离开 GPU。下一个前向传播直接从 GPU 内存中读取它作为输入。我们最终仍然希望在 CPU 上有一份副本，用来去 token 化、流式传输，并判断请求是否完成，但这些是可以在后台稍后完成的簿记工作，而下一个前向传播已经在运行。不等这份副本，就是消除 bubble 的关键。

使其安全需要三件事，我们将在本文余下部分覆盖：防止步骤缓冲区冲突（ping-pong slots）、为约束解码正确定序（先 forward 后采样）、以及在请求完成后清理（zombies）。

## Mechanism 1: ping-pong slots（机制一：乒乓槽位）

要运行一个解码步骤，GPU 需要一组工作缓冲区：存放输入的位置（最后生成的 token 及其在序列中的位置）、模型写入其输出的位置（logits，词表中每个词的分数）、存放采样后 token 的位置，以及注意力 kernel 找到每个序列缓存的 keys 和 values 所需的簿记（即 KV cache）。我们在两端都保留**固定（pinned）** 主机缓冲区，这样 GPU 上下拷贝就作为后台 DMA（直接内存访问）传输运行，而不会阻塞 CPU。

这些缓冲区一次性分配，每一步都复用。我们努力避免在运行时执行 GPU 内存分配，因为它们可能导致设备同步并引入 bubbles。固定的缓冲区地址也是将解码步骤捕获为 CUDA graph 并重放所必需的，这能减少 kernel 启动开销。我们把这一整套称为 DecodeSlot。

这行得通，但给流水线化带来一个障碍。缓冲区在步骤完成之前一直被占用，所以我们无法在当前步骤完成前开始下一步。要重叠两个步骤，第二步需要有自己的工作集，否则它可能在 CPU 读取第一步的结果之前覆盖它们。因此我们保留两个 slot 并交替使用，乒乓风格。

![](pingpong-slots.png)
<span style="font-size:12px;color:rgb(153,153,153);">Ping-pong slots 示意图</span>

关于启动需要注意的一点是：当我们从 CPU 发出启动指令时，并不会立即执行 kernel。相反，我们将它们入队到一个**流（stream）** 上——一个有序的队列，GPU 按顺序从中取出工作。同一流上的工作顺序执行，而不同流上的工作可以重叠。两个 slot 都将它们的前向传播放到同一个计算流上。这些 slot 不是为了 GPU 并行，而是为了让 CPU 可以处理一个 slot 的结果，同时 GPU 运行另一个 slot 的前向传播。

所有前向传播共享一个计算流，但拷贝不共享。每一步的设备到主机拷贝——将采样后的 token 带回给 CPU 用于簿记——放在一个**单独**的拷贝流上，这样它就可以在 GPU 忙于下一个前向传播时运行。这就让我们可以不等它。我们将拷贝锚定在写入步骤输出那一刻记录的事件上，因此它恰好等待该步骤的工作完成，而不会等待后面排队的内容。

![](deferred-copy.png)
<span style="font-size:12px;color:rgb(153,153,153);">拷贝在后台运行</span>

一个 slot 只有在它的结果被读取后才变为可用，而不仅仅是 GPU 完成了它。它的固定主机缓冲区是可能仍在传输中的拷贝的目标地址，因此过早将 slot 交给新步骤会覆盖正在传输中的拷贝，导致难以调试的损坏 bug。因此，slot 会保持预留状态，直到读取它的提交完成，然后才释放。

## Mechanism 2: forward now, sample later（机制二：先 forward 后采样）

下一个 forward 可以提前运行，因为它不依赖于 CPU 对上一个 token 所做的任何事情。但关于**下一步**的两件事确实依赖于上一步的提交结果。一个是哪些序列仍在 batch 中：如果某个请求刚刚完成，它就不应该出现在下一个 forward 中。这是下一节（zombies）的内容。另一个是下一步甚至允许采样哪些 token——这就是本节的内容。

这源于**约束解码**。Moondream 的空间技能返回结构化输出而非自由文本：`point` 返回坐标，`detect` 返回边界框，`segment` 返回轮廓。我们通过在每个步骤约束模型可以产生哪些 token 来在同一个解码循环中获得这些输出：我们在采样前将不允许的 token 的分数（logits）设为负无穷。一个 `point` 步骤必须产生一个坐标，一个 `detect` 请求经历一个 x、y、size 循环，以此类推。哪些 token 被允许——即遮罩（mask）——取决于到目前为止已经产生了什么，因此步骤 *t+1* 的 mask 依赖于我们在 *t* 步采样的 token。

这个依赖存在于**采样**中，而不是 forward 中。

![](advance-tick.png)
<span style="font-size:12px;color:rgb(153,153,153);">Forward 不需要 mask，只有采样需要</span>

每个调度 tick 经历三个阶段：**启动（launch）、提交（commit）和最终化（finalize）**：

1. **启动**步 *t+1* 的 forward。它不依赖于 mask，因此立即执行。
2. **提交**步 *t*：等待正在进行的拷贝，推进请求的解码状态。这是决定 *t+1* 的 mask 所必需的。
3. **最终化采样**步 *t+1*：状态更新后，构建 mask 并采样。

在提交 *t* 之后才采样 *t+1*，因为提交正是让 *t+1* 的 mask 正确的关键。我们称之为"提交-后-最终化"（commit-before-finalize）顺序。GPU 在第 2 和第 3 步期间运行 *t+1* 的 forward，因此提交从关键路径上消失了。

对于纯文本，没有 mask，因此 forward 和采样都可以提前一步运行。对于约束序列，forward 仍然提前运行，但采样等待前一步的提交，这限制了我们无需特殊处理就能提前多少。一个循环同时处理两种情况。

## Mechanism 3: zombies: finalize early, release late（机制三：僵尸：尽早终止，延迟释放）

回到"先 forward 后采样"中，我们指出了下一步依赖上一步提交结果的两种方式。采样 mask 是其一。batch 成员关系是另一种，而且需要小心处理。

要启动步 *t+1*，我们首先决定它的 batch——哪些序列在 batch 中——而我们是在提交步 *t* 之前做出这个决定的。那么当一个序列在 *t* 步到达了停止 token，但它已经被嵌入到 *t+1* 的 forward 中时会发生什么？你无法撤销已发出的 GPU 工作。这个序列已经完成，却仍然物理地出现在一个正在执行的 batch 中。

Photon 称这些为 **zombies（僵尸）**，它没有直接添加取消逻辑，而是让行为从两个每序列字段中涌现出来：

- `finalized`：序列达到 EOS 或长度上限后为 `True`。
- `inflight_refs`：仍在引用该序列的飞行中步骤数量（0、1 或 2）。

![](zombie-lifecycle.png)
<span style="font-size:12px;color:rgb(153,153,153);">一个已完成的序列作为 zombie 搭乘步 t+1</span>

当步 *t* 提交并检测到 EOS 时，该序列被标记为 `finalized`，其结果被发出——但它不会被拆除，因为 `inflight_refs` 仍然不为零（步 *t+1* 还在引用它）。在步 *t+1* 提交时，该序列已经是 `finalized`，因此提交被**跳过**：不追加 token，不改变状态。zombie 只是无害地搭了一程——它占了 slot，写了一些没人会读的 KV。只有当 `inflight_refs` 最终变为 0 时，它的 KV 页面和 LoRA slot 才被释放。

这种"尽早终止、延迟释放"的舞蹈是一小部分引用计数逻辑，它取代了原本可能需要一堆"取消这行中途执行"的特殊情况。

## Prefill rides the same pipeline（预填充使用同一流水线）

到目前为止，所有这些都关于解码步骤，但一个真实的 serving 循环不断做两种**不同**的工作：**prefill**（处理新请求的 prompt + 图像，即昂贵的一次性多 token forward）和 **decode**（为所有已运行的请求一次生成一个 token）。

Photon 不会将它们分开。一次 prefill 就只是同一个双 slot 流水线中的另一个 `kind="prefill"` 启动。由于流水线只关心一个 slot 是否空闲，而不关心上次使用了什么类型的工作，一个 prefill forward 可以被启动到一个 slot 中，同时另一个 slot 的解码步骤仍在被提交，反之亦然。昂贵的 prefill forward 在 GPU 上运行，同时 CPU 提交解码结果；下一个解码 forward 运行，同时 CPU 完成将刚 prefill 完成的请求接纳进来。相同的提交顺序（以及相同的 `inflight_refs` 簿记）使一切在两类型之间保持正确，因此 zombie 或约束解码逻辑都不需要为"如果 prefill 正在飞行中"做特殊处理。

这当输出长度很短时最为重要。一个只产生三个 token 的请求，其几乎整个生命周期都花在 prefill 和接纳上，而非 decode 上。因此，大量短请求的工作负载实际上是 prefill 流中夹杂少量 decode。共享一个流水线正是让该流能重叠自己的 CPU 簿记，而不是将 prefill 序列化在 decode 之后然后再回来。

## A cost model for the bubble（气泡的成本模型）

流水线化实际上应该能带来多少收益？你可以从解码步骤的组成部分来预测，然后将预测与实测对比。

一个解码步骤由三部分工作组成：

- **forward**：繁重的 GPU 矩阵乘法。在解码阶段，这是内存带宽受限的：每个 token 将整个权重集流过计算核心，因此它有一个接近 `weight_bytes / memory_bandwidth` 的底部。随着内存变快或模型变小，它也会缩小。
- **sampling**：将分数转化为已提交的 token：约束解码 mask、argmax/采样、空间（grounding）解码，以及结果从设备到主机的拷贝。全是 GPU 工作。
- **bookkeeping**：围绕它的 CPU 工作。选择下一个 batch（`plan`）、启动 graph（`launch`）、提交前一步骤（`commit`）。

阻塞循环三者串行运行，因此 GPU 在 bookkeeping 期间闲置——这段闲置就是 bubble。流水线化将一步的 bookkeeping 滑入下一步的 `forward + sampling` 之下，因此周期向着 `forward + sampling` 收缩，bubble 消失。按步骤测量，流水线化之后，这恰好是我们看到的——GPU 在整个周期内几乎一直忙碌（稳态中位数，moondream2，ms）：

| | forward (ms) | sampling (ms) | period (ms) |
|---|---|---|---|
| **3090 · 1 stream** | 4.87 | 0.20 | 5.10 |
| 8 streams | 6.66 | 0.27 | 6.97 |
| 32 streams | 10.24 | 0.26 | 10.52 |
| **B200 · 1 stream** | 2.45 | 0.14 | 2.63 |
| 8 streams | 3.12 | 0.14 | 3.30 |
| 32 streams | 3.80 | 0.14 | 3.98 |

`forward + sampling ≈ period`；剩余的 GPU 闲置不到 0.05ms。那么它到底值多少钱呢？这归结为两件事之间的拉锯——你成功藏匿了多少步骤工作量，对抗提前运行的一小幅代价：

```
speedup  =   T_block / T_pipe    ×      (1 − z)
            └─ bubble hidden ─┘     └─ zombie tax ─┘
```

两个符号，两个思路。第一项是收益，也是整个 GPU 速度故事的全部：一个步骤阻塞需要多长时间（`T_block`）对比流水线化需要多长时间（`T_pipe`）——即一旦 bookkeeping 被藏在下面后步骤跑得有多快。

第二项 `z` 是提前运行的代价——来自机制 3 的 **zombie tax**。在提交 *t* 之前启动步 *t+1*，一个刚完成的序列仍然有一个 forward 在飞行中：浪费的一步。在单流上，每 `L` 个生成的 token 就浪费一次 forward，因此在 `L ≈ 110` 时大约 1%。但当你装满一个 batch 时，它几乎消失了——zombie 只是已经支付了全价来流经权重的一步中的额外一行，因此它几乎免费地搭了车。这笔税在单流时最重，恰恰在吞吐量所在的地方消失。这就是为什么预测它需要同时知道 `L` 和 batch size。

以下是该步骤两种方式的实测结果——阻塞让每一步都闲置，等待 CPU 提交上一个 token 并重新启动；流水线化将该工作（以及异步 mask 上传）置于 forward 之下运行，因此 forward 从不停止：

现在把真实数字代入。分别测量每个部分——两个步骤时间和 `L`——模型的预测应该正好落在基准测试实际交付的结果上（depth-1 阻塞 vs depth-2 流水线，其他不变）：

| | blocking (ms) | pipelined (ms) | L | predicted | observed |
|---|---|---|---|---|---|
| **3090 · 1 stream** | 5.44 | 5.10 | 104 | +5.7% | +6.5% |
| 8 streams | 7.52 | 6.97 | 113 | +7.6% | +7.8% |
| 32 streams | 11.74 | 10.52 | 113 | +11.1% | +11.6% |
| **B200 · 1 stream** | 3.11 | 2.63 | 115 | +17.2% | +17.6% |
| 8 streams | 4.04 | 3.30 | 115 | +22.2% | +21.9% |
| 32 streams | 5.55 | 3.98 | 104 | +39.1% | +35.4% |

三件事值得注意：

1. **收益随 GPU 速度增长。** 同样负载，3090 上 +12%，B200 上 +35%（32 流）。Bookkeeping 不随 GPU 速度变化，因此随着 forward 缩小——更快的内存或更小的模型——bubble 在步骤中占更大比例。流水线化是对 GPU 变快的保险，而对我们来说，这和模型变小是一回事。

2. **Zombie tax 真实但微小，且能摊销。** 单流时 zombie 是整整浪费一次 forward——在 L≈110 时约 1%。在 batch 中，它只是已经权重内存带宽受限的一步中的额外**一行**，因此几乎不花成本：在 32 流时，3090 观测到的 +11.6% 正好落在**无 zombie** 的每步比率上。这笔税在单流时最重，恰恰在吞吐量存在的地方消失。（B200 的 32 流行比预测低几个百分点有一个更索然无味的原因——在约 4ms/步时，整个运行不到半秒，因此 prefill 和运行结束时的 batch 缩减占可见比例。）

3. **它只在 bubble 确实可以被隐藏时才有回报。** （事实上，这正是我们如何抓住一个 bug 的：流水线化数字出来时是**阻塞**速度，追溯到构建约束解码 mask 时的一个意外同步拷贝。将其移到拷贝流上在 3090 上值 +11%，在 B200 上值 +34%。）

## It's never just one thing（从来不只是单一技巧）

以上就是整套技术：乒乓槽位让两个步骤不冲突，forward/sampling 拆分让即使是约束解码也能提前运行，以及一点 zombie 引用计数让已完成的请求干净地拆除。GPU 不再等待 CPU，你得到从几个百分点到三分之一的收益；加速器/模型越快，收益越大。

但 Photon 之所以快，不是因为这一个技术，也不是因为任何单一技术。它之所以快，是因为数十个这样的细节在整个 serving 栈上累积：我们如何在输入时调整和拼接图像、运行模型的 kernel、这里的调度器顺序，以及我们从热路径上移除的同步点。没有哪个部分就是全部；当足够多的部分排成一线时，整个栈才变快。
