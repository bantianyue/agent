# AI 模型协同设计：硬件友好的 LLM 设计

AI 性能归结为三个维度：
- 准确性：模型推理和输出的质量
- 吞吐量：数据中心每秒能生成的 token 数
- 交互性：用户感受到的响应速度，主要由延迟决定

部署必须平衡三者：准确性再高，如果响应慢也是浪费；原始吞吐量再大，如果每个用户的体验卡顿也无意义。因此实际系统必须同时优化准确性、吞吐量和交互性。

本文聚焦于吞吐量和交互性，以及模型设计选择如何在**不牺牲准确性**的前提下塑造这两者（我们在出现准确性权衡时会标注出来）。

在准确性固定的前提下，问题变成了一个二维帕累托前沿：优化一个指标通常以牺牲另一个为代价。目标是将整个前沿向外推，最大化曲线下面积（见下方图 1）。

我们将从当今最突出的 AI 工作负载——LLM 开始。这个权衡有两个视角：系统部署者（优先考虑集群吞吐量，即 tokens/s）和用户（更看重低首 token 延迟和 token 间延迟）。token 间延迟的倒数是 tokens/s/用户，数值越高表示响应性越好。

一个典型的响应流程是：提示词 → [首 token 延迟] → 第一个 token → [token 间延迟] → 下一个 token，依此类推。

这是一个面向模型开发者的实用入门指南，帮助他们的模型在现代硬件上高效运行。思路很简单：与硬件对齐的模型不仅运行更快，而且扩展性更好、成本更低、覆盖更广。

首先关注部署环境的两个维度（见下方图 2）：
- 工作负载范围从短上下文到长上下文
- 服务目标从吞吐量导向（最大化 tokens/s）到延迟导向（最小化响应时间），许多场景介于两者之间

每个象限需要不同的优化：长上下文、吞吐量导向的服务大部分时间花在 attention 上；延迟导向的服务则增加模型并行度来缩短 attention 和 FFN，但代价是通信开销和固定开销。短上下文、吞吐量导向的服务在 attention 和 FFN 上的时间分配更均匀，可以在大规模上受益于并行（如专家并行）。

阿姆达尔定律适用：优化某一部分的帮助程度取决于该部分占运行时间的比例。如果 attention 占运行时间的 77%，优化前馈层只能带来边际收益；attention 路径才是值得投入的方向。了解你的工作模式就知道该聚焦何处。

本文提供简单的经验法则，帮助在早期就做出这些决策，适合那些希望充分利用硬件但又不打算成为系统工程师的读者。本系列的后续章节将分别针对硬件感知设计的不同维度，帮助你避免计算瓶颈、在数据中心规模上无缝部署、根据使用场景匹配设计，并进行实际扩展。

设计更聪明。部署更快速。扩展更宽广。开始吧。

## 硬件友好的 LLM 线性层维度设计

Transformer 的一个关键设计选择是其宽高比：模型宽度和层数 L 之间的平衡。在解码器风格模型中，这些因素主导了计算和内存如何在堆栈中分布。宽度本身由两个维度决定：隐藏维度 H 和 MLP 层中的中间投影维度 H′。

H、H′ 和 L 三个维度共同决定了模型映射到并行策略的平滑度以及跨 GPU 扩展的效果。本文关注这三个选择如何影响吞吐量、交互性和可扩展性，重点聚焦于线性层。

### 算术强度的作用

在任何硬件上，可达到的性能都受到屋顶线模型（roofline model）的约束。工作负载的位置取决于其算术强度，即每移动一个字节的内存所执行的计算操作数。

算术强度低的工作负载受限于内存带宽（memory-bound）；算术强度高的工作负载受限于设备的峰值计算吞吐量（FLOPS，即 compute-bound）。当目标是最大吞吐量（每秒 token 数）时，你希望将工作负载推入 compute-bound 区域，以便充分利用硬件的全部计算能力。

延迟敏感的 decoding 则相反，它以低并发运行，是 memory-bound 的，因此减少内存访问时间是降低响应延迟的关键。

提高每字节操作数的一个直接方法是增加 batch size，但模型形状同样重要。让我们看看 H 和 H′ 如何决定一个 GEMM 是 compute-bound 还是 memory-bound。在单设备上运行时，H 和 H′ 设定了 GEMM 的如下形状：

C = A * B

按照典型线性代数库的惯例，A 是 M×K 矩阵（M 行，K 列），B 是 K×N。乘积 C 有 M×N 个输出，每个是长度为 K 的点积，需要 M×N×K 次融合乘加运算（FMA）。每次 FMA 计为 2 FLOPs（一次乘法、一次加法），因此成本为：

FLOPs = 2×M×N×K
ReadBytes = M×K×bytes_A + N×K×bytes_B
WriteBytes = M×N×bytes_C

其中 bytes_A/B/C 是精度决定的每元素字节数。将 A 视为输入、B 视为权重，下表 1 将 token 数（Tokens = 并发数×序列长度）、H 和 H′ 映射到每个线性层 GEMM 的 M、N、K。

考虑一种情况，每个 GEMM 都是"方阵"，即 Tokens = H′ = H。单个 GEMM 执行 2H³ 次 FLOPs，同时移动约 3H² 个元素的内存，因此算术强度随 H 增长。实际结果是：当 H 或 H′ 较小时，即使 token 维度很大，GPU 花费在数据传输上的时间比例也远高于计算。

以一个具体例子来说明：在 GB300 上使用 4 位输入和 8 位输出的 FFN-2，H′ = 512，H = 8192。如下表 2 所示，即使在 token 数很大（高 GEMM-M）的情况下，这一层仍然保持 memory-bound，由数据传输主导；写入成本占主导地位，因为输出是 FP8 而输入是 FP4，小的 reduction 维度使 GEMM 停留在 memory-bound。

图 4 的曲线图在 GB300 芯片上展示了这一点。使用 NVFP4 GEMM，token 维度（GEMM-M）固定为 8192，我们扫描 reduction 维度（GEMM-K，左图）和投影维度（GEMM-N，右图）。在两种情况下，当被扫描的维度较小时吞吐量急剧下降，这证实了小 N 或 K 值使硬件利用率不足（N 和 K 对应 H 或 H′，取决于所处层；见上表 1）。

这对模型设计师来说是一个重要观点：对于饱和计算能力，模型维度与 batch size 同样重要。

**指南 1：在固定参数量的模型中，倾向于接近方形的权重矩阵，避免投影维度或 reduction 维度过小。**

但仅有尺寸还不够。要达到高 Tensor Core 利用率，GEMM 的维度还必须干净地映射到底层分块（tiling）几何结构上；对齐不良会导致 tile 量化，即使在算术强度很高的情况下也会降低吞吐量。

### GPU 如何执行 GEMM

GPU 通过将输出矩阵拆分为 tile 来执行 GEMM，每个 tile 由一个流式多处理器（SM）计算。在最近的 GPU 上，SM 无需独立工作；它们可以协作处理一个更大的 tile：通过 clusterMMA，两个相邻 SM 联合处理一个 tile；Cooperative Grid Array（CGA）让整组 SM 作为一个集群协同工作。

协作提高了数据复用，但也放大了有效 tile 的尺寸，因此维度必须是更大值的倍数才能保持对齐。当一个维度不是有效 tile 的倍数时，边缘 tile 只被部分填充，但仍然启动并运行了完整 tile 的计算量；未使用（填充）的部分不做任何有用工作，浪费了周期并降低了吞吐量。图 5 展示了这一点：使用 256×128 的基础 tile、clusterMMA 和 4×2 CGA，以细粒度步长扫描 GEMM-N 时，N 是 256（clusterMMA 的 2×128）或 512（CGA 的 2×256）的倍数时产生局部吞吐量峰值。

为避免这种浪费，选择模型维度时应是大倍数 tile 尺寸并与 GPU 缓存行宽度对齐。128 的倍数是一个安全、可移植的下限；256 的倍数（clusterMMA）或 512 的倍数（CGA）与更大的协作 tile 对齐，能获取最高吞吐量。

**指南 2：模型维度至少应为 128 的倍数，以对齐 GPU tile 尺寸和缓存行宽度；优先选择 256 或 512 的倍数，以匹配 clusterMMA 和 CGA 形成的更大 tile。**

### 宽模型比深模型更硬件友好

在固定参数量预算下，宽模型通过更大的权重复用和更短的串行关键路径，提供更高的算术强度和更低的延迟。这使得宽模型对吞吐量导向和延迟导向的服务目标都有利。

也就是说，宽高比也影响模型质量：深度有助于表征能力，因此存在一个有用的宽度-深度区间，而不是"越宽越好"。只在准确性允许的范围内优先宽度，而不是为了加宽模型而剥离层。

**指南 3：在有选择时，优先考虑更少但更大的运算，而不是许多小运算；这能最大化算术强度并提高硬件利用率，对吞吐量和交互性都有利。换言之，更宽的 Transformer 模型比更深的模型更硬件友好。**

## 量化作为性能杠杆

量化同时帮助 compute-bound 和 memory-bound 工作负载，同时提高数学吞吐量和减少内存流量。Blackwell 系统支持 NVFP4，以及 FP8 和 FP16/BF16 等其他位宽格式（见下方图 6）。

NVFP4 专为平衡模型准确性和速度而设计；它对每 16 个值的微块施加细粒度的 FP8（E4M3）缩放，再加上每张量的二级 FP32 缩放。这种分层缩放大幅减少了量化误差，同时保持了 4 位计算的速度，使 NVFP4 在广泛的 LLM 工作负载上紧密匹配更高精度的准确性（见下方图 7，DeepSeek-R1 示例）。

NVIDIA 提供端到端工具链使这变得实用：TensorRT Model Optimizer 和 LLM Compressor 支持训练后量化（PTQ）、量化感知训练（QAT）和高级校准，能以最小的准确性损失将模型量化为 NVFP4。

因此，大多数矩阵乘法密集的操作（如线性层）可以充分利用 NVFP4 获得更高吞吐量，同时保持模型保真度。要了解更多关于低位宽训练的信息，请查阅 Pretraining Large Language Models with NVFP4（NVIDIA Research，2025）。

**指南 4：在向网络中引入计算密集操作时，考虑是否可以在部署时进行量化。设计能从低精度执行中受益的层，是从现代 GPU 中获得最大收益的关键。**

## 大规模专家并行提升吞吐量

在吞吐量导向的服务中，目标很简单：用最少的 GPU，尽可能快地为尽可能多的用户提供服务。由于大多数最先进的 LLM 现在都是混合专家（MoE）模型，一种非常有效的方法是专家并行（EP）：将 attention 做数据并行，并将 FFN 的专家分布在多个 GPU 上。

将数据并行（DP）用于 attention 避免了张量并行（TP）的一个关键限制——合并部分结果所需的昂贵的 AllReduce。这个开销随着并发度增长并拖低吞吐量，使 TP 在这里不太合适。DP attention 扩展更自然：增加 GPU 直接提升全局并发度，更高的并发度意味着 MoE FFN 中更大的 GEMM-M。

假设均匀的路由分配：

GEMM-M = (global_concurrency × top_k) / #experts

其中 global_concurrency 是每 GPU 并发 token 数 × GPU 数量，top-k 是每个 token 激活的专家数（DeepSeek-R1 为 8），#experts 是专家总数（DeepSeek-R1 为 256）。因为 GEMM-M 随并发度增长、随模型稀疏性缩小，提升并发度是稀疏 MoE 模型中实现高 GEMM 利用率的关键；而由于每 GPU 并发度受 KV cache 容量限制，跨更多 GPU 扩展 EP 是提高它的主要杠杆。

即使每个专家的有效 batch（它的 GEMM-M）很小——不论是由于有限的并发度还是不均衡的路由分配——扩展 EP 仍然在两个方面有帮助：
- 通过聚合带宽加速执行：将专家分布在更多 GPU 上，增加了加载专家权重的有效内存带宽，减少了端到端 FFN 延迟。
- 减少每 GPU 内存占用：每个 GPU 只存储专家的一个子集，释放了内存来增加每 GPU 的有效并发度，更好地饱和计算。

EP 确实带来两个挑战：all-to-all 通信开销和专家负载不均衡。但 NVIDIA 在 TensorRT-LLM 中的 Wide-EP 特性解决了这两个问题：
- 高性能 all-to-all 内核，支持 EP 在 Blackwell 多节点 NVLink 系统上扩展
- 自适应负载均衡器，基于实时负载模式重新分配专家流量，在 token 和专家分布偏斜时保持稳定

详情参见 TensorRT-LLM 文档中关于专家并行扩展的内容。对于吞吐量导向的 MoE 部署，关键杠杆是专家并行。

**指南 5：复杂、稀疏的大规模 MoE 模型，在采用正确的并行策略部署时，仍然可以实现高吞吐量，最显著的方式是进行大规模的专家并行扩展。**

## 为流水线并行而设计

当你将 prefill 和 decode 分离时，流水线并行变得相关。这可以是对某些模型大小、流量模式和延迟目标的有效服务策略，正如我们在 Beyond the Buzz: A Pragmatic Take on Inference Disaggregation（NVIDIA Research，2025）中所分析的：用不同的模型分区来运行 prefill 和 decode，可以让两者各自优化和扩展，从而提高整体吞吐量。

对于 prefill，在高吞吐量的同时降低首 token 延迟（FTL），特别是在长上下文中，需要激进的并行化。分块流水线并行（CPP）非常适合这里：它将模型层跨 GPU 拆分，并将输入上下文分割成块，通过流水线流动（见下方图 8）。

这让 prefill worker 能在紧张的 FTL 预算内处理长序列，而无需诉诸宽张量并行（见下方图 9）。

CPP 只有在流水线阶段平衡时才有价值；阶段不平衡会引入流水线气泡，导致部分 GPU 空闲。保持阶段均衡的一个有效方法是构建具有可重复层模式的模型，这些模式可以均匀地划分。

**指南 6：设计具有规则、可重复层模式的模型，使其易于拆分为平衡的流水线阶段。这样的模型非常适合分块流水线并行（CPP），能在满足紧张的首 token 延迟目标的同时实现更高吞吐量。**

## 混合并行策略满足延迟导向的服务目标

到目前为止我们聚焦于吞吐量；延迟导向的服务遵循不同的约束。更低的延迟需要每 GPU 更少的工作（更低并发度）或更多 GPU。然而，缩小 batch 最终只减少了 attention 延迟：FFN 延迟会变成 memory-bound，因为 GEMM-N 和 GEMM-K 维度在 GEMM-M 缩小时仍然很大，使得权重读取（N×K 矩阵）成为瓶颈。

在这种低并发度模式下，attention 和 FFN 应该被独立地并行化。FFN 通过 TP、EP 或 TP×EP 将权重分布在 GPU 上来加速。TP 偏好粗粒度 MoE 模型（大专家），而 EP 更适合细粒度 MoE 模型——其较小的 H′ 在 TP 下会产生低效的小 GEMM。

相比之下，attention 受益于 TP 和 KV 并行化。然而，TP 只能扩展到 KV 头部数量；超过这个限制，KV cache 必须被复制，引入冗余工作。由于现代 MQA/GQA/MLA 模型 KV head 很少，这很快成为瓶颈。Helix 并行（NVIDIA Research，2025）通过在 attention 期间沿序列维度分片 KV cache，然后在 FFN 中重用相同的 GPU 进行 TP×EP，克服了这个问题。Helix 在 TensorRT-LLM 中得到支持。虽然这些混合方案引入了额外的通信开销，但 Blackwell NVL72 的高带宽 NVLink 结构吸收了大部分成本，剩余部分可以与计算重叠。

**指南 7：设计模型和部署方案时，将 attention 和 FFN 的并行化解耦，使得扩展 GPU 能通过策略性地针对主要瓶颈来改善交互性。**

## 下一步

设计下一个模型时，将这些指南作为设计检查清单：

- 保持维度接近方形并对齐到 128（理想情况 256）
- 优先宽度而非深度
- 设计模型以支持低精度（NVFP4）推理
- 使用规则、可重复的层模式，能干净地映射到流水线并行上

像这样的小选择可以显著提升 GPU 利用率，在同等的硬件上实现更快的推理、更高的吞吐量和更好的交互性。

要将这些付诸实践，请探索 NVIDIA TensorRT Model Optimizer 用于 NVFP4 量化，以及 TensorRT-LLM 用于专家并行、流水线并行和 Helix 并行。
