What actually happens when a MOE token gets routed to an expert?

Let me explain to you what happens at the atomic level with an architecture overview. MoEs let very large models use only a small subset of their expert parameters for each token, instead of running every FFN parameter every time.

What usually happens in a dense model is that every token is sent to one giant FFN (feed-forward network) but in an MoE, we have multiple smaller FFNs called 'experts' and instead of choosing everyone, our router only chooses a few of them for a particular token.

So if an MOE had 64 experts in total and the router is Top-2, then we say only 2 of these experts get activated per token.

But let's understand this at the atomic level

1. Token arrival at MOE layer

The word or token itself dosent get routed, instead the transformer has already converted it into a hidden-state vector, something like: 

token = [0.18, -0.42, 0.07, ...]

This vector is what gets routed.

2. Router Scoring

Once these vectors arrive, the learned router now takes its hidden state and produces a score for each available expert. So let's say we have 4 experts available:

E1: 0.03
E2: 0.71
E3: 0.08
E4: 0.52

Now if we choose a top-2 routing, E2+E4 may get the token. Additionally, these routers also give us weights that help us determine how much each expert's result should contribute later.

3. Every token may get different experts.

In real scenarios, every token will get different combinations of experts assigned, so if Tn is token n, then things may look like:

T1 = E2, E4
T2 = E1, E7
T3 = E2, E5
T4 = E7, E8

In layman's terms, every token may depict different meanings, and it might need an expert who knows about the meanings and relationships. (T1= can be cat, whereas T3 could be Sodium chloride)

4. Reorganization of tokens

Running every token at a time will be ugly for production workloads so whats usually done is inference runtime permutes the hidden states and groups tokens that selected the same expert. So instead of processing T1,T2,T3....

you get something closer to: 

E1 = [T2]
E2 = [T1, T3]
E4 = [T1]
E5 = [T3]
E7 = [T2, T4]

This will let each expert process its assigned tokens together using efficient matmul.

5. Multi-GPU

In production workloads, the model might be distributed across multiple GPUs, that means every token has to travel across clusters or GPUs and now this becomes an inference problem as we have to take care of communication overhead. 

So we usually handle this using expert parallelism, where different GPUs hold different experts. So things may look like: 

GPU 0 = E1, E2
GPU 1 = E3, E4
GPU 2 = E5, E6
GPU 3 = E7, E8

So T1 may want to use E2 on GPU 0 but also E5 on GPU 2 which means it now becomes an all-to-all-style communication step:

Tokens -> router -> group by expert -> 
GPU 0 <-> GPU 1 <-> GPU 2 <-> GPU 3

6. Expert finally runs

An expert is usually an FFN, which is basically the expensive MLP part of transformers, so each GPU now runs the experts it owns on the tokens routed to it.

Since many tokens may hit different experts, runtimes often try to turn these into grouped GEMMs rather than launching matmuls for tokens individually.

7. The expert outputs have to come back

Once the computations are done, we need to send the tokens back, since they were grouped by expert and may be sitting on completely different GPUs.

So the runtime sends the outputs back and reverses the permutation.

E2 output for T1 = back to T1
E4 output for T1 = back to T1
E7 output for T2 = back to T2

8. Outputs from the selected experts are combined

Remember those router scores from the beginning?

If T1 selected:

E2: 0.71
E4: 0.52
Their outputs are weighted using those routing values and combined into one hidden state.

Then the transformer can now continue as if this giant routing operation never happened and this repeats every time a token encounters another MoE layer.
