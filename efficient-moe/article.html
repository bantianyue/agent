什么是 TorchTitan？

TorchTitan 是 Meta 基于 PyTorch 原生构建的蓝图，用于跨多 GPU 和多节点集群的大规模训练。它将现代 LLM（大语言模型）和 MoE 模型经过验证的配方打包成一个可配置的训练栈，使你能够从早期实验到全规模运行复用同一套代码路径。

广泛的架构覆盖

在单个 TOML 文件中设置流水线并行、张量并行、数据并行或专家并行的度数，TorchTitan 会自动构建任务、连接 NCCL/RCCL 通信组，并在单块 GPU 或上千块 GPU 上运行相同的脚本。

模块化设计

通过统一的 TorchTitan 配置，训练密集模型（Llama 3）、混合模型（Qwen 3）和稀疏 MoE 模型（DeepSeek-V3、Llama 4）。

理解混合专家模型

像 AMD 的 FP8 Primus-Turbo 这样的优化 kernel 无需修改代码即可直接使用，相同的钩子（hook）也能兼容未来的训练后工作流。

简而言之，TorchTitan 提供了一条统一、可组合的路径，用于扩展任何模型——无论是密集还是稀疏——从笔记本电脑原型到集群生产环境。

图1：Dense Layer（密集层）与 MoE Layer（混合专家层）架构对比

混合专家模型（Mixture-of-Experts）是密集 Transformer 的一种稀疏激活替代方案。在标准模型中，每个 token 都流经同一个前馈块，因此参数翻倍意味着计算量翻倍。MoE 层用一个由多个专家组成的池替换了单个 MLP。一个学习到的路由器（router）检查每个 token，并将其发送给其中少数（例如 k 个）专家。

MoE 预训练的挑战

由于每个 token 只运行少数几个专家，每个 token 的计算预算现在随这个小 k 值而非专家总数扩展。内存遵循相同的模式：如果应用专家并行（expert parallelism），每个 GPU 只存储其拥有的专家的参数，从而为扩展隐藏维度、序列长度或词表大小留出空间，而不会超出设备限制。专家本身是普通的 MLP 块，因此增加容量只需复制更多副本，而无需加宽每一层。

这种经济性使得 MoE 模型能够达到数千亿参数规模，同时以密集模型的速度进行训练。DeepSeek-v3 和 Llama 4 展示了这种回报，它们混合使用 MoE 和密集层，以在当今硬件上平衡容量、准确性和效率。

内核效率

虽然 MoE 模型提供了引人注目的优势，但大规模训练它们会带来独特的挑战，必须加以解决才能实现高效的分布式训练。

通信

小矩阵乘法（GEMM）→ GPU 利用率不足：路由后，每个专家只处理少量 token，因此产生的矩阵乘法（GEMM）操作变得非常小。这些微 GEMM（micro-GEMM）无法让 GPU 的计算单元完全满载，并引入了显著的启动和数据移动开销。

并行性

全对全通信过重 → 网络瓶颈：专家并行（Expert Parallelism）将 token 嵌入分散到拥有所选专家的 GPU 上。因此，每次前向传播都会触发大量的全对全集合通信，随着集群规模扩大，通信时间可能超过计算时间，成为主要瓶颈。

路由与稳定性

并行策略复杂 → 流水线不同步导致的空闲气泡：现代训练通常同时使用全分片数据并行（FSDP）以节省内存、流水线并行（Pipeline Parallelism）以增加深度，以及专家并行（Expert Parallelism）以扩展宽度。如果它们的微批次或调度不同步，就会出现“气泡”——部分 GPU 工作时其他 GPU 空闲的时段——导致利用率低下。

并行策略设计

路由不稳定 → 专家负载不均：学习型路由器必须在遵守容量限制的前提下，将 token 均匀分配给各个专家。token 计数偏斜、专家过载或 token 被丢弃，都可能减慢收敛速度或降低最终模型质量。

我们从三个方面应对这些预训练挑战：AMD Instinct MI325X GPU 提供 256GB HBM3E 内存、超过 6TB/s 带宽以及 FP8 张量核心，使 MoE 专家保持本地化且计算密集；TorchTitan 并行策略（FSDP + PP/VPP + EP）平衡计算与通信；Primus-Turbo 的 FP8 注意力机制和分组 GEMM 内核将 MoE 的小型 GEMM 转化为高占用率、高吞吐量的运算。

AMD Instinct™ MI325X：硬件与软件栈

图 2：AMD Instinct MI325X 规格

Instinct MI325X 配备 256 GB HBM3E 内存、超过 6 TB/s 的片上带宽以及千万亿次级别的 FP8/BF16 矩阵核心。如此大容量的高速内存使得 MoE 可以在本地设备上运行大部分专家，而无需将它们分散到整个集群，这同时带来了三个好处：

每块 GPU 可容纳更多专家——容量增长无需将模型分割成更小的碎片。

更高的容量因子，更少的 token 丢弃——路由器可以将额外的 token 分配给繁忙的专家而不会耗尽内存，从而稳定训练。

更少的 All-to-All 通信——更小的 Expert-Parallel 度缩小了集合通信的规模，因此通信不再主导挂钟时间。

在实践中，MI325X 的内存余量和带宽将通常的网络瓶颈转变为套接字内的工作负载，即使在大规模下也能使 MoE 训练保持计算受限。

Primus-Turbo：AMD 加速库

Expert Parallelism (EP) 将专家池划分到节点内的 GPU 上，并且当模型无法再容纳在单个节点上时，跨节点划分。这使我们能够增加专家数量，同时保持每个 GPU 的专家状态有界，并避免过小的专家分片。

Fully-Sharded Data Parallelism (FSDP) 将参数、梯度和优化器状态切片到数据并行组中，将每个 GPU 的模型占用空间减少大约数据并行度，从而使大型检查点能够舒适地容纳在 MI325X 的 256 GB HBM 中。

Pipeline + Virtual Pipeline Parallelism (PP + VPP) 将层拆分为阶段，并交错执行前向和后向步骤；VPP 进一步将每个阶段细分为虚拟块，以便微批次交错排列，减少流水线空闲时间。

通过 EP 吸收宽度、FSDP 处理内存以及 PP + VPP 重叠前向和后向传递以减少流水线气泡，该技术栈协调了 GPU 算术、HBM 带宽和 400 Gb RoCE 流量——因此没有任何单一维度成为瓶颈。

Primus-Turbo 是一个高性能加速库，专用于在 AMD GPU 上进行大规模模型训练。在该技术栈中，Primus-Turbo 是经过 ROCm 优化的 kernel 库，用于此项工作。它提供了高性能算子（GEMM、attention、grouped GEMM）、通信原语（包括 All-to-All/DeepEP）、优化器工具，以及低精度 kernel（如 FP8），以在 AMD Instinct™ GPU 上实现高效训练。

结论与后续步骤

在上述实验中，我们采用了 EP=8，因为增加专家并行度会使 All-to-All 通信步骤变得过于昂贵。为了在扩展 EP 度时缓解这一影响，Primus-Turbo 还提供了 DeepEP 来加速 All-to-All 性能。下图比较了在 16 节点 MI325X 集群上训练 DeepSeek-V3 671B（24 层，PP 4 + VPP 3，local batch 16）时，标准 All-to-All 实现（红色）与 DeepEP（蓝色）的性能。当专家并行度（EP）从 8 提升到 32 时，普通 All-to-All 的吞吐量从大约 2000 TPS 下降到约 750 TPS，其在总运行时间中的占比从 10% 激增到近 50%。DeepEP 将吞吐量稳定维持在 2000–2100 TPS 左右，即使在 EP=32 时，通信占总运行时间的比例也限制在约 18%，使得可扩展性曲线变得平坦。
