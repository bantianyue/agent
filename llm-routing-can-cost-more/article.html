要点速览
- 核心现象：一个编码 agent 会话里有难易悬殊的多种任务，固定单一模型就让简单任务也按贵模型计价

- 真实代价：Uber 约 5000 名工程师用 Claude Code，不到半年烧光全年 AI 预算

- 关键结论：路由能省 85% 成本，但 agent 回合内切模型会击穿前缀缓存：会话必须固定在同一模型

一次编码 agent 会话通常会做五类事：分析代码库、写新函数、根据测试输出修 bug、解释方法、查文档。这些任务难度天差地别，但在一个写死模型的系统里，它们却按同一个费率计费。换句话讲，一个只需要查 docstring 的请求，和一个重构分布式系统的请求，叫价是一样的。

本文借 Uber 与 Claude Code 的真实账本，讲清楚“固定单一模型”为什么在不知不觉中烧钱，再对比自己 DIY 路由层与把路由下沉到基础设施两种做法，最后落到一个常被忽视的关键点：agent 循环里的会话固定（session pinning），才让路由真正省下钱。

Uber 的账本：单一模型包打天下

Uber 在 2025 年 12 月把 Claude Code 推广给了大约 5000 名工程师。到 2026 年 4 月，整个年度 AI 预算就花光了。重度用户一个月要烧 500 到 2000 美元，有位高管在一次两小时会话里就花掉 1200 美元。

这不是用错了工具：工程师们就是在用 Claude Code 处理它设计来对付的那些负载，一切都没坏。Uber 的对策是给每款工具设一个每月 1500 美元的上限，这能压制成本，却是在用“节流产能”换“省钱”，只治了症状。

真正的问题在于：查 docstring 和重构分布式系统被按同样的价格计费。一个轻负载请求本该走便宜模型，却和重负载请求一起被塞给最贵的模型。

路由才是没人想建的修复

直觉上的修复是路由：把每个请求发给能把它办好、且最便宜的那个模型。分类、抽取、格式化、短摘要这些任务，用成本低一个量级（约十分之一价格）的模型，产出几乎一致；而前沿模型应当只留给真正需要它的活。

这方面的研究其实已经成熟。RouteLLM 发表在 ICLR 2025，用 Chatbot Arena 的人类偏好数据训练路由器，再在标准 benchmark 上测试。它的矩阵分解路由器在 MT Bench 上能达到 GPT-4 Turbo 约 95% 的质量，同时只把 14% 的查询发给了强模型，对应约 85% 的成本下降。

这些路由器还能泛化到它们没训练过的模型配对，说明这套技术并没有过拟合到某一种配置。

把账算到自己的流量上也成立：把 70% 的请求发给 0.10 美元/百万 token 的模型，30% 发给 3 美元/百万 token 的模型，混合成本大约是 0.97 美元/百万，比统一用 3 美元的模型省得多。2026 年一篇 arXiv 动态路由综述也指出：设计良好的路由系统甚至能通过利用各家模型的专长，胜过单一最强模型。

技术已被证明可行，团队之所以仍写死单一模型，是因为路由层本身才是难啃的部分。

自己 DIY 路由，四种会崩的姿势

路由的概念很直白：分类意图，转发到对应模型。但真落地到生产中，实现层面的失败模式会不断叠加。原文逐一拆了四种。

每个请求要为两次推理买单

最直觉的做法是在前面放一个小 LLM 当分类器，于是每个请求都变成一次分类调用加一次真实推理调用。即便分类器再便宜，也是在给每个请求叠加一笔固定税。想真正省钱，分类器必须明显比你的模型层级差便宜，而且准到误导路由不会吞掉差价。

通用模型不擅长当路由器

像“fix this”“make it faster”这样的指令本身几乎不带任何信号，意图藏在整段对话历史里。通用大模型从没有被优化来解决“对照一组路由定义判定意图”这件事，现在却要它们去做训练时没练过的活；而编码负载恰恰是它们最容易翻车的地方。

路由逻辑会烂掉

新增一个模型、重命名一个任务、改一次价格档位，你就是在没有任何评估工具接护城河的情况下手改路由代码。没有任何信号会提示你某次路由改动悄悄降低了质量，直到有人报 bug 你才察觉。

翻模型会毁掉你的缓存

这一条专门针对 agent，也是最容易被忽略的失败模式。提供商会对重复的 prompt 前缀缓存注意力状态：当同样的 token 序列再次命中同一模型，缓存被复用，这部分 token 只按正常价格的一小部分计费。

若在一次会话中途切换模型，新模型对这段对话没有任何缓存状态，于是每条 token 都会按全价重新计算。一个写死单模型的系统虽然贵，但至少缓存是生效的；一个在回合间乱切模型的自制路由器，却可能比不路由更烧钱。

把路由下沉到基础设施

这四种问题其实源于同一个根因：路由逻辑长在你的应用里，于是分类器、判定逻辑、日常维护、缓存行为全都归你管。

DigitalOcean 的 Inference Router 思路正相反：把这些全挪进基础设施。你只需描述自己的任务、以及允许服务每个任务的模型池，剩下的每一次路由决策都由平台来做。

两阶段路由引擎：Plano

驱动它的核心是 Plano，一个开源的、面向 AI 的原生代理。每一次路由决策都分两个阶段。

阶段一：解析意图

一个小模型读取整段对话，把它对你的自然语言任务描述做匹配，返回一个路由决策。如果你觉得这听起来像前面说的“双重推理”问题，区别就在于：这次做分类的，是专门为此训练的模型。

Katanemo 的第一代路由模型 Arch-Router 只有 1.5B 参数，唯一任务就是读对话、对照路由描述、输出 JSON。在准确率上它赢过了 Claude 3.7 Sonnet，运行还快了 28 倍。路由不需要散文生成、不用调用工具、也不做多步推理，所以能力面够小，小模型就能完全覆盖。

它跑在代理内部，而不是作为第二笔独立 API 调用跟你计费，代价只是约 200 毫秒的额外延迟，而不是账单上多出来的一行。

现在生产环境用的是 Plano-Orchestrator，专门针对更刁钻的对话模式训练，比如含糊的追问、对话中途跑题、以及根本不该被路由的消息。它在整体路由准确率上略胜 GPT-5.1 与 Claude Sonnet 4.5，在编码这类意图最含糊的任务上领先最多。“Fix this”“try again”，只有对照它们之前的对话才有意义，而这种读法正是用它训练过的模态来读，胜过拿通用模型硬顶。

阶段二：给候选模型池排序

判定任务后，候选池收窄到至多三个模型，第二阶段就是在它们之间做选择。你可以在配置里排一次序然后永远取队首，但这种做法迟早失效：不同时段提供商的延迟会随负载波动 2 到 3 倍，凌晨 2 点最快的模型到了下午 2 点往往变成最慢的；价格、延迟、速率限制都在漂移，上个月写的配置描述的是已经不再存在的条件。

这个排序引擎从 DigitalOcean 的定价 API 拉成本、从 Prometheus 拉延迟，再按任务对应的策略给候选池排序：Cost Efficiency 按 token 成本排，Speed Optimization 按首 token 时间排，Manual Ranking 完全按你给定的顺序不做重排，Optimal 用 DigitalOcean 的基准排序。后台一个循环不断刷新这些指标并写进内存缓存，因此请求时的读取几乎零成本。

每个路由器还带一份 fallback 清单：如果被选中的模型宕了、被限流或不可用，就按策略切到下一个候选，再不行才落到你配置的 fallback 模型。

模型亲和：为什么 agent 需要不同的路由

上面两个阶段都把每个请求当成独立的来对待。但 agent 循环并不是这样工作的，而且现在几乎没有什么严肃应用还在跑单轮。编码 agent 要读文件、调工具、推理结果、写代码、再检查自己的输出，每一步都需要之前的一切，这正是循环能成立的原因。

这会把路由的计算方式整个改掉，值得仔细走一遍。

前缀缓存的账

每次 LLM API 调用都是无状态的，提供商不记得你的上一轮，于是 agent 每一轮都得把整段对话历史重新发一遍。提供商靠基于前缀的 KV 缓存来兜底：当一个请求以模型处理过的 token 序列开头，就复用缓存的注意力状态而非重新计算。命中缓存的输入 token，大约只按正常输入价格的 10% 计费。

agent 循环本质上是“重复的前缀”：一次 15 轮的编码会话会不断积累系统提示、工具 schema、文件内容、前面轮的推理。到后面的轮次，你发送的内容约 90% 都是模型已经处理过的文本。这本来是前缀缓存最理想的场景，几乎全部输入都应该命中缓存。

逐轮路由如何毁掉这一切

如果路由在每一轮都评估意图：第 3 轮是代码生成任务跑去模型 A，第 4 轮变成修 bug 又切到模型 B：这个模型 B 从没见过这段对话，堆在 A 上的缓存前缀全部作废，于是那 5 万个 token 每轮都会按全价输入重新算一遍。

一次会同时坏掉三样东西。成本：在一条约 90% 输入都命中缓存前缀的 15 轮会话里，保持模型亲和能在输入 token 上省 45% 到 80%；一旦切换模型，每轮都是 0 缓存命中、全价计费。行为一致性：不同模型的输出风格与工具调用格式不同，中途切换会破坏 agent 的解析。连贯性：推理思路被交给一个思考方式都不同、format 也不一样的模型。

解法是会话固定

路由器对某次会话的第一个请求做一次全新路由决策，然后把这个会话里后续的所有请求都钉在同一个模型上。DigitalOcean 用 X-Model-Affinity 加一个会话 ID 来实现：第二次带同一 affinity ID 的调用会跳过路由，直接返回 pinned:true 和同一个模型。

于是你只为那次路由决策付一次钱，往后的每一轮都能持续吃到缓存红利。没有这一层，agent 循环里的路由真的会让你比不路由花得更多。

结语
固定单一模型省心却烧钱，真正的问题不是“要不要路由”，而是“在哪个粒度路由”。把每个请求都当独立单元来切分的朴素路由，在 agent 场景里会因为击穿前缀缓存而比不路由更贵；只有把路由决策绑定到会话、让 agent 的整条推理链始终固定在同一模型上，缓存的账才重新划算。

对做 agent 基建与成本治理的人，这是最值得带走的一条工程判断：省 token 的关键不在模型选得有多聪明，而在别打断 provider 端已被缓存覆盖的对话前缀。定价数据（同目录里最便宜的模型和 Opus 5 差 62 倍）、延迟波动 2 到 3 倍这类事实也在提醒，路由排序必须基于实时指标而非写死配置，才会持续成立。
