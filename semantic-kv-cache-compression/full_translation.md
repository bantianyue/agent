### Semantic KV Cache Compression for Long-Context Inference

**作者：Abhinandan (@abhibuilds)**

前沿模型并不以文本形式"记住"提示词。它们将其记忆为分布在多个层和注意力头上的内部 key-value 状态。在解码过程中，模型不会从头重新读取原始提示词，而是回溯到这个缓存状态。

这个细节听起来像实现层面的机械操作，但它改变了我们思考 RAG 和 Agent 的方式。如果推理服务系统压缩了 KV Cache，它就是在决定提示词的哪些部分对模型仍然是可用的。换句话说，KV Cache 压缩不仅仅是为了节省内存，它是在选择模型还"被允许"记住什么。

对于短提示词，KV Cache 只是一个服务层面的细节。但对于长上下文 RAG、代码 Agent、文档 Agent 以及多步工作流来说，它就成了系统记忆路径的一部分。如果缓存被压缩得不好，模型可能会丢失恰好支撑着答案的那个精确 token。

这就产生了一个微妙的失败模式：检索成功了，但生成仍然失败。文档找对了，正确的句子进了提示词，答案仍然是错的——因为压缩后的 KV Cache 在解码前把关键证据丢弃了。

### KV Cache 存储了什么

Transformer decoder 一次生成一个 token。对每个新 token，每个注意力层将当前 query 向量与之前 token 的 key 进行比较，然后用匹配的 value 构建下一个隐藏表示。

没有缓存的话，模型需要在每个生成步骤对所有之前的 token 重新计算 key 和 value。KV cache 避免了这一点。在 prefill 阶段，模型处理提示词并存储每个 token 在每个层的 key 和 value 张量。在解码阶段，它追加新 token 的 KV 状态并复用旧的状态。

这使得解码速度大大加快，但缓存随上下文长度增长。提示词 token 越多，GPU 需要存储和读取的历史状态就越多。H2O 论文直接描述了这一点：KV cache 是除了模型参数之外额外存储的临时状态，其大小与序列长度和 batch size 成线性关系。

对于长上下文 RAG 来说，这是很痛苦的。用户的问题可能很短，但提示词可能包含成千上万个检索到的 token。每个检索到的块在 prefill 时都会变成 KV 状态。每多一份文档就会增加内存压力。

Grouped-query attention（GQA）通过让多个 query 头共享更少的 key-value 头来帮助降低这个成本。GQA 论文将其定位在 multi-head attention 和 multi-query attention 之间，展示了接近 multi-head attention 的质量，同时接近 multi-query attention 的解码速度。但 GQA 并没有消除问题——它减少了 KV 头的数量，而长上下文仍然推动缓存内存上升。

所以推理系统会选择压缩或驱逐 KV 状态。

### 近期性很简单，但不够

最直接的驱逐策略是滑动近期窗口（sliding recency window）：保留最新的 token，丢弃较旧的。这对于一些语言建模任务有效，因为下一个 token 通常最依赖于近期的局部上下文。如果模型在继续一个句子，附近的 token 很重要。

但长上下文任务往往需要远离提示词末尾的信息。一个 RAG 提示词可能长这样：系统指令 > 用户问题 > 检索文档 1 > 检索文档 2 > 检索文档 3 > 最终答案指令。最后的 token 可能包含格式规则或用户问题的复述，而关键证据可能埋在第 2 份文档中。一个近期性窗口可以保留提示词的结尾部分，同时丢弃证据。

StreamingLLM 在流式生成中发现了类似的问题。纯窗口注意力在文本长度超过缓存大小时会失败，但保留初始 token 可以恢复大部分性能，因为一些早期的 token 充当了注意力汇点（attention sinks）。论文还指出，这些注意力汇点即使在语义上不重要时也能接收到强烈的注意力。

这个观察很重要。高注意力并不总是等同于有用的证据。有些 token 在结构上对注意力稳定性有用，有些在语义上对回答问题有用。一个好的缓存策略不能混淆这两者。

### Heavy hitters 和注意力分数剪枝

一个更进阶的思路是保留那些收到大量注意力的 token。

H2O 引入了 heavy-hitter token 的概念：一小部分 token 贡献了注意力计算中的大部分价值。它的缓存策略动态地保持近期 token 和 heavy hitters 的平衡，在减少内存占用的同时保持任务质量。

这比纯粹的近期性改进了一大步。如果一个 token 持续收到注意力，它很可能是有用的。但是"很可能"说了很多不确定性。

注意力分数剪枝在 grounded 长上下文系统中有两个弱点。第一，注意力可能偏爱结构性 token——初始 token、分隔符、格式锚点和重复术语可能会获得高注意力，但不包含答案。第二，跨多个头聚合的注意力会冲淡专门化的行为。不同的注意力头可能做不同的工作——有些追踪语法，有些追踪位置，有些追踪近期上下文，有些检索语义重要的证据。如果驱逐策略将一切平均化，语义检索信号就会被稀释。

SnapKV 将领域向前推进到了 head-aware 压缩。它观察到每个注意力头在生成过程中可以一致地关注特定的提示注意力特征，并且可以从提示末尾附近的一个观察窗口来估计这种模式。然后它对每个注意力头选择重要的 KV 位置，而不是使用一个统一的策略。这个方向是正确的：缓存策略应该尊重不同头部在做不同的事情。

### 语义检索头

CompressKV 建立在同样的问题上，但专注于一个特定的长上下文失败模式：保留语义上重要的证据。

它的主张是，现有的 KV 驱逐方法通常对基于 GQA 的 LLM 中所有头部应用启发式评分，但这忽略了不同头部的功能，可能驱逐关键 token。相反，CompressKV 识别了语义检索头（Semantic Retrieval Heads, SRHs）——那些捕捉初始 token、最终 token 和语义上重要的中间上下文证据的头部。然后用这些头部来选择哪些 token KV 对应该保留在压缩后的缓存中。

这是一个有用的思维模型。不是每个头部都应对保留什么记忆有同等的投票权。如果某些头部更擅长从长提示词中间检索承载答案的证据，那么它们的注意力模式应该在缓存保留决策中具有更大的权重。

简化的语义 KV 保留策略如下：

```python
def retain_kv_tokens(tokens, attn, semantic_heads, layer_budget, pinned_spans):
    retained = set()

    # Always keep tokens that define task authority and answer framing.
    for span in pinned_spans:
        retained.update(span.token_ids)

    for layer in attn.layers:
        scores = defaultdict(float)

        # Score tokens using heads that behave like semantic retrievers.
        for head in semantic_heads[layer]:
            for token_id, weight in attn[layer][head].items():
                scores[token_id] += weight

        # Prefer evidence spans over isolated high-attention tokens.
        scores = smooth_over_neighboring_tokens(scores, window=3)

        budget = layer_budget[layer] - count_retained_in_layer(retained, layer)
        retained.update(top_k(scores, k=max(0, budget)))

    return retained
```

首先，固定那些不应被驱逐的 token：系统指令、用户问题、答案格式约束，有时还包括来源分隔符。其次，使用那些看起来在检索语义重要信息的头部来对候选 token 打分。第三，在小范围内平滑分数，因为证据很少是单个孤立的 token。第四，应用按层分配预算，因为不同的层可能对驱逐的容忍度不同。

关键的变化是，缓存预算不再只花在近期性或全局注意力上，而是花在任务关键结构加上承载证据的 token 上。

### 为什么层预算很重要

KV cache 压缩不仅是一个 token 选择问题，也是一个层分配问题。

一个 transformer 层不仅仅是相同计算的重复。低层、中层和高层可能扮演不同的角色——有些编码局部词法信息，有些建立长程关联，有些对丢失特定 token 状态更敏感。

CompressKV 包含使用离线估计的逐层驱逐误差来进行按层预算分配。在其报告的结果中，它使用仅 3% 的 KV cache 就保留了超过 97% 的全缓存性能（在 LongBench 问答任务上），并使用 0.7% 的 KV 存储在 Needle-in-a-Haystack 上达到了 90% 的准确率。

重要的不只是报告的数值，更是系统设计原则。均匀压缩很方便，但模型并不是均匀的。如果一个层对丢弃中间上下文证据高度敏感，而另一个层是稳健的，它们不应该收到相同的预算。缓存压缩应该知道驱逐在哪里会造成损伤。

这与生产系统中的资源分配类似——你不会在所有组件间均匀分配 CPU、内存和延迟预算，而是根据瓶颈和故障敏感性来分配。

### RAG 失败模式

考虑一个支持 RAG 系统回答这个问题："这个客户能在 30 天后获得退款吗？"

检索器找到了三个块。一个包含通用退款政策，一个包含特殊的企业合同条款，一个包含如何处理退款的操作说明。关键的句子在中间块中："30 天后，退款需要经理批准，除非客户在企业豁免名单上。"

完整的提示词包含了这个句子。检索成功了。

现在推理引擎在解码前压缩了 KV cache。一个近期性策略保留了最终的指令和最近的用户问题。一个注意力-heavy 策略保留了初始 token、来源分隔符和重复的政策术语。那条关键的例外句子在早期解码阶段收到了较低的聚合注意力，被驱逐了。

最终答案变成了："不，30 天后的退款不被允许。"

这并非通常意义上的幻觉。不是检索器未命中，不是分块策略不好。信息进入了模型的上下文，但保留的缓存不再足够好地保存它以供生成使用。

这就是为什么 KV cache 压缩必须作为 grounded 生成的一部分来评估，而不仅仅作为一个推理优化。

### 缓存压缩不是提示词压缩

另一个常见的混淆是将 KV cache 压缩等同于提示词压缩。

提示词压缩在模型处理之前改变输入文本——它从提示词中移除或重写 token。KV cache 压缩发生在 prefill 之后——模型已经处理了完整提示词，系统决定保留哪些内部 key-value 状态用于解码。

两者的失败方式不同。提示词压缩可以在模型看到证据之前就将其移除。KV cache 压缩可以让模型在 prefill 期间看到证据，但在生成依赖它之前移除其可用状态。

对调试来说，这个区分很重要。如果证据不在提示词中，检查检索、重排序、分块或提示词构建。如果证据在提示词中但被从保留的 KV 跨度中丢弃，检查缓存策略。如果证据被保留了但答案忽略了它，检查注意力行为、指令冲突或解码。

生产追踪应该使这些阶段可分离。

### 评估什么

通用的基准分数是不够的。

LongBench 很有用，因为它覆盖了长上下文任务——单文档 QA、多文档 QA、摘要、少样本学习、合成任务和代码补全（中英文）。Needle-in-a-Haystack 式的测试很有用，因为它们将目标事实放在一个更大的上下文中，测量模型是否能检索到它。

但生产环境的评估应该更进一步。对于 RAG 系统，构建那些答案依赖于一个小型中间上下文证据跨度的测试用例。改变证据的位置。在开头和结尾放置干扰块。包含策略例外、日期、否定句和特定实体的条款。然后比较全缓存、近期性驱逐、heavy-hitter 驱逐和语义保留。

测量超越最终准确率的内容：
- 保留 token 与金标准证据的重叠
- 答案对保留证据的忠实度
- 引用支持
- 按层的缓存预算
- 丢弃的关键跨度
- TTFT 和解码延迟
- batch 负载下的吞吐量
- 每请求节省的内存
- 按证据位置的失败分布

最有用的指标往往是"关键证据被保留"。如果证据 token 消失了，答案只能靠运气或先验知识正确。

### 生产系统的可观测性

一个生产系统不需要向每个工程师暴露原始 KV 张量。但它应该暴露足够的元数据来调试缓存引起的失败。

对每个请求，记录提示词跨度：系统、用户查询、检索块、工具输出、记忆条目和答案指令。然后记录哪些跨度在压缩策略下被保留或丢弃。出于隐私考虑，可以使用跨度 ID、token 范围、内容哈希和来源文档 ID，而不是原始文本。

如果最终答案是错的，你想知道相关的来源块是否被检索到、被放入提示词、在缓存中被保留、并在最终引用中被使用。

这就给出了一个清晰的失败树：检索遗漏了来源 → 提示词构建器排除了它 → 缓存策略丢弃了它 → 解码器忽略了它 → 引用层错误归属了它。每个失败对应不同的修复方案。

没有这个追踪，团队可能不断改进检索，而真正的 bug 是驱逐。或者他们可能完全禁用缓存压缩，而更窄的修复是固定来源跨度或为语义检索头分配更多预算。

### 生产权衡

语义 KV 压缩不是免费的。它可能需要分析头部特征、估计层敏感性、追踪跨度来源，以及在 prefill 期间运行额外的评分逻辑。如果实现得不好，开销可能会蚕食延迟收益。如果语义头识别是模型特定的，每次模型升级都可能需要重新校准。如果系统固定了太多跨度，压缩比就会下降。

还有一个质量-风险的权衡。更激进的预算节省更多内存，可能提高 batch 吞吐量，但也增加了丢弃重要证据的概率。保守的预算保持质量但节省较少。合适点取决于产品——一个摘要工具可能容忍小的压缩伪影，但法律、医疗或金融 RAG 系统不能。

Agent 系统增加了另一个复杂性。工具追踪和记忆条目可能很长，但有些 token 承载权威性：用户批准、提交边界的决定、工具输出、错误消息和政策约束。丢弃这些可能会改变后续运行中的行为。一个编码 Agent 忘记了确切的堆栈跟踪或测试失败，可能会自信地补丁错误的文件。

因此，保留策略应该知道跨度类型，而不仅仅是 token 位置。指令、批准、证据、工具输出和临时闲聊不应得到相同的对待。

### 大多数人误解了什么

第一个误解是，大的上下文窗口意味着模型可以同样好地使用所有内容。上下文窗口是容量，不是保证可用的记忆。一旦推理系统压缩了 KV cache，有效的记忆就是任何在驱逐中幸存下来的内容。

第二个误解是，注意力分数等于语义重要性。注意力是模型内部的路由机制——它可以突出有用的证据，但也可以突出锚点、分隔符、近期 token、频繁 token 和注意力汇点。StreamingLLM 的注意力汇点结果是一个清晰的警告：token 可以在注意力上是重要的，而不在意义上重要。

第三个误解是，检索和推理可以独立优化。在简单的 RAG 架构图中，检索发生在生成之前。在生产中，这个边界是不够的——检索到的块变成提示词 token，提示词 token 变成 KV 状态，KV 状态可能被压缩，压缩后的状态影响解码。答案依赖于整条路径。

有用的工程观点是：检索决定什么证据进入提示词，KV 保留决定什么证据在解码期间仍然可用。如果两者都没有被评估，grounded 生成可能会以看起来神秘的方式失败。

### 实践意义

对于一个生产 RAG 或 Agent 系统，安全的起点不是最大压缩，而是跨度感知的保守压缩。

固定系统指令、用户任务、最终答案指令和高置信度的证据跨度。如果引用很重要，保留来源分隔符。对其余预算使用语义或 head-aware 评分。追踪金标准或被引用的证据是否幸存。按流量类别而非全局地推出压缩。

对于长上下文 Agent，将工具输出和批准事件包含在受保护的跨度分类中。一个说"迁移失败，因为列 X 缺失"的工具结果可能比最近的对话轮次更重要。一个用户批准不应该因为发生在距离上下文末尾较远的地方而被驱逐。

对于评估，创建那些答案依赖于一个中间上下文子句的测试用例。那是缓存驱逐的自然压力测试。如果系统只在证据是最近的时候才通过，那么缓存策略就不够稳健。

语义 KV 压缩是一个推理创意变成应用质量问题的好例子。它始于一个内存优化，但触及了答案忠实度、RAG 调试、Agent 可靠性和安全边界。

模型只能使用幸存下来的记忆。这就是为什么 KV cache 驱逐应该作为 AI 系统设计的一部分，而不是一个不可见的服务细节。
