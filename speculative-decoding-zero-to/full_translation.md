## Speculative decoding, from zero to DSpark

大模型生成慢，验证快。Speculative Decoding（投机解码）利用的就是这个落差。本文讲它怎么工作，以及 DSpark 如何把它推进真实的 serving 系统。

本文由 Muse Spark 辅助起草、编辑和绘图，所有错误都归它。

最近出了一篇叫 DSpark 的新论文（来自 DeepSeek 团队），我想弄明白它相比普通投机解码到底加了什么。基本套路是廉价地起草若干 token，然后用大模型一次性验证。DSpark 在此基础上加了两个点子：更好的长草稿，以及更聪明地决定生产环境中要验证多少个起草 token。

### 1. 每个 token 都要一次完整前向

自回归语言模型一次产出一个 token。要生成第 t+1 个 token，它需要以到第 t 个 token 为止的所有内容为条件做一次前向传播。

要判断这是不是问题，我们跟着一次解码步骤走过 GPU，看看时间花在哪。要生成一个新 token，模型必须产出它的 logits（词表上的 softmax 前分数）。拿到它们意味着模型里的每个权重矩阵都要从 GPU 主存搬进计算单元。这块主存叫 HBM（High Bandwidth Memory，高带宽内存），它存着模型权重和 KV cache（存下来的注意力状态）。对一个 70B 模型、16-bit 精度，生成一个 token 的 logits 大约要读 140GB 权重。

相比之下做的算术少得可怜：每个权重对每个 token 大约只参与一次乘加。一块 H100 每秒能做约一千兆次乘加，但从 HBM 里读数据只约 3 TB/s。所以这个解码步骤是内存受限（memory-bound）的：它的墙钟时间由权重读取耗时决定，而不是由计算决定。另一极——算术本身成为瓶颈——叫计算受限（compute-bound）。解码远远没到那一步，而这个落差就是整个机会所在。在内存受限区间，算术单元大部分时间是闲着的：乘法器瞬间干完活，然后干等下一批权重流入。

漏洞在于：权重读取是按前向传播付费，不是按 token 付费。把 8 个 token 位置塞进同一次传播，权重从 HBM 只读一次，然后乘以 8 个向量而不是 1 个。内存流量几乎不变。你做了 8 倍的算术，但算术本来就是闲置资源，所以一次过 8 个位置比过 1 个只慢一点点。

你早就认识这个效应，它叫 prefill/decode 落差。Prefill 是模型读入你的 prompt。所有 prompt token 事先已知，所以它们一起过模型，每次传播几千个位置，权重读取成本被分摊到所有 token 上。解码每次传播只生成一个新 token，每次都付全价。

解码不能像 prefill 那样批处理，因为位置 t+1 的输入是位置 t 采样出的 token；在上一次传播结束前它不存在。但假设有人递给你接下来 8 个 token 的猜测。现在你就暂时有了全部 8 个输入，大模型可以 prefill 风格地一次过完。而且同一次传播还给模型在每个位置上的 next-token 分布。这些分布正是它需要的、逐位置检查这个猜测哪里开始不对的东西。验证是 prefill 形状的，生成是 decode 形状的。

谁来写这个猜测？一个更小更便宜的模型。这就是投机解码：本文里所有东西都是在把慢生成转成快验证加一个廉价猜测。

### 2. 廉价起草，并行验证

投机解码跑成一个循环：起草几个 token，验证它们，保留好的前缀，重复。大家用的版本来自 Leviathan 等和 Chen 等。一个轻量的草稿模型提出一个含 γ 个候选 token 的块。目标模型对整个块跑一次前向，在每个位置得到自己的 next-token 分布。然后它从左到右走这个块，逐位置决定是否与草稿一致。

设最后一个确认的 token 是 D，叫它锚点（anchor）：这一轮草稿挂着的那个已确认 token。草稿提出 E F G H。目标可能接受 E 和 F、拒绝 G。拒绝不是白干：目标已经在 G 的位置算出了分布，所以它从一个修正版里采样出替代 G*。G* 叫修正 token（correction token）。第一个拒绝之后的所有东西（H）都被扔掉，因为它们是以一个从未发生的 token 为条件的。

如果每个草稿 token 都被接受，这一轮就白赚一个额外 token：这次传播还在最后一个草稿 token 之后的位置算出了目标的分布，所以目标从那里采样并追加这个奖励 token（bonus token）。

### 4. 两种造草稿器的方法

自回归草稿器（EAGLE、DeepSeek 的 MTP 多头预测）是小语言模型，一次一个 token 地生成草稿，每个都以最后一个为条件。它们产出连贯的草稿，但起草成本随块大小线性增长，Tdraft ∝ γ。为了让起草便宜，它们必须保持浅（EAGLE 式草稿器通常只有一层 transformer）并让 γ 小，这同时限制了块长度和草稿器能知道多少。

并行草稿器（Medusa，以及最近的 DFlash）在单次前向里填完所有 γ 个位置。喂入锚点 token 加一排 mask token，一次性读出所有位置的 logits，diffusion 风格。现在 Tdraft 几乎与 γ 无关，所以你用得起深得多的草稿器（DFlash 用 5 层，EAGLE 用 1 层）和长得多的块（γ = 16 的成本约等于 γ = 4）。

DFlash 是 DSpark 所基于的并行草稿器，值得细说，因为 DSpark 重用了它的整个骨架。草稿器是个小 transformer，论文里 5 层。它一次起草轮的输入是锚点 token 的 embedding（目标实际确认的最后一个 token）后接 mask-token embedding（要填位置的占位符）。所有位置双向互相 attention，一次前向给块里每个位置产出 logits。草稿器甚至不拥有自己的 embedding 表或输出头，它借目标模型的、冻结的。

它的核心技巧是它看对话的方式，叫 KV injection（KV 注入）。目标处理上下文时，它几层的隐藏状态被存下来，投影降维到草稿器的宽度，并预置到每个草稿器层的 keys 和 values 之前，于是每个草稿位置都能 attend 到目标自己对所有已说内容的内部表示。这一切在 prefill 时算一次，之后每轮复用。草稿器不是用自己的 5 层去理解对话，而是读大模型的笔记，这正是它能模仿比自己大几千倍模型的重要原因。（机制与图：附录 A3。）

所以并行草稿器既跑得更快，又可以免费更深。这听起来应该完胜，但并没有……

### 5. 并行草稿器在哪崩：多峰碰撞

并行草稿器一次性、一步预测每个位置。位置 3 看不到位置 2 实际采了什么，只能看到共享上下文。所以当上下文允许多个同样好的续写时，每个位置都在它们之间对冲。

拿上下文“Sure, ”来说。目标模型对 of course 或 no problem 都满意。一个并行草稿器，从它的边际分布逐个位置采样，可以愉快地吐出 of problem 或 no course：两个有效答案的碎片缝进了一个无效答案。这就是多峰碰撞（multi-modal collision）问题，自非自回归机器翻译时代（Gu 等，2018）就为人所知。每个 token 单独看都合理，组合起来是垃圾，目标拒绝它。

损伤表现为后缀衰减（suffix decay）：接受率随块内位置迅速下滑。论文用一个漂亮的指标衡量它，叫逐位置条件接受率（position-wise conditional acceptance）：在位置 k，只统计位置 1…k−1 都被接受的情况，然后问 k 被接受的频率。这剥掉了复合存活惩罚，露出草稿器在每个深度的原始预测质量。

### 6. DSpark 点子 #1：给并行草稿器拧上一个 bigram

后缀衰减的显然修法是让草稿器重新自回归，但那样你又回到 Tdraft ∝ γ。DSpark 只在几乎零成本的地方加自回归。昂贵的部分——5 层 KV 注入的 DFlash 主干——照旧完全并行：一次传播，给每个位置产出隐藏状态 h₁…hᵧ 和 base logits U₁…Uᵧ。之后，一个小的顺序头（sequential head）从左到右扫过块，给每个位置的 logits 加一个修正，这个修正依赖于它之前已采样的 token：

在这个公式里，Uₖ 是并行主干已经给我们的：位置 k 的 base logits，对每个候选 token v 一个分数（词表 V ≈ 10⁵ 个 token），所以 Uₖ(v) 是 token v 的分数。Bₖ(x₀, x<k, v) 是顺序头对这个分数的修正，也是唯一允许看块历史的项：锚点 x₀ 和更早位置已采样的草稿 token x<k。

默认的 B 是一个小 Markov 头。它扔掉除紧邻前一个 token 之外的一切：修正变成 B(xₖ−₁, ·) ∈ ℝᵛ，一整向量 logit 修正，每个候选 next token 一个，由刚来的那个 token 选定。写成表就是个 V×V 矩阵，每行一个可能的上一个 token、每列一个可能的下一个 token。换句话说，一个学到的 bigram 模型，以秩 256 分解存储：每位置顺序循环的成本是一次表查找加一次小矩阵-向量乘，相对目标的验证传播可以忽略不计。而且它和草稿器其余部分一起学，不是从语料里数出来的（维度与训练：附录 A4）。

回到碰撞。主干并行地给出位置 1 为 {of, no}、位置 2 为 {course, problem}。顺序循环先采样位置 1 得到 of。当它移到位置 2 时，“of” 的 bigram 偏置抬高 course、压低 problem，于是草稿器不再把“of problem”缝在一起。

一个 token 的记忆够吗？作者也试了一个 RNN 头，一个小的门控递归，携带整个块内前缀而非仅最后一个 token。它只在长块上略有帮助。我认为这个近乎为零的结果正是论文里最有用的东西：并行草稿器的后缀衰减主要是相邻 token 不连贯的问题，而不是缺长程信息。

通过 KV 注入（第 4 部分），每个草稿位置已经看到目标对整个对话的表示。缺的那块是相邻位置采了什么，而这在前向结束前不存在。只有采样时跑的东西能补上这个缺口，而 bigram 是最小的这种东西。

在 Qwen3-4B/8B/14B 上，DSpark 的 macro 平均接受长度比 Eagle3 高 27–31%、比 DFlash 高 16–18%，而且 2 层的 DSpark 已经打败 5 层的 DFlash，所以增益来自依赖建模而非额外参数。在条件接受曲线上，DSpark 在 DFlash 打开的地方打开、在 Eagle3 持平的地方持平。

### 7. Serving 问题：草稿 token 争抢批空间

之前一切都是单用户故事：一个请求，一个 GPU，最小化那一个用户的延迟。生产里目标模型是共享的。一份拷贝同时服务几百个用户，它的每次前向处理一个批。批由 serving 引擎（拥有 GPU、跑模型的软件层，开源例子有 vLLM 和 SGLang，DeepSeek 跑自己的）完成。每次传播，引擎收集很多请求的待处理 token，一起推过去：第 1 部分里摊销权重读取的技巧，从跨位置改成跨用户。

但批是共享的、有限的资源。小批让传播保持内存受限，所以额外的 token 免费搭车（第 1 部分）。但一直加 token，到某个批大小算术单元不再是闲着的那个；过了这个点，每多一个 token 都让传播对所有在里面的人明显变慢。这给每个引擎一条特征曲线，SPS(B)：每秒步数作为批持有 token 数的函数。在传播内存受限时它持平，一旦批把它推入计算受限区间就开始掉，就是第 1 部分那两个区间。

一个请求提交验证的每个草稿 token 占批里一个 token 槽，被拒绝的 token 浪费它的槽。在曲线平的那段，浪费无害，所以哪怕 20% 的长 shot 也值得查。在陡的那段，同一个 token 贡献 0.2 个期望 token、却拖慢共享这次传播的其他几百个，它不值这个槽。

该验证多少也取决于内容。草稿器在结构化文本上表现好、在开放式文本上差：Qwen3-4B 上论文测到数学约 5.6 个接受 token/轮、代码 5.1、聊天 3.5。所以一个固定长度两头都错：在聊天请求上浪费那些永远到不了位置的晚期 token，在能更长的代码请求上又截断太早。

在这篇论文之前，DeepSeek 的生产系统每轮只起草一个 token，即 MTP-1 设置，尽管他们已经造了多头草稿器（MTP-3、MTP-5）。静态 3-token 起草下，每个请求给每个批加 3 个 token，不管负载或内容是否配得上，而在生产并发下其中很多是注定被拒的晚期聊天 token。批变大，每次传播变慢，跨所有用户的减速超过了多接受的 token：总吞吐下降。生产停留在从不翻车的最大设置——每轮一个 token——代价是：γ = 1 时一轮最多产两个 token（草稿加奖励），所以上限大约 2x 加速，而第 4 部分为大并行块做的所有事都没用上。

跳出这个两难的出路是别再给所有人挑一个长度，而是逐请求、逐步决定：给定此刻的负载，这个请求多少个草稿 token 配得上一个批槽？草稿器已经产出了整块 γ-token，所以那部分成本已沉没；唯一的选择是哪些 token 拿到槽，被砍掉的就悄无声息地丢了。决定需要每个 token 一个「槽能回本」的概率估计，加一条把那些估计和 SPS 曲线转成长度的规则。

### 8. DSpark 点子 #2：按期望吞吐挑验证长度

调度器是引擎（第 7 部分）的一部分，在目标模型每次前向之前决定这次传播里放什么：哪些请求参与，以及（这里的新自由度）每个请求贡献多少个草稿 token。它每步回答一次第 7 部分的问题，为整个批一次性回答。

对一次验证步骤，有 R 个活跃请求，每个都刚起草了 γ-token 块，调度器要给每个请求 r 挑一个验证长度 ℓᵣ ∈ {0, …, γ}：验证前 ℓᵣ 个草稿 token，丢掉其余。一个长度选择由这一步整个系统的期望 token 吞吐来评判：

SPS(B) 是第 7 部分的成本曲线；引擎在启动时对一系列批大小计时测一次，把结果存成查找表。τ 是这次传播会给整个批产出的期望输出 token 数，即第 3 部分逐请求的 τ 跨 R 个请求求和。两个 +1 都是锚点：即便 ℓᵣ = 0，一个请求仍送一个 token 过传播、拿一个回来，即第 2 部分的奖励或修正。每个被接纳的、位置 j 的草稿 token 然后给 τ 加 aᵣ,ⱼ：它在验证中存活并真正进输出的概率。每步期望 token 数乘每秒步数得期望每秒 token 数。唯一缺的那块是那些存活概率 (aᵣ,ⱼ)。

**置信度头（confidence head）**

一个槽「回本」意味着什么？一个草稿 token 在从左到右的检查真的走到它（块里每个更早 token 都被接受）且也接受了它时才在验证中存活。「走到它」是批验证的代价：整块一次过，但接受只认前缀，所以位置 3 的拒绝意味着位置 4 及之后被丢弃、从没被查过，不管它们的 token 多好。

为此他们用一个置信度头，每个位置输出一个标量 cₖ，存活的条件部分：在检查走到位置 k 的前提下它被接受的概率。这就是第 5 部分曲线测的那个条件接受率，现在逐 token 预测而非在 benchmark 上平均。头本身很小。它读主干隐藏状态加前一个 token 的 Markov embedding，过一次线性投影加 sigmoid。它的训练标签是免费的：第 2 部分的精确接受概率在每步训练都可算，直接当软标签用（附录 A4）。

这些每请求算出的 aₖ，正是目标函数吃的 aᵣ,ⱼ，只有一个要求：算术只在分数被校准（calibrated）时才成立，即一个被打了 0.8 的 token 真的约 80% 的时候被接受。原始头过于自信；逐位置温度缩放把预测-观测差距从 3–8% 缩到约 1%（附录 A5）。

一次性挑所有 R 个长度听起来是组合问题，但存活概率有个性质让这变简单。在一个请求内，aᵣ,ⱼ = cᵣ,₁·cᵣ,₂⋯cᵣ,ⱼ 是 0 到 1 之间数的乘积，所以再添一个因子只能让它缩小：aᵣ,₁ ≥ aᵣ,₂ ≥ … ≥ aᵣ,ᵧ。换句话说，活到 j+1 需要先活到 j，所以它是更严的条件。

这个顺序正是贪心算法能用的理由。把请求 r 的长度从 j−1 扩到 j 给 τ 正好加 aᵣ,ⱼ、给 B 正好加一个 token，一得益一成本都事先已知。所以把所有请求的候选扩展倒进一个池，按 aᵣ,ⱼ 排序，从顶上接纳，每接纳一个重算 Θ（一次查表）。请求内约束（没位置 1、2 就不能验证位置 3）自己就强制了：因为每个请求的存活概率已经递减，它的位置 2 候选总在位置 3 候选之上。

当批几乎空时，SPS(B) 停在平的段，接纳另一个 token 几乎免费抬高 τ，调度器验证得长：论文数字里每请求 4–6 个 token。随着批填满，每个被接纳的 token 把 SPS 往下拖，只有存活概率胜过拖累的 token 才进得去，预算缩水。在一个批内，0.9 置信度的代码请求保持长验证，而置信度在位置 2 就崩的聊天请求在那被砍，全程没有设任何阈值。

**一个破坏无损性的版本**

无损性除了第 2 部分的接受/拒绝规则还需要一个条件，这个落在调度器上：token k 是否被接纳验证不能依赖 token k 的值。证明管这叫非预知性（non-anticipation）。固定验证长度平凡地满足它，但上面贪心搜出来的长度可能违反它。

违反穿过置信度头，它读前一个采样 token 的 Markov embedding：c₂ 因而 a₂ 是抽了哪个 x₁ 的函数。块在调度前就完全采样了（第 7 部分），所以 a₂ 可用；问题是调度器能不能查它。假设它评估整条接纳路径取 argmax：长度 0、1、2 的 Θ。长度 2 的值用了 a₂，而 a₂ 用了 x₁。所以决定 x₁ 是否被接纳的比较已经依赖抽了哪个 x₁，而导向自信续写的草稿 token 比不自信的被更多地接纳。

例如二元词表：目标想要 {A: 0.7, B: 0.3}，草稿从 {A: 0.5, B: 0.5} 采样，假设抽 A 导向高 c₂、抽 B 导向低 c₂，于是 argmax 调度器在抽 A 后接纳草稿、抽 B 后跳过。抽 A 时（概率 0.5）它被接纳、以 min(1, 0.7/0.5) = 1 被接受。抽 B 时什么都不接纳、目标从 {0.7, 0.3} 重新采样。总计：P(输出 = A) = 0.5 + 0.5 × 0.7 = 0.85 而非 0.7。

干净算法的解决方案是一个 early-stopping 断点：走排序的接纳路径，在第一个降低 Θ 的接纳处停。于是关于位置 k 的决定在查任何由 xₖ 算出的东西之前就定下了，证明才走得通。

### 9. 让它在真实引擎里跑起来

在 DeepSeek 的真实引擎里，第 8 部分的算法在两处崩。第一处是 SPS 曲线不平滑。Kernel 是为特定批形状调的，所以传播时间在 tile 大小和 dispatch 边界处跳变而非渐升。在锯齿曲线上，early-stopping 断点变成负担：Θ 可能在悬崖处跌、刚过悬崖又恢复，而在第一个坑就退出的搜索把系统困在局部最优。

第二处关于 timing。现代引擎在当前传播跑着时就在组装下一次传播，而用 CUDA-graph replay 时下一次批大小必须在当前传播结束前定好。第 8 部分的调度器赶不上这个截止，因为它需要当前步的置信度分数，而那些在步做完前不存在。同步跑它，GPU 在每对步之间停顿。

部署版通过把批容量提前几步算好，绕过这两个问题。调度器用两步之前的置信度分数定下 K——下一次传播能负担验证的 token 数——于是它在传播启动前就准备好了。真正填满那 K 个槽的 token 仍在这一刻从当前步的真实置信度分数里挑，按第 8 部分排序活候选、保留前 K 个。

这个设计也了结了第 8 部分那个无损性问题，那里危险在于算截断时查了下游 token 值。这里截断是 K，从两步前的旧数据定下、在这一步任何 token 存在之前，而填槽的新鲜排序只查块里更早的 token，从不是 token k 自己或它之后的任何东西。这正是非预知性要求的，所以它构造上成立，early-stopping 断点可以去掉，在锯齿曲线上的搜索可以全局跑到真最大值。同一个设计选择既修了流水线停顿又恢复了精确性；我猜流水线约束是先来的，无损性论证是事后才注意到的。

### 10. 真正要记住什么

DSpark 重要的不只是它让投机解码更快。更早的工作大多问怎么造更好的草稿器：更便宜、更深、或更准。DSpark 表明这只有一半故事。在真实 serving 系统里，问题不是「我能起草多少 token？」而是「此刻哪些起草 token 值得花目标模型批容量？」论文的两个主要点子回答了这个问题的两面：一个半自回归的 Markov 头让长并行草稿连贯得多，一个吞吐感知的调度器决定在当前负载下验证草稿的多少。

### A. 附录：细节

**A1. 为什么拒绝规则精确**

查任意 token v。它两种路进输出：被起草并保留，或被拒并重采样。若 pᵗ(v) ≤ pᵈ(v)，保留路单独贡献 pᵈ(v)·pᵗ(v)/pᵈ(v) = pᵗ(v)，残差在 v 上质量为零。若 pᵗ(v) > pᵈ(v)，保留路贡献 pᵈ(v)，重采样正好补上缺的 pᵗ(v) − pᵈ(v)，因为整体拒绝概率等于残差的归一化常数。任一种路都得到 pᵗ(v)。同样的账说明为什么替代不能简单从 pᵗ 抽：接受已经给了每个 token min(pᵗ, pᵈ)，所以拒绝支可能只补给短欠。pᵗ = {A: 0.7, B: 0.3}、pᵈ = {A: 0.5, B: 0.5} 时，从完整 pᵗ 重采样会给 P(A) = 0.5 + 0.2 × 0.7 = 0.64 而非 0.7，把输出偏向草稿过提议的 token。

**A2. 距离是全变差不是 KL**

接受公式里的距离是全变差（total variation, TV）不是 KL。TV 对称，所以没有前向或反向版本，Pinsker 不等式（TV ≤ √(KL/2)）说压任一个 KL 下去也都把接受率推上去。论文的蒸馏损失跳过代理、直接最小化 L1 项，所以它优化的是接受率本身。

**A3. KV 注入，细说**

它的核心技巧是看对话的方式，叫 KV 注入。草稿器从不在文本上读上下文，也从不在它上面跑自己的前向。它回收目标已经做完的工作。目标处理上下文时，它的每一层对每个 token 产出一个隐藏状态：一个在该层把之前所有信息混进来之后编码那个 token 的向量。DFlash 从这些目标层存下隐藏状态；不同深度带不同抽象级别，从早期表层特征到晚期语义，于是草稿器拿到的是横截面而非单一视图。对每个上下文 token，存下的向量跨所选层拼接，过一个学到的投影降维到草稿器小得多的隐藏大小，给每个上下文 token 一个紧凑上下文向量。这一切在目标 prefill 时算一次，之后每轮复用。

这些向量通过 attention 进草稿器。回想那的角色划分：queries 问，keys 和 values 是被读的。在草稿器的每一层，上下文向量被投影成 keys 和 values，预置到该层自己的 keys 和 values 之前，于是从草稿位置的视角看它们像可以 attend 的额外 token。草稿位置做查询；目标的表示做回答。每个草稿位置因此同时看到两样：它块里的其他位置，和目标自己对一切已说内容的内部摘要，在多个深度上。草稿器不是用自己的 5 层去理解对话。它在读大模型的笔记，而笔记正是由它要模仿的那个网络写的，这正是 5 层模型能预测比自己大几千倍的模型接下来说什么的重要原因。

一个构造细节：原 DFlash 里锚点加 γ 个 mask 进去、只预测 mask 位置；DSpark 把它削成锚点加 γ−1 个 mask、也在锚点槽预测，同样质量下省一点计算。

**A4. Markov 头与置信度头：维度与训练**

在这个词表大小下 bigram 表会有约 10¹⁰ 项，所以分解存储：B = W₁W₂，W₁ ∈ ℝ^{V×256}、W₂ ∈ ℝ^{256×V}。W₁ 的第 xₖ−₁ 行是前一个 token 的 256 维 embedding（论文的 Markov embedding，第 8 部分的置信度头也读它），乘 W₂ 把它扩回 V 维修正。每位置：一次表查找加一次 256×V 矩阵-向量乘。

W₁ 和 W₂ 不从语料统计数出来。它们和草稿器其余部分一起用梯度下降学，训练去模仿冻结目标的输出，以第 2 部分的 TV 距离为损失一部分。

置信度头的训练标签是免费的。第 2 部分表明一个位置的接受概率正是 1 − ½‖pᵈ − pᵗ‖₁。训练草稿器本来就要算两个分布：冻结目标在训练数据上跑提供监督，给出每个位置的 pᵗ，pᵈ 是草稿器自己的输出。所以真实接受概率在每步训练都以闭式可得，置信度头直接用它当软标签监督，从不需要模拟接受/拒绝决定。

**A5. 校准置信度头**

一个置信度头被校准，如果它的数字意味着它说的：所有被打 0.8 的 token 里约 80% 真的被接受。更简单的方案不需要这个。像「丢掉 0.4 以下一切」的阈值规则只把分数和 cutoff 比，所以只要更好的 token 分更高就工作，哪怕每个分都膨胀。DSpark 的调度器用分数做算术。它把它们乘进存活概率、把那些求和成整个批的期望 token 数，所以如果头说 0.9 而真相是 0.7，计数就错，调度器最后最大化一个不存在的吞吐。神经置信度估计可靠地、正是这样地过于自信。

修法是温度缩放加一个转折，论文叫 Sequential Temperature Scaling（顺序温度缩放）。因为调度器吃累积乘积 aₖ = c₁⋯cₖ，校准针对的是乘积而非原始分数：从左到右走，每个位置得一个温度，在留出集上拟合来缩预测和观测到的累积乘积接受之间的差距，更早位置保持固定。温度缩放只重标分数，从不重排它们，所以头学到的排序保留。预测和观测接受之间的平均差距从 3–8% 降到约 1%。

**A6. 空系统极限**

在空系统的极限，最大化说要验证整块 γ-token，因为一个被接纳的 token 只能给 τ 加东西。所以轻负载速度上限由 γ 和草稿器质量而非调度器决定，这也是第 6 部分拼命在长块保持高接受率重要的部分原因。轻负载不原谅的唯一成本是 T_draft，不管验证什么每轮都付。
