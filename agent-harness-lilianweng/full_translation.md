# 递归自我改进的概念

递归自我改进（RSI）的概念可以追溯到 I. J. Good（1965 年），他将"超智能机器"定义为一个能在所有智力活动上超越人类、并设计出更好的机器来改进自身的系统。Yudkowsky（2008 年）用"递归自我改进"这个短语来描述一个特定的反馈循环：AI 利用它当前的智能去改进产生其智能的认知机制。

在现代 AI 中，这个反馈循环可能意味着模型直接重写自己的权重，或者更广泛地说，模型改进训练流水线和部署系统，这反过来又催生出在经济价值任务上表现更好的后继模型。已经有研究表明，AI 的研究开发速度在顶尖实验室（Anthropic、OpenAI）中已经大幅加速。

我特意提到"部署系统"，是因为原始模型和真实世界上下文之间的这一层，似乎和模型原始的智能（即预训练之后立刻做的评测）一样重要。Harness 是 AI 部署的重要组成部分，像 Claude Code 和 Codex 这类成功的编码 Agent 产品就证明了这一点。Harness 是包围着基座模型的一套系统，它编排执行、决定模型如何思考与规划、如何调用工具和行动、如何感知和管理上下文、如何存储产物、以及如何评估结果。

这一篇博文将聚焦于围绕 Harness 工程的研究，以及它如何贡献于 RSI。近期的许多关于自动研究、自我改进 Agent、以及进化式程序搜索的工作，都可以围绕这个问题来组织。其他关于模型自我博弈、合成数据、测试时训练，以及更广义的持续学习主题的工作也符合 RSI 的愿景（例如 Yuan 等人 2024、Chen 等人 2024、Zhao 等人 2025、Choi 等人 2026），但它们不是本文的重点。

# Harness 设计模式

与早期的 Agent 框架"Agent = LLM + 记忆 + 工具 + 规划 + 行动"相比，Harness 工程还额外包含了工作流设计（例如循环工程）、评测、权限控制，以及持久化状态管理。它不再只是提示词模板，而更接近运行时和软件系统设计：模型如何观察、行动、记忆、自检并改进。

设计应当刻意保持简单和通用，以实现泛化能力，并且很可能要参考已有的软件工程实践，从而受益于预训练知识。Harness 与操作系统之间也存在强烈的类比。和操作系统类似，Harness 应当封装复杂的逻辑，同时让接口保持简单。与此同时，配置、工具接口和其他协议可能会逐渐在整个行业中被标准化。

## 模式一：工作流自动化

定义一个模型可以在其中操作、测试、迭代的工作流，是自动化的一个关键设计。Karpathy 的 autoresearch 仓库是一个清晰的例子，展示了如何构建这样的工作流。一个常见的工作流遵循"目标导向的循环"：规划、执行、观察/测试、改进，然后再次执行，直到目标达成。这个过程可能会主动向用户请求澄清任务规格或执行偏好。

一个简化的 Codex Agent 循环：Agent 调用工具，工具的响应影响模型的下一步生成。

工作流图还强调模型分析自身的轨迹和失败案例，然后通过一个"Agent 运行时"而非静态提示模板来迭代推进它的进展。

## 模式二：文件系统作为持久记忆

在长期任务（long-horizon）的 Agent 系统中，一个反复出现的模式是对丰富状态和产物进行简单的控制。Harness 不应该把整个工作流和所有日志都塞进上下文；相反，它应该把持久状态保存在文件中。在长期任务的 Agent 展开中，像实验日志、代码 diff、论文摘要、错误追踪、以及过去的展开轨迹这样的产物，往往会增长得比模型训练时所适应的上下文窗口长得多。

学习如何读写和编辑文件系统（通常通过 bash 命令）是 LLM 的一项基础技能，因此以文件这种简单形式来管理持久记忆，自然会受益于核心模型能力的提升。

## 模式三：子 Agent 与后台任务

一个 Harness 可以生成多个子 Agent 并行执行，并监控后台任务。当主 Agent 需要搜索多个假设、并发运行实验、或把孤立的子任务委派出去而不污染主上下文时，这很有用。然后父 Agent 需要一个小型进程管理器：启动任务、检查日志、取消失败的运行、并把结果合并回主 Agent 线程。

关键的设计选择是让并行显式化且可检查。如果子 Agent 的输出只活在短暂的聊天上下文里，它们很快会变得过时和隐蔽。如果它们被存储为文件、日志和状态记录，模型就能在中断后恢复，并基于自己的执行历史进行推理。

# Harness 层 vs 核心智能？

很难预测未来 RSI 会在多大程度上依赖 Harness 工程，但 RSI 的近期路径不太可能直接从一个模型重写自己的权重开始。我对一个务实的近期路径的预测是：

Harness 工程会朝着元方法论（meta-methodology）的方向演进，也就是改进"获得更好答案的机制"，而不仅仅是改进答案本身。Harness 系统本身成为一个优化目标，启发式规则更少，通用机制更多。

反过来，成熟的 Harness 支撑起模型自我改进的自动研究循环，而更聪明的模型又防止 Harness 过度工程化，让系统保持可持续。

最终，许多 Harness 改进有可能被内化进核心模型行为中，但与外部上下文和工具的接口应当保留。我们已经在提示工程上看到过这个模式的温和版本：随着指令微调和模型推理能力的提升，手工提示技巧变得不那么核心，但"指定目标、约束、上下文和评测"的需求并没有消失。

# Harness 优化

Harness 系统中被优化对象的演进大致是：指令提示词 → 结构化上下文 → 工作流 → Harness 代码 → 优化器代码。随着模型变得更聪明、更强大，我们转向更复杂的优化目标和通用方法。

## 上下文工程

简单地把所有的工具响应和模型生成都追加进上下文，随着 Agent 任务跨度显著拉长，会很快失控。上下文管理是一个层，用于为 LLM 构建更结构化、更简洁的上下文，并管理持久状态。毫无疑问，长上下文研究会继续取得进展，但目前长上下文智能和上下文工程有时是交织在一起的。

Agentic Context Engineering（ACE；Zhang 等人 2025）把上下文当作一个演进中的"操作手册"（playbook），而不是一个越来越长的提示词。它有三个组件来维护一份上下文操作手册，由要点组成，每条带一个标识符和一段描述。

生成器（Generator）：参考要点，产生任务轨迹。

反思器（Reflector）：从成功和失败的轨迹中提炼洞见。

策展器（Curator）：用增量的、逐项的方式更新结构化上下文。

ACE 的框架。（图片来源：Zhang 等人 2025）

为了防止迭代重写过程中的上下文坍缩和简短偏见（brevity bias），ACE 的一个关键设计选择是：策展器不重写整个提示词块。它转而输出一组结构化的、逐项的要点，形式为（标识符，描述），这些要点以确定性逻辑合并进一份结构化的上下文日志。上下文条目会被定期细化和去重。

ACE 从展开中学习洞见，这帮助我们走向自我管理的记忆，但更新规则和整体工作流仍然是手工设计的。为了走向更自我改进的循环，Meta Context Engineering（MCE；Ye 等人 2026）把机制（如何管理上下文）与产物内容（上下文中是什么）分离开，在元优化层面运行技能进化，在基础层面运行上下文优化。

一个 MCE 技能 s∈S 定义了一个上下文函数 c_s=(ρ_s, F_s)，并把一个输入 x 映射到上下文 c=F_s(x; ρ_s)，其中：

ρ_s={ρ_1,…,ρ_m} 是静态组件（提示词、知识库、代码库）。

F_s={F_1,…,F_k} 是动态算子（搜索、选择、过滤、格式化）。

双层优化是在训练数据上找到给定技能 s 的最佳上下文 c_s*，而外层循环在验证集上找到提供最佳性能的最佳技能：

内层：c_s*=argmax_{c_s} J_train(c_s; s)

外层：s*=argmax_{s∈S} J_val(c_s*)

技能数据库追踪先前技能、上下文函数和评测指标的历史：H_{k-1}={(s_i, c_i, J_i^train, J_i^val)}_{i=1}^{k-1}。一个元级 Agent 针对给定任务 τ 对先前技能执行 Agentic 交叉（crossover），创造新技能：s_k=crossover(τ, H_{k-1})。

然后一个基础级上下文工程师执行技能 s_k，并从展开反馈 R_k 中学习上下文函数，在当前技能引导下：c_k=engineer(τ, s_k; c_{k-1}*, R_k)。

MCE 的框架：元级技能进化搜索上下文管理机制，而基础级优化任务上下文。（图片来源：Ye 等人 2026）

MCE 不像 ACE 那样强制规定如何结构化上下文的启发式规则。它使用自由形式的技能来存储任务最重要的知识，并迭代地共同进化技能和"技能条件化"的上下文。在实现上，一个上下文函数 c 被实例化为一个专用目录中的一组文件，包含静态（skill.md）和动态（上下文与数据展开）组件。元级和基础级的优化都在 Agentic 编码环境中、用标准工具集 T={Read, Write, Edit, Bash, Glob, Grep, TodoWrite} 执行。

Meta-Harness（Lee 等人 2026）又往深了一层：被优化的对象是"决定并优化应当存储、检索和呈现给模型哪些信息的代码"。它名字中的"Meta-"意味着它是一个用于优化 Harness 的 Harness。

Meta-Harness 外层循环优化算法。（图片来源：Lee 等人 2026）

用于创建新 Harness 的提议者（proposer）本身就是一个编码 Agent，最终输出是帕累托前沿上的一组 Harness 候选。

整个执行历史通过文件系统可访问，因此编码 Agent 使用 grep 或 cat 这样的命令去通读历史，而不是把所有内容都铲进单一提示词上下文。

被提议的 Harness 是一个存在于文件系统中的字典，包含它自己的源代码、分数、展开轨迹和状态更新。

Meta-Harness 循环迭代地创建新 Harness，只保留合格的那些。

Meta-Harness 在（左）文本分类（少量迭代）和（右）TerminalBench-2 上的表现。注意 TerminalBench-2 实验的搜索是从 Terminus-KIRA 和 Terminus-2 这两个很强的 Harness 初始化的。（图片来源：Lee 等人 2026）

尽管如此，重要的一课很清楚：一旦 Harness 设计变成一个可执行的搜索空间，强大的编码 Agent 就能利用人类工程师所用的同一套设计空间。

# 工作流设计

Harness 工程中的工作流设计可以由领域专家手工完成。以自动研究为例，已经提出并测试了各种框架。AI Scientist 系统（Lu 等人 2026）构建了一条流水线，用于提出研究想法、写代码、运行实验、分析结果、撰写手稿并进行同行评审。Meng 等人（2026）在 ScientistOne 中把"可验证性"作为中心设计约束，其中每一个主张（引用、数值、方法、结论）都必须追溯到证据来源，并由 Chain-of-Evidence 检查来审计。

AI Scientist 用于想法生成、实验、论文撰写和评审的流水线。（图片来源：Lu 等人 2026）

Autodata Agent（Kulikov 等人 2026）被设计成一个数据科学家，用于生成训练和评测数据。主 Agent 管理一个挑战者（提出问题的）、一个弱解算器、一个强解算器，以及一个验证者/裁判，目标是合成出"难度恰好合适"的数据，也就是强解算器能成功、但弱解算器会失败。

在 Autodata 中，挑战者提示词根据来自解算器和验证者的反馈迭代更新。这里的局限是：合成任务被用来微调弱解算器，而不是强解算器；如果循环不能迭代地改进强模型，它就更像是针对一个生成提示分布做的间接蒸馏，RSI 的意味较弱。

Autodata 围绕挑战者、解算器和验证者角色生成合成训练与评测数据的 Agentic 工作流设计。（图片来源：Kulikov 等人 2026）

工作流的设计空间极其庞大，我们自然可以把工作流设计看作一个搜索问题，因此我们应当能够通过算法而非仅手工设计找到好的解。沿着这个方向，Automated Design of Agentic Systems（ADAS；Hu 等人 2025）把 Agent 设计本身形式化为一个优化问题，即"元 Agent 搜索"，其中一个元 Agent 提出 Agentic 工作流的新设计。

用一个简单 Agent（如 CoT 和 self-refine）初始化一个 Agentic 工作流档案库（archive）。

让一个元 Agent 参考档案库中已有的解，用代码编写新的 Agent。

元 Agent 先生成新工作流的高层描述，然后用代码实现它。

草稿程序随后经过两次 self-refine 步骤（即让模型提供反馈，再让同一个模型根据反馈精修先前生成的输出；Madaan 等人 2023）来检查它的新颖性。

评估每个新候选，把成功的加回档案库。

重复步骤 2-3，直到达到最大迭代次数。

ADAS 的示意图。（图片来源：Hu 等人 2025）

AFlow（Zhang 等人 2025）把一个 Agentic 工作流表示为一张图，其中节点代表调用 LLM 的动作，边用代码实现逻辑操作。工作流优化依赖 MCTS（蒙特卡洛树搜索）：

用模板在树中初始化起始工作流 W_0。

用分数和均匀探索的软混合选择一个工作流节点。

通过让 LLM 基于其评测表现产生一个修改后的工作流来扩展它。

如果新工作流在 N 轮预算内显示出改进，就把它加回树中。

重复步骤 2-5，当 top-k 平均分数趋于平稳或达到预算时停止。

AFlow 在问答、代码和数学任务上的实验显示，它相比手工设计的工作流和 ADAS 都有不错的提升。

# 自我改进的 Harness

无论是上下文工程还是工作流设计，都只是 Harness 的一部分。我们需要搜索整个设计空间，并把上下文管理逻辑、工作流、权限以及许多其他 Harness 组件一起优化。正如我们在 Meta-Harness、ADAS 和 AFlow 等工作中看到的，代码是定义程序和系统的通用语言。简而言之，一个 Harness 就是一段代码，它编排了提示词、工具调用、子 Agent、控制流、记忆和工作流逻辑如何协同工作。如果一个 LLM 能优化执行 Agent 的代码，它就能进入比手写提示词大得多的设计空间。

Self-Taught Optimizer（STOP；Zelikman 等人 2023）是递归脚手架改进的早起例子之一。一个种子改进器 I_0 在步骤 t=0 时，接受初始解 s、效用函数 u 和一个黑盒语言模型 M，返回一个改进的解 s'，即 s'=I(u, s; M)。STOP 的目标不是直接改进 s，而是改进改进器 I 本身。

首先，我们把元效用（meta-utility）定义为给定改进器函数 I 在一组下游任务 D 上的平均效用：û(I)≜(1/|D|)E_{(u,s)~D}[u(I(u, s; M))]

因为改进改进器函数本身就是一个优化问题，我们可以基于 I_{t-1} 用元效用度量的表现，通过自我改进更新递归地得到 I_t 的新版本：I_t=I_{t-1}(û, I_{t-1}; M)

STOP 的算法。（图片来源：Zelikman 等人 2023）

在 Zelikman 等人（2023）的实验中，改进后的改进器发现了各种策略，如遗传算法、分解并改进局部、多臂提示词赌博机、模拟退火、改变温度，以及束/树搜索。这类似于一个 Harness 工作流如何被表示为一个可供优化的对象。

STOP 发现的自我改进策略示例。（图片来源：Zelikman 等人 2023）

他们发现中一个警示性的结果是：STOP 在 GPT-4 上随迭代提升了下游平均表现，但在更弱的模型（如 GPT-3.5 和 Mixtral）上却退化了。仅靠递归结构是不够的。基座模型必须有足够的能力去改进这个机制。这意味着 Harness 改进能实现更好的模型部署，但智能仍然是核心。

一个更近期的工作 Self-Harness（Zhang 等人 2026）依赖 LLM Agent 通过"提议-评估-接受"循环来改进自己的 Harness。

Self-Harness 使用"弱点挖掘、有界 Harness 提议、验证"的循环来更新一个 Harness。（图片来源：Zhang 等人 2026）

Self-Harness 中的循环分三个阶段：

弱点挖掘（weakness mining）：把失败聚类成"以验证器为根据的失败模式"（verifier-grounded failure patterns）。

当前的 Harness h_t 被用来在任务上做评测，并收集执行轨迹用于分析。

注意两次运行可能在错误日志的表面共享相同的验证器结果（如超时或缺失产物），却有不同的因果机制。因此我们需要一份信息丰富的失败记录，包含终端验证器层面的原因、相关 Agent 行为的因果状态，以及轨迹暴露出的抽象 Agent 机制，从而揭示根因。

Harness 提议（harness proposal）：基于挖掘出的失败模式，提出有界的 Harness 修改。

同一个模型在 h_t 下被调用，充当提议者。

模型被提供一份"有界提议上下文"：（1）当前 Harness 的可编辑面；（2）来自评测系统的、以验证器为根据的失败模式；（3）应当保留的"已通过行为"记录；（4）先前尝试过的修改的摘要。

Harness 修改应当优先处理可解决（例如不是任务特定的难度）且能通过窄改动解决的反复出现的错误模式。

Harness 修改候选应当彼此不同且多样。

提议验证（proposal validation）：验证并合并合格的修改，创建新 Harness h_{t+1}。

候选修改通过"held-in 数据 D_in"（用于测试弱点是否被解决）和"held-out 数据 D_out"（用于检查是否引入了其他未知问题）上的回归测试来评估。

只有当候选在 held-in 和 held-out 数据上都没有回归时，才被接受。

被接受的候选被合并以把 Harness 更新到 h_{t+1}，而被拒绝的候选会被记录，但不改变活跃的 Harness。

当在 Terminal-Bench-2 上运行 MiniMax M2.5、Qwen3.5-35B-A3B 和 GLM-5 时，Self-Harness 被证明能学到针对不同基座模型不同弱点的、模型特定的 Harness 指令，并提升 held-out 通过率。

Self-Harness 这类工作确实让我担忧：如果一个程序被允许编辑操作系统，抽象边界就被打破了。可编辑面需要被恰当设计，权限控制和安全层需要存在于这个循环之外。围绕奖励黑客（reward hacking）的所有挑战仍然存在。

# 进化式搜索

进化式搜索是一种受自然选择启发的优化方法（见我关于进化算法的旧文）。它通过变异来进化一组解，只保留种群中"适应度"高的那些。当（1）搜索空间很大或形状古怪；（2）很难用梯度直接优化、却容易评测算力时，进化式搜索就派上用场。Harness 搜索似乎正好契合这种情形。

进化式搜索在过去的研究中已被用于提示词工程。Promptbreeder（Fernando 等人 2023）通过一组丰富的变异操作来优化任务特定的提示词，有趣的是，那些用于变异的提示词（即让 LLM 去变异任务提示词的指令）本身也通过进化被改进。GEPA（Agrawal 等人 2025）把基于反思的提示词与进化式搜索结合，利用对试错轨迹的自然语言反思来提出提示词更新。

Novikov 等人（2025）提出了 AlphaEvolve，一个编码 Agent 的进化式搜索系统，它存储一组候选程序和提示词，并冻结 LLM 来生成用于改进的 diff。随着系统反复评测子程序并保留成功的那些，它会随时间发现更好的解。

AlphaEvolve 如何工作。（图片来源：Novikov 等人 2025）

AlphaEvolve 的设计中有几个细节很重要：

提示词包含父程序、结果、指令，有时还有元信息。

编码 Agent 能访问整个仓库，但用于改进的代码区域用 # EVOLVE-BLOCK-START 和 # EVOLVE-BLOCK-END 显式标记。

元提示词（meta-prompt）随指令和上下文共同进化，就像我们进化解程序的方式一样。

消融实验显示了进化过程、提示词中的上下文、元提示词、全文件进化，以及使用更强的 LLM 的价值。

消融实验显示了 AlphaEvolve 中若干设计的价值。（图片来源：Novikov 等人 2025）

近期的变体如 ThetaEvolve（Wang 等人 2025）把进化式搜索与 RL 和上下文学习结合。而 ShinkaEvolve（Lange 等人 2025）引入了三个新组件来提升 LLM 采样效率：

通过设计父代采样来平衡性能排名和子代数量，实现更省样本的探索。

基于嵌入的余弦相似度，丢弃与现有种群过于相似的候选，做"代码新颖性拒绝采样"。

在元记事本（meta-scratchpad）中识别成功解中的好模式，以引导未来的变异。

与上面聚焦于"解改进"的方法不同，Darwin Gödel Machine（DGM；Zhang 等人 2025）明确地把"可编辑的 Harness 代码仓库"的进化作为目标，用一个基于 LLM 的编码 Agent 来实现。准确地说，这个 Agent 被允许修改它自己的 Harness。后续工作 Hyperagents（Zhang 等人 2026）引入了一个元 Agent 来控制如何修改现有的任务 Agent 以创造新的 Agent。

从池中的一个编码 Agent 开始。

每次迭代，以一个概率挑选一个父代（概率与其性能成正比，与其子代数量成反比）来修改并分叉，产生新的 Agent。

被选中的父代 Agent 检查它自己的基准评测日志，然后对自己的 Harness 代码库提出改进，生成新版本的编码 Agent。代码编辑用两个基本工具实现：（1）bash（参数：<bash_command>）；（2）编辑器（参数：view/create/edit <file_path>）。

新的编码 Agent 被评测，只有性能足够高的才被加回池中。

重复步骤 2-4，直到满足某个停止准则。

DGM 是在固定模型下的 Harness 进化。在以 Claude 3.5 Sonnet 为基座 LLM、简单初始 Harness 配置的实验中，DGM 发现的 Agent 在 SWE-bench Verified（20% 到 50%）和 Polyglot（14.2% 到 30.7%）上可与手工设计的 Agent 媲美甚至超越。

这类方法在候选解可自动评测、候选适应度易于量化时表现良好，例如矩阵乘法、GPU 核优化、算法竞赛、数据中心调度。它们在评测缓慢、模糊、或主要靠启发式的领域会遇到困难。进化的计算效率和效果也是顾虑。

# 与模型权重的联合优化

Harness 进化改变的是模型周围的非参数化系统。为了实现完整的自我改进，完全可以同时允许模型更新它自己的权重。权重更新可以通过改进模型训练流水线或测试时持续学习来实现。持续学习的主题值得未来单独写一篇文章。

SIA（Hebbar 等人 2026）是早期尝试在同一个优化循环中结合 Harness 改进和模型参数更新的工作，设计中包含三个组件：

元 Agent（Meta-Agent）：提出初始 Harness。

任务特定 Agent（Task-Specific Agent）：执行任务。

反馈 Agent（Feedback-Agent）：根据近期的轨迹，决定是更新 Harness 还是更新模型权重。

SIA 中的反馈 Agent 决定下一轮迭代的类型。（图片来源：Hebbar 等人 2026）

SIA 的实验中有些混淆性的选择，使结果难以解读。例如，任务特定 Agent 比用于元 Agent 和反馈 Agent 的模型（gpt-oss-120b vs Claude Sonnet 4.6）弱得多，而且基线太弱，难以和相关方法做干净的对照。我认为这个方向有趣，但证据是初步的。然而许多挑战，如训练稳定性和古德哈特效应（Goodhart effect），仍然悬而未决。

# 未来的挑战

AI Scientist 这一系列工作有力地证明，一个专家设计的 Harness 可以协调很大一部分自动研究循环，其形式表现为撰写研究论文。但论文产出并不等同于科学发现。一个系统可以写出一篇看起来可信的手稿，同时却存在捏造的引用、实现漂移，或薄弱的实验结果。

Trehan & Chopra（2026）测试了 LLM 能否在极少脚手架和基本工具（即 read_file、write_file、llm_search、list_files）下，从一个研究想法走到一篇论文。每个想法有一个专门的工作空间，Agent 可以在其中生成和读取文档作为上下文。他们在三个领域（世界模型、多 Agent RL、AI 安全与对齐）做了实验，每个领域包含 45-50 篇高质量种子文档来启发新想法。只有四个想法被人类专家选中走完整个流水线，只有一个被完整执行成论文。他们观察到实验中有六种反复出现的失败模式：

偏向训练数据默认值：使用旧的库、过时的命令、标准格式，或未立足于实际仓库或数据集的假设。

执行压力下的实现漂移：当实现在技术上变复杂时，模型可能走向常见的更简单解，而非所提议的方法。

记忆与上下文退化：长期任务会丢失关键细节，除非日志被写成持久产物。

过度乐观：模型在实验嘈杂或失败时仍宣布成功，类似于 Bubeck 等人（2025）观察到的"p-hacking 和 eureka-ing"模式，模型会引入"数值胶带"（numerical duct tape）并在信号仍是噪声时就宣告胜利。

领域智能不足：模型缺乏隐性的手艺知识，例如预测实现复杂度、判断实验结果是否可信、或知道哪些基线重要。

科学品味薄弱：实验可能可执行，却没能回答正确的问题。

通往完整 RSI，研究者已经取得了真正的进展，但几个瓶颈仍然存在。

1. 薄弱而模糊的评测器。许多研究主张没有快速而精确的验证器，许多真实世界任务也是如此。当前的自我改进循环在评测指标可度量且客观的任务上表现最好，就像 RL 的工作方式一样。

研究品味、新颖性和长期科学价值更难度量。例如，研究品味常常混合了问题框定、实验设计，以及"哪些意外结果值得追求、哪些失败案例值得重试"的判断。

2. 上下文与记忆生命周期。随着 AI Agent 变得更自主和独立，记忆会增长。一个有用的 Harness 需要管理上下文和记忆，以补足长上下文生成现有的局限，同时最大化长期任务的成功。既然人类能在整个一生中维持记忆，我在这里看到一个类比：上下文工程将会、也应当成为智能的核心部分，而不是停留在软件系统层。

3. 负面结果。研究者有动机发表成功结果，因此文献偏向于成功。在大量数据（至少目前大多是人创造的，lol）上训练的 LLM，可能不擅长决定何时放弃一个假设、报告一个负面结果、甚至承认一次失败，因为数据中成功与失败样本的不平衡。

一个研究 Harness 应当让失败的尝试易于保存，因为从失败中学习是精简任务搜索空间的最佳方式。

4. 多样性坍缩。进化和 RL 循环倾向于利用已知的高奖励模式。我们需要机制来防止种群坍缩成同一解的各种变体。这对开放式研究尤其关键，因为最佳路径在当前的评测器下起初可能看起来更差。

5. 奖励黑客。一个自我改进循环会优化它得到的任何信号。如果奖励来自单元测试，Agent 可能过拟合到测试；如果来自裁判模型，它可能学会针对这个裁判的奖励黑客技巧；如果来自基准分数，它可能利用基准的瑕疵。

评测器和权限控制应当可能位于"演化 Harness 的循环"之外，用 held-out 测试、轨迹审计，以及在关键决策点上的人工审查。我们能将多少监督规模化并自动化，仍是一个开放的研究领域。

6. 长期成功。一个外在的优化循环作用在奖励上，这些奖励在训练沙盒中可模拟的、单个展开之外。

以编码 Agent 为例。编码 Agent 已经提升了软件工程的日常生产力，但许多优化目标仍然太短期。它常常能完成手头的任务，却不太清楚它应如何保护一个由成百上千工程师共同维护的仓库的长期健康。标准的基于沙盒的 RLVR 式训练很少捕捉可维护性、所有权边界、迁移成本、向后兼容性，或未来的调试负担。

7. 人类的角色。人类应当向上移动到技术栈的上层，而不是从循环中移除，意味着人类应在正确的时间、正确的抽象层级提供监督，而我们的系统设计应当考虑何时、如何建立这样的接触点。

上面列出的许多挑战需要人类的反馈和引导。毕竟，我们是在为人类的更好未来构建技术，而不是反过来。
