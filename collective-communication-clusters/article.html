为什么关心集合通信

2026年,训练与服务于transformer本质是大规模分布式问题。数据并行靠all-reduce(反向同步梯度);张量并行与FSDP重度依赖all-gather与reduce-scatter;MoE专家并行靠Aall-to-all。要推理现代系统性能,终究要懂数据在集群里怎么动。

先从硬件与拓扑讲:TPU均匀、GPU分层。主推ring(大消息),小消息则tree(log2步)更好。全篇七部分。

TPU集群拓扑: Superpod / Slice / DCN / PCIe / ICI

TPU芯片直连近邻,每颗4或6个最近邻:2D torus=v2/v3/v5e/v6e(4邻);3D torus=v4p/v5p/TPU7x/8t(6邻)。(新款推理芯片8i走boardfly式high-radix,本文略。)

2D torus就是带环绕边界的网格:左出右回、上出下回;把离散网格盖在甜甜圈上仅为找直觉。下面两张分别是2D直觉与3D六向连接。

(承接上图)

TPU芯片经ICI(inter-chip interconnect)连邻居。最大ICI连通岛叫TPU Pod(常也叫superpod)。一个v4 pod=16³=4096;v5p=16×20×28=8960。

反观GPU的scale-up域:传统很小,通常单NVLink域8颗,近年GB200 NVL72到72(稍后详谈)。

对6邻pod,能整出满3D torus的最小组合是4×4×4。若只要2×2×2,会失去wrap而得mesh:该轴向ring型集合大约慢2×。术语:slice=单pod内经ICI连通的一块(v5e可为2×2/2×4/8×8,最大即pod本身);通信重的应用尽量选能保住torus的形状,如4×4×8。

v5e=16×16 2D torus,wrap成立在尺寸16;只要8×16会在短轴向丢wrap,同类惩罚大约2×。

单pod之外用DCN(data center networking)。DCN吞吐远低于ICI,过度跨pod流量易成瓶颈。多个pod经共享DCN fabric可连成更大集群;每颗芯片还经PCIe挂一块专属CPU host(v5e:一个host接2×4八颗)。

到DCN骨干必经PCIe,故DCN通信甚至比PCIe慢。跨pod路径:源chip HBM→PCIe→源host→DCN→目的host→PCIe→目的HBM。由此得出带宽层级:die越近越快、越出集群越慢。

数值例1:把 (2048,2048) bf16(≈8MiB)从(3,3)搬去(0,0)。经两条并行ICI路径各6跳。这里忽略时延：ICI实际约1μs/跳,本例两路并行各6跳≈6μs,大块下可忽略但小消息不行。

关键是要知道自己处于延迟主导还是吞吐主导。估法:打满单向ICI 45GB/s,1μs能过多少?45GB/s×1μs=45KB。消息chunk落在这量级,延迟就翻盘：忽略1μs/跳会大幅估错,纯带宽近似不再成立。

数值例2:(128·1024)² 的bf16分到4×4(每chip(32·1024)²)且已放host DRAM;搬到(0,0)并与(128·1024,128)向量matmul要多久?(VMEM=片上SRAM,≈ shared memory,细节不展开。)

Reduce-Scatter与All-Reduce:All-Gather的对偶

动机:前向用All-Gather的场景,后向常要Reduce-Scatter;例如把不同chip各持的部分和归并、再让结果分布开。

Reduce-Scatter几乎是All-Gather的对偶:通信schedule相近,但shard边传边reduce而不是边传边拷贝。吞吐主导下时间量级相同。

(旁注:二者存在漂亮对偶：多数分片模式下,前向All-Gather后向就Reduce-Scatter,反之亦然。)

用减少归并再接All-Gather,即可叠出All-Reduce。

一致性起见也覆盖单向1D ring的Reduce-Scatter(假想,v5e需16颗才成环)。

没wrap的slice(4×4 v5e)退化成1D path/chain再跑一遍。

若横跨多轴,则可并行多动几条ICI;吞吐主导下总时延随所用拓扑轴数近似反比减少。至此All-Gather / Reduce-Scatter / All-Reduce收工。

All-to-All: 一次分片式转置

最后原语出现在MoE:假设top-1路由、每chip一个expert。router把每个token附上目标expert ID;若每expert独占一chip,那ID就指明token该送去哪颗。每chip开始手握一批本地token,却可能要去往很多不同chip的experts。All-to-All做这种互换:把去Expert j的token全发往TPU j。所以All-to-All有点像分布式转置：开始时按源芯片分组,结束后按目的expert分组。

NVIDIA GPU集群拓扑: Node / Scalable Unit / Fat Tree

与TPU的近邻torus不同,GPU集群通常是分层交换网。本文专注NVIDIA DGX H100 SuperPod参考架构：一个以fat tree组织的1024-GPU集群。所谓fat tree:树往根越走越胖,上层聚合带宽更高,众多节点的流量不会塌进单一窄瓶颈。

组织构件:最低一级node。本文用node指本地NVLink/NVSwitch scale-up域;例如DGX H100 node=8颗H100经NVSwitch全连(GB200NVL72则72颗)。node内GPU通过NVSwitch fabric实际全连接:任意两颗之间一跳可达。

Node之间用InfiniBand(IB)串成scale-out网。DGX H100 SuperPod参考架构里,32个node组成一个Scalable Unit(SU),经IB leaf switch连;多个SU再由更高层spine switch相连,构成fat tree。

满fat tree是不oversubscribe的。所谓oversubscribe:下游设备灌进leaf的流量大于leaf通往spine的上行能力(如一组可注入12.8TB/s,但leaf只有6.4 TB/s上行,则2:1 oversubscribe)。满fat tree每层上行带宽==下行注入带宽,意味着full bisection bandwidth。

Bisection bandwidth=等切集群两边可用带宽。把128-node劈成两个64,一边可按全部聚合注入带宽与另一边通信。一般化:任何分法,跨分区的带宽被切得更小的那侧node数限制。例:DGX H100每node 8×50GB/s进IB,给400GB/s单向注入;满fat tree下,N个node那侧可跨分区分向N×400GB/s发出。node内:8颗劈两半为两组4,一边可向另一边发4×450GB/s=1.8TB/s(正是那4颗上限);全双工→双向bisection 3.6TB/s。

SU有32 node:劈16/16,一侧16×400=6.4TB/s(双向12.8)。劈64/64:一侧64×400=25.6TB/s(双向51.2)。不均匀如88对40:小侧40×400=16TB/s。

GPU节点内集合: Ring / Tree / SHARP

node内((单节点)TPU与GPU算法表面很像：都作用在抽象ring上,但底层拓扑不同。TPU的ring是过ICI的物理路径;GPU的ring是在NVSwitch全连接上人为挑出的逻辑序。

既然All-Reduce可拆Reduce-Scatter+All-Gather,无特别硬件时它成本≈单一原语2×。NVIDIA交换芯片(NVSwitch与IB switch)带SHARP优化：一个in-network reduction计算单元:平时switch只路由数据;有SHARP还能自己执行归约(如GPU把部分和送进switch,switch加好把结果发回)。于是把偏内存的All-Reduce让网络在天上归约,GPU专心算有用活。

参考:H100 node里的NVLink4 NVSwitch的SHARP有400 GFLOP/s FP32归约吞吐。理论上SHARP能把All-Reduce拉到接近2×;N很大时趋近2×,8-GPU node理想约1.75×。但实际中归约与multicast pipeline无法完美重叠：实测加速常见仅 ~1.3×(见文末ref)。务必对具体集群跑microbenchmark。

(NVLink SHARP也加速All-Gather的multicast:先把内存区登记为某GPU组的multicast target,此后对multicast地址做普通CUDA store,便被NVSwitch复制给组内每颗：kernel无需特殊指令。低效点在它连源GPU一起发(源已有数据),H100 node里白耗1/8)。)

在NVSwitch node内,均衡All-to-All通信可比双向1D torus ring少约半(带宽相等时),因为每颗直接可达每目的。

(注:对GB200NVL72,MoE推理里72颗只挑8个expert/token时,每个token只需到约8/72≈11% 的GPU,通信变稀疏带裂缝,不再是均匀All-to-All。)

跨node前先看tree思想:每轮GPU两两配对、每轮数据量翻倍 → log2(N) 步而非N−1。

ring好流水(多chunk连续绕环让链路常忙);recursive doubling延迟低,但大消息有效带宽常不及ring(不擅流水)。理想带宽模型下字节成本相同;主因步数ring(N−1)对tree(log2N)。实际上NCCL会按消息大小与拓扑在ring/tree/hybrid里选。

GPU跨节点: InfiniBand上的分层算法

跨node算法的低层细节因多级流水(节点级、SU级、spine级)而复杂。好心智:想象整集群(不超卖的满fat tree让这可行)挂一个跨node的ring。大消息下All-Gather/RS的一阶近似(T_tot≈D/BW_node=D/400e9);再准点会加intra-node段：分层集合通常scale-out(IB)与node内(NVLSwitch)可流水,故总时更接近max(D/BW_gpu,D/BW_node)。

(只画单SU内因为加了spine不改变算法性质,只再多一层;画面会复杂故略。另:rail优化：node的跨node总带宽并非总能被任意GPU匀着用,通常成并行rails,要吃到node级满带宽得拿rail-aware rank摆放与跨路径均衡。)

微妙处:被All-Reduce的张量本身可能又横跨另一并行轴。例:Megatron式(tensor/model并行)训练里,权矩阵按tensor-parallel轴Y分片,而其梯度按数据并行轴X归约。归约并不跨tensor-parallel那些rank(它们各执不同shard,无对应元素可加);而是对每个固定shard、把沿数据并行的replica做AllReduce。

最后SU上的分层All-to-All。与All-Reduce不同,它无法靠先做本地归约压缩(每chunk都指向特定目的)。

收拢GPU端成本模型(节点内与跨节点)。

结语
最值得带走的是作者怎么把四原语还原成可背的估算而非魔法。吞吐主导时,torus上All-Gather/Reduce-Scatter一阶通信时间≈D/BW单向;能并行两轴就近似再减半,延迟主导时(log2N步的tree、消息chunk尺寸)决定主项。GPU则是两级分域:node内NVSwitch全连(满速直达、无绕行),node外InfiniBand经SU/spine(fat tree不超卖才有跨分区的N×400GB/s)。

作者反复夹一句现实提醒:SHARP理论2×实测只1.3×、混装fat tree才满bisection、GPU大到GB级才拉满带宽：理想模型到真集群之间要靠microbenchmark校准,别照搬论文数字。这正是读性能文最该学的习惯。
