# 全文翻译（逐句对照基线）

## 关键要点

- 模型选择决定的是那组固定的权重，也就是模型的整体能力上限。虽然可以给模型提供上下文或加以引导，但模型的整体知识库和能力在选定那一刻就已确定。
- effort（投入程度）不只是"思考时间"。它控制 Claude 为你的请求所做的总体工作量，包括读取的文件数量、使用的工具，以及在回头向你确认之前走了多少步。
- 更常规的任务选更小的模型，更复杂或模糊的任务选更大的模型。从每个模型的默认 effort 级别开始，再根据你平时的工作类型把它调成通用偏好，而不是针对每个任务单独调。
- 如果 Claude 已经掌握了所有相关上下文、明显努力尝试过，却仍然出错，那是该换更强模型的信号。如果 Claude 是因为跳过了某个文件、没跑测试、或中途放弃重构而出错，那就选更高的 effort 级别。

## Claude Code 的 effort 级别与模型选择

Claude Code 给了你两个看起来都能"让答案更好"的设置：模型设置和 effort 级别。你可能会以为更大的模型（比如 Claude Fable 5）比 Claude Sonnet 输出更聪明，而更高的 effort 级别意味着 Claude 在回答前思考得更久。

第一个假设是对的。根据行业基准测试，我们最大的模型能力更强。

但 effort 不只是"思考时间"。effort 级别控制的是 Claude 为你的请求所做的总体工作量。这确实包含模型思考的时长，但也包括：

- 它读取了多少文件；
- 它做了多少验证；以及
- 在一个多步任务中，它在回头向你确认之前推进到了哪一步。

在更高的 effort 下，Claude 会在回来找你之前做更多这类动作（比如读文件、跑测试、反复核对）。在更低的 effort 下，它宁可向你索要更多上下文，也不愿自己花 token 去搞清楚。

## 模型选择如何运作

当你按下回车，Claude Code 会把你的消息连同系统提示、工具定义、你的 CLAUDE.md、对话历史，以及上下文中所有文件，打包成一个请求发给 API。

Claude Code 拥有的一切都被打包进一个 API 请求。在服务器端，文本在被送到模型之前先经过分词。

但模型从未把这些当作纯文本看待。服务器上发生的第一件事就是分词；文本被切分成片段，每个片段映射到一个固定词表里训练好的整数。const 可能映射到 1978，await 可能映射到 4293。从此刻起，你的提示变成了一个整数数组。

分词器把你的文本切分成片段，并把每个片段映射到固定词表中的一个整数。上面一行里的每个块变成它的 token ID（下面一行）；图中 ID 仅为示意。

模型的工作是接收这个数组，预测下一个 token 是什么。它通过为词表中的每个 token 计算概率，并从中挑选概率最高的那个来实现。在 const x = await 之后，一个训练良好的模型会给 fetch 很高的概率（非常可能），而给 banana 接近零的概率（完全不可能）。

模型的预测是对词表中每个 token 的一个概率。最优猜测和一个不相关的猜测之间的差距是巨大的。

把你的输入 token 变成这些概率的，是权重（也叫参数）。它们是组织成大矩阵的数十亿个数字。要预测一个 token，模型把你的输入通过这些矩阵跑一遍，经历一长串矩阵乘法，最后读出概率。权重就是模型"知道"的一切所在。

每个模型的权重在训练期间设定，等到你发请求时它们已经是只读的。你的提示、你的 CLAUDE.md、你的上下文，都无法改变它们。（如果你见过 inference 这个词，它指的就是这个：训练完成后、权重固定时使用模型。）

你的提示进去，概率出来。中间的权重不会改变。

Claude 关于 TypeScript、流行框架、地道的 Go，或任何其他通用编程知识的一切，都是在训练时编码进那些权重的。

你的提示和上下文仍然可以引导预测（把你的真实代码摆在 Claude 面前就是一种引导，而且效果很好），但它们不会给权重本身增加任何东西。

如果一个库在模型训练时还不存在，它就不在权重里。你可以把文档放进上下文，Claude 会使用它们，但那是引导，不是教学。Claude 的回应只会在那一次请求里受影响；底层模型并没有记住这些信息。

所以，当 Claude 信心满满地调用一个并不存在的 API（幻觉）时，那是权重基于训练模式生成了一个看起来合理的 token 序列，而不是一次失败的查找。

那么更换模型到底做了什么？它切换了由哪一组冻结的权重来处理你的请求。

模型不是一次性生成整个答案。它先预测一个 token，把它追加到序列末尾，再重新跑一遍整个计算去拿下一个。一个 200 token 的回复就是 200 次穿过权重的独立过程。这个循环就是你大部分等待时间和输出成本的来源。

序列每一步刚好增长一个 token。模型每次都重读整个数组来预测接下来是什么。

所以模型设置决定了由哪组权重处理你的请求，也决定了每个输出 token 的成本。

它决定的不是会生成多少个 token。对于同一个提示，这个数字可能因 Claude 决定做多少工作而大不相同。

这就是 effort 级别控制的东西：Claude 为每一轮决定做多少工作。

## effort 如何运作

当 Claude Code 在处理一个任务时，它生成的 token 落在几个类别里：

- 思考（Thinking）：你在动作之前和动作之间看到的流式推理。
- 工具调用（Tool calls）：命名某个工具（如 Read 或 Edit）及其参数的结构化块，Claude Code 随后解析并执行。
- 给你的文本（Text to you）：计划、进度更新、结尾的总结。

这些都是来自同一个循环的普通输出 token，按相同费率计费。比如，思考 token 的生成方式和其他输出 token 完全一样，并且在那一轮的剩余时间里留在上下文中。

当 Claude 开始写代码时，它早期的推理和读到的文件一样，都是输入的一部分。

Claude 的所有输出都是 token。思考、工具调用、给你的文本，都来自同一个循环。

effort 怎么改变这一切？effort 级别作为请求的一部分发给模型，和你的提示并排在一起。模型在训练时就学会了如何在每个 effort 级别下行为，而这种学到的行为被烘焙进了冻结的权重。

当你的请求到达时，effort 级别是模型要响应的又一个输入，就像它响应你的提示文本一样。这为 Claude 的行为设定了：在认为任务完成之前，它需要多少彻底、多少确定。

这在每一轮都会被考量，并导致生成更多 token 以产出更高置信度的答案。

同一个提示，两个 effort 级别。高 effort 路径会生成大约 7 倍的 token 以到达更高置信度的答案。

在更高的 effort 级别，Claude 通常会从制定一个计划开始，而 effort 级别会影响这个计划的深度和广度。不过计划不是冻结不变的。随着 Claude 从它的动作中接收到结果，它会更新已经取得的进展，以及它对累积结果的确定程度。

所以当一个三假设调试计划的第一步就找到了 bug 时，"调查假设 2 和 3"可能就不再必要了。Claude 通常会明确说出来："第一次检查就找到了，所以剩下的检查不需要了"，然后跳过去。你在 Claude Code 里看到任务列表在运行中途被修改，就是这种情况。

Claude 在更高的 effort 级别会更倾向于反复核对额外假设或验证正确性，但它一般不会在简单任务上人为抬高用量。事实上，我们的团队在模型训练期间会密切关注"过度思考"，因为它会降低有效性。

## 如何选 effort 级别

我们的建议是，对大多数任务你应该使用模型的默认 effort 级别。默认级别是 Claude 会根据大多数人愿意在一个任务上花费的量来扩展其 token 用量的那个级别。

把 effort 看作一个手动覆盖，用来缩放 Claude 工作得有多努力、有多久。当你基于你的领域或工作类型，对彻底性还是速度有强烈偏好时，再刻意去选它。把它更多当作一种通用偏好，而不是逐任务的决策。

在 Claude Opus 4.8 发布后，一些可能对你有帮助的实战观察：在我们的测试中发现，当你对 Opus 4.8 使用默认 effort 设置时，相比对同一个任务使用 Opus 4.7 的默认 effort 设置，它会在大致相同的 token 数下产出更好的结果。

## 当 Claude 出错时该改什么

当 Claude 出错时，你的第一反应不应该是去调某个旋钮，而是去检查你提供的上下文。是你的提示太模糊？Claude 连上了正确的工具？装备了正确的技能？

如果你在一个本不需要更高 effort 的任务上提升 effort，修复往往在上游，在你的上下文、你的 CLAUDE.md，或任务的范围界定里。

但假设你已经提供了清晰的上下文，Claude 仍然出错，那你要问自己的问题是：它是没努力够，还是懂得不够？

两个问题，一个兜底。把这个启发式当作选起点的依据，而不是硬性规则。

模型：问题太难了

当问题真的很难时，选更大的模型。比如，微妙的 bug、不熟悉的领域，或架构决策。当更小的模型无论你给多少上下文都自信地错时，更大的模型更有帮助。

更大的模型也更能处理模糊性，而具体的、指导执行的指令，是在更小模型上取得成功的更好配方。

当工作是常规性的，选更小的模型。比如你能精确描述的改动、机械性的更改，或关于已经在上下文里的代码的问题。没有理由为任务不需要的能力付费。

如果 Claude 掌握了所有相关上下文、明显尝试过，却仍然出错，那是该选更大模型的信号。如果你已经在更大的模型上，而工作一直都很常规，降下来会提升速度，通常还能在不影响输出质量的前提下降低成本。

effort：Claude 没努力够

如果 Claude 是因为跳过了文件、没跑测试、或没核对自己的工作而出错，选更高的 effort 级别。这最相关的情况是：你选的 effort 级别低于模型的默认值。

## Fable、Opus、Sonnet：专才、专家与通才

我喜欢用一种方式理解这两个设置的关系：Fable 是专才，见过几乎没人见过的难题；Opus 是专家；Sonnet 是相当好的通才。effort 级别决定它们中任何一个会在你的任务上花多少时间。

低 effort 的 Opus，就像得到一个有丰富类似问题经验的专家的五分钟。他们带来不在你代码库任何地方的知识：他们以前见过的模式、知道要检查的坑，这种只有解决过很多类似问题才能得到的东⻄。但只给五分钟，意味着快速读一遍你的代码，而不是仔细读。

高 effort 的 Sonnet，就像给一个相当好的通才整个下午。他们会读所有东西、运行东西、反复核对工作，最终彻底理解你特定的代码。他们带得较少的，是那种"我 exactly 见过这个"的辨认力。

Fable，即使低 effort，也是那个专才瞥一眼所有人都卡住的问题，仍然能指出没人会注意到的东西。那种辨认力是你付得最多的，所以值得留给真正需要它的任务。

这些都不是 universally 更好。模型设置大致是"多强"；effort 设置大致是"多彻底"。大多数真实任务两者都需要一点。

## effort、模型与 token 消耗

那么模型选择、effort 和 token 消耗三者如何相互作用？取决于任务。

在同等 effort 级别的常规工作上，两个模型一般都能做对。更大的模型以更高的单 token 价格，通过额外的验证步骤消耗更多 token。这就是为什么在常规阶段降到更小的模型能省下真金白银而质量不降。

曲线仅用于说明目的，展示的是单个足够简单、两个模型都能快速完成的任务。它们不代表真实的基准数据。

在更难的、多步工作上，等式不同。更小的模型不得不朝着自己能力的极限死磨，烧掉迭代次数，而更大的模型用更少的步数达到同样的质量门槛。

你为更大的模型付更高的单 token 价格，但在真正拉伸更小模型的任务上，每个任务的总成本反而可能更低。更重要的是，更大的模型能完成即使最高 effort 设置下更小模型也无法完成的任务。

这一点在 Fable 上最明显。在长程、多步工作上，它领先得最远。在我们的测试中，它完成了 Opus 和 Sonnet 在任何 effort 级别都够不到的工作。它的单 token 价格也最贵，这是另一重用它只做需要它的工作的理由。

曲线仅用于说明目的，展示的是单个难到足以拉伸两个模型的任务。它们不代表真实的基准数据。

另一个细微之处：effort 塑造 token 消耗，但不限制它。系统里唯一硬的 cap 是 max_tokens，命中时会中途截断一个回复。它是个粗暴的工具，主要和 API 开发者相关。更软的控制，比如任务预算，或在提示里让 Claude 保持简短，是更有用的工具。它们作为模型训练去遵循的指引：如果接近上限，它会寻求结束任务，而不是撞上一堵墙。

## 先用默认值，再去拧旋钮

大多数时候，你不该去想这两个设置中的任何一个。当一个结果没达标时，问一句"是 Claude 懂得不够，还是没努力够？"，然后按需调整。
