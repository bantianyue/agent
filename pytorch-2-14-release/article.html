性能改进

大规模MPS算子迁移至原生Metal

延续2.13版本开始的迁移工作，又有一批MPS算子从Apple的MPSGraph框架迁移到手工编写的Metal计算内核上，包括index_add、index_select、argmin、argmax、conv3d、median、nanmedian、linspace、arange、nan_to_num、log_sigmoid、sigmoid_backward、mish和GLU。

归约操作获得了一次专门的五部分重写，涵盖完整归约、内维归约、跨步和批处理外部归约、小维度和窄内核，以及argmax和argmin的split-K路径。最后一部分将min和max从MPSGraph迁移出来。跳过输入升格并使用vec4加载消除了MPSGraph路径无法避免的工作。

原生Metal路径消除了MPSGraph的逐算子编译成本，并让PyTorch直接控制线程调度和内存访问模式，从而降低了Apple Silicon上常见训练和推理工作负载的内核启动延迟。

Inductor中的组合内核与归约

组合内核将多个小内核批量合并为一次启动，但此前批次中单个超大规模归约会影响整个内核的形态。现在，大规模归约会从组合分区中拆分出来，组合归约获得动态RBLOCK缩放，子内核主体以非内联设备函数形式发出以降低寄存器压力。每个组合内核的主体共享，并为GB200调优了拆分归约启发式算法。净效果是内核启动次数更少、资源使用更紧凑，弥补了单个超大归约可能拖累整个融合批次的差距。

安装

Python 3.15和3.15t的wheel包未发布到PyPI：只能通过download.pytorch.org下载，可使用以下任一命令：

# CPU

pip3 install torch –index-url https://download.pytorch.org/whl/cpu

# CUDA（替换CUDA版本，例如cu126 / cu130）

pip3 install torch –index-url https://download.pytorch.org/whl/cu130

# ROCm（替换ROCm版本）

pip3 install torch –index-url https://download.pytorch.org/whl/rocm7.14

# XPU

pip3 install torch –index-url https://download.pytorch.org/whl/xpu

在自由线程解释器下运行时，相同的命令会安装自由线程的3.15t构建版本。

自由线程构建版本同样适用。安装到3.15t解释器时，pip会自动解析cp315t轮子包。

torch.compile尚不支持Python 3.15

2.14版本中对Python 3.15的支持仅限eager模式。在Python 3.15下调用torch.compile会抛出RuntimeError，而非静默回退，因此限制会立即显现，而不是以隐性的性能损失形式存在。如果工作负载依赖torch.compile，请暂时使用Python 3.14或更早版本。

Dynamo对3.15的支持正在积极开发中，针对新解释器的字节码和符号转换处理已落地。进展跟踪见pytorch/pytorch#184352。

DTensor的分片规则历来是针对整个设备网格按算子编写的，因此每条规则都必须枚举所有网格维度上的各种放置组合：一旦网格超过一个维度，编写起来冗长且容易出错。本次发布继续将算子覆盖范围迁移到单维度策略函数，该函数描述一个网格维度如何对算子进行分片，并让框架将其扩展到整个网格；此处转换了矩阵、数学和张量算子，将直接的register_op_strategy注册从158个减少到114个。卷积还在窗口恰好平铺最后一个空间维度时（零填充、膨胀为1、步幅等于卷积核宽度，且维度可被卷积核宽度乘以网格大小整除）获得了该维度上的分片支持：因此这些卷积在前向和反向中本地运行，而无需通过allgather进行复制。新规则比它们替换的规则更严格，因此先前意外匹配基础策略的注解现在会被报告为需要重新分布，并且迁移后的算子不再生成Partial("product")。这使得已注册分片规则的算子总数达到1239个，高于2026年1月的585个。

对称内存：NCCL后端修复与分配布局

对称内存的NCCL后端存在仅在运行时才暴露的缺陷：barrier() 抛出未实现错误，且信号填充区在分配后从未清零，导致信令协议缺乏可靠基础。两者均已修复：barrier现在复用现有的CUDA barrier内核，填充区在分配时清零。信号填充区也移至所有三个后端（CUDA、NCCL、NVSHMEM）的每次对称分配的前端，因此回收或调整大小的分配不会继承被污染的填充区，且仅清零填充区而非整个块：大分配不再在每次alloc() 时支付全缓冲区memset的开销。在多流场景中，信号填充区清零的时机可能很微妙，用户可能希望在用户空间代码中执行此操作以确保顺序正确。当驱动报告支持时，CUDA分配现在会设置GPUDirect RDMA能力标志。信号填充区槽位在同一分配上的进程组之间仍然共享，因此来自重叠组的并发barrier可能会相互干扰。

单秩编译

分布式任务中的每个秩都会独立编译相同的模型，因此在训练开始前，一次耗时数分钟的编译会被重复执行N次。单秩编译（Compile-on-one-rank）使得一份编译产物可在各处复用：make_fx不再将追踪秩的设备信息固化到工厂和转换操作中，Inductor的代码生成和Triton启动器在加载时解析设备，因此生成的源代码在各秩间保持一致，在cuda:0上编译的内核可在cuda:3上加载运行。DeviceMesh.get_group() 同样从网格中获取组信息，而非固化一个torchbind ProcessGroup（这曾导致图无法序列化），并且在相应标志下，dist.all_reduce等旧式集合操作会以其函数形式进行追踪。torchtitan的实验性graph_trainer展示了预期形态：单个进程提前编译并写入一份产物，每个秩在启动时加载该产物，无需N-GPU任务即可生成：但该模式假设每个程序只有一个加速设备，并拒绝涉及第二个设备的图，且需通过torch.compiler.config.compile_on_one_rank显式启用。

使用dynamic_spec声明动态形状

告知PyTorch哪些输入维度会变化，在不同入口点需要不同的机制：torch.export需要dynamic_shapes字典，torch.compile需要粗略的dynamic= 标志，make_fx需要全局追踪模式：且每种情况下声明都位于调用点，远离其所描述的模型。此版本在torch.fx.experimental.dynamic_spec下新增了ShapesSpec API：您可以一次性命名一个维度（ShapeVar("batch", min=2, max=128)），在多个输入间复用，构建如batch×2的派生维度，并附加诸如batch % 2 == 0的假设，三个入口点现在都通过相同的dynamic_shapes= 关键字接受该API。dynamic_spec装饰器可将该规范直接附加到函数或模块的forward方法上，因此torch.compile、严格或非严格模式的torch.export.export以及make_fx(tracing_mode="fake") 都无需在调用点传递任何参数即可自动识别。以此方式声明的维度成为无支撑符号（unbacked symbols），因此编译器无法静默地针对追踪时碰到的批次大小进行特化：代价是形状相关的分支现在会以数据依赖错误的形式出现，而非触发保护并重新编译。该API仍处于实验阶段且持续演进中：make_fx支持仅限于tracing_mode="fake"，且将规范与prefer_deferred_runtime_asserts_over_guards=True结合使用，或将装饰器与调用点的dynamic_shapes= 参数结合使用，都会引发错误。

为torch.while_loop实现CUDA Graph捕获

依赖数据的循环次数一直是工作负载无法完全被CUDA graph捕获的标准原因之一，这迫使进行设备到主机的拷贝以决定迭代次数，并在你最希望保持完整的地方中断捕获。torch.while_loop现在可以使用CUDA的while条件节点捕获到CUDA graph中：条件在节点添加前于父流上评估，并在每次主体执行结束时重新评估，因此单个捕获的graph在重放时能运行运行时确定的迭代次数。这本身并非吞吐量的提升：关键在于循环不再迫使你退出graph捕获，因此诸如对可变长度索引张量进行归约，或对可变数量的打包序列应用损失等场景，都能保持在单个graph内。通常的while_loop约束仍然适用，包括固定的最大行程次数和仅张量携带的输入。

RDNA3的FlexAttention Tile配置

AMD RDNA3 GPU（Radeon工作站和消费级显卡，而非MI系列数据中心产品线）上的FlexAttention此前使用的tile大小未针对该架构进行调优，导致中短序列长度下的性能未能充分发挥。此版本新增了针对RDNA3专门性能分析的序列长度感知tile配置，使Inductor根据实际序列长度选择匹配的tile大小，而非使用固定默认值。结果是在数百token范围内延迟降低约2-8倍，且极短序列无回退。若您在其他AMD或NVIDIA硬件上运行FlexAttention，此更改不适用。

API不稳定（PR #177840由Robert Esclapez，AMD提交）

MPS（Apple Silicon）

原生线性代数

MPS线性代数历来依赖Apple的MPSGraph原语，或对于超出基础范围的操作完全回退到CPU，这使得CPU/MPS混合往返成为数值代码中常见的性能瓶颈。本次发布通过原生Metal内核填补了其中多项空白。SVD、eigh和lstsq现在通过Jacobi风格内核原生支持float32和complex64类型（对于float64回退到CPU，因为Metal没有double类型，对于GPU启动开销不值得的小矩阵/批次也回退到CPU）：这也使得依赖它们的matrix_rank、pinv、cond和norm计算得以加速，但非Hermitian的eig/eigvals留待后续处理。Cholesky采用了更快的面板分解算法，使用基于matmul2d的尾部更新（根据尺寸不同大约快1.2–2.8倍），并修复了复数dtype的正确性问题，此前该问题缺乏dtype保护，可能静默产生错误结果。lu_factor和lu_solve从Apple的MPSMatrixDecompositionLU迁移到手工编写的Metal内核，算子级别的加速效果显著：提交者测得小批量矩阵加速超过100倍，较大单矩阵加速2–9倍。此外，新增了geqrf，并将linalg_qr重构为与CPU和CUDA共享相同的设备无关代码路径，matrix_exp和linalg.polar（包括其反向传播）现在也支持MPS：尽管matrix_exp仅在约512×512以上尺寸时才会超越CPU性能。

FlexAttention改进

在FlexAttention于2.13版本登陆MPS的基础上，本次发布填补了用户在实际模型中使用后暴露的多项空白。KV批次广播允许键/值张量在查询批次间共享，而无需精确匹配：这是分页注意力（paged attention）的先决条件，后者需要此功能以针对共享KV缓存服务多个序列。flex_attention现在可以返回log-sum-exp和max-score辅助输出以及主要结果，这对于任何消费注意力权重（而非仅输出本身）的功能（如自定义损失、分析以及最终MPS原生反向支持）都是必需的。score_mod / mask_mod函数现在可以直接捕获动态形状值（SymInts），因此基于运行时大小构建的掩码（如序列长度相关的截断）在torch.compile(dynamic=True) 下不再因形状变化而强制重新编译。后续优化在值可容纳时将捕获的SymInts窄化为32位整数，因为内核中的64位算术性能明显较慢。

MPS Prefill注意力加速

Apple的Metal Performance Primitives (MPP) 在macOS 26.2中新增，为注意力类工作负载提供了更底层的构建模块，这些此前在Metal内核中不可用。本次发布利用这些特性，为MPS引入了第二个prefill注意力内核，移植了MLX在M5芯片上使用的方法，并将其扩展到更早的Apple silicon系列，支持fp16/bf16输入，头维度为64、96、128或256，查询长度大于8（macOS 26.2+；其他形状和数据类型继续使用现有的simdgroup-matrix内核）。收益显著：作者自己的基准测试显示，在各种头维度和序列长度下，相比之前的内核约有2–4倍加速，在较小的头维度和较长的序列上增益最大。对于在Apple silicon上运行注意力密集型模型的用户，这是一个有意义的prefill加速，无需修改代码：当形状和数据类型符合条件时，MPS会自动选择更快的内核。该内核的性能优势最好在Apple M5硬件上确认，底层每通道数据布局正是针对此验证的；在更早Apple silicon系列上的行为尚未针对此版本独立验证，可能无法反映上述数字。API不稳定（PR #182256，作者Irakli Salia，Hugging Face）

CTC Loss的MPS加速

ctc_loss：支持语音识别和OCR等免对齐序列模型的损失函数：首次在MPS上同时获得前向和反向传播，填补了此前Mac用户在此操作上不得不回退到CPU的空白。该实现采用与CUDA内核相同的对数域方法，包括正确处理变长（填充）批次。在Apple silicon上端到端训练基于CTC的模型不再需要为损失计算切换到CPU。API不稳定（PR #187716和 #188187，作者Kurt Mohler，OpenTeams）

性能分析与调试

固定CPU内存的内存快照

内存快照已覆盖设备分配一段时间，但未覆盖用于暂存主机到设备传输的固定（页锁定）主机内存：因此，如果该内存意外增长，在您已使用的同一工具中无法查看。固定缓冲区也容易丢失跟踪：它们通常分配一次并在进程生命周期内保持，因为CUDA图要求任何捕获的复制操作具有固定的主机地址。现在，向torch.cuda.memory._record_memory_history()传递record_host=True也会捕获固定分配，作为新的host_segments和host_traces键与现有设备数据一起显示。这为主机和设备内存提供了单一、一致的视图，用于追踪泄漏或意外增长。memory_viz可视化工具尚不渲染主机数据，且通过PyTorch分配器之外的原始cudaHostRegister调用进行的分配不会被捕获。

API不稳定（PR #182407，作者Edward Yang，Meta）

弃用及向后不兼容变更

· TorchScript弃用警告现已可见，且TorchScript已从导入路径中移除。已弃用的isIntegral重载已被删除。参见#189914和#187115。

· Python函数事件默认从性能分析器的key_averages()中排除，这是性能分析器输出的可见变化。参见#188631。

· 在性能分析器中，已弃用的use_cuda选项被移除，with_modules被弃用；模式匹配器、BasicEvaluation、profiler_metrics和profiler_measure_per_kernel被移除。参见#192543、#192808、#187362、#187439和#187204。

· Dynamo TVM后端的Relay路径在FutureWarning弃用后被移除；请使用relax前端。参见#189639和#190766。

· 在分布式环境中，_set_pg_timeout让位于torch.distributed.set_timeout，setSequenceNumberForGroup成为弃用的无操作，控制集合通信实现被移除，单秩编译的torch.distributed别名让位于torch.compiler.config。参见#187387、#188611、#188617和#187869。

· CUDA绿色上下文设置和弹出功能已弃用，绿色上下文移至CUDA Python绑定。参见 #188419和 #185527 。

· 使用weights_only加载稀疏张量时，会验证其一致性。参见 #184750 。

· 从linear_cross_entropy中移除了平衡准确率策略。参见 #188283 。

结语
这版2.14的重心不在特性堆叠，而在编译器与分布式两条栈上的生产化收口。NVGEMM由2.13的实验性CuTeDSL路径定型为完整的GEMM代码生成后端，能拿出与Triton、ATen正面竞争的候选内核，epilogue融合与NVFP4低精度都做进了内核这一层；通信与计算默认重叠那条线则意味着，无需改任何代码就能吃到更满的GPU利用率。

分布式侧是更长的信号。nccl2把容错、单边RMA这些曾属后端细节的能力抬成c10d层的一等概念，进程组可原地重建，坏掉的rank不必整集群重启去丢热状态；单秩编译把每次训练前的N份重复编译压成一份，节点越多省得越多。对跑大规模分布式训练的人，这版是把「坏节点能续跑、多点不重复编」从奢望变成了默认配置。
