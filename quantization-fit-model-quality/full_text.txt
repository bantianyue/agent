Quantization: Fit a Model Without Losing Required Quality

A key technique in inference engineering! Model memory can determine which customer devices an AI application supports. Quantization stores selected model values with fewer bits, reducing storage and potentially improving execution speed. This article explains the approximation, follows llama.cpp’s Q4_0 format, and shows how to test memory, response time, and output quality together.

It builds on A Beginner’s Guide to Inference Engineering, which introduces the field, why it matters, and how software engineers can get started.

A model inside a support application

A desktop support application classifies tickets locally. A ticket such as “I was charged twice” should receive the category billing. Other categories include account access, bug, and needs review. The application parses the model’s output before showing a route to the support agent.

The team selects a model that meets its classification requirements. It must now make the model run on the supported laptops without exhausting memory or delaying the agent’s work. The engineer owns the device limits, classification errors, complete response time, and update path.

Quantization is one option when model weights occupy too much memory. It is useful only if the resulting application still meets those requirements. A smaller download does not by itself establish a working deployment.

 

What changes inside the model

A tokenizer converts ticket text into tokens: words, word parts, or punctuation. The runtime loads the model and runs its operations. llama.cpp is an open-source inference runtime with CPU and GPU execution paths. A CPU is the general-purpose processor; a GPU is a processor designed for many parallel numerical operations.

Model layers transform numerical arrays. A tensor is an array with a defined shape, such as a vector or matrix. Weight tensors hold learned parameters. Activation tensors hold intermediate results for the current ticket. The same weights can process many tickets, while their activations differ.

A data type determines how a stored number is represented. FP16 is a 16-bit floating-point format. One byte contains eight bits, so each FP16 value occupies two bytes. Billions of parameters make even a few bits per weight important.

This article focuses on post-training weight quantization: converting selected learned values after training. Activations and the key-value cache can also be quantized, but those are separate configuration choices. The KV cache stores attention data from processed tokens and can grow with input length and active requests.

 

From a weight to an approximation

A quantized representation has fewer available values. Many formats store a small code plus scaling information. Dequantization uses that information to reconstruct an approximate numerical value for computation.

For a simple rounding example, use a step size of 0.1. A weight of 0.26 maps to code 3 and reconstructs as 3 × 0.1 = 0.3. The absolute error is 0.04. This illustrates uniform rounding, not the Q4_0 conversion algorithm.

That approximation can change a layer’s result. If an input value is 2, its contribution with the original weight is 2 × 0.26 = 0.52. With the approximation, it is 2 × 0.3 = 0.6. Later operations use the changed result. This does not predict whether a particular ticket will receive the wrong category; that requires task evaluation.

Some errors matter more than others. A small average accuracy change can hide repeated failures on refund disputes or ambiguous account requests. Compare categories and disagreement cases, not just one aggregate score.

 

Follow Q4_0 into llama.cpp

Q4_0 is a concrete format for inspecting packed weights and per-block scales. It is a teaching example, not a claim that it is the best format for the support application.

The quantize_row_q4_0_ref() function processes rows in blocks of 32 values. For each block, it finds the signed value with the largest absolute magnitude and calculates a scale d = max / −8. Here, max is the source variable holding that signed weight, not necessarily the greatest positive value. It stores the scale in FP16, converts values to four-bit codes, and packs two codes into each byte.

A four-bit code has 16 possible patterns. In the dequantize_row_q4_0() function, the low and high halves of each byte become separate codes. Subtracting 8 recenters a code to the range −8 through 7. Multiplication by the stored scale reconstructs its approximate value. The scale can be signed; this is more specific than the earlier rounding example.

For example, a stored scale of 0.5 and code 10 reconstruct as (10 − 8) × 0.5 = 1.0. In the C code, packed & 0x0F extracts the low four-bit code; packed >> 4 extracts the high code. Each packed byte supplies two values. The packed positions come from two halves of the source block, not necessarily adjacent weights.

 

Count the whole block

The block_q4_0 definition contains 32 four-bit codes and one two-byte scale. The codes occupy 16 bytes; the complete block occupies 18 bytes. The average is 18 × 8 ÷ 32 = 4.5 bits per represented weight.

The same 32 values in FP16 occupy 64 bytes. The block-storage ratio is 64 ÷ 18 ≈ 3.56. Scale metadata explains why “four-bit” does not mean exactly four bits of total storage per weight.

 

This ratio excludes other tensors, file metadata, runtime buffers, activations, and KV state. It is not a measured whole-model memory reduction or speedup. A model that loads successfully can still fail when long tickets allocate additional state.

Storage format and execution are different

Kernels are low-level routines that perform numerical operations on a specific processor. A compact weight format reduces bytes that must be stored or moved, but unpacking codes and applying scales take work. The selected kernel may reconstruct values or fuse conversion with the operation.

Four-bit weight storage does not require four-bit arithmetic for every model operation. Speed depends on the processor, backend, kernel, and workload. Keep the CPU/GPU placement fixed when comparing formats, or report a changed placement as a separate deployment comparison.

GGUF is the model file format used by llama.cpp. One file can hold tensors with different numerical types. A .gguf extension does not tell you the precision of every layer. Keeping some tensors at higher precision can preserve quality at an additional memory cost.

 

Build comparable artifacts

Start from the same source model revision. The llama.cpp quantization guide describes conversion to GGUF, then quantization with llama-quantize. It also documents per-tensor formats and optional importance data used to guide conversion.

Use a high-quality source artifact rather than repeatedly quantizing an already quantized file. Record the converter revision, command, target format, and any calibration data: representative inputs used to guide the approximation. Similar downloaded filenames do not establish that precision is their only difference.

Save checksums for the baseline and candidate files. A checksum identifies their exact contents. Record the tokenizer, prompt template, context limit, output settings, backend, and hardware beside them.

 

Test the ticket classifier

Define the supported device memory budget, maximum complete response time, and quality floor before conversion. Include ambiguous tickets and critical categories. Keep a separate quality set for final acceptance.

Run the accepted-quality baseline and one quantized candidate from the same model revision. Keep unrelated settings fixed.

Measure loading separately. Warm both configurations with the same procedure before measuring steady operation.

Run the same tickets one at a time. Record output validity, correct classification, complete response time, and peak memory.

Repeat runs and retain raw observations. Inspect tickets where the outputs disagree and errors within each category.

Test the longest supported inputs and intended concurrency: the number of requests active at once. Repeat on each supported device class.

For this application, response time ends after parsing and validation. A partial label cannot route a ticket. Record input and output lengths so shorter or incomplete outputs cannot appear to be an efficiency gain.

Separate model-file size, process memory, and device memory where the platform exposes them. On shared-memory systems, avoid adding counters that describe overlapping allocations. Include operating-system and application headroom in the device budget.

If the baseline cannot fit on the target device, record that result as infeasible. Establish its quality on suitable hardware, but do not present timings from different devices as an isolated quantization speedup. Compare feasible target-device candidates under the same conditions.

 

Decide what to ship

Adopt the candidate only if it meets the application’s quality, memory, and response-time requirements. If important categories fail, test a less aggressive format or preserve sensitive tensors at higher precision. Re-run acceptance after each change.

If memory falls but response time rises, inspect the backend and conversion overhead. The tradeoff may still meet a device-capacity requirement, but it must be explicit. Weight quantization may not resolve pressure caused mainly by KV state or many active requests.

Keep the accepted artifact and configuration available for rollback. Test the installation and update path. Repeat evaluation after changes to the model, runtime, prompt, or supported hardware.
