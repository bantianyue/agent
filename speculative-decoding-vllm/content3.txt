S# 基准测试设置
T 为了衡量真实收益，测试在受控的生产环境里用 vLLM 完成。
T 需要先说明覆盖范围：前面介绍了五种技术，这次实测只跑其中三种，包括 N-Gram Matching、Suffix Decoding、EAGLE（含 EAGLE 与 EAGLE-3 两个变体），再加上一个不做推测的基线作为对照。
T 只测三种的原因很直接：在本次使用的 vLLM 0.12.0 稳定版里，草稿模型（独立权重）与 MLP Speculator 的实现还没有完全支持，因此只选了当前最可靠的方法。

H# 数据集：两个真实负载的代理
T **ShareGPT（1000 条提示）**：真实的人与 ChatGPT 多轮对话集合，随机采样 1000 条构成测试集。
L **为什么选它**：代表通用对话场景。
L **高方差**：人类对话跳跃、发散、难以预测。
L **压力测试**：输出重复度低，能真正考验草稿模型是否具备思考与泛化能力，而不只是记住模式。它也是评估通用指令模型的标准数据集。
T 下载命令：
X bash
wget https://huggingface.co/datasets/anon8231489123/ShareGPT_Vicuna_unfiltered/resolve/main/ShareGPT_V3_unfiltered_cleaned_split.json
X-END
T **SWE-bench Lite（300 条样本）**：基于真实 GitHub issue 与 PR 构建的数据集，来自热门 Python 仓库，要求模型解决真正的软件工程问题，本次使用 300 条样本。
L **为什么选它**：代表智能体与代码场景。
L **结构性强**：代码天然重复，import、变量名、循环与类结构频繁复用。
L **模式密集**：理论上更有利于模式匹配类方法（Suffix Decoding、N-Gram），可以检验它们在专门的高重复任务上能否超过更聪明的草稿模型。
T 下载并转换成 vLLM 兼容格式的脚本：
X python
from datasets import load_dataset
import json

ds = load_dataset("princeton-nlp/SWE-bench_Lite", split="test")

with open("swe_bench_vllm.jsonl", "w") as f:
  for row in ds:
      prompt = f"Repo: {row['repo']}\n\nProblem:\n{row['problem_statement']}\n\nCode Context:\n{row['hints_text']}\n\nPlease generate the patch to fix this issue:\n"
      f.write(json.dumps({"prompt":prompt}) + "\n")
X-END
T 两个数据集分别覆盖了两种极端的负载特征：一个高度发散，一个高度重复。

H# 硬件与模型
T 测试用两类规模差距明显的模型，观察推测解码从单卡低成本部署扩展到企业级大模型时的表现差异。
T **8B 模型（效率档）**
L **GPU**：1 张 NVIDIA L40S（48GB 显存）。
L **原因**：单卡 L40S 对较小模型有足够的算力密度，48GB 显存能轻松放下 8B 模型权重（bf16 约 16GB），同时留出足够空间给较大的 KV cache 与批量。
T **70B 模型（性能档）**
L **GPU**：2 张 NVIDIA H200（每张 141GB 显存）。
L **原因**：Llama-3.3-70B 的权重在 bf16 下就要约 140GB，用两张 H200 才能避免显存容量成为瓶颈，从而测试长上下文与高并发而不会 OOM。
T 两档配置的差距，正好对应真实部署里最常见的一小一大两种形态。

H# 测试方法：服务端与压测客户端
T 为了模拟生产环境，测试采用客户端加服务端的架构，使用 vLLM 自带的压测工具，从而把 HTTP 开销与调度器在高负载下的行为一并纳入统计。
T **第 1 步，启动 vLLM 服务**：先用 vllm serve 以在线模式起一个模型，作为 API 端点。所有实验共用下面的基础命令，唯一变量是 --speculative-config 参数。
T 针对 Llama-3.1-8B，单张 L40S：
X bash
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --dtype bfloat16 \
  --seed 42 \
  --tensor-parallel-size 1 \
  --gpu_memory_utilization 0.8 \
  --speculative-config <INSERT_CONFIG_STRING_HERE>
X-END
T 针对 Llama-3.3-70B，两张 H200：70B 模型单卡放不下，用张量并行（TP=2）拆分到两张 H200 上，同时把显存利用率调高，以获得更大的上下文窗口。
X bash
vllm serve meta-llama/Llama-3.3-70B-Instruct \
  --dtype bfloat16 \
  --seed 42 \
  --tensor-parallel-size 2 \
  --gpu_memory_utilization 0.9 \
  --speculative-config <INSERT_CONFIG_STRING_HERE>
X-END
T **第 2 步，用压测客户端施压**：服务跑在 127.0.0.1:8000 之后，用 vLLM 自带的 vllm bench serve 发起压测。它作为负载客户端向服务端打请求，并测量吞吐、时延、每个 token 耗时等关键指标。
T 测试覆盖两个场景。
L **场景 A，通用对话（ShareGPT）**：向服务端发送 1000 条多样化提示。
L **场景 B，代码任务（SWE-bench Lite）**：为编码基准写了自定义数据集适配器，使用 300 条样本。
T 通用对话的压测命令：
X bash
vllm bench serve \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --dataset-name sharegpt \
  --dataset-path ./ShareGPT_V3_unfiltered_cleaned_split.json \
  --host 127.0.0.1 \
  --port 8000 \
  --request-rate inf \
  --max-concurrency 10 \
  --seed 42
X-END
T 代码任务的压测命令：
X bash
vllm bench serve \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --dataset-name custom \
  --dataset-path swe_bench_vllm.jsonl \
  --host 127.0.0.1 \
  --port 8000 \
  --request-rate inf \
  --max-concurrency 10 \
  --seed 42 \
  --num-prompts 300
X-END

S# 结果与分析
T 测试结果给出的是一个有条件的结论：谁更快，取决于模型规模与具体负载类型，是对话还是代码。
T 同一套方法在 8B 与 70B 上出现了完全不同的排名，这本身就说明选型不能照搬。

H# 8B：通用对话（ShareGPT）
T 8B 模型跑在单张 L40S 上，这是成本敏感型微服务与边缘场景里最常见的部署形态。
T 与更大的模型不同，8B 模型是计算受限而不是显存受限：权重能舒服地放进显存，瓶颈转移到 GPU 做矩阵乘的速度上。这意味着目标模型本身已经很快，推测解码必须有极低的开销才能带来有效加速，草稿模型产生的额外计算会直接与目标模型争抢 GPU 周期。
T 在开放式对话里，EAGLE 的两个版本（1 与 3）表现更好。人类对话不可预测，简单的模式匹配很难看得很远；EAGLE 用学出来的草稿头，也就是一个很小的、理解上下文的组件，可以一次准确预测 2 到 3 个 token。
F fig06.png|图 6：Llama-3.1-8B 在 ShareGPT 1000 条提示上的吞吐与时延对比。
T 各项结果如下。
L **EAGLE**：8B 模型上标准 EAGLE 拿到最高的输出吞吐 601 tokens/s，相对基线加速 1.43 倍，证明它在复杂的开放式对话里更具优势，靠的是利用模型内部特征做更聪明的 token 预测。它每一步的耗时更长（Inter-Token Latency 31.1ms，基线为 23.4ms），因为它一次预测并验证多个 token；但用块状生成换来的整体速度明显更快，写完整段回答的时间反而缩短。
L **Suffix Decoding**：585 tokens/s，加速 1.39 倍，在通用对话里同样有效，只比 8B 上的 EAGLE 慢 2.7%，这挑战了它只适合重复性代码任务的假设。开销低于 EAGLE，让它在免训练方案里成为一个很强的即插即用选择。
L **N-gram Matching**：491 tokens/s，加速 1.17 倍，是几种推测方法里收益最低的，比领先的 EAGLE 慢 18.3%，说明它在自然对话这种重复度低的场景里捕获模式的能力有限。
L **基线（原始解码）**：421 tokens/s，一次只生成一个 token，是所有加速方法的对照基准。
B t4

H# 8B：代码任务（SWE-bench Lite）
T 到了代码场景，排行榜完全翻转。代码高度结构化，变量名、缩进、模板化 import 反复出现，各方法的相对优劣随之改变。
F fig07.png|图 7：Llama-3.1-8B 在 SWE-bench Lite 300 条样本上的吞吐与时延对比。
L **Suffix Decoding**：以 534 tokens/s 领先，相对基线 370 tok/s 加速 1.45 倍。它本身就是为代码与智能体循环这种重复、结构化的环境设计的，通过匹配提示词与历史输出里的长模式把接受率拉到最高。
L **N-gram Matching**：在代码这类重复文本上表现尚可，达到 406 tokens/s，加速 1.10 倍，但比 Suffix Decoding 慢 24.0%，因为它捕获长距离模式的能力更弱。
L **EAGLE 与 EAGLE-3**：8B 模型上两个 EAGLE 变体都没能追上 Suffix Decoding 的效率。标准 EAGLE 为 398 tok/s，加速 1.08 倍；EAGLE-3 反而略低，379 tok/s，加速 1.03 倍，几乎贴着基线。这说明在较小模型加刚性任务上，简单的启发式匹配常常胜过复杂的训练式预测器，原因是目标模型本身已经很快，或者任务高度可预测时，EAGLE 草稿模型的开销超过了它带来的收益。
L **基线（原始解码）**：370 tokens/s，是所有方法的下限。它也说明代码任务上任何预测式方法都能带来加速，但选哪种方法强烈依赖模型规模。
B t5

H# 70B：通用对话（ShareGPT）
T 70B 跑在两张 H200 上，测试显示显存带宽，也就是数据在显存与计算单元之间搬运的速度，才是最终瓶颈。
T 对 Llama-3.3-70B 这种大模型来说，每一步、每一次显存访问都很贵，推测解码方法的效率因此变得关键。LLM 推理通常是显存受限，搬运权重数据的时间是最大瓶颈，模型越大越明显。
T EAGLE-3 正是在这里拉开差距。标准 EAGLE 在这套配置上很难获得收益，EAGLE-3 用更先进、更轻量的草稿头做出准确率高得多的预测，显著减少了访问 70B 完整权重的次数。
T 为看清 EAGLE-3 在这类大模型上的优势，下面所有加速比都以基线的输出吞吐 343 tokens/s 为基准计算。
F fig08.png|图 8：Llama-3.3-70B 在 ShareGPT 1000 条提示上的吞吐与时延对比。
L **EAGLE-3**：以 537 tokens/s 的吞吐拿下第一，相对基线加速 1.57 倍，表现优于标准 EAGLE，说明改进后的草稿头架构在扩展到 70B 时是必要的。
L **Suffix Decoding**：455 tokens/s，加速 1.33 倍，比 EAGLE-3 慢 15.3%，但不需要任何额外训练或草稿模型管理，是一份近乎免费的加速。
L **N-gram Matching**：385 tokens/s，加速 1.12 倍。在这类大模型上，简单的统计式预测难以对抗 EAGLE-3 的前瞻能力。
L **EAGLE（标准）**：351 tokens/s，加速仅 1.02 倍，几乎与基线持平。这给出一个重要结论：对 Llama-3.3-70B 架构来说，升级到 EAGLE-3 才能拿到真正的收益。
L **基线（原始解码）**：343 tokens/s。它与 EAGLE-3 之间接近 200 tokens/s 的差距，说明了不做推测解码会浪费掉多少 GPU 潜力。
B t6

H# 70B：代码与智能体（SWE-bench Lite）
T 这一场景原本预期排行榜会翻回 Suffix Decoding，就像 8B 那样。在智能体工作流里，模型经常读自己的历史输出，文本重复度极高，通常有利于模式匹配。
T 但 70B 上的结果给出了不同的答案：Suffix Decoding 表现依然不错，而 EAGLE-3 作为当前最先进的方案，效率足以在这个结构化领域继续保持领先。
T 代码密集任务的基线吞吐约为 375 tokens/s。
F fig09.png|图 9：Llama-3.3-70B 在 SWE-bench Lite 300 条样本上的吞吐与时延对比。
L **EAGLE-3**：以 601 tokens/s 拿下最高吞吐，相对基线加速 1.60 倍。与 8B 上 Suffix 胜出的情况不同，70B 的 EAGLE-3 草稿模型足够强，预测结构化代码模式的能力超过最好的启发式方法。
L **Suffix Decoding**：522 tokens/s，加速 1.39 倍。虽然没有拿到第一，仍是很有竞争力的选择，比 N-gram matching 快 25.5%，在不需要训练的方案里是代码任务的最优解。
L **N-gram Matching**：416 tokens/s，加速 1.11 倍，比 Suffix Decoding 慢 20.3%，再次说明它有限的回看窗口不如 Suffix 更宽的模式匹配。
L **EAGLE（标准）**：377 tokens/s，加速仅 1.01 倍，几乎与基线打平，进一步说明标准 EAGLE 草稿模型可能没有针对 Llama-3.3-70B 架构的模式做优化。
L **基线（原始解码）**：375 tokens/s，作为对照组。EAGLE-3 每秒能多生成接近 226 个 token，这正是推测解码在大规模智能体工作流里的价值。
B t7

S# 选型建议
T 如果只记一句话：模型规模会改变规则。在 8B 这类轻量模型上最优的方法，未必适合 70B 这类大模型。
T 按场景给出的起点建议：
B t8
T **建议的起步姿势**：先用 Suffix Decoding，它是低垂的果实，不用训练、不额外占显存，开箱即用；如果部署的是 70B 以上的大模型并且追求极致吞吐，再考虑投入成本配置 EAGLE-3。
T **需要注意的边界**：这些结论针对 Llama 系列模型（3.1-8B 与 3.3-70B）以及 ShareGPT、SWE-bench 两个数据集。换模型架构、换数据特征、换硬件配置，结果都可能不同，最好在自己的真实负载上重新测一遍。
