S# Suffix Decoding：把历史输出建成后缀树
T Suffix Decoding 是一种完全不需要模型的加速方法，专为智能体循环、代码生成这类重复度高的负载设计。它不加载耗显存的草稿模型，而是利用历史文本里的模式，全程跑在 CPU 上，因此能在不增加任何显存开销的前提下拿到加速。
T 它和 N-gram matching 的思路接近：都是取最近生成的一段 token 回历史里找。区别在搜索方式。N-gram matching 在提示词和已生成文本里做线性扫描，Suffix Decoding 用的是预先建好的树结构，文本历史越长，查找速度的优势越明显。

H# 双后缀树缓存
T 核心是高效的后缀树（Suffix Tree）结构，它从两个来源收集历史模式：
B t0
T 两棵树分工明确：本地树负责同一个请求内的自我重复，全局树负责跨请求的统计规律，后者在智能体循环里尤其关键。

H# 搜索机制
T 每一步，Suffix Decoding 都会寻找足够长的匹配模式，用它作为本轮推测的依据。
L **进行中的序列（x₁ 到 xₜ）**：到当前 token t 为止已经生成的全部文本。
L **模式长度（p）**：要在历史里匹配的最近序列长度。
L **模式序列（x 从 t-p+1 到 t）**：当前请求最后 p 个 token。
T 系统沿着两棵后缀树向下行走来匹配这段模式。一旦匹配命中，就落在节点 Nₚ 上，该节点下的所有路径都是这段模式可能的延续。

H# 打分与贪心扩展
T 逐个检查所有可能的未来序列代价太高，Suffix Decoding 改用贪心扩展（Greedy Expansion）策略降低成本。
T 它不会铺开所有分支，而是构建一棵聚焦的推测树（Speculation Tree），只保留最可能的未来 token 路径。决定往哪根枝上长，靠两个概率分数：
L **步概率 C(N)**：这个 token 紧跟在上一个 token 之后出现的可能性。
L **路径置信度 D(N)**：从根节点走到当前 token 的整条序列正确的可能性，它是决策阶段的主要筛选依据。
T 置信度的算法很直观：新节点的置信度建立在到达它的那条路径之上。
T **D(N) = D(父节点) × C(N)**
T 也就是说，一个新节点的路径置信度等于父节点的置信度乘以这个 token 的步概率。如果位于最开始的根节点，置信度就是 1，也就是 100%。
T 贪心过程包含四个动作：
L **起始**：从最后匹配到的那个 token（Nₚ）开始。
L **评估**：查看可选的下一步，计算各自的路径置信度。
L **选优**：把置信度最高的叶节点加入推测树。
L **重复**：持续加入最可能的分支，直到推测树达到允许的最大规模 MAX_SPEC。
T 这样算力只会花在模型真正可能用到的序列上。

H# 三阶段图解
T 下图展示了 SuffixDecoding 的完整算法，来源是 Oliaro 等人的论文 SuffixDecoding（arXiv:2411.04975）。
F fig02.png|图 2：SuffixDecoding 的三阶段流程，从模式匹配到推测树，再到并行验证。
T 整个过程可以拆成三个阶段。
T **阶段 1，找模式。**
L **双树匹配**：当前 token 序列（例如 8、5、4、8、5）分别与两棵后缀树匹配，上面那棵对应进行中的推理，下面那棵对应此前的输出。
L **扩展候选**：匹配结果会生成所有可能的推测树候选，也就是图中左侧中间框里的序列。
T **阶段 2，建推测树。**
L **打分与选择**：用接受概率 D(N) 给候选打分，贪心选出最有希望的分支，最终得到一棵紧凑的推测树，也就是图中标注 1、2、3 的那条路径。
T **阶段 3，验证与生成。**
L **验证**：目标模型拿到原始序列和整棵推测树，用一次前向完成验证。
L **接受 token**：token 并行验证。在结果框里，目标模型接受了 token 1 和 token 3（绿色标记），它们被追加到最终输出后面，序列变成 8、5、4、8、5、1、3。一次接受多个 token，生成因此提速。
T 整个模式匹配与起草过程都在 CPU 上执行，速度极快，而且具备自适应性：推测的 token 数量 MAX_SPEC 会根据模式匹配长度动态调整，避免浪费算力。

S# MLP Speculators：挂在目标模型上的多头预测器
T MLP Speculator 建立在 Medusa 架构之上，由 IBM 改进成型：目标是拿到接近完整草稿模型的预测准确率，但不付出再加载一整个 LLM 的显存代价。

H# 架构：多头轻量预测器
T 推测器是一个多阶段、多头的 MLP，直接挂在目标模型上。相关方案见 Wertheimer 等人的 Accelerating production LLMs with combined token/embedding speculators（arXiv:2404.19124）。
F fig03.png|图 3：MLP 推测器的多头架构，用目标模型的上下文嵌入向量驱动 3 个预测头。
T 与只预测一个 token 的常规模型不同，它有多组头、多个预测阶段，分别负责向前看 1 步、2 步、3 步。
L **挂载与输入**：MLP 以目标模型的上下文嵌入向量（图中的内部状态 Z）为基础。每个后续头还会把前一个头采样出的 token 作为条件。例如 T2 由 Z 与目标模型生成的 T1 共同决定。
L **分工**：1 号头预测 token T2，2 号头基于这个预测继续预测 T3，以此类推。
T 由于目标模型保持冻结，推测器只是挂在其内部状态之上，参数规模被压得很小。

H# 训练：逐头计算损失
T 训练过程是细粒度的：目标模型冻结，MLP 用交叉熵损失训练，而且不是只算一个总误差，而是为每个推测步单独计算一份损失。
L **第 1 步（Loss_t+1）**：1 号头的预测与 token t+1 真实值之间的误差。
L **第 2 步（Loss_t+2）**：2 号头的预测与 token t+2 真实值之间的误差。
L **第 3 步（Loss_t+3）**：3 号头的预测与 token t+3 真实值之间的误差。
F fig04.png|图 4：三个预测头各自的训练损失曲线，越往后的预测越难收敛。
T 分开计算是有原因的：这几个损失的行为并不一致。预测最近的 token（t+1）相对容易，损失下降很快；预测更远的 token（t+3）更难，且依赖前面几步的准确度，损失曲线整体更高。分开跟踪可以避免近期误差被远期误差掩盖。

H# 两阶段训练方案
T 训练刻意分成两个阶段，目的是同时拿到稳定性和准确性。
L **阶段 1，输入对齐（代理数据）**：用长上下文的标准文本批次训练，让推测器学会把目标模型的嵌入映射到有效的后继 token。
L **阶段 2，输出对齐（模型蒸馏）**：改用目标模型自己生成的输出作为真值，损失函数迫使 MLP 精确模仿冻结的目标模型会生成什么，从而把推测器的行为对齐到目标模型的脾气。

H# 推理流程与生产环境优势
T 推理阶段，推测器会连续预测多个 token。
L **第 1 趟，目标模型前向**：目标模型跑一次前向，产出当前 token 的上下文嵌入向量。
L **第 2 趟，推测器前向**：MLP 推测器拿到上下文向量后快速生成 K 个候选 token，并用第一个预测 token 的 logits 去条件化第二个预测，依次构建 T_t+1 一直到 T_t+K。
L **验证**：整段候选序列打包交给目标模型，用一次前向完成验证。
T 在生产环境里，它的优势集中在三点。
L **显存节省明显**：MLP 很小，通常只有目标模型参数的十分之一甚至更少，相比完整草稿模型，内存开销可以忽略。
L **接受率高**：借助目标模型自身的上下文，预测准确度很高，墙钟推理速度可以提升 2 到 3 倍。
L **部署简单**：直接挂在目标模型上，不需要额外管理一个独立模型。

S# EAGLE：从草稿头到 EAGLE-3
T EAGLE（Extrapolation Algorithm for Greater Language-Model Efficiency）代表了推测解码的一条新路线：草稿模型需要一整个独立 LLM，带来显存与 tokenizer 的麻烦；MLP 推测器只做简单投影；EAGLE 取两者的中间路线。
T 它训练一个轻量的草稿头，通常只有 1 到 2 层 Transformer，直接插进目标模型，复用目标模型内部的特征图来预测 token。参数开销极小，70B 模型上不到 5%，却能带来显著的加速。

H# 三代演进
T 要理解 EAGLE-3 为什么是当前最先进的方案，需要看它的三代演进。
F fig05.png|图 5：EAGLE 1、2、3 三代方案的对比。
T **EAGLE-1（初代）**：提出用单层草稿头复用目标模型顶层特征，也就是最终输出前的那些特征。
L **局限**：存在特征不确定性。它用完美的真值数据训练，推理时却只能基于自己有噪声的预测往下走，预测越远，接受率掉得越快。
T **EAGLE-2（动态树）**：改进推理策略，引入动态草稿树，按上下文调整推测树的形状。
L **改进**：更懂得怎么猜，会提前剪掉低置信度分支，但仍沿用 EAGLE-1 的特征提取方式，准确率上限被限制住。
T **EAGLE-3（突破）**：改变草稿头学什么、看什么。
L **创新 1，多层融合**：不再只看顶层，而是抽取并融合目标模型低、中、高三层的特征，为预测提供更丰富的上下文。
L **创新 2，训练期测试**：在训练阶段就模拟推理时的噪声过程，解决分布不匹配问题。

H# 训练策略：Training-Time Test
T EAGLE-3 的训练策略是关键。传统做法用完美的真值输入训练草稿头，但真实推理时，草稿头要基于自己对 token 2 的猜测去预测 token 3，一旦 token 2 猜偏，后面就会跟着乱。
T Training-Time Test（TTT）把这个问题放到训练阶段解决。
L **原生步骤**：用目标模型给出的完美特征预测下一个 token。
L **模拟步骤**：随后把自己的预测结果再喂回去，预测后面的 token。例如预测 How can I help 时，为了得到 help，它用到的是自己对 I 的预测，而不是真值，哪怕这个预测并不完美。
T 这让草稿头学会从自己的错误里恢复，即便生成序列拉得很长，接受率依然能稳定在 70% 到 80%。

H# 推理策略：Tree Attention
T 推理阶段，EAGLE-3 不生成单条文本，而是生成一棵候选树。
L **树的构建**：从提示词 The weather is 出发，它可能预测 sunny（高概率）和 getting（较低概率），然后从这两个分支继续展开。
L **约束**：用基于置信度的剪枝，停止生长不太可能被接受的分支。
L **Tree Attention 验证**：目标模型用一次前向验证所有分支，并用专门的树注意力掩码，确保 A 分支的 token 看不到 B 分支的 token。
L **选择**：保留有效路径，其余丢弃。
T 树状候选加掩码验证，让 EAGLE-3 在一次前向里同时评估多条可能的续写，而不是只赌一条。
