要点速览
-核心观点：Pinned memory一旦被CUDA graph捕获、或因copy事件未完成而无法释放，就可能永久滞留：PyTorch每个pinned buffer内部都套着事件跟踪，你删除tensor并不能真正归还内存。

-关键机制：CachingHostAllocator只在事件确认DMA完成后才把块放回空闲链表；CUDA graph会把host buffer烘焙成永久固定件，导致pinned内存实际上没人还回去。

-实用建议：想真正归还pinned内存：torch.accelerator.empty_host_cache()（注意不是empty_cache），或用PYTORCH_ALLOC_CONF=pinned_max_cached_size_mb控制单块上限。

披露声明。 本文由Claude（Anthropic的编程助手）起草，并由ezyang编辑。

很长一段时间，我总以为pinned memory是你在代码中四处 洒下的东西，用来向GPU做async transfers。事实上， 旧的Caffe2曾 把每一个CPU tensor都pin住， 即使它从未真正参与过GPU计算。在这种模式下，你可能以为需要 一个pinned memory分配器，以便按需分配和释放pinned memory。

然而，如果你仔细思考async transfers对 pinned memory生命周期的含义，以及对CUDA graphs的含义，就会明白 你其实……并不真正想释放pinned memory。tl;dr：

CUDA graphs禁止这样做：captured graph会将host buffer的地址固化进其节点，因此任何参与 graphed copy的pinned buffer都必须在该地址保持存活，只要graph 被重放。

重新pin的成本很高：cudaHostAlloc需要花费毫秒级时间， 因此，在稳态下释放内存只是意味着在下次迭代中再次支付该代价。

使用pinned memory的工作负载具有固定的工作集：每一步 shape都相同，因此在步骤之间释放不会带来任何收益。

其余部分将详细讲解其中的机制。

顺便说一句，要想快速验证这一论断，值得看看Megatron-LM和vLLM 到底如何使用pinned memory，因为两者都从不 释放它。两者都有自己的pinned pool。两者都提前分配并持有 内存直到进程退出。其中一个有一个config flag，其全部 文档记载用途就是阻止pinned buffers被释放。

pinned memory的实际用途

Pinned (page-locked) host memory指操作系统承诺不会交换或 移动的内存，这使GPU的DMA引擎能够通过物理 地址直接读写它。这给你带来四点好处：

带宽。从pageable memory进行的拷贝必须经过driver-internal bounce buffer中转。pinned memory直接通过interconnect传输， 在PCIe上通常可达到2-3倍性能，在NVLink C2C上更高。

异步性。从pageable memory执行copy_(non_blocking=True) 实际上 无法与任何操作重叠：驱动程序必须分阶段拷贝，因此会阻塞。 只有从pinned memory发起时，non_blocking=True才能在传输完成前返回， 并让拷贝与计算重叠。如果你试图用计算掩盖传输延迟却忘了pin， 那就什么也没得到。

直接硬件路径。RDMA NICs和GPUDirect Storage需要已注册的 page-locked buffers。没有pageable选项。

CUDA graph中的D2H。下文详述，但简而言之：涉及pageable memory的async copy 表现为同步行为，而同步操作 在图捕获期间不允许。

复杂之处：你并不拥有你以为自己拥有的buffer。

当你发出时

gpu_tensor.copy_(cpu_pinned, non_blocking=True)

调用会立即返回，DMA仍在执行中。缓冲区并不 能安全重用：当Python语句结束或最后一个引用 释放时；只有复制真正在流上完成时才可安全重用， 而只有GPU知道何时完成。如果过早回收缓冲区， 会得到静默的数据损坏。

PyTorch的固定内存分配器可帮助你避免这个use-after-free问题。 每次涉及固定内存的copy_(non_blocking=True) 都会记录一个CUDA事件 到主机块 (aten/src/ATen/native/cuda/Copy.cu:481-486)：

const auto& host_tensor = (dst_device == kCPU ? dst_tensor : src_tensor);
auto* ptr = (dst_device == kCPU ? dst : src);
auto* ctx = host_tensor.storage().data_ptr().get_context();
at::getHostAllocator(at::kCUDA)->record_event(ptr, ctx, stream.unwrap());

注意，它同时以数据指针和存储上下文为键，因此一个切片 固定张量的切片，或通过from_blob基于分配器内存构建的张量，仍然 归属于正确的块。释放时，块被放置到事件队列中 并且在所有已记录事件结束前不会返回空闲列表 (参见aten/src/ATen/core/CachingHostAllocator.h:428-500)。设置 PYTORCH_ALLOC_CONF=pinned_use_background_threads:true会将轮询移到 一个辅助线程上，从而避开分配快速路径。

由于Python中的释放始终是隐式的（通过引用计数），我个人 认为，确保已释放的缓冲区不会被过早重用，是PyTorch 固定内存分配器提供的一个非常重要的防误用机制。

固定内存使用的一些示例

你不必使用PyTorch的固定内存分配器；自己调用cudaHostRegister相对 简单。

vLLM在worker初始化时一次性分配其host端输入缓冲区，大小调整为 max_num_reqs，并在进程的整个生命周期内每一步复用它们 (vllm/v1/worker/gpu_model_runner.py， 大约二十个pin_memory=PIN_MEMORY分配，大部分在初始化时)。这是 对图友好的input-prep模式：在host上填充固定缓冲区，一次 异步H2D，重放图。

对于KV offload，vLLM更进一步，完全绕过PyTorch的分配器 (vllm/v1/simple_kv_offload/cuda_mem_ops.py:23-32):

def pin_tensor(tensor: torch.Tensor) -> None:
    """Pin a CPU tensor via cudaHostRegister.

    This bypasses PyTorch's CUDACachingHostAllocator which rounds
    every ``pin_memory=True`` allocation up to the next power of 2
    (e.g. 100 GB becomes 128 GB).
    """
    err = torch.cuda.cudart().cudaHostRegister(tensor.data_ptr(), tensor.nbytes, 0)

Megatron有自己的固定内存池， OffloadTensorPool， 它是构建在PyTorch固定内存池之上的抽象：

所有三个实现（PyTorch、vLLM、Megatron）有一个共同点： 在稳定运行期间，它们都不会将固定内存归还给操作系统。 它们分配一个工作集，复用该工作集，并一直持有到进程退出。

那么，删除张量会解除其固定吗？不会

当对固定张量的最后一个引用消失时，PyTorch会记录所有接触过它的流上的事件，一旦这些事件完成，该内存块就进入空闲列表（maybe_cache_block, CachingHostAllocator.h:808）。没有任何代码调用cudaFreeHost。这些页面保持页锁定状态并已在驱动程序中注册。

import gc, torch

MiB = 1024 * 1024

def report(label):
    s = torch.cuda.host_memory_stats()
    print(f"{label:20} owned={s['allocated_bytes.current']//MiB:5} MiB"
          f"  checked_out={s['active_bytes.current']//MiB:5} MiB"
          f"  cudaFreeHost calls={s['num_host_free']}")

t = torch.empty(256 * MiB, dtype=torch.uint8, pin_memory=True)
report("after alloc")

del t
gc.collect()
torch.cuda.synchronize()
report("after del")          # checked_out -> 0, owned stays at 256 MiB

torch.accelerator.empty_host_cache()
report("after empty_cache")  # owned drops, num_host_free increments

active_bytes是已签出给调用方的内存；allocated_bytes是分配器拥有的内存，包括活跃和缓存部分。删除张量会将字节从前者移动到后者，只有empty_cache才会将它们从后者移除。

在分析PyTorch中的内存分配时，必须区分三件不同的事情。释放张量是引用计数且确定性的。使内存块可复用是延迟的，但只会延迟到流事件完成，而且这种延迟是正确性要求，而不是惰性。将页面归还给操作系统永远不会自动发生。

当你确实想要收回它时，以及如何收回

对于独占机器的训练任务来说，“一次分配并持有”是正确的。 有两种情况并非如此：

对于这些情况，你可以强制将pinned memory归还给操作系统：

torch.accelerator.empty_host_cache()   # public, device-generic, 2.12+
torch._C._host_emptyCache()            # CUDA-only, private, since 2.5

torch.cuda.empty_cache() 并不会这样做。它只是为设备分配器调用 _cuda_emptyCache，并且有意不提供 torch.cuda.empty_host_cache()。

empty_cache只回收位于空闲列表上的内存块，因此它是安全的， 可以在任何时间调用；如果仍有异步传输正在进行，它释放的内存可能少于 你的预期。

如果完全刷新过于粗暴（之后每次分配该大小的内存都要付出一次 耗时数毫秒的全新cudaHostAlloc），则改为限制缓存大小：

PYTORCH_ALLOC_CONF=pinned_max_cached_size_mb:512

超过此大小的内存块会在其复制事件完成后立即释放，而不是 被缓存。此外还有pinned_max_round_threshold_mb，它会禁用给定大小之上的 二次幂舍入；它晚于上面提到的vLLM的cudaHostRegister变通方案出现， 并且可以解决同样的100 GB变成128 GB的问题。

有一点在任何情况下都不会释放：如果你启用了 pinned_reserve_segment_size_mb，该内存块会被free_block明确跳过 (aten/src/ATen/cuda/CachingHostAllocator.cpp:95)，并且按设计会一直存活到进程 退出。

解除内存固定

如果你想把pinned memory视为发生在普通CPU内存上的一种属性， 你可以直接在普通CPU tensor上使用cudaHostRegister / cudaHostUnregister， 这些函数可通过公开的torch.cuda.cudart() 从Python访问。PyTorch附带了一个 四行包装器，位于 torch/cuda/_pin_memory_utils.py （它是私有的，但底层调用不是），分布式检查点使用它 作为暂存缓冲区。你将获得完全显式的生存期，没有缓存，没有舍入；但你必须 确保事件处理正确。

不使用CUDA可以使用锁页内存吗？

_pin_memory是一个加速器专属的API，在没有 加速器时会报错（例如纯CPU构建）。这可能有点 不方便，如果你有时喜欢用CPU设备测试。除了写那种烦人的条件表达式测试（ t.pin_memory() if torch.accelerator.is_available() else t）之外，我确实没什么建议。

注意，从技术上讲，可以在没有加速器 参与的情况下获得页锁定主机内存：例如被mlock的缓冲区，或 O_DIRECT / libaio NVMe卸载所需的页对齐分配。这与CUDA无关， PyTorch不为此提供API。

结论

希望这能解答你关于锁页内存以及 如何使用它的一些疑问。确实，直接从Python实现你自己的 锁页内存分配器相当容易，而且你应该可以随意这样做 如果合适的话（不过我怀疑你要是这么做了，就不需要这篇文章了。）但 我认为内置的锁页内存分配器也相当好用，而且你 大多数情况下应该考虑不使用它，如果你想要精确大小匹配而不是 二次幂桶，或者如果你承诺自己处理 释放。

结语
pinned memory是高性能host-device传输的根基：带宽、异步copy、RDMA、CUDA graph内D2H都离不开它。但正因为它被CUDA graph和copy事件‘钉住’，PyTorch的CachingHostAllocator在删除张量后并不会立刻把内存还给系统：只要还有in-flight的异步操作引用它，块就留在缓存里，直到事件确认完毕。

如果你真的想强制归还：用torch.accelerator.empty_host_cache()（它不会像empty_cache那样只清理空闲链表），或通过pinned_max_cached_size_mb让超大块用完即释放。记住，唯一永不释放的是被CUDA graph捕获的buffer：除非重建图。
