要点速览
-SM分区加workqueue配给：Green contexts让应用显式选定SM子集与workqueue资源，CUDA 12.4进Driver API，13.1进Runtime API，创建销毁轻量、不隐式同步无关工作。

-关键kernel实测：Blackwell 148 SM上，关键kernel延迟：green-ctx分区0.007 ms，高优先级无分区0.140 ms，同优先级3.727 ms。

-显式编程模型：cudaGreenCtxCreate拿句柄、cudaExecutionCtxStreamCreate建流，不再依赖线程局部device状态；其余代码沿用stream模型。

一张GPU上同时跑延迟敏感算子和吞吐型后台kernel时，stream优先级救不了关键任务：bulk kernel占满SM，高优先级kernel也只能等block排空。NVIDIA的Green Contexts把解法做彻底：直接把SM切块划给关键负载。

实测数据很直白：148 SM的Blackwell上，关键kernel延迟从同优先级的3.727 ms，到高优先级的0.140 ms，再到green-ctx分区的0.007 ms。下面拆机制、看代码、摆数字。

单进程多组件,GPU资源不够分

GPU应用越来越多由同一进程内的多个独立组件同时跑：延迟敏感算子配吞吐型后台kernel，数据预处理配模型推理，或者一条处理流水线的多个阶段共享一张GPU。

组件之间怎么分资源，一直不好控制：互相干扰不可预测，现有工具的划分能力有限。Green contexts让应用显式选定GPU执行资源的一个子集，把工作直接打到这些资源上。传统CUDA context不是为这种用法设计的：笨重，有硬件context切换开销，还带着早年假设：那时GPU小，应用通常是一个独占式大负载。

Green contexts在CUDA 12.4起可用于Driver API，CUDA 13.1起可用于Runtime API。应用在自己的进程内显式定义工作跑在哪里、执行资源怎么切。

Green contexts的工作方式

第一个主要用途是SM划分。给green context指定一个SM子集，经它提交的工作就跑在这些SM上。多个负载可以并发跑在同一张GPU上，不抢同一批计算单元。

除了SM划分，green contexts还能配给workqueue资源。传统模型下，独立的stream有序workload可能映射到同一底层workqueue，执行资源明明够，却被意外串行化。显式配给workqueue后，应用能表达预期的并发，减少假依赖。

Green contexts创建销毁轻量，建/销不隐式同步无关的GPU工作。编程模型也更显式：应用把工作打到选定的green context，而不是只依赖隐式的current device状态。

显式编程模型

历史上CUDA Runtime应用的典型流程是cudaSetDevice() 选卡、建stream、向stream提交工作。stream的执行目标从建流时调用线程的current device/context推断出来。

Green contexts让目标选择显式化：应用为选定的资源建green context，再从它建stream；提交到这些stream的工作就归属该green context的资源。

Runtime API里green contexts用cudaExecutionContext_t类型表示（CUDA context的Runtime抽象）。关键点是cudaGreenCtxCreate() 返回的句柄可以直接传给cudaExecutionCtxStreamCreate() 这类API，不再依赖隐式的线程局部device/context状态。

对stream，这个变化直接体现在建流方式上。下面代码为简洁省略了完整错误检查，生产代码要检查所有CUDA Runtime API返回值，kernel launch后用cudaGetLastError()/cudaPeekAtLastError()，cudaStreamSynchronize() 等同步调用也要检查异步执行错误。

传统Runtime流程：stream目标来自current device状态。

cudaSetDevice(device);
cudaStream_t s;
cudaStreamCreate(&s);
kernel<<<grid, block, 0, s>>>();

Green-context流程：stream目标显式选定。

cudaExecutionContext_t greenCtx;
cudaGreenCtxCreate(&greenCtx, desc, device, 0);
cudaStream_t s;
cudaExecutionCtxStreamCreate(&s, greenCtx, 0, 0);
kernel<<<grid, block, 0, s>>>();

代码改动很小，心智模型更清楚：不再依赖隐藏的线程局部device状态，而是显式选green context、为它建stream。其余代码继续用同一套基于stream的CUDA编程模型。

想打满整卡的应用可以继续用传统Runtime模型；对那些接受显式context句柄的API，用cudaDeviceGetExecutionCtx() 拿device级context。

示例:关键kernel与吞吐kernel同卡

GPU负载常需要一个小而延迟敏感的kernel和一个大的吞吐型worker同卡跑。典型例子：分布式训练/推理里的通信与GEMM overlap，或NVIDIA Holoscan这类AI传感器处理平台里要求尽快启动的延迟敏感算子。

这类关键工作的标准工具之一是CUDA stream priority。但光设优先级不够：当bulk kernel占满全部SM，高优先级kernel到了也得等。调度器只能把关键kernel的thread block交给下一个空出来的SM；stream优先级抢占不了已经在SM上跑的block，只能等部分block排空。

做个示例看结果。先写setup代码，这是新增的部分：第一步，查device上全部SM：cudaDeviceGetDevResource(dev, &all_sm, cudaDevResourceTypeSm)；第二步，按架构的coscheduled对齐切出一个关键组：crit_params.smCount = all_sm.sm.smCoscheduledAlignment，再cudaDevSmResourceSplit(&critical_res, 1, &all_sm, &remaining_res, 0, &crit_params)；第三步，给每个分区配独立的workqueue-config资源（队列压力也隔离），再生成descriptor：wq.type = cudaDevResourceTypeWorkqueueConfig，wq.wqConfig.sharingScope = cudaDevWorkqueueConfigScopeGreenCtxBalanced，wq.wqConfig.wqConcurrencyLimit = 2，然后crit_pack = {critical_res, wq} 生成crit_desc，bulk_pack = {remaining_res, wq} 生成bulk_desc；第四步，各建green context再建stream：cudaGreenCtxCreate(&crit_ctx, crit_desc, dev, 0)，cudaExecutionCtxStreamCreate(&crit_stream, crit_ctx, cudaStreamNonBlocking, prio_high)，bulk同理用prio_low。

// 1. Query all SMs on the device.
cudaDevResource all_sm {};
cudaDeviceGetDevResource(dev, &all_sm, cudaDevResourceTypeSm);
// 2. Carve out one critical group (arch's coscheduled alignment).
cudaDevSmResourceGroupParams crit_params {};
crit_params.smCount = all_sm.sm.smCoscheduledAlignment;
cudaDevResource critical_res{}, remaining_res{};
cudaDevSmResourceSplit(&critical_res, 1, &all_sm, &remaining_res, 0, &crit_params);
// 3. Pack each partition with its own workqueue-config resource so queue
//    pressure is isolated too, then generate the descriptor.
cudaDevResource wq {};
wq.type = cudaDevResourceTypeWorkqueueConfig;
wq.wqConfig.device = dev;
wq.wqConfig.sharingScope = cudaDevWorkqueueConfigScopeGreenCtxBalanced;
wq.wqConfig.wqConcurrencyLimit = 2;
cudaDevResource crit_pack[2] = { critical_res, wq };
cudaDevResourceDesc_t crit_desc{};
cudaDevResourceGenerateDesc(&crit_desc, crit_pack, 2);
cudaDevResource bulk_pack[2] = { remaining_res, wq };
cudaDevResourceDesc_t bulk_desc{};
cudaDevResourceGenerateDesc(&bulk_desc, bulk_pack, 2);
// 4. Create each green context, then a stream on it.
cudaExecutionContext_t crit_ctx{};
cudaGreenCtxCreate(&crit_ctx, crit_desc, dev, 0);
cudaStream_t crit_stream{};
cudaExecutionCtxStreamCreate(&crit_stream, crit_ctx, cudaStreamNonBlocking, prio_high);
cudaExecutionContext_t bulk_ctx{};
cudaGreenCtxCreate(&bulk_ctx, bulk_desc, dev, 0);
cudaStream_t bulk_stream{};
cudaExecutionCtxStreamCreate(&bulk_stream, bulk_ctx, cudaStreamNonBlocking, prio_low); // define prio_low

其余代码都是熟面孔：先打满bulk分区，20次bulk kernel launch；再在关键分区上launch关键kernel，前后打event计时，最后cudaStreamSynchronize(crit_stream) 等结束算毫秒数。

// Saturate the bulk partition.
for (int i = 0; i < BULK_LAUNCHES; ++i) {
    bulk_kernel<<<bulk_grid, bulk_block, 0, bulk_stream>>>(
        d_bulk, N_BULK, BULK_ITERS);
}
// Launch the critical kernel on its own partition.
cudaEventRecord(t_start, crit_stream);
critical_kernel<<<crit_grid, crit_block, 0, crit_stream>>>(d_crit, N_CRIT);
cudaEventRecord(t_stop, crit_stream);
cudaStreamSynchronize(crit_stream);
float crit_ms = 0.0f;
cudaEventElapsedTime(&crit_ms, t_start, t_stop);

stream自带分区，kernel只能看到允许跑的SM。测三种模式，critical + bulk负载相同：模式A，green-ctx分区、关键stream高优先级；模式B，默认context、关键stream高优先级（不分区）；模式C，默认context、双stream同优先级（无优先级、无分区）。关键kernel是个小整数负载，bulk kernel是20次背靠背launch的4M线程sqrtf循环，目标是打满device。测bulk运行时关键kernel的wall-clock延迟。

在148个SM的Blackwell GPU上：green-ctx（关键8 SM / bulk 140 SM）0.007 ms；默认context高优先级关键kernel 0.140 ms；默认context同优先级3.727 ms。

光stream优先级就是巨大胜利：比同优先级抢SM快约27倍。但优先级有天花板：bulk block排空之前，高优先级kernel还要再等约20倍的时间，哪怕调度器已经优先它。Green contexts直接跳过这段等待，因为关键SM专属于这个负载。代价是bulk kernel能用的SM少了。

同一套骨架也能用来拿并发而不是延迟，比如让通信kernel和GEMM kernel overlap、齐头并进。高级用法常把green context分区和stream优先级一起用，打到想要的性能目标。

什么时候用green contexts

五种情况最对味：同一张GPU上并发跑多个独立负载；要可预测的性能而不是best-effort的stream调度；想显式控制GPU执行资源怎么切；workqueue失控导致性能退化；应用正往单进程内pipeline式、多组件执行演进。

上手

四步：应用用CUDA 13.1或更新构建；查device资源，为想要的分区建green context；为该green context建stream，继续用同一套基于stream的CUDA编程模型提交工作；对接受显式context句柄、要打满整卡的API，用cudaDeviceGetExecutionCtx()。

Green contexts是opt-in、增量的：现有应用可以不改、继续打满整卡，只在需要更细控制的地方逐步采用。

结语
Green contexts的本质是把GPU资源划分从隐式调度变成显式声明：SM子集、workqueue配给、stream归属，一次配好、处处显式。0.007 ms对0.140 ms说明，优先级只能缓解排队，分区才能消灭排队；代价是bulk侧SM变少，这是可计算的trade-off，不是不可预测的干扰。

对推理serving、多租户、端侧pipeline这类单卡多组件场景，一个可复用的模式是：关键路径单独分区加高优先级，吞吐部分吃剩下的SM，workqueue配给顺手配上。CUDA 13.1的Runtime API让接入只是几次调用的事，可以增量采用。
