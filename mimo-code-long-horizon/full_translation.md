MiMo Code 是小米 MiMo 团队在 OpenCode 基础上构建的、基于终端的编码 Agent，以 MIT 许可证开源。它专为长周期自动化编程任务设计，核心关注点是：在几十步甚至几百步的执行过程中，如何维持决策质量和状态连续性。本文通过三个主题——计算（computation）、记忆（memory）和进化（evolution），介绍 MiMo Code 的核心技术设计。

1. 设计动机

编码 Agent 的基本结构，是把一个语言模型放进运行时（runtime）里，然后用循环不断调用它：模型负责推理和决策，运行时管理工具、持久化状态，并为每一轮组装输入。模型本身是无状态的——每次调用都从空白开始，所有连续性都由运行时提供。

对于短任务（通常少于 10 轮），这种结构运行良好：只要把完整的对话历史传给模型就够了，因为历史本身充当了足够的工作记忆。但随着任务轮数增加，两个问题逐渐浮现。

第一，上下文窗口最终会被耗尽。无论窗口多大，几十轮的工具输出、代码片段和错误日志最终都会把它填满。到那时，必须压缩或丢弃部分历史。一种常见做法是生成摘要来替代被丢弃的内容。但简单的压缩会不断强化临近信息、削弱远处信息。这种方法会遇到一个与 Mamba 等循环模型类似的内在困境：它有状态，却无法按需回头查看。我们需要的不是更好的压缩，而是一个显式的存取机制，来决定哪些信息应该写入持久化结构、以及何时被召回。

第二，即使上下文窗口足够大，模型的指令遵循能力也会随着输入长度增长而下降。有用的约束和意图被大量工具输出稀释，使模型越来越难提取出下一步该做什么。

我们观察到，最突出的瓶颈在不同时间尺度上各不相同：一次会话内单轮决策的质量主要受计算约束；一次会话内多轮任务的连续性主要受状态管理约束；而跨会话的改进主要受经验蒸馏机制约束。这三个时间尺度恰好对应计算、记忆和进化。MiMo Code 就是围绕这三个主题设计的。

2. 计算：扩展单轮推理

当任务增长到几十甚至几百步时，每一步的错误率会随时间累积，而 Agent 在长周期执行中往往缺乏外部纠正信号。一个直接的应对方式是在不同粒度上投入额外计算，以换取可靠性：在单步层面降低决策错误的概率，在任务层面防止过早终止或方向漂移，在执行层面减少不必要的来回开销。

2.1 并行采样与选择（Max Mode）

Max Mode 在每一轮并行生成 N 个候选解（N 默认设为 5）。每个候选独立完成推理和工具调用规划，但并不真正执行计划。然后用同一个模型作为评判者，比较所有候选的推理过程与行动规划，选出最好的一个来执行。

默认 temperature 设为 1，所以五个独立样本几乎不会产出相同结果。如果多个候选恰好收敛，这本身就表明该方向置信度很高；当候选差异显著时，用一个低温评判者选择最稳健的计划，比依赖单个样本更可靠。

在 SWE-Bench Pro 上，Max Mode 相比单次采样带来 10–20% 的性能提升，代价是大约 4–5 倍的 token 消耗。

注：Max Mode 目前是实验性功能，必须手动通过配置开启。

2.2 独立完成验证（Goal）

Max Mode 解决的是"做对"；Goal 解决的是"做完"。

长任务一个常见的失败模式是：在后几轮看到已有进展后，Agent 倾向于过早宣布"已完成"或提问。这在自动化执行中尤其危险，因为没有人工在旁边纠正或反馈。

Goal 机制的工作方式如下：用户定义一个自然语言停止条件，例如"所有测试通过且代码已提交"。每当 Agent 试图终止时，系统自动发起一次独立的模型调用，审查完整对话历史，判断条件是否真正满足。若不满足，就把具体缺口反馈给 Agent 让它继续；若确认任务不可能完成，就标记为不可能。

这个验证器不参与实际工作，所以不会对 Agent 已完成的部分产生对齐偏差。每次它都接收到与 Agent 完全相同的上下文，包括真实的工具输出。

在实践中，误阻塞（条件已满足但验证器判为未满足）比误通过更常见。这主要发生在因环境问题导致测试失败时。总体而言，无限循环的概率低于 0.5%，系统可在达到上限后自动退出。

Max Mode 和 Goal 代表了测试时计算（test-time compute）的两个正交方向：Max Mode 是并行的，在同一轮上花费 N 倍计算来选出最优选项；Goal 是串行的，在同一任务内花更多时间自检和继续执行。两者可同时开启。

2.3 工具调用语法

模型发出工具调用的格式直接影响准确性和 token 效率。某些模型（尤其是 GPT-5.5 系列）在输出结构化 JSON 时格式错误率相对较高，而 XML 比 JSON 略好。我们最终发现，一种受约束的命令行语法（constrained command-line syntax）表达同样的工具调用意图所需 token 更少，产生的格式错误也更少，因为大多数模型都在密集的 shell 环境数据上训练过。该语法刻意受约束：不支持管道、重定向或变量展开。目标是借用 shell 的简洁性，而不是给模型一个不受控的执行环境。

注：MiMo Code 尚未将工具调用迁移到该格式。替换可能在未来版本中逐步完成。

2.4 大规模并行编排（Dynamic Workflow）

上述机制解决的是单轮和单 Agent 层面的质量问题。当任务规模足够大——例如把整个项目从一种编程语言迁移到另一种——需要同时协调几十甚至几百个并行工作单元时，一轮一轮的工具调用就不再够用了。

传统做法是把流程写进 SKILL.md，用自然语言告诉模型："先做 A，再做 B，如果发生了 C 就做 D。"这在简单场景可行，但在复杂工作流中会系统性失败：上下文压缩可能吞掉步骤，模型可能跳过某些阶段，分支和重试逻辑依赖模型判断而非代码保证，同一工作流两次运行可能走不同执行路径。根本问题在于：编排逻辑存在于自然语言之中，而自然语言是模糊的、易忘的、不可验证的。

Dynamic Workflow 把编排逻辑从 prompt 变成代码。主 Agent 生成一个 JavaScript 脚本，在隔离沙箱里确定性地执行。脚本通过 agent() 派发子 Agent，通过 parallel() / pipeline() 控制并发——if 语句不会忘记分支，for 循环不会提前退出，barrier 不会漏掉某个子 Agent。模型的判断只用在它该用的地方，比如理解和生成代码，而不是浪费在流程控制上。

我们的实现兼容 Anthropic Dynamic Workflow 的核心语义，并在若干方面做了扩展。workflow() 原语允许脚本调用其他脚本，因此编排逻辑可以组织成可复用、可组合的积木。每次 agent() 调用的结果同步写入磁盘，使流程在中断后能基于日志恢复，而不是从头重跑。文件也可以在沙箱内部直接读写。我们相信，许多当前以 prompt 形式定义的 skill 将逐渐演化为代码形式的 workflow 脚本。当流程的每一步都必须执行、分支条件必须精确、重试逻辑必须可靠时，应该由代码而非自然语言来保证。

3. 记忆：跨多轮任务维持状态连续性

扩展单轮计算能降低每一步的错误率，但解决不了多轮任务的核心问题：上下文终究会耗尽。本节讨论如何让一个逻辑会话无限延伸，同时保持每个物理窗口有界。

3.1 Cycle：无界会话的基本单元

把会话想象成从左到右排列的一串轮次。窗口有上限，轮次不断累积，窗口终会被填满。若不干预，会话要么到达上限时结束，要么悄悄退化。

在到达上限之前，运行时（runtime）在几个固定位置介入。我们称这些位置为检查点（checkpoint）。在每个检查点，运行时派发一个独立的 writer 子 Agent：它读取到目前为止的对话，把结构化状态文件写入磁盘。主 Agent 在 writer 运行的同时继续工作，二者互不干扰。

当窗口接近真正的上限时，运行时执行一次重建（rebuild）：切断当前窗口，开一个新窗口，并用持久化文件作为种子重建上下文。主 Agent 在新窗口中醒来，状态已经铺在它面前，然后继续工作。从模型视角看，对话从未中断；从运行时视角看，一个新的物理窗口已经开启。

一段被检查点标记、并最终以重建结束的轮次序列，就是一个 cycle。cycle 的数量没有上限——每个 cycle 受物理窗口大小限制，但逻辑会话是 cycle 的链条，这条链条没有最大长度。

3.2 为什么提前提取

一个自然的直觉是：等到窗口快满时再提取。我们发现这恰恰弄反了。

第一，模型能力在高上下文利用率下会退化。文献中这被称为"lost in the middle"（中间迷失）：随着输入变长，对中间部分的注意力下降，结构化提取的可靠性显著下降。在模型压缩能力正在退化的那一刻，让它执行最关键的压缩，是个糟糕的权衡。

第二，提取本身需要空间。writer 必须读取历史、维持自己的理解、产出结构化输出——这些都在同一个窗口内。利用率 95% 时没有思考余地；利用率 30% 时则有充足空间。

因此，检查点在远低于上限的位置触发——大约在配置预算的 20%、45% 和 70%。每次触发都是对上一次增量更新；没有一次是一次性摘要。接近上限的最终重建不是仓促压缩，而是把沿路积累的结构化记录转化为工作上下文的时刻。

3.3 Writer：独立于主 Agent 的提取器

最自然的反应是让主 Agent 维护自己的笔记。我们发现这在长任务中站不住脚：让一个正在调试棘手问题的模型同时维护结构化日志，常常导致两件事都做更差。

所以我们施加了不同的约束：主 Agent 不维护自己的记忆。提取完全移出主循环，由运行时触发、由一个独立的 writer 子 Agent 执行——它不共享主 Agent 的注意力或 token 预算。

writer 写入一个固定结构的检查点文件（11 个字段：当前意图、下一步动作、工作约束、任务树、当前工作、涉及文件、跨任务发现、错误与修复、运行时状态、设计决策、杂项笔记），并在需要时更新项目级记忆。对于每个结构化文件，恰好允许一个写入者——single-writer 是防止并发写导致状态不一致的最简单不变式。

3.4 记忆的四层

writer 不只写一个文件。它维护一个分层记忆系统，每层有不同的生命周期：

会话记忆（checkpoint.md）：仅存活于当前逻辑会话内，记录该会话的完整工作状态。

项目记忆（MEMORY.md）：持久化的项目级知识——架构决策、用户规则、以及反复验证的技术事实。当一个观察在多个会话检查点间稳定下来，writer 把它从会话层提升（promote）到这一层。

全局记忆（Global memory）：跨项目适用的用户级偏好。

历史（History）：每次会话的完整 SQLite 轨迹——每条消息和每次工具调用的原始文本，未经索引地存储。当结构化记忆中找不到某细节时，Agent 用 history 工具回溯到原始记录。

四层之间的关系如下：上层更精炼、更持久、更小；下层更完整、更大、更慢。writer 负责向上蒸馏，而 history 作为下方的兜底。

主 Agent 对结构化文件有只读访问权限，只有一个例外：notes.md，一个会话级的自由格式草稿本。主 Agent 可随时把零散发现追加进去；在每个检查点，writer 读取它，把内容路由到合适的结构化字段，然后清空它。这是主 Agent 唯一可用的写入通道。

3.5 重建注入

当运行时执行重建时，它把持久化文件组装成一个分层 prompt，注入新窗口，每个 section 有独立 token 上限。大致顺序是：任务列表（Agent 首先得知道自己该做什么）→ 会话检查点 → 近期用户消息的逐字切片（防止 writer 的改写偏离用户原始意图）→ 项目记忆 → 全局记忆 → notes → 一个可按需读取的记忆文件路径索引 → 一个告诉 Agent 下一步做什么的尾部提醒。

即使每个 section 都到达上限，注入的总内容也控制在大约 65K token 以内——远低于任何合理上下文窗口的工作预算。从这些信息中恢复状态后，Agent 直接继续工作，无需重新确认目标或重读已处理过的文件。

4. 进化：从经验中持续改进

前两节讨论的是如何在单轮和单会话内把工作做好。但在真实开发中，一个用户可能与同一项目交互几十甚至几百次。如果每次会话结束所有经验都丢失，Agent 永远无法从过去的工作累积；它每次都得重新发现相同的项目约束、重复相同的错误。

4.1 项目记忆

MiMo Code 维护一个项目级记忆文件（Markdown 格式），跨会话持久化存储知识：项目背景、用户明确指定的规则、架构决策及其理由、以及反复验证的技术事实。

选择文件而非纯向量数据库的核心原因是可审查性（reviewability）：一旦记忆影响了 Agent 后续行为，用户需要能看到系统记住了什么、删除错误条目、修改过时知识。文件可以用标准读写工具直接操作，无需为每个维护操作配备专用界面。全文索引在文件之上提供快速检索。

检查点 writer 每次被触发时只更新当前会话的检查点，且写入权限在代码层面强制执行。后台 writer 只能写入指定文件路径，任何越界写入都被直接拒绝。

4.2 记忆维护（Dream 与 Distill）

项目记忆文件随时间增长。若不维护，过时的条目、重复记录和无效文件引用逐渐累积，拉低信噪比。

Dream 每 7 天自动触发。一个独立 Agent 读取历史会话对话和现有记忆文件，然后执行合并、去重、路径有效性验证和压缩——把分散的记忆收敛为当前状态的紧凑表示，并更新全局记忆。

Distill 每 30 天自动触发。它也由独立 Agent 执行，读取历史会话，但它的焦点不是知识，而是流程。它识别反复出现的工作模式，把它们固化为可复用的 skill、CLI 命令、自定义 Agent、SOP 文档以及类似产物。

MiMo Code + MiMo-V2.5-Pro 在三个评测上均优于 Claude Code + Claude Sonnet 4.6。不过需要指出，这些基准衡量的仍是个别仓库级问题上的单次解题能力。MiMo Code 大多数设计目标——多轮记忆、后台状态维护、完成验证、跨会话进化——主要在有几十轮持续的真实开发场景中才显现价值。这些优势只有在真实使用中才能充分反映。

5.2 人类双盲 A/B 测试

为弥补离线基准的局限，我们搭建了一个人在回路（human-in-the-loop）的双盲 A/B 评估：在开发者自己的真实项目中，为同一任务并行启动两个匿名编码 Agent。它们独立完成任务后，由开发者打分，并用自动轨迹评分和 diff 量化做三角验证。

报告期内，内部测试覆盖 576 名开发者和 474 个真实私有仓库，产出 1,213 个有明确胜负判定的 A/B 对，在相同目标模型下比较 MiMo Code 与 Claude Code 的端到端真实开发体验。

评估中我们发现，MiMo Code 的优势随任务复杂度上升而增长：当执行步数在 200 以内时，两套系统胜率接近 50%；当步数超过 200（包含多轮用户交互）时，MiMo Code 胜率升至 65% 以上。
