你的 KV 缓存是坏的

一份面向实践者的 KV 缓存管理指南。一种现代缓存架构如何把输入 token 成本砍掉 90%，并把 LLM 推理速度提升最高 14 倍。

斯坦福的研究人员研究过 AI Agent 实际上是如何花掉它们的推理预算的。最突出的一个发现是：每次调用发给 Agent 的内容里，大约 62% 只是重复的内容。同样的系统提示词、同样的工具定义、同样的文档，一遍又一遍地喂进去。

所以每当 Agent 迈出一步，你都要把所有的东西从零交给他。所有的指令、所有的上下文、所有的背景。哪怕他一秒钟前刚处理过完全相同的信息。

昂贵的部分不是思考或推理。昂贵的是 AI 一遍又一遍地重读同一份笔记。

Agent 循环在每一步都重新发送相同的提示载荷（系统提示词、工具定义、文档）。

2023 到 2026 年间，每个 token 的价格下降了 80%，GPT-4 级别的模型从每百万 token 30 美元降到了 0.40 美元。但 Agentic 工作流每个任务消耗的 token 是标准聊天机器人查询的 5 到 30 倍，因为每一步都会把所有上下文重新发送一遍。所以即使每个 token 变便宜了，总账单却涨上去了，因为用量超过了降价的幅度。

Uber 是吃了苦头才学到这一点的。把 Claude Code 铺开到整个工程组织，四个月就烧光了他们 2026 年全年的 AI 预算。Gartner 现在预测，到 2027 年，40% 的 AI Agent 项目会因为成本超支而被取消。

行业在优化一个错误的变量。如果大多数 token 本就不该存在，让 token 变便宜并没有用。

所以，在这篇文章里，我们要学习一种新的开源架构，它把缓存管理完全移出了推理引擎。运行它的团队看到了最高 14 倍的更快首 token 延迟，而且大多数实践者还没追上它，所以现在搞懂它，能让你领先于今天几乎所有跑推理的人。

当你发送一个提示时发生了什么

每次你向模型丢一个提示，它都会把每个 token 通过注意力机制跑一遍。对每个 token，模型在每一层注意力上计算一个 Key 向量和一个 Value 向量。这些 K 和 V 向量捕捉了模型如何"理解"每个 token 与上下文中其他所有 token 的关系。

这些 K 和 V 向量的集合就叫做 KV 缓存。

注意力机制如何产生 KV 缓存

计算量随输入长度呈二次方增长。上下文翻倍，注意力计算大约变成四倍。在 4K token（一个简单的聊天机器人回合）时这很便宜。在 128K token（一个带有工具、文档和历史的 Agent 循环）时，它就贵了。

4K、32K 和 128K 上下文长度下的二次计算成本曲线：上下文翻倍，成本变四倍

单张 MI300X GPU 每天大约产生 15 TB 的 KV 缓存。其中大部分在每次请求之后就被丢弃了。

你的系统提示词的 KV 缓存，每次发送它时都是完全一样的。你上传的某个文档的 KV 缓存，每次用户问起它时都是完全一样的。但模型每次都从头重新推导出同样的理解。

想想这就像每次有人问起第 7 章的后续问题，你都要从第 1 页重新读一遍教科书。你已经理解了第 1 到第 6 章，但你没有办法保存并复用那种理解。所以你从头再来。

前缀缓存解决了什么，又在哪里停下

行业注意到了这种浪费，于是造了一个叫提示缓存（prompt caching）的功能来应对它。

它是这样工作的。如果两个连续的请求共享相同的开头 token（"前缀"），提供方就会把第一个请求的 KV 缓存存起来，在第二个请求上复用它。模型跳过重新计算那些 token，只处理新来的东西。

节省是真实的。Anthropic 的实现在缓存的输入 token 上给出了 90% 的成本削减。对于稳定的工作负载，60% 到 85% 的命中率是可实现的。对于拥有稳定系统提示词和工具定义的团队来说，这是今天单个杠杆率最高的优化。

但前缀缓存有一个硬性天花板。

被缓存的部分必须是新请求的精确的、逐字节的前缀。在缓存区域里改任何东西（哪怕一个字符），你都会得到一个完全的缓存未命中。

这在三种常见场景下会崩掉：

三种前缀缓存场景：什么时候有效，什么时候无效

带多个文档的 RAG：你单独缓存了文档 A，也单独缓存了文档 B。一个新的查询需要两者。第二个文档的缓存 KV 状态是无效的，因为它是在不知道第一个文档的情况下计算的。

文档顺序变化：相同的三个文档在不同请求里以不同顺序出现。每种排列都是一个缓存未命中，哪怕文档本身完全一样。

不断增长的对话历史：每一个新回合都会改变前缀之后的完整上下文。超出稳定前缀的早先缓存状态变得没用。

阿里云的生产数据证实了这一限制。10% 的 KV 缓存块服务了 77% 的所有命中。大多数被缓存的内容从未被复用，因为僵化的前缀匹配规则阻止了它。

前缀缓存是一个有意义的优化，但它只在你的上下文有一个长而不变的开头时才有帮助。很多真实世界的工作负载不是这样的。

缓存的性能税

今天的缓存方式还有第二个问题，它影响每一个可用的 KV 缓存工具。

每一个 KV 缓存库都运行在推理引擎的进程内部。这意味着缓存操作（存储、加载、在 GPU 之间搬动 KV 张量）和实际的推理计算共享相同的资源。它们不能同时运行。

当引擎忙着管理缓存时，它就停止做推理。当它在做推理时，缓存操作就得等着。

推理和缓存 I/O 在单一进程内轮流进行

想想这就像一家餐厅，厨师还不得不在每道菜之间跑到储藏室去取食材。烹饪和取货不能同时发生，所以厨房慢了下来，哪怕厨师完全胜任。

影响是可测量的。Google 的 TurboQuant 是近期的一种 KV 缓存量化技术，把缓存压缩到每个值 3 比特，且零精度损失。但当它运行在推理引擎内部时，会造成 20% 以上的推理减速。

压缩工作得完美，但它在和推理同一个进程里运行这个事实，抵消了好处。

缓存管理和推理服务是根本不同的工作负载。一个是 I/O 密集型的（在 GPU、CPU 和存储之间搬动大张量）。另一个是计算密集型的（在 GPU 上做矩阵乘法）。

把两者强行塞进同一个进程，就像在一个线程里同时跑数据库和 Web 服务器。在负载上来之前它能工作，然后所有东西都开始争抢同样的资源。

LMCache 与 disaggregated（解耦）方法

LMCache 是一个开源项目，采取了根本不同的方法。它不把缓存管理跑在推理引擎内部，而是作为一个完全独立的进程，在它旁边运行。

回到餐厅类比，这就像为储藏室雇了一个专门的跑腿。厨师再也不离开厨房。跑腿独立处理所有的取和存。两者都全速工作，互不等待。

传统单进程设计 vs LMCache 的解耦架构

在实践中，LMCache 通过共享 GPU 内存连接到推理引擎。引擎只是告诉 LMCache"我需要这些 block ID"（极小的消息，几乎没有数据）。

所有在 GPU、CPU 和存储之间真正搬动 KV 张量的重活，都发生在 LMCache 自己的进程内部。推理引擎甚至都没注意到这正在发生。

这种分离带来了三个具体的胜利。

无资源争抢：缓存 I/O 永不阻塞推理，推理也永不阻塞缓存 I/O。在引擎内部跑优化技术带来的 20% 吞吐损失消失了。

跨 GPU 的零拷贝共享：在传统设置里，在两个 GPU 之间共享缓存数据需要多次内存拷贝。LMCache 让两个 GPU 直接读写同一块内存区域，完全跳过那些拷贝。

多层并行加载：缓存数据可以分布在 GPU 内存、CPU 内存、本地 SSD 和远程存储上。传统方法逐一检查这些层，卡在最慢的那一层上。LMCache 同时检查所有层，并从任何找到匹配的地方并行地流式传输数据。

四个存储层（GPU 内存、CPU 内存、本地 SSD、云存储），逐层顺序检查 vs LMCache 一次性跨所有层并行查找

性能差异是显著的。在 H200 GPU 上，使用 Qwen3-235B 模型和 50 个并发用户，LMCache 相比进程内缓存带来了 14 倍更快的首 token 延迟和 4 倍更快的解码速度。启动时间从超过 3 分钟降到了大约 30 秒。

而且哪怕在极低的缓存命中率下，经济账也算得过来。一个被缓存的提示每周只需要被复用两到三次（大约 1% 的命中率），系统就能回本。在 1000 节点部署上 10% 的命中率，三年下来节省大约 2900 万美元。

LMCache 与所有主流推理引擎（vLLM、SGLang、TensorRT-LLM）集成，并支持 NVIDIA 和 AMD 的 GPU。

用 CacheBlend 解决前缀问题

LMCache 的架构解决了缓存的性能侧问题。但还记得前面那个前缀缓存的天花板吗。你单独缓存了文档 A 和文档 B，现在有个查询需要两者。第二个文档的缓存是坏的，因为它是在隔离状态下计算的。

LMCache 团队的研究论文 CacheBlend（赢得了 EuroSys 2025 最佳论文奖）直接针对这一限制。

问题归结为一件事。当你独立缓存两个文档时，没有一个"知道"另一个。所以当你把它们的缓存状态缝合在一起时，模型无法联合理解它们。两个文档之间的连接从未被计算过。

但事实证明，在现代 transformer 模型里，大多数 token 主要只关注自己的局部上下文。只有一小部分 token 在文档边界上有强连接。

CacheBlend 利用了这一点，只识别那少数几个 token，并有选择地只重新计算它们。其他一切都原样复用自独立缓存。

前缀缓存重新计算第一个文档之后的所有东西 vs CacheBlend 复用所有被缓存的文档

结果是多文档查询（你在 RAG 应用里见到的那种）快了 2 到 4 倍，且没有任何质量损失。当文档被组合时，不再从头重新计算所有东西，CacheBlend 只以一小部分成本恢复了缺失的跨文档理解。

对于构建 RAG 系统、多文档问答、或从多个来源积累上下文的 Agent 的团队来说，这把知识库里的每一篇文档都变成了可复用的缓存资产，不管它以什么顺序出现，也不管它旁边坐着哪些其他文档。

为生产而构建

LMCache 不是一个研究原型。它自带生产团队所期望的基础设施。

Prometheus 和 OpenTelemetry 集成，用于追踪缓存命中率和 I/O 性能。

用于部署的 Kubernetes operator。

用于调试和基准测试的 CLI。

容错设计值得一提。

如果推理引擎崩溃，LMCache 会在 CPU 和存储上保留所有缓存的数据，所以恢复不会从冷状态开始。

如果 LMCache 自己崩溃，推理引擎进入降级模式，缓存被禁用但推理继续正常进行，并在缓存进程恢复时自动重连。

两种故障都不会把整个系统拖垮。

更大的图景

AI 应用现在每台 GPU 每天大约产生 15 TB 的 KV 缓存，其中大部分被丢弃。管理、存储和复用这些数据的基建正在此刻被搭建。

对于在自托管模型上运行 Agentic 工作负载的实践者来说，KV 缓存管理不是一项未来的优化。它是你今天就在做的成本结构决策，不管你是否意识到了。

LMCache 正处于这股浪潮的最前沿。它是 100% 开源的。
