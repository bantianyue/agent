Flash-MSA：用稀疏注意力 Kernel 加速百万 token 训练

[Github] [MiniMax 论文] [Trainer]

Flash-MSA 与 Flash-Attention 在单个训练步上的对比。

多家前沿模型[1, 2, 3, 4, 5]都使用稀疏注意力来大幅加速推理，但至今没有任何人发布过能高效训练它的代码。今天我发布了世界上第一个高性能的开源训练 kernel：用 CuTeDSL 为 Hopper 和 Blackwell GPU 实现的 MiniMax Sparse Attention（MSA）训练 kernel。我所有的开发工作都是在 Spheron 的 H100 和 B200 租用机上完成的，并参考了 FA4、MSA 推理实现和 Codex。

免责声明：这不是 MiniMax 的官方实现，我也与 MiniMax 没有任何关联。

关于 MSA

MSA 与 DeepSeek 稀疏注意力（DSA）类似，但有几处核心改动。

图 1 来自 MSA 论文。

1. 块状稀疏（Blockwise sparsity）

代理注意力（proxy attention）不再为每个主注意力挑选单独的 KV，而是以 128 为块、通过对代理分数做最大池化来挑选块。这为 kernel 带来一些很好的缓存特性。

2. 主注意力用 GQA 而非 MLA

这一点尤其重要，因为据我所知，没有一家西方实验室在训练中采用过 MLA，这使得像 GLM-5.2、DSv4 这类基于 MLA 的前沿模型所采用的稀疏注意力形式，在这里的模型上无法直接使用。

3. 代理头的分组专门化（Group-wise specialization of proxy heads）

用 GQA 替换 MLA 后，每一层内部出现了相互独立的查询组，让我们可以让每个代理头挑选不同的 KV 子集，而不是像 DSA 那样把整个注意力层求和后再统一打分。有一些证据表明，注意力头会天然地关注不同的 token，因此这一改动应该能提升主注意力的表达能力。

Kernel 设计

kernel 序列的高层概览。

要高效跑 MSA，我们需要尽量少地重复计算，同时不要过度占用寄存器/共享内存。除了常规的 flash 寄存器（Q 分块、KV 分块、O 累加器、LSE 累加器）之外，我们还必须考虑前向中流式（streaming）的 top-k 累加器。在反向中，我们要为「双注意力合并计算」留出空间，这样才能同时算出主注意力的梯度和代理注意力的梯度——因为代理梯度需要同时访问代理注意力概率和主注意力概率。块状稀疏的一个好处是：我们只需要缓存块的索引，而不是像 DSA 那样缓存单独的 token，因此可以把块索引一直存到反向阶段——也就是说，在整个训练步中，只有代理前向相对于上下文长度是二次方的，其余部分都用代理前向前缓存的稀疏块。

前向

操作顺序是：代理注意力 → 稀疏主注意力 → 把主注意力输出送往下一层，并为主注意力保存 LSE 供反向使用。

代理注意力

代理的点积运算与常规 Flash Attn 略有不同：我们不再需要累加输出，但必须在流式扫描 key 的过程中，持续记录 top-k 的注意力分数及其对应索引。与 Flash 不同的是，我也没有为反向累加 LSE，而是在反向时通过一次非常廉价的「在稀疏激活上重算代理点积」来拿到 LSE——在实践中，这比我之前在前向里把 LSE 和 top-k 融合更快。当每一块 QK^T 被算出来时，我会抓取每个 chunk 的因果局部最大分数，并做插入排序，记入每个查询行当前持有的 top-k 值（这些值存在寄存器里）。为了给这些 top-k 寄存器腾出空间，我不得不把 key 块切成两半。此外，MSA 规定每个 token 的局部块必须以滑动窗口方式保持不被掩码，因此我把每个查询对应的局部 KV 块的注意力分数设为 inf。

主注意力

主注意力就是一个块稀疏的 flash attention 前向。这在 MoBA 里已经做过，所以我直接借用了他们那个聪明的技巧：把块稀疏注意力重新参数化为变长（varlen）flash。

反向

要计算代理头的梯度，我们必须把代理注意力和主注意力的反向融合起来，因为代理的训练信号需要同时访问代理注意力概率和主注意力概率。

由于我们从前向保存了块索引，并且只在这些稀疏 KV 激活上训练两种注意力，反向可以以线性时间运行。首先，我们取出缓存的块索引，并把映射 B[batch, proxy head, query, top_k_slot] → [key block] 反转为 B*[batch, proxy head, key block] → [使用该块的查询]。我们用 B* 来调度查询分块，以优化对共享稀疏 KV 块的复用。

然后我们对选中的块快速跑一遍稀疏代理注意力（同样用 MoBA 的 varlen 技巧）拿到代理 LSE，接着流式执行融合的「代理-主」反向任务，加载 QKV、Q_proxy、K_proxy 和 main_lse 的分块。为了容纳这么多要放进寄存器的头，我们不得不缩小每次使用的 Q 分块和 KV 分块的尺寸。在每一个流里，我们先计算主注意力和代理注意力的概率，算出 dQ、dK、dV，再从 KL 训练项算出代理的 dQ、dK。

KL 散度损失

回顾 DSA 原始的 KL 损失项：L_i = Σ_t D_KL(p_t, s_t ‖ softmax(I_t, s_t))。

把索引器注意力和主注意力概率两个分布都实体化、再累加 KL 散度，需要对共享内存做大量读写，并占用额外寄存器，这会显著拖慢训练。好在我们可以用一个技巧来原子化地反向传播，同时在数学上等价于完整的 KL 损失。

主概率 p_t 从代理/KL 损失图中被 detach，因此在这个偏导里是常数。

我们知道 softmax 在位置 t 的输出（p_px,t）对 softmax 前 logit（z_px,i）的偏导是 δ_it − p_px,i（Kronecker delta 函数 δ_it 只在 i==t 时非零，所以 Σ_t p_t δ_it = p_i）。因为 p_t 是概率分布，Σ_t p_t = 1。

换句话说，KL 损失对代理分数的梯度 = 代理概率 − 主概率。这就是我在 kernel 里用来计算代理梯度、却永远不需要完整实体化 KL 的项。

预热 kernel（Warmup kernels）

在预热模式下，主注意力前向是稠密的、不使用块索引，因此代理前向可以完全跳过，我们可以在反向里把它完整地训练出来。对于主注意力的预热前向 kernel，我直接调用 flash 并保存它返回的输出和 lse，再返回一个占位的 KL。在反向里，我对索引器调用稠密 flash 只是为了拿到 LSE，然后复用稀疏 MSA kernel 里那套融合的「代理+主」反向。

正确性（Correctness）

为了验证 kernel 前向和反向的正确性，我用 eager 模式的 PyTorch 实现了 MSA，并在多种配置下扫描两个实现之间前向输出与反向梯度的余弦相似度。扫描在 bf16 精度下进行，反向同时包含目标输出损失和内部的 KL 损失。bf16 下精度的通常容差是 0.01。

接下来要做的（What's next）

提升融合反向的并行度

目前的反向受限于较低的张量核心利用率，以及融合反向因要同时跑两种注意力而带来的沉重寄存器/共享内存需求。例如，在这篇博客的吞吐扫描中，Flash-MSA 反向用了 138 寄存器/线程、105 KB 共享内存/CTA，而 H100/B200 支持的最大值是 255 寄存器/线程和 228 KB 共享内存/CTA，因此我被限制到 1 CTA/SM。为了增加可用 warp，我试过把 Q/KV 切得更窄以达成 2 CTA/SM，但这种做法带来的 CTA 总数增加反而造成了净 slowdown。Flash-MSA 反向的理论占用率是 12.5%，而 Flash-Attention 是 18.75%。

路由架构层面的加速

GLM 已经证明，用 IndexShare 在层间共享代理头既稳定又更快。此外，索引器在推理时似乎总是以低精度提供服务，因此如果在训练中它也用低精度，只要稳定，就能很好地解决「训练-推理不匹配」问题并大幅加速训练。

上下文并行（Context parallelism）

要扩展长上下文下的 LLM 训练，某种形式的 CP 是必须的，否则 trainer 会很快耗尽内存。这里有几个选项。

1. 按头全收集（Headwise all-gather）

为了表述清晰，我把一组注意力头称为「MSA 组」：即分配给每个代理查询头的那部分主注意力查询头。由于 MSA 组在前向/反向里都相互独立运行，用 TP 风格的 CP 折叠（CP rank 最多到代理头数）是轻而易举的——每个设备持有（序列长度 / CP rank）个 token 及其 MSA 组，然后在调用 MSA 前对完整序列做一次 all-to-all 通信。这不需要改动 kernel，事实上，你大概率现在就能在当前的 Megatron MSA fork 里这么做了。

2. 环形（Ring）

在这里实现 Ring 式并行更困难，但大概是 MSA 做 CP 的最优方式，因为它允许更好的 overlap 以及更高的 CP rank。Ring 需要类似这样的设计：在代理前向内做 overlap-exchange，把 top-k 的值和索引跨设备流式传递，再广播回所有设备，然后做一个跨设备的、巧妙的稀疏 key 主机-设备查找与检索，供主注意力使用。我还不知道怎么把它接进 kernel，所以在放出这个核心特性之前得先请教我本地的 CP 专家；不过无论如何，这会是下一篇博客的主题。

关于联合索引器-主注意力训练的说明

虽然论文确实给出了 MSA 的一种形式：给代理头加上 value 和 output 投影，再把代理输出加到主注意力输出上，从而把 CE 损失的梯度引入代理权重、据称能提升知识类评测；但实现它会因为在前向/反向里加入新头和累加器而拖慢训练。MSA 自己在论文的表 6 中也指出，恰当的预热可以弥补「不用人 CE 损失训练索引器」的不足。

关于调度器要求代理头数 ≥ KV 头数的说明

由于我是把每个代理头映射到它对应的主注意力 GQA 组来调度的，当前 kernel 要求 MSA 组 ≥ GQA 组。大概有简单的办法能反转这个映射（用于调度器/融合反向），但这只在模型拥有的 KV 头多于代理头时才需要。不过我预期稳定训练至少需要 4 个 MSA 组，所以要让 KV 头 > 代理头，就得有 >4 个 GQA 组；而在当前这代 transformer 里，我对「每层 KV cache 超过 1024 的模型」深恶痛绝，所以我对实现这条路径毫无兴趣。

跨 Top-k 的扫描（Sweep across Top-k）

我觉得把稀疏的收益随着块减少可视化出来会很有意思。等拿到算力，我还想做更多跨 GQA 和代理 MQA 配置的扫描。我也想用 MSA 继续预训练一个已有的 GQA 基座模型（比如 Qwen3）来测试这种转换，这会需要更多算力。

扫描配置：16 个 Q 头、2 个 KV 头、4 个代理 Q 头、1 个代理 K 头、128 的头维度、B=1、dtype 为 bf16，在 H100 上使用 PyTorch 2.12.0 和 CUDA 13.0，每个序列长度下取 5 个预热步之后 5 个训练步的平均。我没能再在 B200 上跑一轮扫描，但我猜测 FA4 在 B200 上会比在 H100 上快得多，但在长上下文下仍会被 Flash-MSA 拉开差距。
