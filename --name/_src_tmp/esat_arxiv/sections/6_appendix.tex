\label{app:stats-ESAT-AW7}

\subsection{Synthesis Throughput and Yield}
\label{app:appworld-throughput}

\paragraph{Task synthesis throughput.}
\Cref{tab:task_synthesis_stats} reports the number of tasks surviving each stage of the synthesis pipeline. Starting from 29,676 candidate tasks produced by the task generator, the initial judge accepts 14,361 (48.39\%), filtering out roughly 52\% of the generations as ill-formed, unsolvable, or inconsistent with the requested bucket attributes. The rewriting step then successfully reformulates 13,805 of these into concise, intent-level requests, with a small fraction (556 tasks, 1.87\% of the original pool) discarded due to rewriting failures. Finally, the second judge re-validates the rewritten tasks against the original specifications, approving 12,242 tasks (41.25\% of the initial pool). For any rewritten tasks rejected by this second judge, the pipeline falls back to the corresponding initial tasks for trajectory synthesis.

\paragraph{Trajectory generation throughput.}
\Cref{tab:trajectory_stats} reports the yield of the trajectory synthesis stage. Out of 14,361 input tasks, the teacher agent successfully completes 11,445 trajectories (79.70\%), meaning the agent terminates with a final answer regardless of its correctness. The judge then filters these completed trajectories for solution quality, retaining 9,352 trajectories (65.13\% of the input tasks) for supervised fine-tuning. Across all 245,762 simulated API calls issued during generation, only 15,037 (6.12\%) required a retry from the simulator due to schema or semantic validation failures. This low retry rate indicates that the simulator produces well-formed and consistent responses on the first attempt in the majority of cases.

\subsection{Failure Analysis}

\paragraph{Failure type of trajectory generation.}
\Cref{tab:failure_distribution} breaks down the 5,009 discarded trajectories by failure mode. The dominant cause is \emph{simulation failure} (45.38\%). Most of these failures stem from simulator timeouts when an agent issues too many simulated API calls within a single step. The remainder occur when the simulator cannot produce a response that passes both the schema check and the LLM-as-a-judge consistency check within the retry budget. The second largest category is \emph{judge rejection} (41.78\%). These trajectories complete end-to-end but are filtered out by the LLM judge for incorrect or low-quality solutions; this represents the intended quality-control mechanism of the pipeline rather than a pipeline error. \emph{Agent's unexpected App use} (10.72\%) occurs when the agent calls an API outside the expected set derived from the task, prompting early termination. The remaining failures are minor: \emph{agent model execution failures} (2.00\%) are caused by transient errors from the teacher LLM serving stack, such as rate limits or decoding errors, and \emph{max solve steps exceeded} (0.06\%) happens when the agent fails to terminate within the step budget, while three \emph{unexpected} runtime errors (0.06\%) account for the remainder. Overall, judge filtering and simulator-side validation account for roughly 87\% of all discarded trajectories, with agent-side failures contributing only a small tail.

\section{Implementation Details}
\label{sec:app-impl}

\paragraph{Data synthesis.}
For task synthesis (Stage 1), we use GLM-4.7-FP8 as both the task generator and the LLM judge that validates generated tasks. For trajectory synthesis (Stage 2), GLM-5.1-FP8 serves as the teacher agent and the API simulator, and the maximum number of agent steps per trajectory is set to 50 for AppWorld and 30 for OfficeBench. Trajectories that exceed this limit are aborted as described in the trajectory termination rules. For trajectory filtering (Stage 3), we use Gemini-3.1-Pro as the LLM judge.

\paragraph{Training.}
We fine-tune all models with supervised learning on full multi-turn trajectories. Each trajectory is decomposed into individual turns, and the model is trained to predict the tokens of the current turn conditioned on all preceding turns, with the loss masked out over the context tokens. We use the AdamW~\citep{adamw} optimizer with a learning rate of $2\cdot 10^{-5}$, a linear decay schedule, and a warmup ratio of 1\%. Training is performed with a context length of 32{,}768 tokens and a per-device batch size of 1. For models smaller than 14B parameters, training is distributed across 8 H100 GPUs, whereas for models 14B and larger, we utilize 8 B200 GPUs. We leverage the Transformers library~\citep{wolf-etal-2020-transformers} for model implementation and use PyTorch native FSDP2 for distributed training. To improve training efficiency, we apply sequence packing, which concatenates roughly 4 samples into a single sequence on average. We train for 10 epochs by default, except for the Qwen3.5 family, where we observed overfitting beyond 5 epochs and therefore reduce training to 5 epochs. For the first stage of training on synthetic data, we use both the AppWorld train and dev splits for checkpoint selection. For the second stage, which further fine-tunes the model on the AppWorld train split, we keep all hyperparameters identical and select the best checkpoint based on the dev split alone. For OfficeBench, as there is no dedicated development set, we apply the exact same hyperparameters used for AppWorld.

\paragraph{Inference and evaluation.}
For efficient, high-throughput inference, we evaluate all models using vLLM~\citep{kwon2023efficient}. During evaluation, we set the sampling temperature to 1.0. Following the evaluation protocol of AppWorld and OfficeBench, the maximum number of agent steps is capped at 50 for AppWorld and 30 for OfficeBench. For both benchmarks, we generate 8 independent samples per task and report the average pass@1 metric to robustly measure agent performance.

\section{Training with AppWorld Train splits}
\label{app:upsampling}

We investigate the effect of upsampling filtered teacher trajectories on student model performance. Specifically, we use the 90 training tasks from the AppWorld train split and prompt a teacher agent to generate 8 solution trajectories per task. We then filter out trajectories corresponding to incorrect solutions, which results in a variable number of valid trajectories per task (at most 8). To examine whether balancing the per-task contribution matters, we compare two settings: (i) \emph{w/o upsampling}, which directly uses the filtered trajectories as-is, and (ii) \emph{w/ upsampling}, which randomly duplicates the remaining trajectories until each task contributes exactly 8 trajectories. We fine-tune four Qwen variants (Qwen3-4B, Qwen3-8B, Qwen3.5-4B, and Qwen3.5-9B) under both settings and evaluate on the Test-N and Test-C splits.

\Cref{tab:upsampling} reports the results. Overall, upsampling does not yield consistent improvements over the non-upsampled baseline. On Qwen3.5-9B, upsampling slightly improves Test-N accuracy (73.14 vs.\ 71.21) but marginally degrades Test-C (51.89 vs.\ 53.84). For the remaining three models, upsampling underperforms the baseline on both splits, with the largest gap observed on Qwen3.5-4B Test-C (42.39 vs.\ 46.70). These results suggest that naively duplicating trajectories to balance per-task counts does not help and can in fact hurt generalization, likely because duplicated trajectories reduce sample diversity and amplify the influence of tasks with few valid trajectories. We therefore adopt the non-upsampled setting in our subsequent experiments.

\section{Task Synthesis}

\label{sec:task_synthesis}
The goal of task synthesis is to produce a large and diverse pool of natural, multi-step user tasks that can be solved using only the available APIs. The only input to this stage is a set of API specifications, where each specification provides an API's name,
purpose, input-parameter schema, and output-response schema. From these specifications, we generate, judge, and rewrite candidate tasks. We use a single LLM, GLM-4.7-FP8~\citep{glm-4.7}, for all three roles (generator, judge, and rewriter) by varying the prompt.

\subsection{Bucketized generation.}
\label{sec:bucket-gen}
To ensure broad and balanced coverage of the task space, generation is organized into a combinatorial grid of \emph{configuration buckets}. Each bucket is a tuple (\text{difficulty}, \text{action\_type}, \text{task\_focus}, \text{num\_apps}, [\text{min\_apis}, \text{max\_apis}]), where (i) \emph{difficulty} $\in\{\textsc{easy},\textsc{medium},\textsc{hard}\}$ controls the depth of reasoning required (\Cref{tab:taskgen_difficulty}); (ii) \emph{action\_type} $\in\{\textsc{read},\textsc{write},\textsc{mixed}\}$ controls the mix of \texttt{GET} vs.\ \texttt{POST}/\texttt{PATCH}/\texttt{DELETE} calls (\Cref{tab:taskgen_action}); (iii) \emph{task\_focus} (\eg, constraint satisfaction, derivation, iteration, open) controls the high-level reasoning pattern (\Cref{tab:taskgen_focus}); (iv) \emph{num\_apps} $\in\{1,2,3\}$ specifies the number of distinct apps a task must span; and (v) $[\text{min\_apis},\text{max\_apis}]$ specifies the per-app API budget. The per-app API budgets are pinned to match the typical per-app load needed at each app count: for $\text{num\_apps}=1$, we sweep five pinned values $[k,k]$ for $k\in\{2,\dots,6\}$; for $\text{num\_apps}=2$, we use ranges $\{[1,2],[2,3],[3,4]\}$; and for $\text{num\_apps}=3$, we use $\{[1,2],[2,3]\}$. This yields $3\cdot 3\cdot 4\cdot(5+3+2)=360$ buckets in total. Buckets are processed sequentially in a random order, and each bucket targets a fixed number of accepted tasks, $N_{\text{bucket}}$.

For each bucket, the pipeline issues $\lceil N_{\text{bucket}}/n_{\text{per\_call}}\rceil$ parallel calls to the task generator LLM, each asked to produce $n_{\text{per\_call}}$ distinct candidate tasks. For
hard buckets ($\text{difficulty}=\textsc{hard}$, $\text{num\_apps}=3$, or $\text{num\_apps}\cdot\text{min\_apis}>5$), we double the maximum-completion-tokens budget for the generator, judge, and rewriter to accommodate longer outputs.

\subsection{Inverse frequency-based sampling.}
To prevent the generator from collapsing onto a small set of apps and APIs, we maintain running usage counts $c(a)$ and $c(\alpha)$ for every app $a$ and every API $\alpha$ across all tasks generated so far. Coverage is refreshed at the start of each bucket from this
job's own outputs. When constructing a generator call:
\begin{enumerate}[leftmargin=*,topsep=2pt,itemsep=2pt]
\item \textbf{App sampling.} We sample $\text{num\_apps}$ apps without replacement using
$p(a)\propto 1/(1+c(a)),$
which assigns the highest probability to the least-used apps.

\item \textbf{API spotlighting.} For each selected app, we provide the generator with the full set of API specifications for that app, but additionally surface a list of the top-10 APIs ranked by inverse coverage as \emph{focus APIs}. These are listed under a dedicated section of the prompt with instructions to prioritize them, while still leaving the generator free to use any of the provided APIs to satisfy other requirements.

\item \textbf{Prompt assembly.} The selected app/API specification, the focus-API list, the bucket-specific difficulty, action-type, task-focus clauses (\Cref{tab:taskgen_difficulty,tab:taskgen_action,tab:taskgen_focus}), and the per-app API-count range are inserted into the task generation prompt template shown in \Cref{lst:taskgen_prompt}.
\end{enumerate}


\subsection{Task judging.}
Each surviving candidate is then evaluated by an LLM judge that is given the same API specification and the exact requirements section that was shown to the generator (the universal requirements plus the bucket-specific difficulty, action-type, task-focus, coverage, and required-apps clauses. Refer to \Cref{lst:judge_prompt}). The judge is instructed to think through how the task would be solved, since this is necessary for it to assess API coverage, difficulty, and focus compliance, and then output a single yes or no verdict. Tasks receiving a No are excluded from downstream stages.

\subsection{Task rewriting.}
\label{sec:task_rewriting}
Tasks generated directly from API specifications often suffer from \emph{procedural verbosity}: the generator tends to enumerate intermediate steps that any agent would infer on its own (\eg, ``first look up X, then check Y, then if Z\dots''). To convert these into
natural, intent-level user requests, every task that passes the judge is rewritten by a second LLM call. The rewriter is shown (i) the original task, (ii) the same task-requirements block used by the generator and judge, and (iii) only the API specification of the APIs
covered by the task (rather than the full bucket-level pool) so that it stays focused on preserving the original API coverage. To anchor the desired writing style, we append three in-context examples to the prompt body that pair a verbose, procedural original with its
compact, goal-oriented rewrite (\Cref{lst:rewrite_prompt}, \Cref{lst:rewrite_examples}). The rewriter is explicitly instructed to preserve every detail the user actually cares about, while stripping setup phrases and obvious intermediate steps. \Cref{tab:rewrite_examples} shows two representative before-and-after pairs. In both cases, the initial generated task reads as a detailed, multi-sentence walkthrough that explicitly enumerates the steps the agent should take. The rewritten task preserves the same underlying intent, but expresses it as a short, natural user request that omits the procedural scaffolding.

\subsection{Final re-judging.}
Because rewriting can occasionally drop a required entity or change the task's scope, every rewritten task is passed through the judge a second time with the same prompt template. Only tasks that pass both judging rounds are added to the final pool. Tasks
rejected at the final judge stage are recorded with their original generation metadata for diagnostic purposes but excluded from the task pool.

\section{Simulator Details}
\label{app:simulator}
This section provides a detailed description of the LLM-based API simulator used during trajectory synthesis. The simulator is purely text-based: there is no real backend, no database, and no network call. Its job is to take an API call issued by the teacher agent and
produce a JSON response that (i) conforms to the documented response schema, (ii) is internally consistent with all responses returned so far in the same task, and (iii) plausibly reflects the user profile and the current task.


\subsection{Per-Task, Per-App Histories}
\label{app:sim_history}
For each task, the simulator maintains an independent rolling history of accepted (call, response) pairs for each app. Restricting the history to a single app sharply reduces prompt length and prevents irrelevant entities from leaking into one app's simulated state.

When constructing a prompt, the simulator formats the most recent calls in this app's history as ``Call $1$ \dots Call $N$,'' each entry containing the API signature, the input parameters, and the previously simulated response. The history is capped at a
configurable maximum number of calls, but in practice the per-task length stays well below this cap. When a task finishes, its histories are explicitly cleared, so simulator state never leaks between tasks.


\subsection{Deterministic Input Validation}
\label{app:sim_validation}
Inputs of an API call are validated against the API specification using rules that mirror the validation a real backend would apply. If any check fails, the simulator returns an error message \emph{without} calling the LLM. The checks are:
\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=2pt]
\item \textbf{Unknown parameters} not present in the endpoint's parameter list.
\item \textbf{Missing required parameters} for which no default was filled in.
\item \textbf{Type mismatches}, with the same scalar coercions a real backend would perform (\eg, the string ``42'' is accepted for an integer field, but a boolean is not; container types require an exact match).
\item \textbf{Constraint violations}, including length bounds, numeric bounds (with strict and non-strict inequalities), enumerated value sets, and email-format checks.
\end{itemize}
Surfacing these errors deterministically rather than asking the LLM to invent them ensures that the agent always sees the same error message for the same malformed call, which makes downstream filtering and learning more stable.

\subsection{Prompt Construction}
For every call that reaches the LLM, the simulator builds a two-message conversation: a fixed system prompt that lays out the simulator's role, the six categories of context it receives, and the rules it must follow (\Cref{lst:sim_system_prompt}, with the rules block in
\Cref{lst:sim_rules_a,lst:sim_rules_b}); and a per-call user prompt assembled from the template in \Cref{lst:sim_user_prompt}. The user prompt contains, in this order: the fully qualified API name, a JSON dump of the inputs (with defaults filled and the page-limit
cap applied), the full API specification (description, parameters, response schema), the dedicated response-schema block extracted from the specification, which gives the model a clean target for its output, the task description that the teacher agent is currently solving, the per-app interaction history described in \Cref{app:sim_history}; the user profile (first name, last name, email, phone number) drawn from the fictitious supervisor record assigned to this task, and the frozen current date and time. The model is then asked to return raw JSON.

\subsection{Output Schema Validation}
\label{app:sim_schema_check}
Once the LLM's simulated response is received, we first strip any markdown code fences that the model may have emitted in violation of the rules, and then attempt a strict JSON parse. On parse failure, a structured feedback message containing the raw response and the parser error is appended to the conversation (\Cref{app:sim_retry}). After parsing, the JSON value is structurally compared against both (i) the documented success schema and (ii) the canonical error schema $\{\texttt{"message"}: \text{string}\}$. The response is accepted if it conforms to either, since both are legitimate outcomes according to the simulator rules (\Cref{lst:sim_rules_a}). If neither schema matches, both errors are bundled into a structured feedback message, and the loop in \Cref{app:sim_retry} retries.


\subsection{Simulator-judge}
A structurally valid response is still subject to a semantic check, but only for read-only (HTTP \texttt{GET}) APIs. Write APIs (\texttt{POST}, \texttt{PATCH}, \texttt{DELETE}) are accepted as soon as they pass structural validation. This is because their semantic content is typically a simple acknowledgment whose validity is fully captured by the schema, and because gating writes behind a semantic judge would double the LLM cost for state-mutating calls without a proportionate gain in quality. For read APIs, the simulator invokes a separate LLM judge using the system prompt in \Cref{lst:judge_system_prompt} and the user prompt in \Cref{lst:judge_user_prompt}. The judge receives the exact same context as the simulator (specification, inputs, task, history, user profile, and current date/time) alongside the candidate response, and is tasked with returning a JSON verdict containing three fields: a boolean validity flag, a list of issues, and a free-text suggestion block. The judge employs a bounded retry loop to handle any JSON-parsing failures of its own, after which it raises a simulation-failed error.

\subsection{Retry Loop With Structured Feedback}
\label{app:sim_retry}
The structural check and the judge feed into a single retry loop with two independent attempt budgets: a \emph{format} budget for JSON-parse and schema-validation failures, and a \emph{semantic} budget for judge rejections. After any rejection, the conversation is
extended with two messages: an assistant message containing the rejected response verbatim, and a user message containing the structured feedback. For format failures the feedback names the precise error (parse exception, missing keys, type mismatch) and re-states the
two acceptable shapes (success schema or error object). For semantic failures the feedback enumerates the judge's listed issues and reproduces its suggestions verbatim. This in-context conversational format gives the model both a concrete negative example and an actionable hint. We find that it converges within the budget for the vast majority of calls. Once either budget is exhausted, we terminate trajectory synthesis.

\section{Example Agent Trajectories}
\label{app:trajectories}

To illustrate the behavior of our agent in the simulated environment, we present three representative end-to-end trajectories in \Cref{fig:traj-example1,fig:traj-example2,fig:traj-example3}. The examples span varying levels of complexity, ranging from a single-app task ($\langle\mathtt{banking\_app}\rangle$, 15 steps) to a cross-app workflow involving three apps ($\langle\mathtt{expenses\_app}\rangle$, $\langle\mathtt{note\_app}\rangle$, and $\langle\mathtt{action\_item\_list\_app}\rangle$, 25 steps). In each trajectory, the agent discovers relevant APIs through the documentation interface, retrieves credentials from the supervisor app, authenticates, and chains multi-step API calls to fulfill the user's request. All API responses are produced by the LLM-based simulator. For privacy, we mask sensitive virtual user information, including names, email addresses, passwords, access tokens, card numbers, and CVVs, replacing them with \texttt{****} or generic placeholders such as \texttt{user@example.com}. Other fields such as API schemas, product and brand names, monetary amounts, and resource identifiers are kept verbatim to preserve the reasoning context. These examples are synthetic benchmark tasks and do not correspond to real users, real accounts, real credentials, real payment instruments, or real financial transactions.
