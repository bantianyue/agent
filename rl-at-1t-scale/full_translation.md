在这篇博客中，我们将介绍带来这些结果的所有优化，从低精度推理和训练，到 prefill（预填充）和 decode（解码）分离式推理部署。我们将以 zai-org/GLM-5.1 作为我们的模型示例，但我们的优化适用于任何大型混合专家模型，例如 moonshotai/Kimi-K2.7-Code、nvidia/NVIDIA-Nemotron-3-Ultra-550B-A55B-BF16 等。

GLM-5.1 的训练可以在 Slurm 集群上用 prime-rl 通过一条命令运行：

uv run rl @ examples/glm5_llmd/rl.toml --output-dir /shared/outputs/glm5-llmd

从第一性原理出发的智能体 RL

prime-rl 从底层开始构建，以实现高效的智能体后训练，并拥抱异步 RL。智能体任务常常存在长尾离群值；这些 rollout 可能耗时数小时，尤其是长程的编码任务。在等待这些 rollout 完成之前才更新策略，会低利用率地使用 GPU 并损害性能。异步 RL 通过允许在训练器部署上完成优化器步之后立即更新推理策略来解决这个问题。在异步 RL 中，训练器和推理是分离的，可以独立优化。

训练器和推理之间存在一个固有的同步点：策略更新。rollout 策略在每次优化器步进之后用新权重进行更新。在 prime-rl 中，一旦新的权重集可用，我们就立即更新权重。为了不拖慢推理速度，已经分发的 rollout 的活跃前缀缓存不会被重置：这些 rollout 将由各种策略生成的 token 组成，KV 缓存也由多个版本产生。然而，新的 rollout 即使与旧的共享前缀，也会重新填充自己的 KV 缓存；我们使用 KV 缓存盐（salt）来强制这一点。最后，如果请求是由过旧的策略生成的，这些请求会被丢弃；你可以通过 max_off_policy_steps 值来控制这一点。

这些交互从系统优化的角度产生了一个有趣的问题：如何在保持两个系统（训练器和推理）兼容的同时优化它们。

在接下来的章节中，我们将剖析这两个系统以及我们所做的优化。

推理

推理是 RL 训练生命周期的关键部分。正是模型在这里与环境交互，产生 rollout，这些 rollout 被评估并赋予奖励。其中一些功能已经存在于推理框架中；对于其他功能，我们与 vLLM 和 Dynamo 等框架密切合作，目标只有一个：为社区提供经过验证、易于使用的高性能推理配方。

FP8 推理

推理吞吐通常是你的 RL 系统的瓶颈。推理吞吐在 prefill 和 decode 部署上都从更低精度中显著受益。我们大量使用 FP8 推理，结合来自 DeepEP 和 DeepGEMM 的优化内核，以实现更低的延迟和更高的吞吐。

Wide Expert Parallelism（宽专家并行）

在其他关于推理性能的文章中，你可能注意到大量关注点放在最小化延迟上，以实现用户的最高交互性。RL 的情况并非如此：我们的主要焦点是最大化吞吐，同时将延迟保持在某种程度上的有界范围内（稍后详述）。

实现这一点的最佳配置之一是 Wide EP（宽专家并行）：大规模专家并行，通常跨越 ≥32 个 GPU。为了最大化吞吐，我们将此策略与大型数据并行 rank（例如 32）结合，创建一组大型的 GPU 集群，每个 GPU 持有独立的专家，每个都作为一个独立的端点提供服务。同步按层发生，分别在 dispatch（分发）和 combine（合并）操作中。

Prefill 和 Decode 分离

Prefill 吞吐是智能体 rollout 的一个大瓶颈：某些模型↔环境组合产生的 prefill:decode token 比高达 4:1。让相同的推理 worker 同时服务 prefill 和 decode 请求，会增加端到端延迟，显著降低 PipelineRL 的收益。

如前所述，RL 的优先级是最大化推理吞吐，而非最小化延迟。然而，如果延迟因为推理批次被 prefill 请求主导而变得很大，就会观察到已完成的推理 rollout 的"分组"现象，导致训练器和推理步骤的低重叠。

使用 prime-rl，你可以无缝使用 P/D 分离（Prefill/Decode 分离）。当 prefill 和 decode worker 被分开时，长 prefill 请求（冗长的工具输出等）不会节流 decode worker，让它们以可预测的延迟推进。这更快地完成模型轮次，工具调用随后更快地到达沙箱执行，循环重复，有时跨越数百个轮次。

KV 缓存管理

最大化吞吐需要高并发。这反过来需要大量的 KV 缓存空间。如果空间不足，就会发生 KV 缓存抖动和前缀缓存命中率低，从而降低吞吐。prime-rl 紧跟推理框架中的最新功能，提供端到端的支持，其中一个案例就是 KV 缓存卸载（offloading）。

我们支持分层的 KV 缓存卸载到 CPU 和磁盘，同时使用 vLLM 原生卸载和 Mooncake。有了更多的 KV 缓存空间，我们就可以提高并发度，分摊更多的训练器成本。

这两种方法之间有两个主要区别：

vLLM 原生卸载：一种简单的方法，为每个 worker（DP rank）创建一个单一的 CPU/磁盘池；只有这个 worker 才能从该缓存加载。

Mooncake Store 则作为一个集中式存储工作，将来自所有客户端（节点）的 RAM/磁盘汇聚成一个大池，然后可以从任何节点的任何推理 worker 访问：这提供了显著的优势，尤其是在使用更复杂的路由策略时。

请求路由

为了把所有东西串起来，推理请求需要被高效地路由，以实现高效的前缀复用、负载感知路由等。

prime-rl 中的默认路由选项是我们 fork 的 vllm-router，一个极简、轻量的解决方案，以最小的配置开销提供强劲的性能。根据你的需求，你可以选择为负载均衡、KV 缓存复用或其他目标优化的自己的路由策略。

我们也支持 NVIDIA Dynamo router 作为即插即用的替代方案。这让我们能够为更大规模的运行开发和部署更复杂的路由策略。这些策略结合了不同的因素，例如 KV 缓存复用、队列深度、KV 缓存利用率或当前负载，基于推理 worker 的实时指标，为每个 worker 计算一个分数。然后 worker 根据策略和分数被选中。

结合 Mooncake Store（作为集中式 KV 缓存卸载层），这实现了跨副本的前缀缓存命中，同时公平地分配负载并对实时推理指标做出反应。

我们也积极与 vLLM 和 Dynamo 团队合作，持续改进路由解决方案，为推理带来更多性能。

Router Replay（路由器重放）

训练器↔推理的不匹配会悄悄地毁掉你的 RL 训练。为了解决这个问题，你可以使用路由器重放：prime-rl 中的 R3。它的工作原理是捕获推理期间做出的路由决策，然后直接在训练器上重放它们。这有效地将训练器与推理之间的 KL 不匹配降低了一个数量级，带来更稳定的训练。

这并非免费：在大规模部署中，routed-experts（被路由的专家）数据可以达到高达数十 Gbps，给处理带来巨大压力。这给我们带来了很多麻烦，但现在 prime-rl 可以在处理这些数据的同时服务数千个并发的智能体 rollout。

被路由的专家是一个 [num_layers, top_k, seq_len] 形状的大载荷，可以迅速增长到数百 GB，这反过来给 Python 处理带来巨大负载：即使是看似简单的操作，例如将响应转换为 Python 字典，也会造成显著的事件循环延迟和 CPU 瓶颈。为了消除这个开销，prime-rl 将被路由的专家视为不透明载荷，其中唯一的处理由高度优化的 PyTorch 操作处理，从而降低 CPU 压力。

Router Replay 与其他推理优化完全兼容，包括 P/D 分离，让你能够轻松部署生产就绪的堆栈。

训练

我们的训练器基于 torchtitan：一个高性能的、PyTorch 原生的、大规模训练代码库。我们从 torchtitan 改编了大量训练器代码，涵盖 FSDP、EP 和各种其他抽象，同时加入我们自己的调整和改进。

并行

prime-rl 主要依赖 3 维并行，准确地说：FSDP、CP 和 EP。每一个都有自己的用例、好处和缺点。要让大规模运行顺利进行，你需要以不同程度的组合使用它们。对于我们的 GLM-5 案例研究，我们同时使用了全部 3 种。

让我们对它们做一个简短的回顾。

FSDP（全分片数据并行）。这是我们的基线分布策略。参数、梯度和优化器状态在数据并行 rank 之间分片，并在前向和反向传播中按需聚合。对于一个拥有 1T+ 参数的模型，这是摊销完整优化器状态或参数的内存占用所必需的。我们使用 PyTorch 的 fully_shard（FSDP2）作为我们的 FSDP 实现；这允许与其他策略轻松组合，如进一步讨论的。

专家并行（EP）。即使在 FSDP 之后，大型模型层在 FSDP all-gather 之后仍然太大，无法有效放入单 GPU 的 HBM。拥有 78 层、800B 参数以及 float32 主权重，单次层的 all-gather 大约需要 (800B × 4) / 78 ≈ 40GB 的缓冲区。如果 FSDP 重叠 1 层，这仅活动层权重就需要约 80GB 内存。

这就是 EP 的用武之地：我们不是 all-gather 整个层，而是设置一个单独的内部 EP 度，例如 EP=8，专家不会在其中被 gathered。相反，token 将使用 all2all 原语被分发和合并。由于专家是层内存占用的主要贡献者，这显著降低了活动内存。

在 prime-rl 中，我们允许 2 种独立的 EP 配置：torch-native all2all 和 DeepEP。根据我们的观察，torch-native 在单节点 EP 范围（即 EP=8）上提供略好的吞吐，但当 EP 跨节点扩展时会显著下降。这正是使用 DeepEP 变得快得多的地方。

上下文并行（CP）。在 131k+ 的序列长度下，中间激活（而非参数）成为主导的内存成本。上下文并行在 rank 之间对序列维度进行分片，以降低每 GPU 的激活内存。

在 prime-rl 中，我们为所有自定义模型支持上下文并行。我们支持 2 种主要的上下文并行使用方式：

Ring Attention（环形注意力）：批次在整模型前向中按序列分片。当到达核心注意力时，每个 rank 持有其 Q、K、V 的分片，同时以环形模式处理来自其他 rank 的 K 和 V。

Ulysses（尤利西斯）：与环形注意力一样，数据在整模型前向中按序列长度分片。当到达注意力时，all2all 操作将布局从序列分片翻转为头分片，然后注意力在头维度上计算。注意力计算完成后，布局通过另一次 all2all 再次换回。这与大多数非标准注意力（线性注意力、Mamba 等）配合良好，是我们的默认方式。

然而，这有一些例外，其中之一是 GLM-5 中使用的 DSA。

对于无法用 Ulysses 和 Ring Attention 并行的注意力模型，我们编写自定义的上下文并行实现，GLM-5 就是其中之一。

我们的上下文并行实现保持序列分片并计算投影。之后，K 和 V 被聚合：这很便宜，因为它们被投影到一个潜在空间，以允许索引器看到完整序列。索引器计算全局序列的稀疏索引，核心注意力在这些索引上计算。由于 DSA 有固定的 top_k，其成本也是固定的（除了 KV 的内存成本，如前所述可忽略）。

这个方案允许每个注意力层只有一次 all-gather 集合通信，将成本保持在最小。

GLM-5 DSA

为了高效计算 DSA，我们使用自定义内核，大量基于参考实现并适配我们的需求，提供快速的前向和反向。

FP8 训练

如前所述，训练器↔推理不匹配会损害你的训练。为了解决这个问题，我们使用 DeepGEMM 内核执行块缩放 FP8，如 DeepSeek V3 所提出。这与流行观点相反，实际上并没有真正提高吞吐，因为量化开销（除了特定配置）；然而，它显著降低了训练器与推理之间的 KL 不匹配，因为现在两者使用相同的精度，在某些情况下甚至使用相同的内核。这反过来带来更稳定的训练。
