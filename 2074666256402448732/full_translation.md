从第一性原理讲透推测解码

TLDR：推测解码（speculative decoding）能让你在 LLM 工作负载上获得最高 8 倍的加速，而且完全无损，几乎是推理领域的一顿白吃的免费午餐。

前置知识：自回归语言模型与硬件

大语言模型是这样工作的：旧 token 加上 KV 一起送入模型，预测出新的 token 和新的 KV。这个循环反复迭代，不断生成下一个 token。即使在读取用户输入的查询时，这个循环也要跑（只是被预测的下一个 token 会被丢弃）。

token 是模型输出的词，KV 是句子逐步累积起来的知识。

你应该注意到，生成是顺序性的。第 50 个 token 依赖第 49 个，第 49 个又依赖第 48 个，以此类推。这就是为什么你看到 ChatGPT 一个 token 一个 token 地流式输出（自回归），而不是一大块一大块地吐字。

当我们试图优化 LLM 在 GPU 硬件上的运行时，要看 GPU 最基础的两种操作：

计算（compute）：GPU 每秒能做的浮点运算量（FLOP/s）。
内存带宽（memory bandwidth）：GPU 能把多少字节从 HBM 显存加载进 SRAM / SM（真正的计算核心）。

我们可以粗略地把一个任务耗时算成内存时间加计算时间之和。在这个模型里，似乎我们应该同时优化计算量和 GPU 的带宽速度。

T_step = Time_loading + Time_compute

现实中，GPU 是大规模并行处理器。所有操作在加载和计算之间交错进行，所以借助流水线，墙上时钟时间可以近似为较慢那项操作的时间。完成一个操作的实际耗时变成：

T_step = max(∑ bytes_loaded(weights+KV) [memory time], ∑ FLOPs [compute time])

在这个模型里，我们应该专注于减少瓶颈，并确保加载权重的耗时永远不超过计算的耗时（永远不要处于内存受限）。

关键要看的数字叫算术强度（arithmetic intensity）：每加载 1 字节所做计算的量（大致衡量计算受限与内存受限的比例）。

Arithmetic Intensity = amount of work (FLOPs) / amount of bytes loaded

Roofline 分析模型让这一点一目了然：

随着算术强度增加，完成的工作量也增加，直到达到计算受限的点（内存不再是瓶颈）。横轴是算术强度，纵轴是可用的完成工作量。你会看到，随着算术强度提升，我们能做的工作也变多。这是因为在上升区我们是内存受限的，提升每次内存加载能做的计算量会增加总工作量。到了某个点（屋脊点 ridgepoint），我们从内存受限翻转为计算受限。再往后，增加每字节加载能做的计算量也没用了，因为内存带宽不再是瓶颈。

在 A 点，我们需要加载整个文本知识和模型权重，只为生成 1 个新 token，然后重复。所以算术强度极低：

arithmetic intensity = 1 new token / (model weights + KV)

我们的目标是向 B 点（屋脊点）移动，这样就能最优地用满所有可用算力。所以我们的指导性问题/目标是：主要通过提升并行度，来提高算术强度，把传统 LLM 处理从 A 点推向 B 点。

并行方法一：批并行（batch parallel）

两个必须清楚理解的术语：延迟（latency）和吞吐（throughput）。

延迟是每用户 token 之间的时间间隔。延迟越低越好，因为用户更快看到 token。

吞吐是我们每秒产出的 token 总数。吞吐越高越好，因为我们能为更多全局用户产出更多 token。

这两者不总是一同扩展。提升吞吐很可能意味着每用户的延迟变差。例如，提高并发度（叫批大小 batch size）通常意味着每用户的延迟更高（更差），而总吞吐上升。

在到达屋脊点之前，延迟随并发度增加基本持平。一旦计算受限，吞吐就趋于平缓。

这张图展示了批大小与吞吐、延迟的关系。通过增大批大小，我们可以并行化并提高算术强度，如下式：

arithmetic intensity = (B·W + KV·B) / ...

（由于我们把 token 数乘了 B 倍，而除数权重因子保持不变（所有批成员共享权重），我们就提高了算术强度。批大小有助于摊薄把权重从 HBM 加载到 SRAM/SM 的成本。）

在那张批大小对吞吐的图里，你会看到它符合 roofline 模型，因为批大小提高了算术强度。延迟也遵循这个模型（只是反过来，低延迟更好）。在屋脊点左边，延迟温和上升，因为随着批大小增加，KV 内存加载也在增加（尽管增速慢于总计算的上升，因为权重被摊薄了）。在屋脊点右边，我们已是计算受限，增大批大小只是线性地增加要做的工作量。

这也回答了为什么我们不想去 C 点（roofline 图最右端）。去 C 点和去 B 点（屋脊点）在吞吐上一样（我们能产出同样多的 token 数，受限于我们拥有的算力！）。但延迟（每用户的 token/秒）开始显著变差。

还有另一个问题：GPU 在 HBM 的内存容量上有限。如果增大批大小，就需要更多空间存 KV（内存非常贵），最终会耗尽。

所以虽然增大批大小是个该知道的妙招，但它：
不摊薄 KV 加载的成本（因为 KV 是每个序列私有的）
提高了每用户的延迟
由于 HBM 中 KV 内存上限，无法无限扩展

并行方法二：序列并行（sequence parallel）

的确，顺序生成的思维模型在大语言模型中一直被使用。即使下一个 token 已知（比如解析输入提示时），你仍然要做那部分工作（不是为了预测下一个 token，我们已经知道接下来是什么），而是让模型建立内部表征来理解输入（KV）。

Prefill 是并行的，而 decode 是顺序的。

如果你知道接下来是什么，你可以一次性算出接下来几个 token 的概率。例如，如果我一次性传入 5 个 token「Hi my name is shrey」，模型可以完全并行地生成每个词的概率和 KV。LLM 推理的第一部分（读取输入提示）叫 prefill 阶段。它完全可并行化，因为每个输入 token 都已已知，没什么逼迫模型等待。它可以一次性把整个提示塞进去，用这种序列并行来理解它。

生成新 token（decode）才是顺序的。因为我们不知道下一个 token，需要做生成来用预测的 token 重复循环。每一轮的输入是上一轮的输出，所以我们每次前向只能出 1 个 token（低算术强度，内存受限），浪费了闲置的 GPU 资源。

我们来算一下 prefill 的算术强度。它生成 S 个序列 token，并加载该序列的权重 + KV。我们也可以把序列并行和批并行结合，通过输出 S·B 个 token，同时只加载 1 份共享权重和每份批的 KV：

arithmetic intensity = S / (W + KV)，结合批处理：S·B / (W + KV·B)

所以你会看到序列并行不仅摊薄了权重，也摊薄了 KV，因为对每个请求，该请求独有的 KV 在整个序列间共享。而批并行我们只能摊薄权重。

前向 LLM 通过的一个关键组件叫注意力（attention）。这是一个 O(n^2) 操作，每个新 token 都要 attend 到所有之前的 token。所以把 prefill 的并行和这个 O(n^2) 操作结合，会很快让 prefill 变成计算受限。像稀疏注意力这样的技术能减小这个 O(n^2) 分量，但那是另一篇博客了。

Decode 是内存受限，prefill 是计算受限（因为序列并行和注意力）。

批并行和序列并行都爬升 roofline，但批并行只摊薄权重，而序列并行把共享 KV 的加载也摊薄了。

在 decode 阶段借用序列并行：推测解码

Leviathan '23 关于推测解码的原创论文可以在这里找到。

我们知道 prefill 可以并行化，提高算术强度，从内存受限（差）翻转到计算受限（好）。问题是我们怎么在 decode 阶段用上这个 prefill 验证技巧？问题在于 prefill 里我们知道接下来的 token，而 decode 里我们对接下来是什么毫无头绪。

Leviathan 用一个草稿模型（draft model）解决这个问题，并借用了 CPU 推测分支（在知道之前猜一个分支以防止空闲）的思路。思路很简单：在目标（主）模型生成之前，先跑一个微小、快速的草稿模型，自回归地输出 token。我不展开草稿模型怎么训练的，但它就是被训练成尽量模仿主模型。因为它极小，即使生成 5 个 token 也几乎是免费且即时的。把这些当作猜测的「接下来几个 token」，这样我们就能并行验证。

目标模型沿用 prefill 的验证技巧来验证所有草稿 token。在第一次出现分歧的地方，目标模型可以拒绝草稿的答案，保留自己的。验证通过的最后一次输出，是对 n+1 位置 token 的预测。这样，我们称之为 +1 奖励 token（bonus token），因为这次前向总能给我们 1 到 n+1 个正确 token。

草稿器/验证器流程让验证器能纠正错误并给出奖励。

生成的 token 数量增加了，而带宽压力保持不变：

arithmetic intensity = correctly guessed tokens / (W + KV)

这把我们推得离 roofline 上的计算受限更近：

推测通过提高算术强度，把 decode 推向屋脊点。

一个前提：如果我们运行的批大小已经够大，以至于在推测之前就已经计算受限，那么推测带来的额外成本就是直接的负收益。

成本（在内存受限时被忽略，但在已经计算受限时要狠狠付出）：
验证成本：算术强度的增加与生成的 token 数线性成正比。换句话说，即使推测了 3 倍 token，也做了 3 倍的工作。
推测器的成本：在同一个 GPU 上计算的推测本身纯属损失！
推测器的延迟纯粹叠加到总延迟上，因为它跑在实际验证通过之前。

这就是为什么平衡以下各项很重要，因为它们以各种方式相互关联：
推测器的占用（不希望推测器用掉比闲置剩余算力更多的部分！）
接受率 / 推测器的长度（太短或不准，验证成本就开始显现！）
推测器的延迟
只在你内存受限而非计算受限时才跑推测器

草稿模型如何保持与目标模型相同的分布？

验证也是一个巧妙的招数。验证通过拒绝采样（rejection sampling）保证最终输出与目标模型有完全相同的分布。所有自回归模型（目标和草稿器）都把概率分布作为对下一个 token 的预测输出。所以如果你的词表是 [「hi」「hello」「hey」]，一个模型可能输出 [.5, .3, .2]，草稿器可能输出 [.2, .7, .1] 等等。通常 LLM 用温度、top-k、top-p 等规则从这个分布中随机采样。

我们来看推测时怎么玩，p(x) 是目标对 token X 的概率，q(x) 是草稿器对 token X 的概率：

accept x with probability min(1, p(x)/q(x))

情形 1，p(x) > q(x)：草稿器对自己选的特定 token 比目标模型更不自信，我们应该总是接受草稿器。

直觉是：如果我们从草稿器随机采样，选了一个比真实值概率更低的 token，那么即使我们只有目标模型，大概率也会采样到同一个 token，而且相对于目标的真实分布没有过度代表的风险。

情形 2：p(x) < q(x)：草稿器对选出的特定 token 过度自信，我们应该只在 p/q 这个比例接受，其余从残差分布采样。

这种情况下，草稿器把置信度放在了目标模型不会放的地方。这听起来像坏消息，但要知道，即使目标有时也会输出 top 分布之外的 token。所以我们只在 p/q 的比例接受草稿器。

当我们拒绝时（1-p/q），我们从残差分布采样，即目标想要但草稿器给了较低概率质量的那个。

例子：
Vocabulary = ["hi","hello","hey"]
p = [.5, .3, .2]
q = [.2, .7, .1]

草稿选了「hello」，但目标只有 30% 的时间会写「hello」。所以我们以 .3/.7 = .43 的比例接受「hello」。在剩下的 .57 比例里，我们拒绝并从残差采样：

max(p - q, 0) = [.3, 0, .1] → normalize → [.75, 0, .25]

从这个分布采样，很可能得到「hi」。

证明同分布：

提出（q(x)）并接受（min(1, p(x)/q(x))）合在一起的概率如下，可以通过相乘化简：

q(x)·min(1, p(x)/q(x)) = min(q(x), p(x))

某 token 被提出、拒绝、再从残差选出 x 的概率：

(∑x' q(x')(1 - min(1, p(x')/q(x')))) [我们多久拒绝一次] · p_residual(x) [给定一次拒绝，抽到 x 的概率]

把第一项乘开并展开残差的定义：

(∑x' max(q(x') - p(x'), 0)) · max(p(x) - q(x), 0) / ∑x' max(p(x') - q(x'), 0)

这个（超级酷）能消成 max(p(x)-q(x), 0)，因为 p-q 在整个分布上和 q-p 相同（因为 p 和 q 各自求和都为 1）。

选中 token x 的总概率等于「提出并接受」加「拒绝并从残差采样」之和：

min(q(x), p(x)) [重叠 Path 1] + max(p(x) - q(x), 0) [剩余 Path 2] = p(x)

通过尝试两种情形（p<q 或 q<=p）都可以验证：p>=q 时 q + (p-q) = p；p<q 时 p + 0 = p。

用这个很酷的拒绝采样数学，我们数学上保证了被接受的草稿和原始目标输出之间有损无损（lossless）、完全相同的分布。

推测器的演进

我在下面选了几篇我觉得给推测解码带来有趣进展的论文，并分组列出。Leviathan 的原创推测解码验证了推测器这个概念，但下面这些论文训练了不同架构，带来了高得多的加速。

更好的草稿模型

Medusa（Cai '24）：Medusa 发现，用一个完全独立的草稿模型会让草稿器偏离目标模型的策略（off-policy）。它不在最后一层之外训练一个独立的自回归模型，而是在目标模型最后一层（主模型训练完成后）接上几个额外的解码头（heads）。这些头分别预测 N+1、N+2、N+3 等未来 token（每头 1 个）。在编码工作负载上发现推理最高 3.5 倍加速。思路来自 MTP：一种训练技巧，让模型预测多个未来 token，从而迫使模型输出带有长远思考的 token，而不只是下一个统计上最可能的 token。这个模型的弱点是每个头互相独立。预测 N+2 的头不知道 N+1 的预测，这伤害了最大接受率 / 长度。

Eagle 1（Li '24）：Eagle 发现仅仅接在最后一层还不够。关键洞察是「目标模型最懂」（the target knows best）。这意味着目标模型的隐藏状态已经包含很多关于接下来几个 token 的上下文，所以我们应该把模型的这些特征传进草稿器。接受率相比 Medusa 跳升约 5-10%。

DFlash（Chen '26）：随着上面的草稿器越变越好、接受率上升，人们开始增加草稿器生成的 token 数，这增加了实际草稿器的延迟。DFlash 通过把草稿器的架构从自回归换成块扩散（block diffusion）模型来解决这个问题。扩散模型在一次前向中给整块被遮蔽的 token 去噪，导致更长的文本块几乎不增加延迟，带来 6 倍无损加速。一个弱点是扩散模型生成的每个 token 彼此有点独立，所以 Medusa/MTP 同样的问题又出现了。

树状验证

SpecInfer（Miao '23）：在 Leviathan 的草稿模型里，如果草稿在某个 token 上错了，那个点之后的整个样本都得被拒绝。在草稿器对某个 token 五五开不确定的情况下，未来 token 取决于在更早位置是否走运。SpecInfer 说：别猜一条序列，猜一棵树，分出多个续写，全部验证。SpecInfer 创造了「树注意力」（tree attention），一种通过只把分支关联回父系血缘来计算下一个 token 分布、从而并行检查树所有分支的方法。

Eagle 2（Li '24）：Eagle 2 在 Eagle 1 之上加了树状验证。而且它创造动态树：在更自信的分支上走得更深，在更不自信时更宽/更浅。

DDTree（Ringel '26）：DDTree 把树状验证应用到 DFlash 的扩散块草稿器。值得一提的是矩阵采样方法怎么运作。扩散模型输出每个 token 的概率，并通过采样最可能分支直到达到最大预测 token 上限来创建分支。你会看到下面，通过把概率沿图相乘，我们先取最长、概率最高的分支，一旦更短的分支有更高的联合概率就停止深入。

用累积概率产生不同长度的分支

这把某些工作负载的加速推到 7-8 倍，而且即使在和 DFlash 相同的总 token 数下，也有更高的加速（因为能捕获 DFlash 可能错过的更浅路径）。

未来的一些想法

用推测提高吞吐而非延迟：推测通常用于较低的批大小、内存受限时。但对于长程运行的 Agent，在更长的上下文（KV）下，即使大批量也会翻转为内存受限。这是 @togethercompute 一篇有趣的博客，它用推测解码（同一目标和草稿模型，只是通过滑动窗口限制 KV 大小）把吞吐提高了 2 倍。

彻底解耦推测器：我们讨论过的成本之一是推测器本身的代价：它占用内存带宽和计算。随着 @taalas_inc、@Etched 这类芯片越来越偏向专用推理，我好奇能否用一个跑着微小模型、作为 GPU 跑目标模型的边车（sidecar）的专用芯片。

MoE 推测：混合专家（Mixture of Experts）是一种模型架构，每个 token 只激活总参数的一小部分，改变了内存与计算的格局。路由感知的草稿器？

推测器自身用 MoE 做架构：随着目标模型越来越专家化，好奇推测器自己是否变成一个微型 MoE？以保持在策略内。

按工作负载路由到不同推测器：代码、通用文本、数据分析的文本风格非常不同。因为草稿器是个小模型，专门化能提升质量。也许在 prefill 之后路由并调优到特定草稿器（用最后 token 的 KV 上的线性层头来分类？）能改善被接受 token 的长度。

推测器的在线训练以实现零数据保留 + 已有隐藏状态：训练推测器需要有在策略数据（且已经过目标模型跑出隐藏状态和最终正确输出），以及客户允许用这些数据训练。@baseten 发表了很酷的工作，展示你可以在服务目标模型给客户的同时训练推测器，数据从不离开 RAM，也不影响生产延迟。@modal 也在做按客户工作负载的专用推测器。
