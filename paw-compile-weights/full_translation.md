# Program-as-Weights 全文翻译基线（用于覆盖率检查）

## 摘要

许多日常的编程任务难以用干净的规则式实现，例如对重要日志行发出告警、修复格式错误的 JSON、或按意图对搜索结果排序，这些任务正越来越多地外包给大语言模型 API，代价是本地性、可复现性和价格。我们提出模糊函数编程（fuzzy-function programming）：把一个自然语言规格说明编译成一个紧凑的、可在本地执行的神经工件。我们用 Program-as-Weights（PAW）实例化了这个范式，其中一个在 FuzzyBench（我们发布的含 1000 万例的数据集）上训练的 4B 编译器，为一个冻结的轻量解释器生成参数高效适配器。一个 0.6B 的 Qwen3 解释器执行 PAW 程序时，匹配了直接提示 Qwen3-32B 的性能，同时只用了大约五十分之一的推理内存，并在 MacBook M3 上以每秒 30 token 的速度运行。PAW 把基础模型从一个「对每个输入的问题求解器」重新框定为「工具构建器」：每个函数定义只被调用一次，它产生一个小型可复用工件，其后每次函数调用都很便宜且可离线运行。

## 1 引言

编程在历史上一直是关于用一门为这个目的设计的正式语言（编程语言）来编写显式规则。一个函数由代码定义，计算机确定性地执行它。对许多任务来说这个范式运行得很漂亮：给数字排序、处理结构化数据、计算矩阵乘积。然而一大类真实世界的函数抗拒精确规格。考虑一下，比如过滤计算机日志，只在那些重要的日志行或消息上告警，修复格式错误的 JSON，或按意图对搜索结果排序。即便是看起来「简单」的任务，比如写一个正则表达式去解析带有很多边界情况的文本，也证明是脆弱的。除了欠规格化，真实世界的输入是有噪声的：拼写错误和格式漂移经常性地破坏手写规则和正则表达式。这些就是模糊函数（Rubio Manzano, 2012）：人们觉得直观、却无法被清晰的符号规则完全捕捉的问题。

今天，开发者频繁地把这种模糊性外包给 LLM API。在代码库里越来越常见地能找到一个远程 LLM 被调用（例如 gpt('extract answer', text)）来实现那些其他方式难以编程的函数。这种方法毫无疑问很方便，但它很昂贵、脆弱，因为提供方可能静默地更新它们的模型（Kim et al., 2023）而破坏了可复现性，并且阻止了软件成为自包含的。

我们提出了一个不同的范式，包含三个步骤：开发者用自然语言描述这个函数；一个神经编译器把那个描述变成一个小型神经二进制；一个冻结的轻量神经解释器，在用户设备上安装一次，像用户定义函数一样运行那个二进制（图 1）。我们称这个范式为 Program-as-Weights（PAW）。任何足够有表现力的参数高效模块（PEFT），只要是由超网络（hypernetwork）发射出来的，都可以作为程序形式；我们实例化了两种，前缀微调和文本到 LoRA，并发现 LoRA 更好，未来可能还有更好的 PEFT。

图 1：Program-as-Weights 范式概览。顶部：在云端编译一次。一个模糊函数的自然语言描述（这里是「分类这是否紧急」）被喂给一个神经编译器，它产生一个神经程序。底部：本地运行。一个小型冻结神经解释器加载编译好的程序，并运行用户的输入（「请在今天 EOD 前签名！」）来产生输出（「紧急」）。编译好的程序是一个单文件，可以缓存、版本控制，并像其他库函数一样离线调用。

一个 PAW 程序有两部分。第一部分是自然语言写的伪程序，是对用户规格说明的重述。第二部分是一个 PEFT 模块，它为这一个任务重新调优冻结的解释器：在我们的前驱系统中，这是一个前缀微调的 KV 缓存；在我们当前的系统中，这是一个由编译器从它自己的隐藏状态生成并注入解释器的 LoRA。离散的那一半保护解释器免受原始规格说明中的拼写错误和歧义影响；连续的那一半提供文本单独无法给出的细粒度行为控制。

编译流水线有两个阶段，都运行 4B 的 Qwen3 模型。第一个阶段是伪编译器，一个我们从不训练的现成模型：用一个小的任务重写模板提示，它把用户的规格说明变成一个干净的伪程序，包含转述的描述加上少量输入-输出例子。第二个阶段是我们训练的 LoRA 编译器：它读取规格说明和伪程序，发射 LoRA。我们在 FuzzyBench 上训练 LoRA 编译器，那是我们随本文发布的含 1000 万例的数据集，它跨 29 个主题版本增量构建，覆盖了 800 多个模糊文本任务类别，比如分类、格式转换、解析、模糊匹配、自然语言命令、智能体工具使用等等。

结果是一个小型、快速且准确的系统。一个执行 PAW 程序的 Qwen3-0.6B 解释器，在大约五十分之一推理内存的情况下，超越了直接提示 Qwen3-32B（73.78% 对 68.70% 精确匹配）。量化之后，同样的系统在 MacBook M3 上以每秒 30 token 运行，基础为跨函数共享的约 430MB GGUF，加上每个程序 23MB 的 LoRA 适配器；一个更小的 GPT-2 路径通过 WebAssembly 完全在浏览器客户端运行。

我们把 Program-as-Weights 看作迈向小模型未来（Belcak et al., 2025）的具体一步，在那个未来里，繁重的活儿在编译时做一次，而运行软件的日常工作发生在本地。我们用五个案例研究说明它的应用：输出分诊（事件驱动的日志监控）、自定义分类（基于意图的站点导航）、模糊搜索（语义搜索重排序）、智能体预处理（一个在 ToolCall-15 上拿到 93% 分的工具调用流水线），以及创意生成（一个多语言猜词游戏）。每一个都是那种抗拒符号实现、却不需要对每个输入都调用一个 30B 参数模型 API 的模糊任务。我们额外展示了这个抽象模态的通用性：只把编译器替换为一个视觉-语言模型、同时保持同一个解释器，就能在图像条件的模糊任务上运行 PAW 程序。我们的代码在 https://github.com/programasweights，公开 demo 在 https://programasweights.com。

## 2 程序即权重

令 f: X → Y 表示一个其行为更自然地通过自然语言、例子或约束来规格说明、而非通过符号代码来规格说明的函数，一个模糊函数。与其反复调用一个 LLM 去近似 f，我们提议编译一个神经程序，它专门化一个固定模型来实现 f。

形式化地，令 s 表示用户规格说明，用自然语言表达，可选地配有输入-输出对 (x, y)。一个神经编译器把 s 映射到一个程序 p。一个小型固定神经解释器在输入 x∈X 上执行 p 来产生输出 ŷ∈Y：p = Compiler(s)，ŷ = Interpreter(p, x) ≈ f(x)。

这种分工镜像经典编程，那里一个编译器把源代码翻译成一个稍后由运行时运行的可执行文件。关键的不同在于这里的可执行文件是一个被学习的参数块，而运行时是一个神经网络。解释器不需要被重新训练：引入一个新的模糊函数只需要编译一个新的程序 p。

混合程序。为概念简单，p 可以被看作一个单一的连续对象。但在我们具体的实例化中，p 是离散和连续两部分的一个混合：p = (p_discrete, p_continuous)。离散部分 p_discrete 是一个变长 token 序列，作为自包含的「伪程序」呈现给解释器作为它输入的一部分。连续部分 p_continuous 可以用任何 PEFT 方法实现，比如注入解释器的 LoRA。

为什么叫「程序」？这个框架很重要，因为它决定了工件如何使用。一个编译好的 PAW 程序是一个单文件（对于 0.6B 解释器，在 Q4_0 下约 23MB，加上一次性的共享基础），它可以被保存、版本控制、通过包管理器分发，并可以用两行 API 从 Python 或 JavaScript 调用。PAW 程序与 Python 模块是同一类对象：它们有一个名字和一个版本，但它们的行为编码在权重里而不是源代码里。编译器是做繁重活儿的部分；解释器是一个固定的运行时，可比于传统软件栈里的 CPU 或字节码解释器。

## 3 编译器-解释器系统

### 3.1 编译器-解释器抽象

PAW 流水线有三个组件，没有一个依赖于程序形式所选的具体 PEFT。一个伪编译器 C_p 读取规格说明 s 并产生离散伪程序 p_discrete。一个 PEFT 编译器 C_PEFT 读取规格说明连同 p_discrete，并从它的隐藏状态发射一个小的参数高效模块 p_continuous。冻结的解释器在运行时摄取 p_continuous——通过把它附着到合适的目标模块上并让用户的输入 x 通过它——来产生输出 ŷ。我们用两种方式实例化 PEFT 模块：前缀微调 KV 缓存（第 3.3 节）和 LoRA（第 3.2 节），后者是我们当前最好的。

伪编译器。伪编译器 C_p 是一个我们从不训练的现成 Qwen3-4B-Instruct-2507 模型。给定一个规格说明 s，我们用一个小的任务重写模板提示 C_p（完整文本见附录 C），要求给出任务的干净重述加上少量代表性的输入-输出例子。输出就是程序的离散部分 p_discrete。

### 3.2 文本到 LoRA：我们当前最好的

LoRA 编译器。LoRA 编译器 C_L 是第二个 4B Qwen3 模型，从与 C_p 相同的检查点初始化，但被训练（第 4 节）。给定规格说明 s 和由 C_p 产生的伪程序 p_discrete，C_L 在拼接 [s | p_discrete | EOS | τ_1, …, τ_T] 上跑一次前向传播，其中 τ_1:T 是一个固定序列的 T=64 个学习的「前缀」token。我们从 C_L 编译器层中按深度比例均匀间隔地提取前缀位置的隐藏状态，并把它们堆叠进张量 H∈ℝ^{L×T×d_teacher}，喂给 LoRA 映射器（图 2）。

LoRA 映射器。LoRA 编译器的隐藏状态 H 被一个小的参数高效模块（LoRA 映射器）转换成每个例子的 LoRA 权重。对每个解释器目标模块类型 m（注意力 q/k/v/o 和 MLP gate/up/down），映射器维护共享的可学习基 A_1:N^(m) 和 B_1:N^(m)。这些隐藏状态在 L 个深度对齐的层和 T 个前缀位置上做均值池化，通过一个浅层 MLP 主干，并通过一个线性头投影成每个层 l、模块类型 m、基索引 n 的混合系数。层 l 和模块 m 上的 LoRA 是这些基的加权和。我们用秩 r=64 和每个模块类型 N=64 个共享基，应用到所有层和模块类型。每个模糊函数，这向解释器注入约 38.5M 个 LoRA 参数。

解释器。解释器是一个冻结的语言模型。为了在输入 x 上执行一个 PAW 程序，我们（i）把式 3 的 LoRA 附着到合适的目标模块上，（ii）把 p_discrete 前置到输入 x 上，以及（iii）自回归地生成输出。因为解释器是冻结的而 LoRA 可热插拔，一个设备驻留的解释器可以服务无限多个 PAW 程序。

### 3.3 前缀微调：一个前驱实例化

我们的前驱系统用前缀微调映射器替换了 LoRA 映射器。前缀编译器 C_P 是第二个 4B Qwen3 模型，以与 C_L 相同的方式训练，唯一的不同在于它的前缀位置隐藏状态如何被消费。给定 [s | p_discrete | EOS | τ_1:T]，C_P 在与第 3.2 节相同的 L 个深度对齐层产生隐藏状态 H，一个小的线性映射器 ψ 把这些隐藏状态按位置投影成 KV 对，被前置到解释器每一层的注意力 KV 缓存中，就像标准前缀微调那样。

两种方法都解决了任务。在受控比较规模（相同训练算力）下，前缀微调实例化在 FuzzyBench 上达到 50.4% 精确匹配，而 LoRA 实例化在 r=18 达到 56.5%（r=18 匹配前缀微调的程序大小）和在 r=64 达到 65.7%（表 1）。两者都超过了无编译器提示基线（9.8%）。LoRA 是更强的 PEFT，也是我们后续实验扩展到全量训练数据所用的实例化。

表 1：两种 PEFT 实例化。两种方法都超过了提示基线。

| 方法 | 准确率 |
|------|--------|
| Prompting | 0.098 |
| Prefix Tuning | 0.504 |
| Text-to-LoRA, r=18 | 0.565 |
| Text-to-LoRA, r=64（默认） | 0.657 |

## 4 训练

只有 PEFT 编译器被训练。伪编译器 C_p 保持现成并冻结；解释器也是冻结的。PEFT 编译器被训练来产生一个 PEFT 适配器，当它和一个固定的伪程序一起注入冻结解释器时，最大化目标输出的似然。两个端点都冻结，这简化成一个单一的监督目标。

目标。对每个训练三元组 (s, x, y)，我们查一个预生成的伪程序 p_discrete = C_p(s)，通过 C_L 在 [s | p_discrete | EOS | τ_1:T] 上跑一次前向传播来获得前缀位置隐藏状态，把它们通过 LoRA 映射器来获得 p_LoRA，并把结果注入解释器。损失是在冻结解释器下目标 y 的负平均 token 对数似然。梯度通过冻结解释器回流到 LoRA 映射器，再从那里进入 C_L 的隐藏状态。

## 5 FuzzyBench：一个含 1000 万例的模糊函数数据集

训练 PAW 风格方法的一个中心障碍是缺乏一个「从规格说明编译模糊函数」的公开数据集。我们构建了 FuzzyBench，一个含 1000 万例的数据集，其中每个例子是一个三元组 (s, x, y)（规格说明、输入、目标输出），用 gpt-5.2 生成。

构建。我们用一个两阶段流水线。第一阶段，我们提示 gpt-5.2 生成模糊函数的自然语言规格说明。每次提示调用产生八个规格说明，我们在不同类别约束下重复调用以覆盖开发者实际遇到的模糊任务广度。第二阶段，对每个规格说明，我们再次提示 gpt-5.2 生成八个输入/输出对。规格说明按规格以 80/10/10 分成训练/验证/测试，所以测试规格在训练时是完全没见过的。为了评估，我们构建了一个验证过的测试集，在一个独立强模型（gpt-5-mini）和 gpt-5.2 对输出达成一致的地方，移除掉目标本身有歧义的例子。

主题覆盖。FuzzyBench 跨 29 个版本增量构建，每个版本增加 10 万到 50 万例子，覆盖一个新的模糊任务家族。图 3 把产生的 1000 万例子归并为七个高层任务家族，跨越开发者在模糊逻辑中实际遇到的任务：从原始文本处理和解析到智能体工具使用、网络智能、代码与命令生成，以及安全/验证。

噪声变体。为了鲁棒性评估，我们额外发布了沿八个轴的噪声扰动测试集版本：拼写错误、语法错误、歧义、格式漂移、「所有噪声」（组合）、简洁措辞、随意措辞和改写。每个轴有三个强度级别（轻、中、重）。

经验上限。数据生成模型本身 gpt-5.2 达到 96.09%；gpt-5-mini 达到 91.87%。这约束了任何在这个数据上训练的编译函数能达到的高度。

## 6 主要结果

我们比较 PAW 与三族基线，都在与 PAW 相同的测试集上评估。

基线。（i）开放权重 LM 的直接提示（Qwen3 0.6B、4B、8B、14B、32B；OLMo3-7B；gpt-oss-20B），以及两个标定经验上限的 API 模型（gpt-5-mini 和 gpt-5.2）。（ii）符号代码生成：ALCHEmist 的 LM-to-code 流水线（Huang et al., 2024b），其中强 LM 写 Python 代码来解决模糊任务，代码在推理时执行。（iii）同一个 0.6B 基础的标准适配：全微调 1-4 个 epoch，以及固定（非编译器生成的）秩为 r∈{18,64,128} 的 LoRA。

主要结果。表 2 总结了主要数字。一个执行 PAW 程序的 0.6B 参数解释器在 FuzzyBench 上达到 73.78% 精确匹配，超越了提示 Qwen3-32B（68.70%），同时用了大约 50 倍更少的推理内存（约 1.2GB 在 bf16 下对约 60GB）。

表 2（摘要）：PAW (Qwen3 0.6B) 在 FuzzyBench 上 73.78%，在 YouTube 上 90.40%，在 SMS 上 80.77%，在 Yelp 上 95.82%，在 IMDB 上 90.64%，每个程序约 23MB。

跨解释器缩放。在三个解释器 GPT-2 124M、Qwen3 0.6B 和 Qwen3.5 0.8B 之间，Qwen3 0.6B 是最强的解释器；混合的 0.8B 稍弱。GPT-2 124M 尽管只有 Qwen3 0.6B 五分之一的参数且没有指令微调，仍达到 54%，说明编译器生成的 LoRA 甚至能编码进很小、能力很弱的基础模型中有用的任务适配。

不改动解释器的多模态泛化。编译器-解释器抽象扩展到图像条件的模糊函数而不改动解释器。我们把纯文本的 Qwen3-4B-Instruct 编译器换成同家族的 Qwen3-VL-4B 编译器，保持相同的 Qwen3 0.6B 解释器，并复用相同的 LoRA 映射器。图像条件完全编码在 VL 编译器发射的 PEFT 模块里，所以小型文本解释器从来看不到像素。表 3 报告了六个图像条件任务。PAW (LoRA) 在三个 CoSyn 图表理解任务上都超过了所有至多 4B 参数的 VLM 基线。

## 7 消融

LoRA 映射器的架构变体。我们试了几个在纸上严格比默认更富表现力的 LoRA 映射器变体，每个都让事情变糟。表 5 报告了这些变体的准确率。把前缀 token 隐藏状态均值池化成一个向量、跑一个残差 MLP、投影到共享基集上的混合系数，这个最简单的设计是最强的。我们没有对此干净的理论解释；我们报告这个发现以便未来工作不必重新发现它。

编译器 vs. 无编译器。表 5 比较了 PAW 与三个同基础「无编译器」基线在 FuzzyBench 上：对 0.6B Qwen3 解释器的全微调，以及三个秩的固定每任务 LoRA。相同的数据、相同的基础模型、相同的训练预算；只去掉了编译器。PAW 超过全微调 15.4 个百分点，超过最强的固定 LoRA 21.7 个百分点，说明增益特别来自编译器生成的 LoRA。

## 8 对噪声规格说明的鲁棒性

开发者写的实际规格说明是有噪声的：包含拼写错误、歧义和语法错误。我们在七个轴上评估 PAW 在噪声扰动测试集上的表现。PAW 在重度噪声下只轻微退化。我们假设这个鲁棒性是由离散伪程序中介的：4B 编译器在小型解释器看到之前把噪声规格说明转换成一个干净的重述。为了测试假设，我们训练了一个绕过伪程序、把原始规格说明 s 直接喂给解释器的变体。结果确认了假设。在干净输入上，喂伪程序而非原始规格说明只好了 1.6 个点。然而在重度拼写错误规格说明上，差距扩大到 4.5 个点。

## 9 本地执行

超越基准，为了让 PAW 实用，我们建了一个开发者接口。一个 PAW 程序是一个单文件，可以被下载、缓存，并通过一个小的 Python 或 JavaScript API 调用。图 4 给出了一个完整的极简 Python 例子。量化而没有可测量的准确率损失。设备端执行需要一个小的足迹。我们把共享解释器基础和每个程序 LoRA 适配器都量化成与 llama.cpp 兼容的 GGUF 格式。表 8 报告了我们的量化发现：一个 4-bit 基础（约 484MB）加上一个 Q4_0 LoRA 适配器（每个程序约 23MB）相对 bf16 只损失 1.3 个点，而一个 Q6_K 基础加上 Q4_0 适配器在噪声内与 bf16 统计上不可区分。

MacBook M3 上的延迟。在带 Metal 加速的 MacBook M3 上，Q5_K_M 基础加上 Q4_0 适配器以每秒 31.6 token 运行，冷加载 0.48 秒。

案例研究。我们把 PAW 应用到五个用例。事件驱动的日志监控把 Cursor 里幼稚的基于等待的终端监视替换成一个只在重要的行上触发的本地分类器。基于意图的站点导航为一个网站提供一个自然语言快查，而没有每个请求一个 LLM API 调用。语义搜索重排序给一个已有的关键词索引加上意图感知的模糊搜索，同样不在请求路径里放一个 LLM。对于工具调用，一个 10 个 PAW 函数的流水线在 ToolCall-15 上拿到 93% 分。多语言猜词游戏（Alien-Taboo）是一个模糊交互游戏，每个玩家回合由一个小型服务器上的 0.6B PAW 解释器服务，每种语言一个 PAW 程序；LLM 只在编译时调用，这正是这类游戏能够经济地托管的原因。

## 11 结论

我们引入了 Program-as-Weights，一个编程范式，其中一个模糊函数被编译一次成一个小型神经二进制，并在一个固定解释器上本地执行。在 FuzzyBench 上，一个执行 PAW 程序的 0.6B 参数解释器匹配了 Qwen3-32B 提示，在大约 50 倍更少的推理内存下，并以每秒 30 token 在量化 GGUF 的 MacBook M3 上运行；我们通过五个案例研究说明了这个范式。同样的抽象通过只把编译器换成视觉-语言模型，扩展到图像条件的模糊任务。我们希望 Program-as-Weights 贡献于一个未来，其中小 LM 充当运行时（Belcak et al., 2025），在那里大模型编译、小模型执行，而基础模型的角色从对每个输入的问题求解器转移到对每个函数的工具构建器。
