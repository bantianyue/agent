引言

前沿LLM（大语言模型）的进展使Agentic（智能体原生）工作流变得实用并被广泛采用（Guo et al., 2025; OpenAI et al., 2024; Jimenez et al., 2024）。Agentic（智能体原生）模型不再产出单段文本答案，而是与执行环境交互：可以浏览代码库、调用工具、执行命令、检查失败、修改文件，或在computer-use任务中通过图形界面操作浏览器和桌面应用（Xie et al., 2024; Zhou et al., 2024）。在这些工作负载中，模型基于反馈迭代直至任务解决。这种执行模式催生了不断壮大的Agent工具与编排harness生态，例如DeepSeek Harness (DSH)（Shi et al., 2026）、OpenCode（Anomaly, 2025）以及多Agent训练harness。训练可靠的Agent需要大规模强化学习（RL），模型通过与真实、隔离的执行环境交互来学习，而非仅依赖静态的输入输出样本。

Agentic训练流水线涵盖环境与数据构建、RL rollout、奖励计算、策略更新以及周期性评估。其中，RL rollout与评估对沙箱平台的压力最大：规模大、并发高，且与训练循环紧密耦合。在RL中（Ouyang et al., 2022; Guo et al., 2025），训练以三阶段的反馈循环推进。第一，rollout阶段，当前模型与沙箱化环境交互：读取文件、发起工具调用、执行命令、观察输出，并为每个任务生成一条trajectory。第二，奖励计算阶段，框架使用原生执行信号对trajectory打分，例如退出码、stdout、测试通过率或任务专用验证器。第三，策略更新阶段，RL算法根据收集到的trajectory与奖励更新模型参数。周期性评估走相似的执行路径，区别在于产生的trajectory用于衡量模型能力，而非更新参数。近期系统进一步通过异步rollout将生成与策略优化流水线化，持续补充完成的样本以维持高并发并缓解长尾拖尾（DeepSeek-AI, 2026）。对Agentic工作负载而言，这种设计使大量有状态沙箱会话同时在运行，并可能在策略更新或调度器抢占时中断并恢复其关联的rollout，进一步提升平台在并发、生命周期管理与状态一致性方面的要求。

对于每个rollout或评估任务，平台必须实例化一个隔离的任务专用环境，包括其仓库、依赖、服务、评估脚本与编码harness。环境必须足够接近真实机器，以运行未经修改的软件栈、包管理器、构建工具、浏览器、模拟器以及任务专用服务。因此，健壮、高吞吐的沙箱运行时是获得准确且可验证的RL与评估结果的基础。

Agentic沙箱负载的共性特征

Agentic沙箱工作负载具有若干影响平台设计的特性：

Rollout与评估任务以突发方式创建沙箱。单个任务最多可请求32K个沙箱实例，平台必须并发接受并放置大量沙箱。这种突发使水平可扩展性成为系统级要求，并要求调度、镜像分发等共享服务避免集中式瓶颈。

沙箱必须以高密度运行。在Agent交互期间，沙箱常等待LLM（大语言模型）生成下一个动作，CPU使用稀疏，天然适合超分。例如在生产中，这允许单节点承载最多800个microVM或3,200个容器，但前提是平台能在节点规模上安全超分资源并管理生命周期压力。

Agent沙箱是有状态且长生命周期的。模型可能修改文件、安装依赖、启动服务，后续工具调用依赖这些累积状态。由于沙箱可在多轮LLM交互中持续存活，内存占用、guest page cache、host page cache与可写状态可能在CPU空闲后仍长期驻留。在高密度超分下，这些常驻开销直接限制集群容量，因此内存共享与回收成为重要的平台要求。

Agent工作负载高度异构。平台必须覆盖类OJ的脚本执行、面向完整仓库的软件工程任务、安全任务、computer-use工作负载、移动开发环境（如Android）以及其他全系统环境。这些工作负载在CPU与内存需求、依赖规模、所需系统功能与隔离强度上差异显著。单一沙箱抽象无法高效覆盖全部。例如，短时无状态任务更适合轻量函数调用，而需要完整商用现成操作系统的负载则更适合虚拟机（VM）。

即使在同一工作负载类别内，环境多样性也很高。训练与评估语料包含大量任务，每个任务可能需要各自的仓库、依赖版本、服务、工具链、评估脚本或VM快照。因此平台必须服务大量互不相同的镜像与环境产物，其中许多复用有限。在突发启动下，从registry拉取这些多样化的任务镜像会使负载集中于分发路径，抬高启动延迟，并引入额外I/O干扰已在运行的沙箱。消融实验中，预先拉取镜像使完成时间拉长1.7×，而按需加载将累计磁盘写入降低57%。

Agent（智能体）执行不可信。 Agent（智能体）可能破坏文件系统、耗尽资源或干扰系统组件，进而扰乱rollout或其他同节点工作负载。因此平台需要细粒度访问控制与异常行为分析，以约束并诊断Agent（智能体）引发的故障。

Agent（智能体）执行可中断。 GPU训练任务可能被抢占，而长时间运行的rollout仍在进行。因此平台必须保存执行状态，并支持跨中断的高效恢复。

SDK入口点

用户通过libdsec访问DSec，这是沙箱服务的Python客户端库。libdsec为用户提供创建和操作沙箱的统一SDK入口点，但仍要求用户选择适合任务的沙箱后端。典型请求指定沙箱类型、镜像或环境标识符、CPU和内存限制、生命周期设置、网络规则和初始用户上下文。创建后，用户可执行shell命令或工具调用，并收集命令输出和返回状态。下面的代码示例展示一个最小容器会话：客户端连接服务端点，请求具有所需资源和网络策略的沙箱，运行命令，然后释放。

client = DSecClient()
await client.open()
args = DSecContainerRunArgs(
    container_image="registry.../sphinx-9658:official",
    memory_limit_mb=4096, cpu_cores_limit=4,
    ttl_running_stop=300,      # idle timeout
    network_rules={"npm": False, "pypi": True},

)
sandbox = await client.run_container(args, timeout=120)
result = await sandbox.run_shell("echo hello world")
await sandbox.stop()

此示例中，网络规则允许访问PyPI（pypi=True），但拒绝访问NPM（npm=False）。细粒度网络控制详见6.5节。该接口有意不设计为对所有后端的完整语义抽象。函数调用、容器、microVM和完整虚拟机具有不同的启动开销、隔离边界、文件系统语义和操作系统能力。libdsec提供统一的访问路径和相似的操作模型，但调用方仍负责选择与工作负载匹配的后端。

用户可见生命周期

尽管各后端内部实现不同，用户看到的是统一的高层生命周期。第一，调用方创建沙箱：选择后端并指定环境产物、资源上限、生命周期策略与网络策略。环境产物因后端与工作负载而异。对容器与microVM，环境产物是基础镜像连同任务专属的workspace与toolkit层，由平台组合为运行环境。对完整虚拟机工作负载，环境产物是预先准备好的VM镜像或快照。对FnCall，环境产物是包含任务类型、依赖文件与待运行代码或脚本的任务描述。这些产物是后文环境组合与镜像分发机制的基础。第二，平台准备环境并使其可交互。第三，用户下发命令或工具调用，观察输出，并运行任务专属的检查或测试。沙箱在整个生命周期内保持有状态：文件修改、已安装依赖与已启动服务跨调用持续存在，后续命令可观察到先前命令的效果。由于沙箱在多轮交互中持续存活，而CPU在轮次之间常常空闲，其常驻状态在最后一条命令之后很久仍被占用，这是高密度挑战之一。最后，沙箱被显式停止，或在time-to-live到期后回收，避免空闲或被弃置的会话无限期占用资源。

部署规模

DSec部署在多个规模单元上，这些单元共享一套3FS（DeepSeek-AI,）分布式文件系统部署，用于基础镜像与工作区存储。单个规模单元内，平台覆盖近160个CPU节点，共30K核与约250 TB DRAM，管理PB级的层与镜像。典型单日，单个规模单元服务约3 M个沙箱实例，峰值并发约380K，创建速率超过每秒5,000个实例。

这些数字对理解后文至关重要。DSec不是单一沙箱运行时，也不是容器的薄封装，而是生产级执行平台，需同时具备面向用户的沙箱抽象、后端专属运行时、可扩展镜像存储、高密度资源管理与训练框架集成。

平台架构

用户视角的DSec包含SDK、一组沙箱后端与会话生命周期。本章转向该接口背后的平台，描述请求如何从SDK到达运行中的沙箱，以及途经哪些组件。架构按集群级服务与沙箱运行时两部分描述。集群级服务提供请求入口、身份与访问管理、沙箱放置，以及集群健康与负载视图。沙箱运行时负责节点本地的准入、沙箱创建、执行与资源回收，镜像数据依赖3FS。

概览

高层流程上，沙箱创建请求首先发送至IAM进行身份认证与授权。授权通过后，请求进入placement engine，后者依据watcher采集的健康与负载信息选择目标节点。放置完成后，apiserver将请求转发至该节点上的edge。edge随后检查本地容量，容量允许则以所请求的后端创建沙箱，否则拒绝请求。沙箱所需的镜像数据存放于3FS，在启动与执行期间按需拉取。容器、microVM与完整虚拟机沙箱运行每沙箱一个代理（aether）以及一个或多个chronus实例，用于命令执行、文件系统访问及其他运行时操作。此类沙箱运行后，其操作经apiserver、edge、aether与chronus路由。相比之下，FnCall既不使用aether也不使用chronus，走独立请求路径：提交的任务直接在预创建容器中执行，随后对任务状态做尽力而为的清理。

集群级服务

集群级服务管理平台访问，并跨计算节点协调沙箱请求。包括IAM、apiserver、placement engine与watcher。

IAM。Identity and Access Management（IAM）对调用方做身份认证，并对发往DSec的所有管理请求做鉴权。例如，创建或删除沙箱、修改用户资源或并发上限的请求，执行前必须通过IAM检查。principal是与管理请求关联的用户或服务身份。IAM用project定义资源管理与访问控制的范围。project内，access policy规定哪些principal可对其资源执行哪些管理操作，resource quota限制资源消耗。

支持多级project嵌套，而非云平台常见的扁平或两级层级。被授权的principal（包括Agent（智能体）与harness）可创建子project、委派父配额的一部分，并在其中授予管理权限。委派受父级约束：principal不能授予自己不持有的权限，子project的policy与quota也不能超过父级的访问控制或资源上限。人类与Agent（智能体）使用同一套管理API和授权模型。

API Server。apiserver是沙箱集群的入站代理。训练与评估代码从可信GPU服务器调用libdsec，沙箱则执行不可信的模型生成代码，且可能访问外部网络。两侧因此网络隔离，apiserver是唯一允许的通信路径。所有沙箱请求，包括创建、命令执行与流式I/O，都经过该入站口。apiserver不保存单个沙箱的状态，仅定期从watcher刷新edge节点集合，而每个沙箱ID已编码其所属edge。因此任一apiserver实例都能解析请求并直接转发到目标edge，入站层可水平扩展。

Placement Engine。placement engine为每个新沙箱选择宿主机节点。放置分两个阶段：过滤与排序。过滤阶段只保留健康、且具备请求所需后端与硬件能力的节点。例如，需要GPU的沙箱请求只允许落在配备所需GPU的节点上。排序阶段随机采样若干候选节点，选择其中负载最低者。

Watcher。placement engine的决策质量取决于所掌握的集群视图，该视图由watcher提供。watcher定期探测各edge与主机的健康状态，并采集调度相关状态，例如按后端类型统计的运行中沙箱数量，并按edge、用户、任务细分。placement engine定期从watcher拉取这些状态，在评估新创建请求时使用最新视图。

placement engine与watcher都不需要持久化状态。placement engine不保存任何沙箱执行状态，watcher重启后可通过再次轮询edges重建集群视图。因此placement engine和watcher实例易于新增或替换，无需昂贵的恢复步骤。

沙箱运行时

沙箱运行时创建与运行单个沙箱，并管理其资源。包括edge、aether与chronus，并依赖3FS提供共享镜像存储。

Edge。每个节点运行一个edge，这是单机组件，处理来自apiserver的容器、microVM、基于QEMU的完整虚拟机与FnCall后端的创建请求。接受创建请求前，edge检查节点当前容量，容量不足即拒绝。这一节点本地准入检查与placement engine基于周期性刷新的集群状态所做的放置决策互为补充。创建过程中，edge分配存储、应用基于eBPF的网络策略并启动运行时。

FnCall与容器运行在QEMU/libvirt虚拟机内部，而非直接运行在宿主机上。该虚拟机提供隔离的内核与网络栈，并作为不可信容器与裸金属之间的额外安全边界。为更好地支持图形密集型工作负载，例如computer-use GUI应用、浏览器、视频游戏和3D渲染，借助宿主机hypervisor的半虚拟化GPU接口（如virtio-gpu）。在完整虚拟机内，既支持图形API与宿主OS原生兼容的工作负载，也支持渲染栈可通过DXVK（DXVK, 2018）等兼容层转换为宿主原生API的工作负载。

除跟踪沙箱生命周期外，edge还协调磁盘与内存快照，并在沙箱停止或TTL到期时释放节点本地资源。

Aether. 容器与虚拟机沙箱内运行aether，这是一个跨平台代理，与edge建立通信通道。该edge到aether的通道使用平台相关传输方式，例如Linux容器使用Unix domain socket，虚拟机后端使用vsock。edge通过该通道监控沙箱健康状态，通道关闭即把沙箱标记为失败。对每个操作，aether用该操作的terminal-session标识符创建或定位对应的chronus实例，再通过本地通道转发该操作。会话结束时，aether终止对应的chronus进程树。

Chronus.chronus在沙箱内提供shell会话抽象，每个实例代表一个独立的shell会话。对外暴露命令执行、文件系统操作、HTTP请求与流式I/O的跨平台接口。同一沙箱内可并发运行多个chronus实例。aether与chronus共同使libdsec为容器与虚拟机沙箱操作暴露统一接口。

基础镜像与工作区存储。 沙箱运行时用3FS作为基础镜像与工作区镜像的共享后备存储。容器镜像离线从OCI转换为EROFS，EROFS将元数据与数据分离，元数据保留在本地，镜像数据留在3FS。microVM磁盘镜像在同一存储上使用OverlayBD（Li et al., 2020）格式。这些镜像格式共同支持在共享基础上按需加载与增量快照，使edge无需先拉取完整镜像即可启动沙箱。第4章刻画了使可扩展镜像分发成为必要的工作负载压力，第5.3节描述了相应的按需加载机制。

云上突发与选择性卸载

DSec用云虚拟机吸收沙箱需求的瞬时峰值，同时在本地承载稳态工作负载。当本地利用率超过80%时，placement engine将一部分符合条件的沙箱创建请求卸载到云虚拟机。

不采用托管容器服务加对象存储的组合，而是在云虚拟机上复用本地容器运行时与基于EROFS的镜像加载路径。EROFS镜像存放于云侧分布式文件系统，由云虚拟机挂载。

生产环境文件访问trace显示，一套紧凑、去重后的EROFS镜像集共30 TB，覆盖了70%容器任务访问的镜像文件。将该共享镜像集离线同步到云侧文件系统。镜像依赖完全包含在该集合内的容器任务被归类为cloud-eligible，其余任务留在本地。生产环境中，一个scale unit内的200台云虚拟机吸收约30%的峰值溢出，在不超分配本地集群的前提下提升容量。

生产环境沙箱工作负载与平台挑战

本章刻画DSec承载的生产负载及其带来的平台挑战。仅报告容器与microVM的测量数据，二者合计占生产环境中绝大多数沙箱实例与资源消耗。测量结果呈现出一组对传统执行服务而言并不常见的组合：请求以大规模突发到达，每个沙箱在长时间交互中保留状态，即使大量沙箱同时存活CPU需求依然稀疏，环境工作集过于多样，节点本地镜像缓存无法覆盖。此处将每项负载特征与其系统后果对应起来，相应机制留至后续章节。

生命周期与突发需求

Rollout与评测任务批量创建沙箱，而非按稳定速率创建。图2显示，一个典型容器任务已创建数千个沙箱，长尾达到数万个。最大规模的生产作业可请求多达32K个沙箱。这些请求在短窗口内到达，因为训练或评测批次在环境就绪前无法使用实例。因此，放置、沙箱创建与环境准备必须吸收剧烈突发，而任一阶段的掉队者都会延迟有效的模型交互。

沙箱创建后依次经历三个主要阶段，如图3所示。setup阶段准备任务依赖、工具与初始化状态。tool-call阶段中，模型在输出生成与沙箱操作之间交替，产生短促的CPU突发，其间沙箱等待下一步动作。test阶段校验结果，并可能再次短暂抬高资源需求。这些阶段没有固定时长，但其资源特征差异很重要：setup成本会随突发规模成倍放大，而后继阶段在CPU活动间歇的情况下仍需保留沙箱状态。

环境多样性与setup压力

第一个挑战是代价高昂的setup阶段，成因是每个沙箱由独立演进的软件组件组合而成。沙箱内容可分解为三部分：提供OS级依赖的基础镜像（如Ubuntu、Python 3.10或Java 8环境）、承载任务代码仓库及其任务特定依赖的工作区，以及一个或多个频繁更新的工具包（如DeepSeek Harness）。在一个生产周内，容器后端服务了11,266个基础镜像和102,171个工作区，microVM后端使用两个共享基础镜像和53,590个任务特定工作区。平台还服务了103个工具包，67.8%的沙箱除基础镜像外还至少需要一个工作区或工具包。

把三个组件融合为单个Open Container Initiative (OCI) (Open Container Initiative, 2026) 镜像会带来组合式维护负担。若平台维护M个基础镜像、N个工作区与K个工具包，升级m个基础镜像可能需以O(m·N) 代价重建其工作区组合；当工具包与工作区组合时，升级k个工具包的成本为O(k·N)。给出一个具体实例：升级Toolkit T1会强制重建所有包含该工具包的单体镜像，即便基础镜像与工作区未变。目标是通过独立地对三个组件做版本管理与分发，将相应维护成本降至O(m) 与O(k)。

一种直接的替代方案是把工作区与工具包以压缩归档形式分发，并在启动时于每个沙箱内解包。但这类重复工作在突发场景下集中发生时，会带来大量CPU与I/O开销，并可能导致沙箱启动超时。另一种做法是在宿主机上将每个工作区或工具包维护为只读目录，并bind mount到沙箱内。bind mount会完全替换目标路径，而这些组件需要追加语义：其文件必须合并进沙箱已有的目录树，且不遮蔽下层内容。严格的只读挂载还与写入自身安装树的工具冲突，例如Python会创建__pycache__ 目录。

稀疏利用率与高密度执行

约90%的容器与microVM沙箱平均使用的CPU不超过其申请量的5%（图5），因此超分是自然选择。2026年初的一天采样显示（图6），每节点峰值达到1,048个容器与524个microVM。但在生产环境中，已观察到的稳定运行密度为每节点至少3,200个容器或800个microVM。这些是已验证的运行点，而非硬性上限。在这样的密度下，内存低效与CPU干扰变得愈发重要。

内存方面，microVM存在两类浪费来源。第一，通过虚拟块设备读取的镜像数据会先被宿主机缓存一次，再被每个guest缓存一次，导致同一份数据在guest与宿主机边界两侧被冗余缓存。第二，guest内部的空闲页若无显式上报就不会归还给宿主机。由于申请的内存容量往往超过实际需求，guest内部几乎没有回收非活跃页的压力。图7表明这些沙箱同样长生命周期：容器的中位生命周期为17.4分钟，microVM为15.5分钟，两种后端的p99生命周期均超过三小时。如此长的生命周期放大了驻留内存的成本。综合这些影响，microVM的内存超分受到制约，在高沙箱密度下尤为明显。

CPU方面，部分任务对每一步的延迟有严格预算，例如每步有固定时间限制的游戏类Agent（智能体）。当best-effort任务与延迟敏感任务运行在相邻的同步多线程上下文上并仍共享核心执行资源时，仅给best-effort任务更低的调度优先级并不足够。平台必须在通过超分提升CPU利用率的同时不干扰延迟敏感任务。

核心系统机制

归纳出三项相互耦合的基础设施挑战。第一，突发式创建与独立演进的环境组件，要求建立路径的成本不随每次沙箱重复解包而增长。第二，稀疏CPU需求使高密度执行具有价值，但长生命周期、驻留内存和混合延迟需求使无约束超分不安全。第三，镜像语料庞大且扇出低、运行时访问比例低，使预先完整镜像分发既昂贵又具干扰性。

可组合的环境层

核心洞察：基础OS环境、每个工作区、每个工具包在逻辑上是各自独立的层，各有自己的生命周期，而非必须融合为单个单体镜像的组件。如图4(b)所示，工具包由此可独立更新，并与已有的基础镜像层、工作区层重新组合。Overlayfs原生提供所需的合并语义：多个只读下层目录叠加时，内核呈现统一的目录树，各层的文件共存，并按优先级顺序解决冲突。可写上层目录位于栈顶，透明吸收所有运行时写入，而不修改下方的只读层。

修改容器运行时（即dockerd），在沙箱创建时动态组合overlayfs栈（即lowerdir）。基础镜像置于底部，请求的工作区作为只读层插入其上，每个请求的工具包再叠加于顶部。这样将工作区与工具包文件合并进基础镜像树而非替换路径，把运行时写入导向可写上层，并允许任意层组合而不耦合其生命周期。因此，升级m个基础镜像现在只需重建这m个基础层，工作区与工具包不受影响，而升级k个工具包只需重建这k个工具包层。单体镜像方案的O(m·N) 与O(k·N) 成本由此降至O(m) 与O(k)。

已发布的环境层不可变，因此存储于EROFS (Gao et al., 2019)，一种专为只读数据设计的文件系统。相比ext4、XFS等可写文件系统，EROFS避免了写相关的簿记，磁盘布局更简单紧凑。EROFS还支持数据压缩，同时保留对文件内容的随机访问。不同于tar.gz归档，EROFS只读取并解压覆盖所需数据的压缩块，因此无需在使用前传输并解压完整镜像。

对于microVM，基础镜像与工具包打包为独立版本化的EROFS镜像，并作为只读块设备暴露给guest。在guest内部，根文件系统使用overlayfs，以挂载的EROFS文件系统为下层，以ext4格式化的可写磁盘上的目录为上层。这让microVM具备与容器相同的可组合层模型。

高密度资源管理

内存效率.

Virtio-pmem with DAX (QEMU Project, 2026) 通过将文件访问直接映射到宿主持有的页而不复制进guest RAM，消除页缓存重复，使共置的microVM共享一份宿主页缓存副本。但virtio-pmem并不适合所有磁盘。第一，通过virtio-pmem with DAX的冷访问可能需要同步缺页处理来建立映射并使后端数据可用。带缓冲的virtio-blk路径则能受益于guest侧的预读与批量块I/O。第二，guest必须为整个pmem后端地址范围分配struct page元数据。在4 KiB页与64字节struct page下，该元数据需要相当于pmem设备容量1/64的guest RAM。例如，128 GB pmem设备需要2 GB guest RAM存放该元数据。

对于不使用virtio-pmem的磁盘，冷文件数据会在guest页缓存中累积，必须单独回收。因此将DAMON (Data Access MONitor) (Park et al., 2019) 与virtio-balloon空闲页上报结合使用。virtio-balloon驱动(Waldspurger, 2002) 支持free-page reporting：guest周期性扫描其伙伴分配器，主动向宿主hypervisor上报空闲页，后者通过madvise(MADV_DONTNEED) 释放对应的宿主内存。默认情况下，空闲页上报以order-9页运行，在4 KiB基础页下对应2 MiB区域，该order可通过内核参数调整。为增强空闲页上报，采用DAMON，Linux中基于采样的内存访问监控框架。DAMON周期性采样页访问位，识别超过可配置年龄阈值仍未被访问的冷文件页，并通过内核回收路径将其逐出。该回收把分散的文件页释放回伙伴分配器，由其合并为更高阶的块，满足空闲页上报的要求。

第8.4节的评估中，DAMON配合balloon空闲页上报将内存消耗降低21.2%，且无明显CPU开销。在生产环境中，对只读EROFS基础镜像层与工具包层启用virtio-pmem with DAX，同时使用DAMON配合balloon空闲页上报为较大的可写磁盘回收内存。

QoS感知的CPU调度.

为消除SMT层面的CPU干扰，DSec将沙箱划分为延迟敏感（LS）与尽力而为（BE）两类。BE沙箱置于SCHED_IDLE下，只要有LS任务可运行就让出CPU。仅靠调度器优先级无法阻止同一物理核上的兄弟硬件线程之间的干扰，因此对LS沙箱同时启用Linuxcore scheduling（Zijlstra et al., 2021），阻止无关的BE工作运行在同一物理核的兄弟线程上。该双层策略在保持LS每步延迟预算的同时，仍允许BE任务利用空闲周期，将SMT引起的延迟膨胀从45.2%降至17.3%，详见第8.5节。

可扩展的镜像分发与按需加载

关键观察是沙箱通常只访问其镜像数据的一小部分，如表3中的采样所示。因此按需拉取不仅解决时序问题，还解决体量问题：总I/O随实际使用比例成比例缩减，而不只是被挪到另一个阶段。

现有按需镜像分发系统常将容器镜像仓库与点对点传输结合，以防镜像仓库成为瓶颈（Wang et al., 2021）。这里改为将镜像托管在3FS上，3FS已大规模支撑生产训练负载。该选择复用现有存储基础设施，避免部署独立的镜像分发层。但3FS的I/O特性高度不对称：大顺序读写可维持高吞吐，小随机I/O表现很差。这种不对称决定了设计：

写保持本地。沙箱写入不规则且不可控，包括日志文件这类小而频繁的写。可写层放在节点本地磁盘，完全避开3FS的小写惩罚。

读按需且批量。只读镜像数据仅在访问时从3FS拉取，且以批量方式执行I/O，以利用3FS对大I/O请求的高吞吐。

元数据尽量保留在本地。文件系统元数据通常通过小读访问。在镜像格式允许时，将元数据与数据分离，并把元数据预取到本地节点。

对于容器，EROFS有助于实现这些设计原则。第一，EROFS严格只读，因此所有运行时写入都落在本地存储的overlayfs upper目录。第二，EROFS通过buffered I/O按需提供文件内容，同时内核readahead把相邻块合并为更大的请求。第三，EROFS提供multi-device模式，将文件系统元数据与文件数据分离。Nydus（Dragonfly Community, 2020）采用相关设计：其兼容EROFS的格式将文件系统元数据与数据blob分离，并支持懒加载，文件数据经用户态后端（如fscache/FUSE）从registry或对象存储按需获取。此处改为将EROFS元数据下载到worker的本地磁盘，把文件数据留在3FS上，因此元数据遍历与路径名查找不产生远程I/O。写路径（本地、对小I/O友好）与读路径（远程、按需、批量）由此分离，与3FS的非对称性能特征相匹配。

该设计避免了全量镜像拉取，但挂载大量EROFS层仍会给容器创建带来开销。因此在离线阶段把大小阈值（如3 GB）内的连续层折叠为一对EROFS镜像，分别承载元数据与数据，同时保留overlayfs whiteout语义以正确表示文件删除。这减少了最终挂载数量，避免过多文件重复，并保留共享公共层的镜像之间的page-cache复用。还使用EROFS file-backed mount模式消除loop-device块映射层及其开销。

容器风格的EROFS/overlayfs栈无法满足microVM的全部文件系统兼容性要求。例如，Docker的overlay2驱动无法使用由overlayfs支撑的数据目录。替代方案是经virtio-fs把宿主挂载的文件系统导出给guest，但Firecracker后端不支持该接口（Agache et al., 2020）。因此microVM存储设计与容器设计并不相同。只读base-image与toolkit层仍使用EROFS，而OverlayBD提供可写ext4磁盘，其中包括直接挂载在Docker data root上的独立磁盘，用于Docker-in-microVM工作负载。

通过ublk（用户态块设备框架）暴露OverlayBD支撑的磁盘。该块级路径提供按需读取与本地写入，并支持增量磁盘快照，无需把修改过的文件重新打包进EROFS。与multi-device EROFS路径不同，ext4元数据仍嵌在块镜像中，因此元数据读取可能触发远程I/O。ublk实现以256 KiB为单位获取OverlayBD数据并存入二级本地文件系统缓存，缓解这些小读。即使某个chunk被逐出page cache，仍保留在本地缓存中，无需再次从3FS获取。两条路径都把写入保持在本地，并把发往3FS的小I/O请求降到最低。

与RL框架的协同设计

从DeepSeek V3.2（DeepSeek-AI, 2025）到V4.1（DeepSeek-AI, 2026）的RL训练与评估中，全部沙箱工作负载均由DSec承载。除高效的沙箱执行外，支撑这些工作负载还需与RL框架在执行生命周期与安全策略上协同。首先介绍Agent（智能体）环境的可扩展构建（6.1）。随后说明agent loop容器如何把rollout执行与GPU训练任务解耦（6.2），以及pause/resume如何把资源回收与训练抢占协同起来（6.3）。最后考察损害任务完整性或干扰执行环境的Agent行为（6.4），以及用于缓解这些风险的访问控制（6.5）。

由Agent构建,为Agent服务的环境

手工构建Agentic（智能体原生）RL所需的大量环境不现实。改为让Agent在训练与评估所用的同一套基础设施上交互式构建环境。DSec通过pack_diff支持该工作流：Agent可在任意时刻对沙箱做增量磁盘快照以建立checkpoint，之后可将其恢复为新的沙箱。这套checkpoint-and-restore接口把交互会话直接变为可复用环境，使环境能在同一套基础设施上构建、验证与消费，无需独立的镜像构建流水线。

内部维护一套规则，打包后的环境必须遵守，以限制其对共享基础设施的运行时性能影响。这些约束以指令形式提供给构建环境的Agent。为跟踪所有环境并与持续演进的基础设施保持同步，研究人员还构建了一个内部平台，对Agent构建的环境做质量检查，并以标准化格式导出，供RL与评估任务消费。

环境在同一套沙箱基础设施上构建与消费，防止两个阶段之间泄漏信息很重要。Builder与运行时Agent使用独立账号，构建期残留数据在打包前从可写层清除，使参考答案不会进入生成的镜像。

将Agent loop与RL框架分离

GPU集群中的训练任务常为提高利用率而被抢占。对长时间运行的Agentic（智能体原生）rollout，将rollout执行与训练任务耦合会使抢占代价尤为高昂：agent loop可能在取得大量进展后被终止，而对应的沙箱状态仍然完好。要恢复这类rollout，系统必须同时保留Agent的执行状态与沙箱状态。

在早期版本的训练流水线中，agent loop与模型服务、RL框架一同运行在可被抢占的GPU训练pod内。GPU任务被抢占时，agent loop丢失而沙箱存留。恢复因此依赖命令日志，将训练框架还原的rollout状态与沙箱的执行状态对齐。重放时，已完成的操作复用记录结果而非重新执行，避免非幂等命令产生重复副作用。

从DeepSeek-V4.1（DeepSeek-AI, 2026）起，rollout执行被移至DSec，并拆分为两个组件：agent sandbox，承载scaffold（如DeepSeek Harness）及其工具；worker container，管理沙箱并提供与scaffold无关的rollout控制层。两个组件都运行在可被抢占的GPU池之外。该设计将rollout生命周期与trainer生命周期解耦。worker container与agent sandbox共同保留完整的rollout状态，并作为其唯一事实来源，使被抢占的GPU任务可以重新连接并继续，无需通过命令日志重放重建执行过程。这使RL框架不再包含rollout状态恢复逻辑，减少跨组件协调，简化故障处理。

为抢占式RL训练挂起沙箱

GPU任务抢占不可避免（6.3），沙箱状态必须留在DSec直到rollout完成。但训练挂起期间，这会让大量空闲沙箱占用内存。RL框架因此主动向被抢占任务关联的所有沙箱发送pause请求，让DSec回收内存的同时保留其执行状态。对容器和microVM，后续发往已挂起沙箱的请求都会先透明地恢复该沙箱，再执行所请求的操作。

容器。edge首先发出docker pause冻结容器的进程树。随后通过容器的memory.swap.max设置启用swap，并通过memory.reclaim触发主动内存回收。这样既从匿名页和文件页回收内存，又保留容器的执行状态。恢复容器时，edge对其进程的内存映射应用MADV_WILLNEED以发起异步预取，然后发出docker unpause恢复执行。

MicroVM。挂起microVM时，DSec将其内存与执行状态保存为快照，然后终止运行中的Firecracker进程以释放microVM的运行时内存。恢复时，DSec启动新进程并还原快照，继续guest执行。

Agent异常行为与系统故障

生产经验揭示了Agent（智能体）执行中的两类风险。任务可能看似通过，但Agent是通过非预期渠道获得答案，从而破坏训练与评估结果的有效性。Agent行为还会破坏执行环境，影响本任务或共享该基础设施的其他任务。

通过非预期渠道获取答案。在沙箱内，Agent在平台管理的文件和通信通道中搜索残留答案。例如，尝试构造RPC消息直接发送到chronus socket以伪造用户请求，并检查chronus日志寻找泄露的答案。由于chronus在某些操作中会调用bash，Agent还尝试覆盖/bin/bash以绕过检查，或向后续shell会话注入命令。在引入文件读写与socket访问控制后，某个Agent尝试使用XFS_IOC_SWAPEXT绕过这些控制，该ioctl交换两个文件的数据extent映射，目的是让受保护文件的内容可通过另一个文件描述符访问。该尝试损坏了XFS元数据并导致文件系统强制关闭，说明寻找答案的行为甚至能破坏基础设施。

在沙箱外，Agent会在任务预期信息来源之外搜索参考实现。例如，扫描端口和服务以发现可达镜像；还使用Go module proxy获取托管在GitHub的代码、安装更新的包版本，寻找所需功能的已有实现。仅靠最终输出检查无法可靠判断Agent是否按预期解决了任务。

篡改执行环境。基础设施故障也源于普通命令和执行失误，而非刻意破坏系统。某案例中，Agent从根目录递归运行grep，遍历/proc并读取/proc/kpagecgroup，触发内核bug导致内核崩溃。类似故障出现在漏洞利用任务中：本应转发到独立目标VM的攻击命令在Agent容器内部执行，导致自身内核崩溃。除内核崩溃外，无限制的命令输出会消耗大量存储。例如，某Agent调用yes，其持续输出被chronus记录，以便用户异步获取命令输出，捕获的stdout在存储上累积了数十GB数据。

访问控制缓解措施

没有单一机制能防止所有Agent不当行为和系统故障。因此需增强可观测性以识别新出现的问题，并随模型演进持续加固DSec。访问控制限制Agent通过非预期渠道获取答案的能力，从而缓解reward hacking (Amodei et al., 2016; Skalse et al., 2022)。这些控制仅解决问题的部分方面，无法通用防御触发内核bug等破坏性行为。

文件与socket访问控制(AppArmor)。使用AppArmor profile控制文件读写权限和socket访问，包括对chronus日志和Unix domain socket的访问。这些策略适用于Agent控制的进程，即使以root身份在沙箱内运行。限制从日志提取残留答案或通过内部通信通道伪造用户请求的尝试。

细粒度网络控制(eBPF)。训练框架按域名或镜像服务指定任务级网络权限。例如允许访问PyPI而拒绝访问NPM。DSec通过每沙箱的eBPF程序执行对应allowlist，按IP地址、端口和协议过滤流量，拒绝allowlist之外的流量。任务在不同连接需求的阶段之间迁移时，策略可动态更新。

实现

补充几个在实践中被证明重要的实现细节。

放置引擎策略 亚秒级数千沙箱的极端突发与重度超分，要求以弹性而非固定预留的方式均匀分散增量负载。从以下三方面解决。1) 采用power-of-k-choices算法（Mitzenmacher, 2001）：调度器随机采样k个节点并选择负载最低者，避免羊群效应，减少突发型RL环境在环境搭建与工具调用期间的相互干扰。2) 每个placementengine实例通过在周期性watcher快照之上叠加自身尚未反映的近期放置决策来维护本地视图，无需跨实例协调即可计入在途负载。3) 每个edge保留最终准入权限：关键资源压力触发拒绝并改选其他节点，使快路径保持轻量，同时防止过期估计覆盖本地资源上限。用户隔离进一步限制资源突发或内核级故障的影响范围，代价是节点级密度下降。

可靠服务。 辅助服务与集群级服务都必须保持可靠，服务中断会导致Agent（智能体）任务失败，污染奖励信号或评估结果。对于API网关、软件包镜像等辅助服务以及控制面入口，采用基于BGP的负载均衡：每个服务的实例宣告同一个虚拟IP，上游交换机在其间执行ECMP路由。当某实例的BGP会话断开时，交换机会撤销其路由并在数秒内将流量重定向至其余实例。集群级服务，包括placement engine、watcher和IAM，运行多个独立实例以保证可用性，并通过定期集群重置验证Infrastructure-as-Code配置能从零重建全部集群级服务、在不依赖累积手工状态的情况下从故障中恢复。

dockerd中的动态下层插入。 修改开源Docker daemon（基于Moby项目（Moby Project, 2026）），在容器创建时动态插入由EROFS支持的下层。具体做法是传入预挂载EROFS层的路径，在挂载前将其插入overlayfs栈，并置于最上层lower layer，从而覆盖下方各层中的文件。改动极小，仅需30行Go代码。

基于Rust的OverlayBD与ublk库。 使用参与贡献的Rust版OverlayBD，配合自研的Rust ublk用户态库，构成Firecracker microVM的按需块存储路径。存储层支持3FS、OSS等对象存储服务以及容器镜像仓库作为远端后端，也可将本地文件系统用作二级缓存，使被逐出page cache的数据在本地即可提供，无需再次远端拉取。这些存储组件已在https://github.com/kvcache-ai/AgentENV/tree/main/storage/overlaybd开源。

内存与CPU QoS配置。 所有机制均复用现有Linux内核特性。带DAX的Virtio-pmem通过Firecracker设备配置与guest内核挂载选项启用。基于DAMON的回收通过guest内核参数与sysfs调优激活。CPU QoS方面，将best-effort任务设为SCHED_IDLE，并通过prctl(PR_SCHED_CORE) 启用core scheduling，按QoS类别对任务分组。无需修改内核，实现完全由配置与同沙箱编排器的集成构成。

用于算子基准测试的GPU FnCall。 为FnCall配备GPU，用于无状态算子基准测试。GPU容量有限，GPU FnCall用三种机制在保持性能隔离的同时提升并发。第一，NVIDIA Multi-Instance GPU（MIG）将每块GPU划分为相互隔离的instances，使基准测试可并发运行并独占所分配的实例。第二，CPU FnCall负责编译并将产物传给GPU FnCall，避免无谓占用GPU。第三，Python进程预热池预先初始化运行时并导入库，使请求可直接开始算子执行。三项机制共同减少执行路径上的非GPU开销，提升GPU利用率与基准测试吞吐。对性能不敏感的任务，另提供共享GPU模式，允许多个工作负载共享同一GPU实例以提高并发。

3FS部署。 每台3FS（An et al., 2024）存储服务器配备20 × 15 TB SSD与2 × 400Gbps RDMA网卡。CPU节点通过基于FUSE的客户端访问3FS，EROFS元数据存放于本地，文件数据按需从3FS提供。数十台存储服务器即可支撑数十万CPU核规模集群的按需镜像加载。

评估

评估衡量四项核心机制的有效性与开销：按需镜像加载、可组合环境层、内存优化与QoS感知的CPU调度。实验聚焦这些基础设施性能机制，框架集成不在评估范围内。

实验设置

本章实验在专用的10节点CPU测试集群上进行，与生产部署隔离。

Hardware. 为避免嵌套虚拟化，microVM直接在裸金属硬件上执行。每个microVM节点配置AMD EPYC 9655处理器，2 sockets × 96 cores × 2 SMT threads，1.5 TB DRAM，3.4 TB本地存储。相比之下，基于容器的实验运行在QEMU虚拟机内，配置为AMD EPYC 9655处理器，1 socket × 96 cores × 2 SMT threads，共192个硬件线程，512 GB内存，5.8 TB本地存储。

内核版本。所有宿主机运行Linux 7.0，所有microVM客户机运行Linux 6.1。

工作负载。工作负载取自真实RL训练与评估场景。任务套件包括内部软件工程基准、SWE-bench (Jimenez et al., 2024)、Terminal-Bench (Merrill et al., 2026)、安全漏洞利用任务及类似领域。

按需镜像加载

对比按需EROFS镜像拉取与两种基线：从远程registry的急切全镜像拉取（Docker Pull (cold)），以及所有镜像层已预缓存在节点上的完全本地基线（Docker Pull (cached)）。实验在真实RL评估工作负载下向10节点集群突发分发8,192个容器，工作负载启动时需要多样化的多GB镜像。测量并发运行容器数随时间的变化、瞬时磁盘写IOPS与累计磁盘写入量。各配置的CPU与内存利用率差异可忽略，故省略。

如图10所示，按需EROFS拉取达到峰值并发的速度几乎与完全本地基线相当，因为镜像层直接挂载，数据在沙箱访问各自工作集时从3FS获取。急切Docker拉取必须在容器启动前下载并解压每一层，导致前20分钟容器创建延迟。按需拉取在约35分钟内完成所有任务，与完全本地基线持平，而急切拉取需要超过60分钟，慢1.71×。

急切拉取的峰值磁盘写IOPS也接近按需路径的两倍，每节点累计磁盘写入超过1,600 GB。按需拉取仅在初期产生短暂突发，随后稳定在约700 GB，比急切拉取少约57%，接近完全本地基线约600 GB。这些结果验证了该设计：按每个沙箱的工作集按需获取镜像数据，可避免全镜像下载与解压，同时接近完全本地性能。

可组合镜像层:EROFS vs. Tar

针对代码仓库与开发环境，比较两种为同一评估工作区与工具包（含任务仓库、scaffold二进制、命令行工具）提供供给的方式。传统方式把这些文件打包为压缩的tar.gz归档，分发并解压到每个沙箱；EROFS方式把同样的文件打包为压缩的只读文件系统镜像，可直接作为可组合层挂载。用预先录制的确定性工具调用序列替代LLM（大语言模型）生成，使各次运行仅在评估工作区与工具包的供给方式上存在差异。

tar.gz是顺序流格式，每个沙箱在工具调用开始前都必须解压归档，并把全部工作区与工具包文件写入本地可写层。端到端任务完成时间因此延长到79分钟。EROFS直接挂载共享层、无需解压，沙箱能更早进入工具调用阶段，完成时间降至45分钟，加速1.76×。如图11所示，基于tar的供给产生约5.5× 于EROFS路径的总磁盘写流量，峰值磁盘写吞吐为后者的3.4×。EROFS的峰值CPU利用率更高，原因是更多沙箱更早进入工具调用阶段并发执行操作；这不表示setup开销更高，EROFS避免了反复解压与展开归档的CPU工作。这些结果验证了可组合层设计的有效性。

超分下的内存

在测试集群上运行真实Agentic（智能体原生）-RL工作负载，比较四种Firecracker配置：未优化的baseline、单独使用带DAX的virtio-pmem、单独使用基于DAMON经virtio-balloon设备实现的空闲页上报（FPR），以及两种机制组合。带DAX的virtio-pmem把各guest冗余的page cache合并为单一共享的宿主映射，峰值宿主内存占用相比baseline降低40.2%。单独使用DAMON + balloon FPR时峰值占用基本不变，但时间积分宿主内存消耗降低21.2%。两种机制组合的总内存消耗最低。如图12所示，virtio-pmem把瞬态峰值CPU利用率从26.5%提高到41.4%。这一上升部分反映冷访问路径的差异：带DAX的virtio-pmem需要同步缺页处理来建立映射并使后端数据可用，而带缓冲的virtio-blk可受益于guest侧预读与批量块I/O。在CPU受限的部署中，运维方可能更倾向于只启用FPR并保留virtio-blk。这些结果共同验证了互补的内存优化：virtio-pmem减少page cache冗余，DAMON配合balloon FPR回收空闲guest内存。

超分下的CPU QoS

运行真实评估工作负载中的延迟敏感（LS）任务，并叠加占节点容量10%到50%的同节点best-effort（BE）负载，测量机制在高密度部署下保持单沙箱性能的效果。比较无保护的baseline、单独使用SCHED_IDLE，以及SCHED_IDLE配合core scheduling三种方案。

如图13所示，测试工作负载是一个延迟敏感的棋类应用。在50% BE负载下，无QoS控制时其单步延迟相比无同节点负载的baseline上升45.2%。单独使用SCHED_IDLE最多把延迟改善3.4%，因为LS线程仍会与其SMT兄弟核上运行的BE工作争抢。加入core scheduling后，低负载下延迟接近无同节点负载的baseline，50%负载下涨幅限制在17.3%。BE争抢越强，改善越明显。这些结果验证了两级CPU QoS设计：SCHED_IDLE优先调度LS任务，core scheduling把LS任务与SMT兄弟线程上的BE工作隔离。残余退化主要来自高多核负载下CPU turbo频率下降，以及core scheduling无法处理的内存带宽与共享last-level cache（LLC）争用。这类剩余干扰已可容忍，因此不启用内存带宽隔离。

相关工作

Serverless计算。SAND（Akkus等，2018）、REAP（Ustiugov等，2021）、TrEnv（Huang等，2024）、RunD（Li等，2022）等Serverless平台针对短生命周期、无状态函数优化冷启动延迟与资源共享。这类工作负载通常以高扇出复用有限的镜像集合，许多系统假定所需镜像已在本地可用。Agentic（智能体原生）训练使用的则是有状态、长生命周期的沙箱，其镜像语料超出单节点存储容量，且单镜像扇出很低。

LLM代码执行平台。近期系统在训练与推理两类LLM（大语言模型）工作流中提供沙箱化代码执行。面向推理的系统包括OpenAI Code Interpreter（OpenAI，2025）、E2B（E2B，2024）与Kimi-K2.5的Agent Swarm（Kimi Team，2026）。MiMo-V2-Flash（Xiaomi LLM-Core Team，2026）、ComputerRL（Lai等，2025）等训练系统提及了其执行环境，但重点在模型与训练设计。DSec关注底层沙箱基础设施，把环境组合、资源超分、镜像服务、抢占安全恢复集成在一个平台内。

容器镜像与文件系统格式。DADI（Li等，2020）与CoFS（Wang等，2026）支持容器镜像按需加载，FaaSNet（Wang等，2021）用点对点分发加速镜像分发。EROFS（Gao等，2019）提供支持随机访问的压缩只读文件系统。DSec基于这些技术构建RL训练与评估，从3FS提供容器与microVM镜像，而非另建独立的registry与点对点分发层。

轻量级隔离。为运行多样化负载，已有多种隔离范式：microVM（Agache等，2020）或基于VM的kata-containers（Kata Containers，2017）、library OS（Tsai等，2017；LiteBox，2025）、WebAssembly运行时（Gadepalli等，2020；Shillaker和Pietzuch，2020）、unikernel（Cadden等，2020）、嵌套内核（Dautenhahn等，2015；Zhang等，2025）以及嵌套虚拟化（Huang等，2023）。这些方案在隔离性、兼容性与性能之间取舍不同。DSec不提出新的隔离机制，而是在统一平台后集成多种沙箱后端，让调用方为每个任务选择合适后端。

RL训练基础设施。Slime（Zhu等，2025）、veRL（Sheng等，2025）、OpenRLHF（Hu等，2025；Hu，2026）、Seer（Qin等，2026）等系统通过高效的GPU调度、通信与样本吞吐实现RL训练的扩展，把执行环境视为黑盒，假定沙箱可用且配置正确。DSec工作在互补的基础设施层，管理沙箱供给与生命周期，并与训练框架协同执行状态与安全策略。

结论

DSec是面向大规模LLM Agentic（智能体原生）训练、评估与环境构建的生产级沙箱平台。DSec通过统一接口暴露多种沙箱后端，使用户能按功能、兼容性与隔离需求选择执行环境。基于EROFS的可组合层避免重复构建与解压环境，互补的内存共享与回收机制支撑高密度部署，QoS感知的CPU调度在超分下保护延迟敏感任务，基于3FS的按需镜像加载降低镜像分发开销。DSec还与RL框架集成，实现抢占安全恢复与任务级网络策略，为Agentic负载提供可扩展的执行基座。

结语
Agentic训练把沙箱从「一次性执行容器」变成了需要长生命周期、突发扩展与状态保持的基础设施。DSec的答案不是更强的单机沙箱，而是把环境构建、镜像分发、资源回收与训练调度放进同一平台协同：在约160节点、日均300万沙箱的规模上，按需EROFS加载把8,192容器突发下的累计磁盘写入压到约700 GB，比急切拉取少约57%；virtio-pmem与DAMON让内存超分在高密度下依然可用。

对正在做Agent训练或评测的团队，这份报告的取舍顺序值得复用：先让环境可组合，再让镜像按需加载，最后才谈资源超分。顺序颠倒，任何一环的成本都会推给另一环。
