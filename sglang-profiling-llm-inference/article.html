Prefill部分

这是我们单个请求的完整prefill区域。Prefill是模型消耗提示词token并生成单个token的阶段。分析器的上半部分显示CPU侧操作，下半部分显示GPU侧操作。

你是否能发现第一个模式？峰值似乎被分成3组，中间有一个较小的峰值。另一个引人注目的是第一个峰值比其他峰值大得多。请记住这一点，随着我们的深入，我们将逐一揭示每个特征。

好的，如果你滚动到最左侧那个较小的峰值并放大一些，你会看到大量的初始化工作。这包括启动torch profiler、sglang准备输入批次、设置CUDA流，一切都为运行前向传播而就绪。

另一个很酷的功能是，如果你想了解某个CPU活动启动了哪个内核，你可以点击该操作，它会将你链接到它启动的具体内核，并附带一些信息。

这种情况下，我们可以看到从固定CPU内存到GPU的主机到设备拷贝。对于这次运行，可能是请求元数据、token ID或调度器需要的某个小张量。

如果你越过所有重复的峰值，进入最后一段，服务器会进入清理阶段，并为解码做准备。这包括最终投影到logits、采样，以及将结果复制回CPU。这一部分容易被忽略，但在这个trace中，logits processor包含了代价最高的内核之一。

如果你点击CPU端的aten::mm并展开参数，PyTorch会显示：

Input type: ['c10::BFloat16', 'c10::BFloat16'] Input strides: [[1024, 1], [1, 1024]] Input dims: [[1, 1024], [1024, 248320]]

从概念上讲，这就是：[1, 1024] @ [1024, 248320] = [1, 248320]

由于词表规模巨大，这变成了一个大型矩阵向量式投影。尽管在此提示的prefill期间仅运行一次，但它仍然是该部分中最慢的内核之一。

内核细节也相当值得阅读（使用Nsight可以做更多操作）

grid: [31040, 1, 1] block: [8, 8, 1] registers/thread: 168 shared memory: 288 occupancy: 25%

这个网格形状是什么？248320个词表元素 / 8 = 31040

不错，最终的线性头将一个1024宽的隐藏向量投影到非常大的词表维度上。如果我要优化这条路径，我会仔细研究这个投影是否可以融合，或寻找类似的优化。

主要预填充内核

下面来看此工作负载中运行的最突出的内核。

最后的gemv内核虽然仅被调用一次，但确实是最昂贵的。128x128 BF16 GEMM出现了24次，与每个块一次大型投影式操作相吻合。较小的CUTLASS BF16 GEMM出现了18次，与18个GDN块恰好对应。

仅凭内核名称有时会显得嘈杂且难以理解，因此结合模型布局和数据流来理解，会让trace更容易分析。

解码阶段

0.8B parameters * 2 bytes = 1.6 GB

解码是与预填充不同的工作负载。预填充阶段，模型处理整个提示序列，许多操作有足够的计算量，从而成为像样的GEMM。而解码阶段批次大小更小，模型大多一次处理一个新token，大量投影工作收缩为瘦长的矩阵向量运算。

在此trace中，高亮区域是重要部分。周围区域主要是profiler的启动/关闭、输入设置、同步和簿记。这些值得理解，但它们不是模型的主要计算路径。

左侧，SGLang加载批次并将此decode步骤的输入复制到固定的CUDA graph缓冲区。中间是实际decode工作发生的地方。出乎意料的是，与prefill不同，CPU时间线没有将每个模型层显示为单个启动的深层堆栈，因为decode路径使用的是CUDA graph replay。

在graph replay之前，有一些用于设置的小内核和复制操作。这些不是层堆栈。它们主要是在准备捕获图所需的固定缓冲区和执行状态。

点击进入graph replay区域后，GPU内核在该replay下方可见。这是对decode至关重要的视图。

Decode阶段由瘦GEMV主导。

Perfetto UI地址：https://ui.perfetto.dev/

重复出现的蓝色条柱与我们之前在vocab projection周围看到的GEMV家族相同。在decode阶段，它们不断出现，这是因为对于batch size 1的decode，它只是将许多线性层转化为矩阵-向量式操作。

这是核心性能问题。GEMV的算术强度远低于大型GEMM。从内存中读取大量权重，但没有足够的复用来让张量核心像庞大的prefill GEMM那样保持忙碌。因此，即使GPU计算能力充足，decode路径也可能受内存带宽限制。

这些微小的红/绿/紫色小点是来自混合块的其他kernel，它们很重要，但对于这次batch size 1的运行，trace的形状主要表明一件事：decode路径是一长串瘦长的投影运算。

这也解释了为什么batching会改变情况。如果增大batch size，其中一些瘦长运算就不再那么瘦长。工作负载更接近GEMM类行为，GPU有更多机会复用权重，并在每次加载的字节上执行更多有效计算。这并不表示batching没有代价，因为KV cache、延迟、调度和内存压力都很重要，但它解释了为什么单请求decode对GPU来说是如此困难的形状。

接下来该怎么做？

下一步是使用更大的batch和更长的prompt重复这一分析。这样就可以区分哪些瓶颈是batch size 1 decode特有的，哪些即使在GPU有更多并行工作可处理时仍然棘手。

结语
剖析SGLang服务的LLM，关键在于先把预计算的roofline假设与trace里看到的实际峰值一一对应：带宽受限的GEMV在decode主导、算术强度更高的GEMM在prefill主导，峰值的分组结构正好映射模型的混合块布局。

对batch size 1的decode，瓶颈几乎总是瘦GEMV的带宽上限而非计算上限；增大batch让这些瘦长运算变成GEMM，GPU有更多机会复用权重。下一步用更大batch和更长prompt重复这套分析，就能区分出哪些瓶颈是单样本特有的、哪些在高压力下仍然棘手。
