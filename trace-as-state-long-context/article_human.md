长上下文推理的瓶颈未必是窗口长度。解题需要的任务状态，常常要到读完整段上下文之后才出现，而因果注意力让这个状态无法回头影响前面已经形成的表示。把第一遍的推理轨迹放到长上下文之前再读一遍，DeepSeek V4 Pro 在 GraphWalks Parents 上的精确匹配从 29.2% 提升到 81.8%。

## 顺序错配：长上下文推理卡在哪里
前沿语言模型的输入长度已经可以覆盖数十万乃至上百万 token，稀疏、压缩与混合序列建模架构把名义上下文窗口推得很大。但自回归 Transformer 保留因果注意力：后出现的信息可以影响之后的推理与答案生成，却无法改变同一遍里较早位置已经形成的表示。
结构性困难在于输入顺序与推理顺序对不上。推理表现不只取决于支持信息出现在什么位置，也取决于它们的相对顺序。很多长上下文任务要求解题者持续维护与任务相关的状态，例如当前目标、搜索前沿、已排除的假设，其中一部分状态只有在读完前面内容之后才会浮现。
论文把这种不对称放进条件状态更新任务里分析：任务从一个由条件指定的状态出发，再把一段信息序列作用上去。条件排在序列前面时，因果处理器可以边读边更新已经实现的那条状态路径；条件排在序列后面时，处理器无法提前确定路径，只能保留这段序列作用在每一种可能条件上会得到什么。两种输入顺序在最坏情况下的工作记忆需求可以相差指数级。
由此得到一条排序原则：如果与任务相关的状态是在一遍处理的后期才被发现，就可以把它挪到下一遍处理上下文之前。图 1 给出完整框架，(A) 因果处理器维护一个运行状态，(B) 在最坏情况的条件状态更新任务里条件在前只需跟踪已实现状态、条件在后可能需要指数级更多工作记忆，(C) 推理轨迹 T 提供任务状态的文本代理，(D) trace as state 在全新的一次因果传递中把 T 放在上下文之前。
现代推理模型在给出可见答案之前会生成推理轨迹，这提供了一个可观察的接口，生成的推理文本可以承载跨步骤的中间计算信息。轨迹可能不完整、有损甚至出错，论文把它当作任务状态的一个可观察文本代理，由此提出 trace as state：先读一遍任务并生成一条或多条推理轨迹，把收集到的轨迹序列化为 T，然后在全新的一遍里把 T 放在长上下文之前重读。
与之对照的是 trace append：第二遍拿到同样的序列化轨迹文本，但放在长上下文之后。trace as state 下，模型重新处理上下文时轨迹已经可用；trace append 下，轨迹仍能影响后续推理和答案，但无法影响前面上下文 token 已经形成的表示。两者的差别只在顺序。
实验在三个模型与三个长上下文数据集上展开：DeepSeek V4 Pro Preview、GLM-5.2、Qwen 3.7 Max，任务来自 GraphWalks 256K、MRCRv2 8-needle 与 NUB-1M。在报告的 27 组模型、任务与指标组合中，trace as state 有 26 组高于 trace append。
论文还设计了一组对照，用来压掉两类替代解释：一类是随便给点轨迹脚手架就有用，另一类是只是让模型看到了第一遍的答案。结果显示收益来自同一道题自身的推理轨迹所提供的任务状态信息。
三项主要贡献：
<span style="color:#0F4C81;font-size:7px;line-height:1;vertical-align:middle;">●</span>&nbsp;用条件状态更新抽象刻画了单遍读取的确定性处理器在最坏情况下的指数级顺序差距，并把它当作长上下文因果处理的一条定性原则。
<span style="color:#0F4C81;font-size:7px;line-height:1;vertical-align:middle;">●</span>&nbsp;提出 trace as state，一种把推理轨迹作为文本状态代理回灌的推理扩展方法，每一遍内部仍然保持因果处理。
<span style="color:#0F4C81;font-size:7px;line-height:1;vertical-align:middle;">●</span>&nbsp;在三个模型与三个长上下文基准上，trace as state 在 27 组组合里的 26 组高于 trace append。

## 条件状态更新：为什么顺序影响工作记忆
论文把因果状态更新处理器定义为按呈现顺序读取每个输入单元、并且只用当前记忆与新读到的单元更新持久工作记忆的处理器。
设 C = (c1, …, cn) 是 n 个信息单元的有序序列，ci 是第 i 个单元。如图 1A 所示，因果状态更新处理器在一个有限状态空间 S 中携带任务状态 si，读完 ci 后应用固定的更新规则 U，从 si-1 走到 si。当初始状态 s0 固定时，处理器沿序列走出的是一条已经确定的状态路径。
条件状态更新任务改变了初始状态的来源：s0 不再固定，而是由任务条件 z 给出。处理器令 s0 = z，把更新规则作用到整段 C 上，最后返回 sn。
两种顺序的差别在于处理器什么时候知道该走哪条路。条件在前 [z, C] 时，处理器在读到 c1 之前就知道 z，因此可以沿着唯一一条已经实现的状态路径更新。条件在后 [C, z] 时，处理器读完整个 C 之后才知道初始状态应该是什么。
在条件在前的顺序下，处理器只需要存下当前的 si，取 b 为状态空间大小的对数，即 b = log|S|，那么 b 位就够用。
条件在后的顺序下，读完 C 时处理器还没有选定任何一条状态路径。每一段可能的序列都对应一个完整的响应画像：对每一种可能的 z，这个画像给出最终会到达的 sn。处理器必须为每一个由合法序列诱导出的不同响应画像保留一份不同的配置。
状态空间 S 到自身共有 |S| 的 |S| 次方种可能函数。最坏情况下，条件在后的顺序至少要保留这么多份配置，而条件在前只需要 b 位，两者相差指数级。
附录里的构造说明了这个差距确实可以被达到。取一个有限非空状态集合 S，令序列长度 n = 1，并选择输入字母表的大小为 |S| 的 |S| 次方，使每个合法输入对应一个从 S 到 S 的函数。读完这段输入时，处理器还没有看到条件 z，因此必须为每个不同函数保留一份独立的配置；而在条件在前的顺序 (z, cf) 下，一个取值于 S 的寄存器就够用，用 z 初始化、再替换成 f 作用后的结果即可。
这个构造是一个存在性论证，适用于所声明的任务族与确定性的、精确的、单遍计算，属于最坏情况下的分析，而不是对平均情况的预测。
论文同时说明，带有限上下文长度与有限精度的因果 Transformer 本身就是因果状态更新处理器：工作的状态包含当前位置、所有层的键值条目以及其他持久的、由输入决定的信息，这些状态的总量有界。kv 缓存会随上下文变长而扩张，但仍然是有限的。
条件状态更新任务不是现实长上下文任务的字面模型。真实的长上下文里，任务状态往往不是外部给出的符号，而是在模型读完上下文开始推理之后才被发现。推理轨迹恰好记录了这类状态，例如当前目标、已经解析完成的指代、搜索前沿。
因此论文不做轨迹等于形式化条件 z 的强断言。轨迹可能不完整、有损或有错，它不是模型内部的某个特权状态。两者之间是功能性的联系：只要轨迹里包含有用的状态信息，把它放在上下文之前，就能让这些信息在上下文被重新处理时生效。
记 M 为因果状态更新模型，x 为长上下文。模型在同一道题上跑 n(tr) 次，第 j 次运行产生一条推理轨迹 r(j) 和一份独立的可见答案 a(j)。序列化函数 π 在所有摆放条件下保持一致，依次把轨迹拼接成文本状态代理 T，保留推理文本的原始顺序，只加上固定的标签与分隔符。
于是 trace as state 这一遍的输入是 [T, x]，模型重新生成推理轨迹 r′ 与可见答案 a′。trace append 保持 x 与 T 的原始顺序，第二遍输入是 [x, T]。两者使用同一段长上下文和同一个文本状态代理，唯一的变量是顺序，比较的正是同一份 T 在重读过程中有用，还是在上下文处理完之后才出现更有用。

## 轨迹块长什么样
序列化函数在每个任务上固定，只在轨迹之间插入固定标签。轨迹块以一个数据集特定的提示开头，说明这些轨迹来自同一道题的多次独立尝试、可能包含错误、只能当草稿提示使用，并要求模型对照原始材料核验。
数据集特定的提示片段属于 T 的一部分，而不是原始任务提示 x 的一部分。以 GraphWalks 为例，提示要求模型把这些轨迹只当草稿线索，最终只输出一行形如 Final Answer: [node1, node2] 的答案，空集写成 []，该行前后不出现任何多余文字。MRCRv2 的提示额外要求不要把任何轨迹文本抄进可见答案。

## 数据集与评分
评测使用 GraphWalks、MRCRv2 8-needle 与 1M-Novel Understanding Bench。GraphWalks 要求模型在长边列表上维护图状态，MRCRv2 要求把最后的请求绑定到更早的正确请求响应对上，两者都提供多个提示长度档位。由于各模型分词器不同，1M 档位里很多问题会因为超长而无法公平测试，因此取 1M 以下最长的档位：GraphWalks 用 256K，MRCRv2 用 256K 与 512K，同时也给附加的轨迹文本留出空间。
NUB-1M 是长篇小说阅读理解基准，问题围绕一部 400K 到 700K token 的新小说展开。数据集按季更新以降低泄漏风险，每一季的题目与答案由人工维护。评测使用第二季小说，报告 20 道题在 5 次重复上的平均准确率。
模型只有在问题出现在提示末尾时才会按预期作答，因此论文把问题从长上下文中分离出来，统一放在每次输入的结尾。真实的顺序因此是 trace as state 的 [T, x, q] 与 trace append 的 [x, T, q]，其中 x 是长上下文，q 是问题。表 1-2 列出数据集与评分方式。
对每个模型与任务，论文比较单遍基线 M([x, q]) 与两个利用轨迹的条件：trace as state 的 M([T, x, q]) 和 trace append 的 M([x, T, q])，两者复用的都是模型自己在第一遍生成的推理轨迹。每道题跑 5 次，第二遍的提示里包含全部 5 条轨迹。部分第一遍轨迹非常长，被截断到前 50000 个字符以避免输入超长。
评分方面，GraphWalks 用精确匹配与集合 F1，MRCRv2 8-needle 用精确匹配与 SequenceMatcher 比值，NUB-1M 用 DeepSeek V4 Pro 作为裁判的准确率。被拦截、超长、格式错误、缺失、没有终止符或被内容过滤的样本都记为失败。
三个数据集的评分细节做过专门核对。GraphWalks 的评测器抽取以 Final Answer 开头的那一行，把解析出的节点集合与金标准集合比对，合法的空预测单独处理；MRCRv2 每道题带一个必须同时出现在预测与参考答案开头的随机前缀，评分器会在比较前校验并去掉这个前缀；NUB-1M 为每道题维护参考答案，由 DeepSeek V4 Pro 比对抽取出的解答与参考答案，人工复核未发现判断错误。

## 顺序消融：把轨迹放在前面才是关键
论文在 DeepSeek V4 Pro 的 GraphWalks 256K 上比较了多种摆放与反馈对照，表 3 列出它们的提示格式、精确匹配与 F1。表里还包含第一遍的 Majority@5 与 Oracle@5：前者对 5 个第一遍答案做多数选择，保留至少在三次重复级预测集合里出现过的答案元素；后者取 5 个答案中评测分数最高的那一个。
问题前置把 q 放到任务之前，在 Parents 上有明显提升，但在 BFS 上与第一遍基线接近，说明对某些任务来说问题本身就是关键的任务状态。
Re2 重复整段提示，比第一遍提升明显，说明重读对这类长上下文任务确实有用，但它仍低于 trace as state，在 Parents 上差距尤其大。这个对比说明 T 携带了超出重复提示的任务相关信息。
答案反馈把第一遍的答案放在原始提示之前，比第一遍好，但远低于 trace as state，说明序列化的推理文本比答案或问题本身更适合充当任务状态代理。
随机轨迹把轨迹替换成同一子任务里其他题的轨迹，结果比不给轨迹的第一遍还差，与 trace as state 的差距更大。这一格排除了格式或脚手架本身带来收益的解释：没有针对同一道题的任务相关信息，光有轨迹形状的文本没有帮助。
上述对照都把一个长上下文的副本放在提示较晚的位置，但都没有超过 trace as state，说明文本越晚越新鲜不足以解释观察到的收益。
只给轨迹的条件不给原始长上下文，表现与 trace append 接近，说明轨迹里确实含有与答案相关的信息；但它远低于 trace as state，说明第一遍轨迹放在上下文之后再读仍然不够。trace as state 也高于 Oracle@5，意味着这一遍反馈重读的效果超过了事后从 5 个第一遍输出里挑最好的那个。

## 轨迹数量：越多越好，顺序优势始终在
论文进一步把复用的第一遍轨迹数量从 1 条加到 5 条，在 DeepSeek V4 Pro 的 GraphWalks 256K 上重跑。每个数量档位包含按重复顺序取的前若干条合格轨迹，因此各档位互相嵌套；每个档位里 trace as state 与 trace append 拿到的是完全相同的 T，并且各自对每道题额外跑 5 次第二遍；0 条那个点就是第一遍 5 次重复的均值。

## 局限与适用边界
实验里的跨遍状态反馈是通过模型自己生成的文本实现的，这个实现方式要求能拿到原始推理轨迹或另一个被暴露出来的状态接口。这个要求来自实验所用的接口形态，跨遍设计本身可以使用任何可访问的状态接口；只暴露最终答案的模型或 API 可能需要换一种接口。
trace as state 要用一次或多次源运行，再加一次对任务的全新传递，额外的传递会增加推理延迟与 token 成本。把状态放在原始上下文之前，也会在多轮场景里降低键值缓存的复用率。
评测覆盖了三个来自不同厂商的因果 Transformer 与三个长上下文任务族，没有评测多轮智能体任务。要确认顺序优势的适用范围，还需要在更多模型、领域、上下文长度与交互设置上测试。
这个方法只复用了模型自己生成的轨迹，除了底层模型与任务本身的风险之外，并没有引入新的伦理问题或滥用风险。

## 结语
**长上下文推理的瓶颈常常不在窗口长度，而在顺序**：同一份推理轨迹、同一段上下文，把轨迹挪到上下文之前，GraphWalks Parents 上的精确匹配就从 29.2% 升到 81.8%。
**① 顺序决定信息何时可用。** 因果注意力让已经形成的表示无法回头修改，把第一遍才发现的任务状态前置，等于让第二遍从更高的起点重新读一遍上下文。
**② 起作用的是同一道题的轨迹，不是脚手架。** 随机轨迹比不给轨迹更差，只反馈答案也远不如反馈推理过程，说明收益来自题目相关的状态信息，而不是文本格式本身。
**③ 代价同样明确。** 多一遍传递意味着更多 token 与更长延迟，状态前置还会削弱多轮场景下的键值缓存复用，轨迹本身有错时反馈也会失真。
对做长上下文推理的人来说，值得先试的不是继续加长窗口，而是给已有的推理产物换一个位置：轨迹前置、问题前置、答案前置各试一遍，成本只是一次额外传递，收益却可能是一个档位。
