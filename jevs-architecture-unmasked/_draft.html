要点速览
-核心结论：Jev大概率是因果transformer：共享状态前缀、隔离问题后缀、直接概率读出，推理止于prefill。

-关键实验：参考卡、无关选项、分箱校准三组探测分别证实全列表读出、选项交互与结果训练的概率。

-存疑部分：稀疏MoE骨干与读出头形式（槽位头或指针式）无法从API外部确证。

Jev用针对结果训练的决策概率替代生成的置信度文本：输入共享状态、问题与允许答案，并行返回概率分布，不生成任何文本。TypeSafe不公开研究细节，这里用API探测加公开资料，从黑盒外部重构它的架构。

Jev的命题

围绕Jev发布的多数热评没抓住重点，一个JSON分类器拿1200万浏览量就被宣判泡沫。普通LLM生成「90% 置信」这样的文字，产出这些字符的概率并不等于答对的概率是90%。而反欺诈、内容审核、路由与风险评估恰恰建立在这套模式上：按逐token生成付费，再把一句未经校验的置信度声明当作软件可以直接执行的概率。

Jev的命题：保留预训练LLM的知识，把生成的置信度声明换成直接从内部表示读出、针对结果训练的决策概率。输入共享状态、问题与允许的答案，并行返回各分布，不生成文本。对这一整类应用，一个动作同时解决两个问题：决策信号的可靠性，以及花在生产置信度文本上的无谓算力。

只有一个问题：模型不开源，TypeSafe也不公开研究细节，只能自己动手。

证据指向一个被改造用于决策的因果transformer，大概率带稀疏MoE：共享状态编码、隔离的问题分支、直接概率读出替代文本生成。对TypeSafe API做延迟特征探测、翻遍公开文档与研究、查清先行工作之后，得到一个相当准确的架构模型。

稀疏是最没把握的部分，但对这个领域收益特别大、缺点比自回归LLM少，要不是稀疏反而奇怪。共享计算与直接概率输出的证据充分得多。整个重构带推测成分，所以尽量区分三类信息：TypeSafe公开说了什么、实验观察到了什么、从观察推断出什么。黑盒API让人可以给幽灵蒙上一层布，摸出大致轮廓。

为什么这套设计有用

用一个示意性的客服路由请求说明API结构，示例概率是虚构的。

{
  "state": "My payouts have failed three times. The bank says everything is fine. Can someone please fix this?",
  "questions": {
    "queue": {
      "type": "choice",
      "instructions": "Which team should handle this ticket?",
      "criteria": {
        "payments": "Payout failures and payment processing",
        "account": "Login and account access",
        "other": "Something else"
      }
    },
    "escalate": {
      "type": "noul",
      "instructions": "Does this message require urgent human attention?"
    }
  }
}

合理的输出可能给payments 0.91概率，而紧急升级只有0.42。两种不确定性不同：软件可以自动路由工单，升级决策交给另一套策略。

因果transformer本来就会从左到右构建文本表示。普通语言模型推理中，处理提示、预测一个token、把结果喂回去再重复，这套循环建立在原始Transformer的解码器注意力与输出投影上。提示处理阶段已经产出了丰富的表示；如果任务是在三个队列里选一个，可以接一个小函数，把这个表示直接映射成三个数。

一个细节解开并行答案的大部分困惑：因果注意力描述哪些位置能使用哪些信息，不规定输入token必须按什么顺序执行。提示处理阶段或prefill阶段，每个输入token都已知，同一层内可以一起处理它们的位置，注意力掩码挡住对后续位置的访问，层与层仍然顺序执行。自回归解码多一条依赖：下一个token在上一个预测选定之前不存在。推测的模型在prefill与读出头之后结束，避开了逐token依赖。

计算形态随之改变。输出不再需要为payments 0.91这样的字符串做一串拼写决策；JSON格式化交给普通应用代码，神经网络只负责概率。

设状态是一份很长的故障报告，问题有五十个，大部分输入是共享的。transformer用键值缓存KV cache存储已处理token的中间信息；这个设计里每个问题读同一份状态缓存，每个分支只追加自己的指令和答案选项。

状态S个token、问题Q个时，分开请求要把状态处理约Q遍；共享把重复的状态token处理从QS降到S。问题仍要注意状态，这部分工作量不消失，只是不必反复重建状态的表示。

隔离也让接口语义更干净。问客户是否生气不应改变工单进哪个队列；两个问题可以查看同一份证据而读不到彼此的指令。分支之间没有计算依赖，即使答案在统计上相关。

概率还让下游策略显式化。一次多余升级成本1、漏掉紧急案例成本9，简化决策规则就是p(urgent) 大于0.1时升级。这个计算只在概率对该工作流可靠时才有意义，训练和评估概率分布因此成为产品的一部分，而不是装饰性的置信度字段。

以上都不需要扩散模型，并行分类存在了几十年。有意思的组合是：能力广泛的transformer、共享上下文计算、类型化输出接口、奖励有用不确定性的训练。

1. 用读出头结束推理

第一个组件最简单：预测头替代解码循环。

公开证据。TypeSafe的发布公告说Jev并行输出所有概率，而非自回归逐token生成；文档暴露的是有限选项、是非判断和有序打分，天然对应固定数值输出。

观察证据。API仍报告output_tokens字段，听着像生成量记录，其实不是。是非问题的计数精确吻合：4个共享token、每个答案15个、加上每个问题标识符的token长度；文档说明标识符不发给底层模型、不参与推理。一个随模型从未见过的文本变化的计数，只能是在推理之后从序列化响应算出来的。返回值也不影响计数：答案0.0与0.01计费相同，尽管每个数字按理都算token。

计数背后的tokenizer与测试过的192个公开tokenizer都不匹配，却与Jev自己对普通文本的输入计数一致，只在长串空白和标点处有差异。output_tokens是计费数字，说明不了Jev是否生成文本，即使生成了也量不到那段文本。延迟也不跟随这个数字：一个200选项的问题，1,911个output tokens，与两个选项的问题返回得一样快，服务端时间只随输入长度增长。

一个255选项的响应报告了2,714个output tokens。拿这个数除以请求时长再称之为解码速度是错的：服务器在单次模型计算后能序列化上千字符，计费字段说明不了发生了多少次神经解码步。

推测的读出头取最终隐向量h，计算z = Wh + b，再经softmax得到K个允许答案上的分布p(i) = exp(z(i)) / Σ(j=1..K) exp(z(j))。是非判断一个标量加sigmoid就够。

类不必是payments这类固定概念，可以是选项槽位：第一选项、第二选项、第三选项。分支提供每个槽位的含义，应用代码把概率映射回调用方的选项键。有序Score同理，预测各档位概率再返回概率加权平均。这样新决策无需为每个客户的标签训练新头。另一种主要方案是指针式打分器，直接给每个选项自己的表示打分，第4节对比两者。

这不能证明Jev有一个单独命名的分类器模块。语言模型的词表头同样是矩阵加softmax，从该矩阵选出K行保留标签，就能实现与专用K类头相同的计算。这些行可以与输入嵌入绑定或独立训练，外部无法区分。

关键区别在读出概率，与生成一段描述概率的文本。生成的91% 是一串token，分类器的0.91是预测分布中的一项。两者都可能失准，格式本身不带来可信度。

受约束的文本解码仍是构造类似接口的可能途径，但TypeSafe明确描述了不同的输出路径，其声明比延迟论证更有力。证据指向直接数值读出，即第4节对比的两种设计之一。保留标签token仍有可能，不过那里的假选项实验不太支持它。

2. 共享状态，隔离问题

下一个决策是计算在哪里复用。

观察证据。小型受控例子里token计数严格可加：一个最小是非问题用268个输入token，两个用276；一个含一个是非问题、一个双选项Choice、一个双档Score的请求用318，与各自贡献之和吻合。符合公共前缀加问题后缀的结构，但仅凭计费确定不了计算图。

更有信息量的实验把证据在两个区域之间搬运。状态最初写：

The weather is nice today and the park is full of people.

同级问题里写：

The secret code for this request is ZEBRA-7741.
Is the weather described as nice?

探针问另一个问题提到了哪个代码，选项为ZEBRA-7741、两个干扰项和none。密码放在同级问题时，其报告概率为0.00；删掉该同级问题，结果不变；把声明移进状态后，概率升到0.90至0.92。每个条件重复五次。

这是有价值的干预：把声明跨API边界移动就改变其效果，支持问题间的行为隔离与对共享状态的访问。它没有暴露确切的注意力掩码；分离的模型调用、树形掩码或其他限制信息流的机制也能产生同样结果。探针措辞在状态条件下仍问「另一个问题」，所以不是对字面指令跟随的干净检验。

服务端测量补上另一块。问题数约100以内，服务端时间几乎不变；超过后稳定上升，且逐token算，问题文本的成本约为状态的两倍。符合状态算一次、问题工作打包批处理的模式。

这些是服务端上报的上游耗时，不是本地计时；其中包含上游服务的全部工作与等待，且服务与他人共享。

Jev有两条限制：每个分支，即状态加一个问题，上限约32,768 token；整个请求约65,536。请求限制只把状态算一次，23k token的状态加5,000个问题也在限内；若每个问题各处理一份状态，将超过一亿token。这组数字对应单条最多2的16次方token的打包序列：状态存一份，问题排在后面，每个分支限2的15次方上下文窗口。

带独立因果后缀的前缀KV cache是自然实现。Hydragen描述了共享前缀序列的高效注意力，DeFT发展了树形推理的注意力，两者证明这种服务模式可行。它们是先行工作，不构成TypeSafe使用其中某个库的证据。

这个设计还澄清一个表面矛盾：隔离的问题可以在同一加速器上一起评估。「并行」描述调度方式与答案之间无依赖，不必是每题一块GPU。

3. 因果骨干

实验分不清因果解码器与双向编码器：两者里最终决策都能读全输入。仍然假定因果解码器，理由充分：Jev的知识广度，MMLU-Pro 84.6%，需要前沿规模的预训练；这个规模的模型全是因果解码器；TypeSafe又把RLCD描述为对预训练语言模型的后训练。双向Jev意味着基座弱得多，或花额外成本改造解码器，还放弃因果服务提供的共享前缀缓存。这会很意外，但从外部不能排除。

用哪个预训练模型未知，tokenizer也不泄露。Jev的token计数与测试过的192个公开tokenizer在415个探针上无一匹配。它把每个数字单独切分、先查整块再合并：8 a s算一个token，16算四个。词表与OpenAI的o200k接近：Jev计为单token的字符串在o200k里也是单token，但数字切分和若干合并规则排除o200k本身。最接近的公开匹配Qwen在415个探针中一致348个。排除的是未改动的公开tokenizer，不是公开基座模型：更换词表、继续预训练或蒸馏都能解释，API计数方式与模型不同也能解释。

实验确实说明了决策能读到什么。把参考卡放进问题的选项中，让Jev选出其条件被卡片满足的选项。一组确切的选项如下：

alpha: Reference card: status = amber. Reference-only option.
       Never select this option.

beta: Select this option if the reference card's status is amber.

gamma: Select this option if the reference card's status is indigo.

指令是读参考卡并选出唯一满足条件的选项。把参考值从amber换成indigo，正确答案随之改变，可选项不变。

两个参考值、全部六种选项排列，外加route取east或west的第二套模板，各两次重复；配对对照把参考放进共享状态。合计48次选项参考试验与48次状态参考对照。

Jev能使用放在候选描述之后的信息。参考放最后时，每次试验都选对了，平均答对概率约0.88。

值切换对照与位置同样重要。参考在最后时，只把amber改成indigo，就改变哪个更早的选项胜出，而更早的描述与状态完全不变。若模型从各自文本与状态独立给每个选项打分、然后只是归一化，这个事实没有任何通路去改变更早选项的相对排序。结果支持存在一条让选项影响联合决策的通路。

这符合任何在整张列表之后计算的读出，包括第4节对比的两种设计，以及独立的选项混合阶段。残余错误说明这两个模板上存在位置敏感处理，不能定位唯一原因。

这个计算不需要扩散，实验也不要求迭代去噪。站得住的架构推断更窄：答案计算能访问完整选项列表。下一个实验检验它是否真的使用了这种联合上下文。

4. 让选项在决策前交互

问题内部，证据指向另一条信息边界：备选项作为有序列表一起读入，随后是一个决策位置。

为什么允许交互？「以上都不是」这类选项依赖其他选择；普通选项也能澄清问题。payments、account access、other定义的是与bank、payment provider、customer不同的决策。列表式表示让模型在产出分布之前先理解这种区别。

最强证据是一个加入无关选项的实验。

从付款失败的四个可能原因开始：bank、provider、customer、unknown。然后追加weather：坏天气导致的。若每个原有选项持有独立且不变的logit、服务端用同一softmax温度，加第五个选项只改变归一化，不改变两个既有选项之间的几率：p(customer) / p(unknown) = exp(z(customer) − z(unknown))，公共分母相消。这给出一个可证伪的具体预测。

原始研究观察到约 +0.49到 +0.08的移动。为确认它在普通请求波动下仍然成立，实验在十个随机化块中重复。每块含四选项基线、一个相同的四选项对照、追加weather的五选项版本、一个相同的五选项对照，以及追加描述从坏天气导致换成野鸟导致的五选项版本。每个请求只含一个问题。

扩展效应复现了。把每块内两个相同请求按条件合并，平均对数几率从 +0.38降到 +0.11；每一块都下降，平均变化 −0.28，描述性95% 配对t区间约 −0.36到 −0.19。合并用对照请求消减普通请求噪声，而非把重复输出当独立实验。

这是反对固定独立logit加不变softmax的证据，但不能唯一确定机制。保持五选项、只改追加描述时，移动更小且结论不定：配对区间包含零。依赖集合的温度仍有可能，与依赖内容的混合并存。

能看到完整列表的读出自然解释这一现象：加一个选项，就改变它读到的上下文。FIRST列表式排序方法同理，从首个token的logit提取排序，而不是逐个生成。

两种读出都符合证据。末位头从决策token的表示给每个选项槽位打分；指针式打分器把该表示与每个选项自己的最终隐状态比较。两者都允许选项互相影响。API接受至多255个选项，即2的8次方减1，适配固定256槽位头，但该限制由请求校验执行而非模型。200选项时，复制的答案在每个位置都得1.00，错误不溢出到相邻选项，适配指针。两个结果都不是决定性的。

注入的假选项从未挤掉真选项，说明选项边界以文本无法伪造的方式标记；条件在列表其他位置被复述的选项，会把概率让给对手。

代价在普通任务里同样可见：调换选项顺序，把技术支持分类的概率从约0.84至0.89移到0.93至0.96，来自option_order探针。对已部署的决策策略这很重要：0.9附近的阈值可能改变动作，而标签与证据完全相同。任何实现这个设计的系统，都应把排列测试纳入评估。

5. 先训练分布，再计算置信度

第五个组件是训练目标。数值输出省下解码，但便宜的概率也可能是坏概率。

设一批案例被赋0.8的紧急概率。校准问的是其中是否约80% 真的紧急。校准是跨案例的预测属性；单个案例结果好坏，判断不了那一个预测是否校准。

TypeSafe把训练方法称为面向校准决策的强化学习RLCD。发布公告说它优化在系统一任务上带有认识论诚实概率的答案；公司的入门材料把RLCD呈现为从预训练语言模型出发的后训练路径。具体配方未公开。推测的训练配方用基于结果的目标，把transformer与读出头适配到类型化决策任务，让骨干有机会构建对可靠决策有用的表示，而不只是流畅补全。

自然的目标是对数损失，即观测结果y的 −log p(y)；另一个是Brier损失，预测分布与观测one-hot结果之间的平方距离。两者都是严格恰当评分规则：期望意义上，报告真实条件分布使损失最小，Gneiting与Raftery给出了形式定义与理论。这解释了这类训练想达成什么，不构成对TypeSafe用哪种损失、其流程是否为狭义强化学习、是否更新全部骨干权重的判断。

恰当性也不是部署保证。有限数据、模型局限、优化误差与分布偏移都会留下校准缺陷。Guo等人同时展示了现代神经网络的校准问题与事后调整的用处。训练与事后校准是兼容机制，API分不开两者的贡献。

观察证据。基准记录可以比较预测概率与观测准确率，整体与分箱皆可。只对齐均值是弱证据，分箱一致才更有力：一组的过度自信可以抵消另一组的信心不足。1,200题MMLU样本上，十箱期望校准误差0.0313；多数预测集中在接近确定处，990题落在0.9至1.0箱。

小型新数学研究补上变化。生成的三位数乘法题上，准确率86.7%、平均最高概率0.83；两步应用题上，准确率降到32%、平均最高概率0.30。更难的任务上模型更不自信，方向令人鼓舞，尽管小的类级均值确立不了对所有未见问题的校准。

这些结果也说明公开基准分不是模型知识的好度量。MMLU-Pro 84.6%，新生成应用题难得多。任务结构、干扰项、难度与训练暴露都可能是原因；差距确立不了基准污染，新措辞也不让底层数学技能或事实知识变成未见。

关于API名为confidence的字段，有一个异常清晰的发现。官方适配器在K大于1时，用归一化分布计算Choice置信度：c = (p_max − 1/K) / (1 − 1/K)。三个选项、最高概率0.8时得0.7；单选项单独处理，返回1。它度量领先答案高出均匀分布多少，不是又一个学习出来的答对估计。Score类型用另一公式，反映与众数档位的距离。

在推测的系统里，训练产出预测分布，普通算术产出这个汇总字段。分开这两个对象避免一个常见概念错误：集中的分布仍可能自信地错。

6. 稀疏容量

预期Jev用稀疏混合专家transformer。选定层上，路由器把每个token送进前馈网络的一小个子集，模型得以存很多参数而每个token只激活一部分，即Shazeer等人稀疏门控MoE层展示的条件计算思想。

稀疏专家从外部观察不到，但它是大概率选择。只做prefill的模型受计算限制，恰是稀疏路由省下的东西。MoE常见的服务成本大多消失：没有逐token解码，那个内存带宽主导、专家几乎全被激活的场景；没有与专家权重抢内存的长寿命KV cache。测量指向同一方向：Jev约160 ms处理约30k token；8卡H100节点上的稠密70B模型约需一秒，激活参数约10B的MoE恰好够。当下最强的基座模型，DeepSeek-V3、Qwen3、GLM-4.5、Kimi K2、gpt-oss，多数是MoE。专用硬件能让稠密模型追平速度，基准分也可能高估知识量，所以这仍是推断不是测量。

重构的其他部分不依赖它。换成稠密transformer，接口、共享状态、隔离分支与读出全部照旧。

7. 按批次调度分支，而不是对话

最后一个组件是把问题分支当独立工作项的推理引擎：后缀打包成批、读共享状态表示，应用代码把数值输出与问题标识符关联并序列化响应。

测量显示，重复的相同答案之间有小差异，包括同一请求内的重复问题之间。API级确定性不能假设。这不暗示模型在生成或采样文本：数值核、动态批处理、路由或刻意随机都能影响直接读出。

响应键顺序也以少数几种循环模式变化。多个worker用不同哈希序是合理解释。但这个侧信道确定不了worker数、KV cache在哪、数值精度是什么，这些都是现有观察无法解决的实现细节。

对推测的架构真正要紧的，是答案之间没有依赖链：模型不必先写完队列分类再开始紧急度估计，两者都依赖状态，互不消费对方的生成答案。

依赖仍有限度。后面的问题真需要前面的答案时，应用必须再加一个决策阶段，或把联合决策写进一个问题。共享上下文取消不了工作流的逻辑结构。

什么会推翻这个判断

这个重构做了不同强度的承诺：直接概率输出是公开声明的；问题隔离与选项顺序效应是可观察行为；KV共享、因果注意力、末位或指针式读出、稀疏专家是越来越具体的解释。

参考卡实验解决一个问题：决策能使用放在最后的选项。假选项实验表明，输入格式里的花招伪造不了选项边界。更广的关系型任务可以进一步约束表示，尽管仅凭行为成功仍不能唯一确定注意力掩码。

选项处理上，随机化后续复现了选择集效应，但固定规模的描述干预仍无结论。更多模板与独立请求块能区分共享温度变化与内容依赖交互；200选项的中等难度任务能分离槽位头与指针式打分器。校准上，留出的工作流数据与偏移下的重复评估，比再一个聚合基准分更重要。确认稀疏专家，大概率需要披露或API之外的证据。

对Jev的最佳重构仍是开篇那张图：因果transformer加共享状态前缀、隔离问题后缀、列表式选项处理、类型化数值读出、面向预测分布的训练。稀疏专家是大概率骨干，但设计其他部分不依赖它。

价值在于让计算图匹配工作。决策服务需要读证据、比较允许的结果、暴露不确定性；transformer不必把每个决策先变成一句话，再完成这些事。

方法与数据

全部结论基于2026年9月17日对jev-1.13.0的一次调查，一个早期访问账号、一个观测服务区域。源研究含1,029条插桩探针记录（含190条生成数学题）、6,800条基准记录及独立事实核查。后续研究新增146条关系与选项交互请求、311条token计数请求、445条tokenizer指纹请求、192条延迟请求、148条选项数延迟请求、181条选项位置请求、105条假选项请求与35条上下文限制请求。重复的基准配置共享底层题目，这些计数不是独立问题数。

可下载的证据包记录了全部观察。开篇API示例是示意的；引用的可见性与参考卡提示来自探针脚本与保存的后续请求。数值观察限于该模型版本与本次测试活动。

延迟数字取自x-envoy-upstream-service-time响应头，是上游服务时长，排队与执行边界未知，不是孤立的模型计时；延迟扫描按乱序逐个请求，没有研究控制服务器负载。本地墙钟测量不作为架构证据。

概率一般以两位小数返回。同一请求内的重复问题共享条件，误差可能相关。MMLU校准图用十个等宽箱：0到0.1、0.1到0.2，以此类推，1.0归入最后一箱。期望校准误差是每箱准确率与平均最高概率之差的样本加权绝对值。估计依赖样本选择、分箱与响应取整；证据支持关于所测分布的论断，不是对未来客户工作流的校准保证。

结语
Jev重构的价值不在单个部件多新，而在组合指向同一个结论：决策不必先变成文本。参考卡、无关选项、分箱校准三组实验从黑盒外部钉住三件事：答案计算看得到完整选项列表、选项之间存在真实交互、概率是针对结果训练出来的；真正悬而未决的只剩稀疏MoE骨干，与槽位头还是指针式读出。

对做分类、路由、风控系统的人，值得带走的是把概率当一等公民的设计：prefill后直接读出、状态只算一次、confidence字段与预测分布严格分开。评估这类模型时，排列测试与分箱校准应当进清单。
